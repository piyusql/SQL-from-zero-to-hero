# Chapter 22 Exercises — The Table Design Checklist

## Practice Session 22.1 — Apply the checklist to a bare table

**Goal.** Take a table with no constraints, no history and no indexes, rebuild it to the
Chapter 22 checklist, and prove each checklist item with a probe that fails on the old
table and is rejected or recorded on the new one.

**Setup.** A scratch database; nothing here touches the sample datasets.

```bash
createdb ch22_ws1
psql -d ch22_ws1
```

```sql
\pset null '(null)'
CREATE TABLE depot (depot_id serial, city text);
CREATE TABLE shipment (
    shipment_id serial,
    depot_id    int,
    awb         text,
    weight_kg   numeric,
    status      text
);
INSERT INTO depot (city) VALUES ('Pune'), ('Bengaluru'), ('Delhi'), ('Hyderabad'), ('Chennai');
INSERT INTO shipment (depot_id, awb, weight_kg, status)
SELECT 1 + g % 5, 'AWB' || lpad(g::text, 6, '0'), 1 + g % 40,
       (ARRAY['booked', 'in_transit', 'delivered'])[1 + g % 3]
FROM   generate_series(1, 5000) g;
```

**Task.**

1. Write one catalog query that reports, for `depot` and `shipment`: the number of
   constraints, the number of indexes and the number of user triggers.
2. Prove three defects of the bare `shipment`: a duplicate `awb` is accepted, a negative
   weight is accepted, and a shipment can point at a depot that does not exist.
3. Build `shipment_v2` and `depot_v2` to the checklist: identity key, `tenant_id`,
   business key (`awb` per tenant), the standard columns with a trigger for `updated_*` and
   `row_version`, a `CHECK` on weight and status, a tenant-carrying composite foreign key,
   and a child-side foreign-key index. Copy the data in, with every row in tenant 1.
4. For each of these, write the probe and show the outcome: duplicate `awb`; negative
   weight; a shipment in tenant 1 pointing at a depot of tenant 2; an `UPDATE` that tries
   to change `created_by`; a stale `row_version` update.
5. State, in one sentence each, your delete policy and your partitioning decision for
   `shipment_v2`, and say which checklist item you would skip if this were a 5-billion-row
   event log rather than a shipment table.

**Solution.**

Step 1 — the inventory. The bare tables have nothing:

```sql
SELECT c.relname,
       (SELECT count(*) FROM pg_constraint WHERE conrelid = c.oid) AS constraints,
       (SELECT count(*) FROM pg_index      WHERE indrelid = c.oid) AS indexes,
       (SELECT count(*) FROM pg_trigger    WHERE tgrelid  = c.oid AND NOT tgisinternal) AS triggers
FROM   pg_class c
WHERE  c.relname IN ('depot', 'shipment')
ORDER  BY 1;
```

```text
 relname  | constraints | indexes | triggers
----------+-------------+---------+----------
 depot    |           0 |       0 |        0
 shipment |           0 |       0 |        0
(2 rows)
```


Step 2 — the three defects on the bare table:

```sql
INSERT INTO shipment (depot_id, awb, weight_kg, status) VALUES (1,  'AWB000001', 5,  'booked');
INSERT INTO shipment (depot_id, awb, weight_kg, status) VALUES (1,  'AWB900001', -3, 'lost');
INSERT INTO shipment (depot_id, awb, weight_kg, status) VALUES (99, 'AWB900002', 2,  'booked');

SELECT count(*) AS duplicated_awbs
FROM  (SELECT awb FROM shipment GROUP BY awb HAVING count(*) > 1) d;
```

```text
 duplicated_awbs
-----------------
               1
(1 row)
```


All three inserts succeeded. Step 3 — the rebuilt tables. The helpers are the ones from the
chapter; `app_user()` names the acting user, and `touch_row()` owns `updated_*`,
`row_version` and the immutability of `created_*`:

```sql
CREATE FUNCTION app_user() RETURNS text LANGUAGE sql STABLE AS
$$ SELECT coalesce(nullif(current_setting('app.actor', true), ''), session_user) $$;

CREATE FUNCTION touch_row() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    NEW.created_at  := OLD.created_at;
    NEW.created_by  := OLD.created_by;
    NEW.updated_at  := now();
    NEW.updated_by  := app_user();
    NEW.row_version := OLD.row_version + 1;
    RETURN NEW;
END $$;

CREATE TABLE depot_v2 (
    id         bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id  int         NOT NULL,
    city       text        NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, id)
);
CREATE TABLE shipment_v2 (
    id          bigint       GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id   int          NOT NULL,
    awb         text         NOT NULL,
    depot_id    bigint       NOT NULL,
    weight_kg   numeric(8,2) NOT NULL CHECK (weight_kg > 0),
    status      text         NOT NULL CHECK (status IN ('booked', 'in_transit', 'delivered')),
    created_at  timestamptz  NOT NULL DEFAULT now(),
    created_by  text         NOT NULL DEFAULT app_user(),
    updated_at  timestamptz  NOT NULL DEFAULT now(),
    updated_by  text         NOT NULL DEFAULT app_user(),
    row_version int          NOT NULL DEFAULT 1,
    UNIQUE (tenant_id, awb),
    FOREIGN KEY (tenant_id, depot_id) REFERENCES depot_v2 (tenant_id, id)
);
CREATE INDEX shipment_v2_depot_idx ON shipment_v2 (tenant_id, depot_id);
CREATE TRIGGER shipment_v2_touch BEFORE UPDATE ON shipment_v2
    FOR EACH ROW EXECUTE FUNCTION touch_row();

INSERT INTO depot_v2 (tenant_id, city) SELECT 1, city FROM depot ORDER BY depot_id;
INSERT INTO depot_v2 (tenant_id, city) VALUES (2, 'Kochi');
INSERT INTO shipment_v2 (tenant_id, awb, depot_id, weight_kg, status)
SELECT 1, awb, depot_id, weight_kg, status FROM shipment WHERE shipment_id <= 5000;

SELECT (SELECT count(*) FROM shipment_v2) AS shipments, (SELECT count(*) FROM depot_v2) AS depots;
```

```text
 shipments | depots
-----------+--------
      5000 |      6
(1 row)
```


Step 4 — the probes. Each block is one checklist item doing its job. The last two are
wrapped in a transaction that sets the acting user with `SET LOCAL`:

```sql
\set VERBOSITY terse
INSERT INTO shipment_v2 (tenant_id, awb, depot_id, weight_kg, status) VALUES (1, 'AWB000001', 1, 5, 'booked');
INSERT INTO shipment_v2 (tenant_id, awb, depot_id, weight_kg, status) VALUES (1, 'AWB900001', 1, -3, 'booked');
INSERT INTO shipment_v2 (tenant_id, awb, depot_id, weight_kg, status) VALUES (1, 'AWB900002', 6, 2, 'booked');

BEGIN;
SET LOCAL app.actor = 'meera.banerjee';
UPDATE shipment_v2 SET created_by = 'someone.else', status = 'in_transit'
WHERE  awb = 'AWB000001'
RETURNING created_by, updated_by, row_version;
COMMIT;

UPDATE shipment_v2 SET weight_kg = 9 WHERE awb = 'AWB000001' AND row_version = 1 RETURNING row_version;
\set VERBOSITY default
```

```text
ERROR:  duplicate key value violates unique constraint "shipment_v2_tenant_id_awb_key"
ERROR:  new row for relation "shipment_v2" violates check constraint "shipment_v2_weight_kg_check"
ERROR:  insert or update on table "shipment_v2" violates foreign key constraint "shipment_v2_tenant_id_depot_id_fkey"
 created_by |   updated_by   | row_version
------------+----------------+-------------
 postgres   | meera.banerjee |           2
(1 row)

-------------
(0 rows)
```


Reading the results: the duplicate `awb` and the negative weight are rejected by the unique
key and the `CHECK`. The cross-tenant shipment is rejected by the *composite* foreign key,
which a plain `depot_id` reference would have accepted. The forged `created_by` was
silently discarded (it is still `postgres`, the loading user, not `someone.else`),
`updated_by` names the actor, and `row_version` advanced from 1 to 2. The stale-version
update matched no row. (The probes run with `\set VERBOSITY terse` because the `DETAIL`
line of a failed row prints the row, including its timestamps.)

Step 4b — the child-side index. Prove it is being used by asking the planner about the
lookup the foreign key check performs when a depot is deleted:

```sql
ANALYZE shipment_v2;
EXPLAIN (COSTS OFF) SELECT 1 FROM shipment_v2 WHERE tenant_id = 1 AND depot_id = 6 FOR KEY SHARE;

BEGIN;
DROP INDEX shipment_v2_depot_idx;
EXPLAIN (COSTS OFF) SELECT 1 FROM shipment_v2 WHERE tenant_id = 1 AND depot_id = 6 FOR KEY SHARE;
ROLLBACK;
```

```text
                         QUERY PLAN
-------------------------------------------------------------
 LockRows
   ->  Index Scan using shipment_v2_depot_idx on shipment_v2
         Index Cond: ((tenant_id = 1) AND (depot_id = 6))
(3 rows)

                      QUERY PLAN
------------------------------------------------------
 LockRows
   ->  Seq Scan on shipment_v2
         Filter: ((tenant_id = 1) AND (depot_id = 6))
(3 rows)
```


Step 5 — a defensible answer. *Delete policy:* hard delete, with the audit trail from 22.2
holding the old row; shipments are never undeleted by the business. *Partitioning:* not
now: nothing leaves in bulk by date, so it is a cost without a benefit; if shipments had
to be purged after seven years, revisit before go-live, and the key would become
`(id, created_at)`. *Event-log skip:* drop `created_by` and `updated_by` and the
`updated_*` columns entirely (an append-only table has no updates), and do not audit it.
The point of the session is that every item is a probe that fails on the old table.

Clean up: `DROP DATABASE ch22_ws1;` from another database.

## Practice Session 22.2 — Trigger-based audit table

**Goal.** Build a `jsonb` audit trail for a table, show what it captures, show three ways
it silently fails and close two of them, then measure what it costs in WAL bytes.

**Setup.** A scratch database and `pg_walinspect` (PostgreSQL 15, superuser). The helper
reports WAL bytes written by one transaction, excluding full-page images, so that
concurrent activity on the server does not contaminate the number.

```bash
createdb ch22_ws2
psql -d ch22_ws2
```

```sql
\pset null '(null)'
CREATE EXTENSION pg_walinspect;
CREATE FUNCTION wal_of(x xid, from_lsn pg_lsn)
RETURNS TABLE (records bigint, wal_bytes bigint) LANGUAGE sql AS $$
    SELECT count(*), coalesce(sum(record_length - fpi_length), 0)::bigint
    FROM   pg_get_wal_records_info(from_lsn, pg_current_wal_flush_lsn())
    WHERE  xid = x $$;

CREATE FUNCTION app_user() RETURNS text LANGUAGE sql STABLE AS
$$ SELECT coalesce(nullif(current_setting('app.actor', true), ''), session_user) $$;

CREATE TABLE payment (
    id         bigint        GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    payer      text          NOT NULL,
    amount     numeric(12,2) NOT NULL,
    status     text          NOT NULL DEFAULT 'pending'
);
INSERT INTO payment (payer, amount)
SELECT (ARRAY['Rajesh Kumar', 'Anita Rao', 'Priya Menon', 'Arjun Iyer'])[1 + g % 4],
       100 + g % 900
FROM   generate_series(1, 5000) g;
CREATE TABLE payment_plain (LIKE payment INCLUDING ALL);
INSERT INTO payment_plain OVERRIDING SYSTEM VALUE SELECT * FROM payment;
```

**Task.**

1. Create schema `audit` and `audit.row_log` (time, actor, transaction id, table name,
   operation, row id, `old_row jsonb`, `new_row jsonb`) with an index on
   `(table_name, row_id, id)`.
2. Write one trigger function usable on any table with an `id` column, using `to_jsonb`.
   Attach it to `payment` for insert, update and delete, `FOR EACH ROW`.
3. As user `fatima.sheikh` (set with `SET LOCAL app.actor`), insert, update and delete one
   payment in a single transaction. Query the trail, then write a query listing the
   *fields* that changed in the update.
4. Show that each of these leaves the trail untouched: `TRUNCATE` (inside a transaction you
   roll back), an update under `SET LOCAL session_replication_role = replica`, and an
   update after `ALTER TABLE ... DISABLE TRIGGER`.
5. Close two gaps: log `TRUNCATE` with a statement-level trigger, and make the row trigger
   fire under `replica`. Show the `tgenabled` value that proves it.
6. Create a role `ch22_app` with `SELECT, INSERT, UPDATE, DELETE` on `payment` only.
   Connect as it and try to read the trail, `TRUNCATE`, disable the trigger, and change
   `session_replication_role`. Say which actors no trigger can catch.
7. Measure the WAL of an identical 500-row `UPDATE` on `payment` (audited) and
   `payment_plain` (no trigger). Report records and bytes, and bytes per row.

**Solution.**

Steps 1–2 — the table and a generic trigger function. `SECURITY DEFINER` lets the
application role write to the trail without any privilege on it; the fixed `search_path`
is the standard hardening for definer functions:

```sql
CREATE SCHEMA audit;
CREATE TABLE audit.row_log (
    id         bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    at         timestamptz NOT NULL DEFAULT clock_timestamp(),
    actor      text        NOT NULL DEFAULT app_user(),
    txid       bigint      NOT NULL DEFAULT txid_current(),
    table_name text        NOT NULL,
    op         text        NOT NULL,
    row_id     bigint,
    old_row    jsonb,
    new_row    jsonb
);
CREATE INDEX row_log_lookup ON audit.row_log (table_name, row_id, id);

CREATE FUNCTION audit.log_row() RETURNS trigger
LANGUAGE plpgsql SECURITY DEFINER SET search_path = pg_catalog, public AS $$
BEGIN
    INSERT INTO audit.row_log (table_name, op, row_id, old_row, new_row)
    VALUES (TG_TABLE_NAME, TG_OP,
            CASE WHEN TG_OP = 'DELETE' THEN OLD.id ELSE NEW.id END,
            CASE WHEN TG_OP IN ('UPDATE', 'DELETE') THEN to_jsonb(OLD) END,
            CASE WHEN TG_OP IN ('INSERT', 'UPDATE') THEN to_jsonb(NEW) END);
    RETURN NULL;
END $$;

CREATE TRIGGER payment_audit AFTER INSERT OR UPDATE OR DELETE ON payment
    FOR EACH ROW EXECUTE FUNCTION audit.log_row();
```


Step 3 — capture, and the fields that changed. `old_row -> key IS DISTINCT FROM value`
compares `jsonb` values, so it works for any table:

```sql
BEGIN;
SET LOCAL app.actor = 'fatima.sheikh';
INSERT INTO payment (payer, amount) VALUES ('Harpreet Singh', 4200.00);
UPDATE payment SET amount = 4800.00, status = 'paid' WHERE payer = 'Harpreet Singh';
DELETE FROM payment WHERE payer = 'Harpreet Singh';
COMMIT;

SELECT id, actor, op, old_row->>'amount' AS old_amount, new_row->>'amount' AS new_amount
FROM   audit.row_log ORDER BY id;

SELECT n.key, l.old_row -> n.key AS old_value, n.value AS new_value
FROM   audit.row_log l, jsonb_each(l.new_row) n
WHERE  l.op = 'UPDATE' AND l.old_row -> n.key IS DISTINCT FROM n.value;
```

```text

----+---------------+--------+------------+------------
  1 | fatima.sheikh | INSERT | (null)     | 4200.00
  2 | fatima.sheikh | UPDATE | 4200.00    | 4800.00
  3 | fatima.sheikh | DELETE | 4800.00    | (null)
(3 rows)

  key   | old_value | new_value
--------+-----------+-----------
 amount | 4200.00   | 4800.00

(2 rows)
```


Step 4 — three silent failures. Each `SELECT` counts trail rows *after* the operation; the
trail had 3 rows before:

`TRUNCATE` removed every payment and the trail stayed at 3. The `replica` update changed a
row and logged nothing. The disabled trigger deleted a row and logged nothing.

Step 5 — closing two of them:

```sql
CREATE FUNCTION audit.log_truncate() RETURNS trigger
LANGUAGE plpgsql SECURITY DEFINER SET search_path = pg_catalog, public AS $$
BEGIN
    INSERT INTO audit.row_log (table_name, op) VALUES (TG_TABLE_NAME, 'TRUNCATE');
    RETURN NULL;
END $$;
CREATE TRIGGER payment_audit_truncate BEFORE TRUNCATE ON payment
    FOR EACH STATEMENT EXECUTE FUNCTION audit.log_truncate();
ALTER TABLE payment ENABLE ALWAYS TRIGGER payment_audit;

BEGIN;
TRUNCATE payment;
SELECT op, row_id FROM audit.row_log ORDER BY id DESC LIMIT 1;
ROLLBACK;

BEGIN;
SET LOCAL session_replication_role = replica;
UPDATE payment SET amount = 1 WHERE id = 1;
SELECT count(*) AS trail_rows FROM audit.row_log;
ROLLBACK;

SELECT tgname, tgenabled FROM pg_trigger
WHERE  tgrelid = 'payment'::regclass AND NOT tgisinternal ORDER BY tgname;
```

```text
    op    | row_id
----------+--------
 TRUNCATE | (null)
(1 row)

 trail_rows
------------
          4
(1 row)

         tgname         | tgenabled
------------------------+-----------
 payment_audit          | A
 payment_audit_truncate | O
(2 rows)
```


The trail grew to 4 in the `replica` case, and `tgenabled = 'A'` (always) is the proof.
Gap three, a table owner disabling the trigger, is a privilege problem, not a trigger
problem. Monitor it with `SELECT ... FROM pg_trigger WHERE tgenabled <> 'O'`.

Step 6 — least privilege:

The application role's update was audited with `actor = ch22_app`. It cannot read the

## Practice Session 22.3 — Measure and mitigate soft-delete cost

**Goal.** Measure, in buffers and pages, what a soft-deleted share of a table costs a
"live rows" query, and show that a partial index and archiving each remove a different
part of the cost, without using a clock.

**Setup.** Two identical copies of a 200,000-row table, 100 rows per customer, scattered
through the heap.

```bash
createdb ch22_ws3
psql -d ch22_ws3
```

```sql
\pset null '(null)'
SET max_parallel_workers_per_gather = 0;
CREATE TABLE doc_full (
    id          bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id int         NOT NULL,
    ref         text        NOT NULL,
    created_at  timestamptz NOT NULL,
    deleted_at  timestamptz,
    body        text        NOT NULL
);
INSERT INTO doc_full (customer_id, ref, created_at, body)
SELECT g % 2000, 'DOC-' || lpad(g::text, 7, '0'),
       timestamptz '2026-01-01' + g * interval '1 minute', repeat('x', 100)
FROM   generate_series(1, 200000) g;
CREATE TABLE doc_partial (LIKE doc_full INCLUDING ALL);
INSERT INTO doc_partial OVERRIDING SYSTEM VALUE SELECT * FROM doc_full ORDER BY id;
CREATE INDEX doc_full_cust    ON doc_full    (customer_id, created_at DESC);
CREATE INDEX doc_partial_cust ON doc_partial (customer_id, created_at DESC)
    WHERE deleted_at IS NULL;
VACUUM ANALYZE doc_full;
VACUUM ANALYZE doc_partial;
```

**Task.**

1. The business rule is "one live document reference per customer". Add it as an ordinary
   unique constraint on `doc_full`, soft-delete a document, and try to re-create it.
   Then fix it with a partial unique index and show the re-creation succeeds while a
   second live duplicate still fails.
2. Write a function that returns the buffers (hit + read) touched by the query "20 newest
   live documents for each of 50 customers" against a named table, using
   `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`. Explain why you run it twice and keep the
   second figure.
3. Soft-delete 0%, 50% and 90% of the rows in *both* tables (choose rows by a hash of the
   id so the run repeats), vacuuming after each step. Record live rows, buffers for each
   table and the index sizes in pages.
4. Show the plan for one customer at 90% dead on the ordinary table and identify the line
   that is the cost.
5. Archive the dead rows out of `doc_full` in a single statement. Report the live and
   archived counts, the buffers afterwards, and the heap size in pages after
   `VACUUM FULL` against the size at 90% dead from step 3.
6. In two sentences: when is soft delete's read cost small, and when is it large?

**Solution.**

Step 1 — the unique problem. Priya's document is soft-deleted; re-creating it collides
with the corpse:

```sql
CREATE TABLE doc_demo (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    ref        text NOT NULL,
    deleted_at timestamptz,
    UNIQUE (ref)
);
INSERT INTO doc_demo (ref) VALUES ('DOC-NEW-1');
UPDATE doc_demo SET deleted_at = now() WHERE ref = 'DOC-NEW-1';
INSERT INTO doc_demo (ref) VALUES ('DOC-NEW-1');
```

```text
ERROR:  duplicate key value violates unique constraint "doc_demo_ref_key"
DETAIL:  Key (ref)=(DOC-NEW-1) already exists.
```


Then the partial unique index (the constraint has to be dropped first, as a constraint
cannot be partial):

```sql
ALTER TABLE doc_demo DROP CONSTRAINT doc_demo_ref_key;
CREATE UNIQUE INDEX doc_demo_ref_live ON doc_demo (ref) WHERE deleted_at IS NULL;

INSERT INTO doc_demo (ref) VALUES ('DOC-NEW-1');
INSERT INTO doc_demo (ref) VALUES ('DOC-NEW-1');
SELECT id, ref, deleted_at IS NULL AS live FROM doc_demo ORDER BY id;
```

```text
ERROR:  duplicate key value violates unique constraint "doc_demo_ref_live"
DETAIL:  Key (ref)=(DOC-NEW-1) already exists.
 id |    ref    | live
----+-----------+------
  1 | DOC-NEW-1 | f
  3 | DOC-NEW-1 | t
(2 rows)
```


The first `INSERT` after the fix reused the deleted reference; the second was rejected
because a live row now holds it.

Step 2 — the measuring function. The first run may read pages from disk; the second is
warm, and buffer counts from a warm run do not depend on cache state:

```sql
CREATE FUNCTION live_buffers(t regclass) RETURNS bigint LANGUAGE plpgsql AS $$
DECLARE j jsonb;
BEGIN
    EXECUTE format($q$EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON, TIMING OFF, SUMMARY OFF)
        SELECT sum(length(t.ref)) FROM generate_series(1, 50) c,
        LATERAL (SELECT ref FROM %s
                 WHERE customer_id = c AND deleted_at IS NULL
                 ORDER BY created_at DESC LIMIT 20) t$q$, t) INTO j;
    RETURN (j -> 0 -> 'Plan' ->> 'Shared Hit Blocks')::bigint
         + (j -> 0 -> 'Plan' ->> 'Shared Read Blocks')::bigint;
END $$;
```


Step 3 — the experiment. `\gexec` runs each generated statement in its own transaction,
which `VACUUM` requires:

```sql
SELECT pg_relation_size('doc_full_cust') / 8192 AS full_index_pages_before,
       pg_relation_size('doc_partial_cust') / 8192 AS partial_index_pages_before;

CREATE TABLE soft_result (dead_pct int, live_rows bigint, buffers_full bigint, buffers_partial bigint);

SELECT stmt FROM unnest(ARRAY[0, 50, 90]) AS pct,
LATERAL unnest(ARRAY[
    format('UPDATE doc_full    SET deleted_at = now() WHERE deleted_at IS NULL AND abs(hashint4(id::int)) %% 100 < %s', pct),
    format('UPDATE doc_partial SET deleted_at = now() WHERE deleted_at IS NULL AND abs(hashint4(id::int)) %% 100 < %s', pct),
    'VACUUM ANALYZE doc_full',
    'VACUUM ANALYZE doc_partial',
    'DO $$ BEGIN PERFORM live_buffers(''doc_full''), live_buffers(''doc_partial''); END $$',
    format('INSERT INTO soft_result SELECT %s, (SELECT count(*) FROM doc_full WHERE deleted_at IS NULL), live_buffers(''doc_full''), live_buffers(''doc_partial'')', pct)
]) WITH ORDINALITY AS s(stmt, n)
ORDER BY pct, n
\gexec

SELECT * FROM soft_result ORDER BY dead_pct;
```

The two tables are identical until rows are deleted. Then the ordinary index pays for
every dead row it has to step over, and the partial index does not. Compare the index
sizes before and after: the ordinary index doubled because every soft delete is an
`UPDATE` that writes a new row version and a new index entry; the partial index did not.

Step 5 — archive. The heap was 6,215 pages at 90% dead (step 3):

```sql
CREATE TABLE doc_archive (LIKE doc_full INCLUDING DEFAULTS);

WITH moved AS (
    DELETE FROM doc_full WHERE deleted_at IS NOT NULL RETURNING *
)
INSERT INTO doc_archive SELECT * FROM moved;

VACUUM ANALYZE doc_full;
DO $$ BEGIN PERFORM live_buffers('doc_full'); END $$;
SELECT (SELECT count(*) FROM doc_full) AS live, (SELECT count(*) FROM doc_archive) AS archived,
       live_buffers('doc_full') AS buffers;
VACUUM FULL doc_full;
SELECT pg_relation_size('doc_full') / 8192 AS heap_pages_after_vacuum_full;
```

Step 6 — a defensible answer: "The read cost is small while few rows are deleted or
queries do not page through the newest rows; it is large when dead rows outnumber live
ones and the hot query reads recent rows (here about 5,200 buffers against under 700 at
90% dead). A partial index removes the read cost but not the table size; archiving
removes both, at the price of a second table and a move statement."
