# Chapter 12 Exercises — CTEs and Recursive Queries

## Practice Session 12.1 — Refactor nested subqueries into CTEs

**Goal.** Turn a query written as nested subqueries into named common table expressions,
and establish from the plans that the rewrite is not only easier to read but does strictly
less work.

**Setup.** The small `retail` dataset.

```bash
psql -d retail
```

```sql
SELECT count(*) FROM orders;    -- expect 2500
```

Output in this book prints NULL as `(null)`. If you have not set that already:

```sql
\pset null '(null)'
```

**Task.**

Here is a query answering *which customers spent more than the average customer spend in
2026, and who are they*. It works. Run it and confirm you get five rows.

```sql
SELECT c.name, c.city, t.spend
FROM   customers c
JOIN   ( SELECT customer_id, sum(total_amount) AS spend
         FROM   orders
         WHERE  placed_at >= DATE '2026-01-01'
         GROUP  BY customer_id ) t ON t.customer_id = c.id
WHERE  t.spend > ( SELECT avg(spend)
                   FROM ( SELECT sum(total_amount) AS spend
                          FROM   orders
                          WHERE  placed_at >= DATE '2026-01-01'
                          GROUP  BY customer_id ) s )
ORDER  BY t.spend DESC
LIMIT  5;
```

1. Read it and identify, in writing, what is duplicated.
2. Rewrite it using two CTEs — one for the per-customer 2026 totals, one for the average
   of those totals — so that the duplicated expression appears exactly once. The second
   CTE must be defined in terms of the first.
3. Confirm the rewrite returns identical rows.
4. Get `EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)` for both. Count the `Seq Scan on orders`
   nodes in each and explain the difference.
5. Answer: given Chapter 12 said a CTE referenced once is inlined, why is the CTE in your
   rewrite *not* inlined?

**Solution.**

**1 — what is duplicated.**

```sql
SELECT customer_id, sum(total_amount) AS spend
FROM   orders
WHERE  placed_at >= DATE '2026-01-01'
GROUP  BY customer_id
```

That block appears twice, character for character. Once as the derived table `t`,
supplying each customer's spend, and once inside the scalar subquery, supplying the
population that the average is taken over. They must stay identical for the query to be
correct, and nothing in the SQL enforces that. Change `2026-01-01` in one and not the
other and you get a number — a wrong one, with no error.

The five rows:

```text
      name       |   city    |  spend  
-----------------+-----------+---------
 Farhan Patel    | (null)    | 8732.54
 Harpreet Shetty | Ahmedabad | 7268.68
 Anita Verma     | (null)    | 6652.96
 Vikram Menon    | Indore    | 6117.48
 Aditya Pillai   | Hyderabad | 6066.10
(5 rows)

```

Two of the five have no city on file. That is a real property of the `retail` customers
table, not a bug in the query, and it is worth noticing now rather than when the chart is
built.

**2 and 3 — the rewrite.**

```sql
WITH spend_2026 AS (
    SELECT customer_id, sum(total_amount) AS spend
    FROM   orders
    WHERE  placed_at >= DATE '2026-01-01'
    GROUP  BY customer_id
),
average_spend AS (
    SELECT avg(spend) AS mean_spend FROM spend_2026
)
SELECT c.name, c.city, s.spend
FROM   spend_2026 s
JOIN   customers c ON c.id = s.customer_id
CROSS  JOIN average_spend a
WHERE  s.spend > a.mean_spend
ORDER  BY s.spend DESC
LIMIT  5;
```

```text
      name       |   city    |  spend  
-----------------+-----------+---------
 Farhan Patel    | (null)    | 8732.54
 Harpreet Shetty | Ahmedabad | 7268.68
 Anita Verma     | (null)    | 6652.96
 Vikram Menon    | Indore    | 6117.48
 Aditya Pillai   | Hyderabad | 6066.10
(5 rows)

```

Identical. Three things are better. The aggregate is written once. `average_spend` is
defined *in terms of* `spend_2026`, which is the chaining that makes CTEs worth using — a
later branch of the same `WITH` may reference any earlier branch. And the query now reads
in the order you would explain it aloud: here are the 2026 totals, here is their average,
here are the customers above it.

The `CROSS JOIN average_spend a` deserves a word. `average_spend` is a single row holding
a single value, so cross-joining it multiplies nothing; it is the tidiest way to bring a
scalar into the `WHERE` clause without re-nesting a subquery.
`WHERE s.spend > (SELECT mean_spend FROM average_spend)` is equally correct and equally
fast here.

**4 — the plans.**

Nested:

```text
 Limit (actual rows=5 loops=1)
   InitPlan 1 (returns $0)
     ->  Aggregate (actual rows=1 loops=1)
           ->  HashAggregate (actual rows=452 loops=1)
                 Group Key: orders_1.customer_id
                 Batches: 1  Memory Usage: 297kB
                 ->  Seq Scan on orders orders_1 (actual rows=672 loops=1)
                       Filter: (placed_at >= '2026-01-01'::date)
                       Rows Removed by Filter: 1828
   ->  Sort (actual rows=5 loops=1)
         Sort Key: t.spend DESC
         Sort Method: top-N heapsort  Memory: 25kB
         ->  Hash Join (actual rows=200 loops=1)
               Hash Cond: (c.id = t.customer_id)
               ->  Seq Scan on customers c (actual rows=1000 loops=1)
               ->  Hash (actual rows=200 loops=1)
                     Buckets: 1024  Batches: 1  Memory Usage: 17kB
                     ->  Subquery Scan on t (actual rows=200 loops=1)
                           ->  HashAggregate (actual rows=200 loops=1)
                                 Group Key: orders.customer_id
                                 Filter: (sum(orders.total_amount) > $0)
                                 Batches: 1  Memory Usage: 297kB
                                 Rows Removed by Filter: 252
                                 ->  Seq Scan on orders (actual rows=672 loops=1)
                                       Filter: (placed_at >= '2026-01-01'::date)
                                       Rows Removed by Filter: 1828
 Planning Time: 0.227 ms
 Execution Time: 0.581 ms
```

CTEs:

```text
 Limit (actual rows=5 loops=1)
   CTE spend_2026
     ->  HashAggregate (actual rows=452 loops=1)
           Group Key: orders.customer_id
           Batches: 1  Memory Usage: 297kB
           ->  Seq Scan on orders (actual rows=672 loops=1)
                 Filter: (placed_at >= '2026-01-01'::date)
                 Rows Removed by Filter: 1828
   ->  Sort (actual rows=5 loops=1)
         Sort Key: s.spend DESC
         Sort Method: top-N heapsort  Memory: 25kB
         ->  Hash Join (actual rows=200 loops=1)
               Hash Cond: (s.customer_id = c.id)
               ->  Nested Loop (actual rows=200 loops=1)
                     Join Filter: (s.spend > (avg(spend_2026.spend)))
                     Rows Removed by Join Filter: 252
                     ->  Aggregate (actual rows=1 loops=1)
                           ->  CTE Scan on spend_2026 (actual rows=452 loops=1)
                     ->  CTE Scan on spend_2026 s (actual rows=452 loops=1)
               ->  Hash (actual rows=1000 loops=1)
                     Buckets: 1024  Batches: 1  Memory Usage: 65kB
                     ->  Seq Scan on customers c (actual rows=1000 loops=1)
 Planning Time: 0.235 ms
 Execution Time: 0.460 ms
```

**Two `Seq Scan on orders` in the nested plan, one in the CTE plan.** The nested version
also builds the same `HashAggregate` over `customer_id` twice, once inside `InitPlan 1`
and once under the `Subquery Scan`. PostgreSQL does not detect that two textually
identical subqueries are one computation — it has no common-subexpression elimination
across derived tables — so it does the work twice. Naming it once made the database do it
once.

Do not read too much into the timings. At 2,500 orders both queries are well under a
millisecond and the ordering flips between runs. The structural difference is the finding;
it is what turns into seconds on the large variant.

**5 — why the CTE was not inlined.**

Because `spend_2026` is referenced **twice** — once by `average_spend` and once by the
final `SELECT`. Inlining applies only to a CTE referenced exactly once. You can see the
decision in the plan: a `CTE spend_2026` node computing the aggregate, and two `CTE Scan`
nodes reading the stored result.

This is the case where materialisation is what you want and you get it for free. Add
`NOT MATERIALIZED` and PostgreSQL will inline both references, computing the aggregate
twice and giving you the nested query's plan back.

## Practice Session 12.2 — Walk the `hr` org chart

**Goal.** Traverse a self-referencing management hierarchy in both directions, computing
each employee's depth, the path of ids from the root, and the total number of people
beneath each executive.

**Setup.** The small `hr` dataset.

```bash
psql -d hr
```

```sql
SELECT count(*) FROM employees;                              -- expect 2774
SELECT count(*) FROM employees WHERE manager_id IS NULL;     -- expect 1, the CEO
```

`employees.manager_id` is a foreign key to `employees.emp_id`. It is NULL on exactly one
row, and there are no cycles and no orphans — which is what makes this dataset safe to
walk with `UNION ALL`. Output in this book prints NULL as `(null)`:

```sql
\pset null '(null)'
```

**Task.**

1. Write a recursive CTE that walks down from the CEO, carrying a `depth` counter and a
   `path` array of `emp_id` values. Report how many employees sit at each depth, and the
   job title found at that level. How deep is the tree?
2. Without recursion, work out how many direct reports each manager has, and produce a
   histogram of that. What is the branching factor?
3. Using the `path` column from step 1, list a subtree in depth-first order — parent
   immediately followed by its children. Do not sort by name.
4. Walk *upwards*: for employee 2774, produce the complete chain of managers up to the
   CEO, one row per level.
5. For the CEO and each of the five executives reporting to them, report both the number
   of direct reports and the total number of people anywhere beneath them. Explain why
   these two numbers need different techniques.

**Solution.**

**1 — walking down, with depth and path.**

```sql
WITH RECURSIVE chart AS (
    SELECT emp_id, full_name, job_title, manager_id,
           1 AS depth, ARRAY[emp_id] AS path
    FROM   employees
    WHERE  manager_id IS NULL
  UNION ALL
    SELECT e.emp_id, e.full_name, e.job_title, e.manager_id,
           c.depth + 1, c.path || e.emp_id
    FROM   employees e
    JOIN   chart c ON e.manager_id = c.emp_id
)
SELECT depth, count(*) AS employees, min(job_title) AS title
FROM   chart
GROUP  BY depth
ORDER  BY depth;
```

```text
 depth | employees |          title          
-------+-----------+-------------------------
     1 |         1 | Chief Executive Officer
     2 |         5 | Senior Vice President
     3 |        18 | Vice President
     4 |        70 | Director
     5 |       280 | Senior Manager
     6 |      1100 | Team Lead
     7 |      1300 | Individual Contributor
(7 rows)

```

**Seven levels**, and the counts sum to 2,774 — every employee is reachable from the root,
which is the check worth running on any hierarchy before you trust a report built on it.
If the sum had been less than `count(*) FROM employees`, the missing rows would be orphans
or members of a disconnected cycle.

The two things to understand:

- **The anchor term is `WHERE manager_id IS NULL`.** It runs once and produces the single
  root row. `depth` is seeded to 1 and `path` to a one-element array there.
- **The recursive term joins `employees` to `chart`.** On each iteration `chart` contains
  *only the rows produced by the previous iteration*, not everything accumulated so far.
  So iteration 1 finds the CEO's direct reports, iteration 2 finds theirs, and so on. It
  stops when an iteration produces no rows.

`min(job_title)` is there only because the select-list rule requires an aggregate; in this
dataset job title is a pure function of level, so the minimum is the only value.

**2 — the branching factor, without recursion.**

Direct reports are one level, so this needs a plain `GROUP BY`, not recursion. Counting
the groups gives the histogram:

```sql
SELECT direct_reports, count(*) AS managers
FROM ( SELECT manager_id, count(*) AS direct_reports
       FROM   employees
       WHERE  manager_id IS NOT NULL
       GROUP  BY manager_id ) t
GROUP  BY direct_reports
ORDER  BY direct_reports;
```

```text
 direct_reports | managers 
----------------+----------
              1 |      421
              2 |      274
              3 |      194
              4 |      108
              5 |       68
              6 |       31
              7 |       22
              8 |        9
              9 |        2
             10 |        2
(10 rows)

```

**Branching runs from 1 to 10**, heavily weighted towards small teams: 421 managers have a
single direct report, two have ten. That unevenness matters for the next chapter you will
use this dataset in — a uniform tree makes "rank within manager" windows degenerate — and
it matters here because it means the recursive walk's per-iteration row counts are lumpy.

`WHERE manager_id IS NOT NULL` is load-bearing. Without it the CEO's NULL manager forms
its own group, and you would report a phantom manager with one direct report.

**3 — depth-first order from the path array.**

```sql
WITH RECURSIVE chart AS (
    SELECT emp_id, full_name, job_title, manager_id,
           1 AS depth, ARRAY[emp_id] AS path
    FROM   employees
    WHERE  manager_id IS NULL
  UNION ALL
    SELECT e.emp_id, e.full_name, e.job_title, e.manager_id,
           c.depth + 1, c.path || e.emp_id
    FROM   employees e
    JOIN   chart c ON e.manager_id = c.emp_id
)
SELECT depth, emp_id, full_name, path
FROM   chart
WHERE  path[2] = 6          -- the subtree under employee 6
ORDER  BY path
LIMIT  10;
```

```text
 depth | emp_id |     full_name     |           path           
-------+--------+-------------------+--------------------------
     2 |      6 | Vikram Singh      | {1,6}
     3 |     13 | Nisha Iyer        | {1,6,13}
     4 |     31 | Fatima Chatterjee | {1,6,13,31}
     5 |    180 | Nisha Iyer        | {1,6,13,31,180}
     6 |    479 | Aditya Gupta      | {1,6,13,31,180,479}
     7 |   1921 | Aditya Singh      | {1,6,13,31,180,479,1921}
     6 |    685 | Sneha Rao         | {1,6,13,31,180,685}
     6 |    786 | Priya Kumar       | {1,6,13,31,180,786}
     7 |   1995 | Karthik Singh     | {1,6,13,31,180,786,1995}
     7 |   2487 | Imran Banerjee    | {1,6,13,31,180,786,2487}
(10 rows)

```

`ORDER BY path` on an `integer[]` compares element by element, shorter array first when
one is a prefix of the other. That is exactly document order for a tree: a node sorts
immediately before its own descendants, and sibling subtrees stay contiguous. Prefix the
`full_name` with `repeat('  ', depth - 1)` and you have a rendered org chart.

`WHERE path[2] = 6` selects a subtree by asking what the second element of the path is —
array subscripting on the accumulated path, which is cheaper and clearer than a second
recursive walk anchored at employee 6. Out-of-range subscripts return NULL rather than
erroring, so the root row (`{1}`, whose `path[2]` is NULL) is excluded by the usual
three-valued-logic rule from Chapter 7.

Two reasons not to build the path as a string of names instead:

- Names are not unique. There are two people called Nisha Iyer in the ten rows above, and
  sorting by a name path would interleave unrelated subtrees.
- Text sorts by the database collation, which orders `'10'` before `'9'` and applies
  language rules you did not ask for. Integer arrays compare numerically.

**4 — walking up to the root.**

Same construct, arrow reversed. The anchor is the employee of interest, and the recursive
term joins the *manager's* row to the current row rather than the other way around:

```sql
WITH RECURSIVE chain AS (
    SELECT emp_id, manager_id, full_name, job_title, 0 AS steps_up
    FROM   employees
    WHERE  emp_id = 2774
  UNION ALL
    SELECT m.emp_id, m.manager_id, m.full_name, m.job_title, c.steps_up + 1
    FROM   employees m
    JOIN   chain c ON m.emp_id = c.manager_id
)
SELECT steps_up, emp_id, full_name, job_title
FROM   chain
ORDER  BY steps_up;
```

```text
 steps_up | emp_id |   full_name    |        job_title        
----------+--------+----------------+-------------------------
        0 |   2774 | Vikram Desai   | Individual Contributor
        1 |   1123 | Fatima Rao     | Team Lead
        2 |     95 | Harpreet Desai | Senior Manager
        3 |     44 | Karthik Reddy  | Director
        4 |     23 | Ananya Desai   | Vice President
        5 |      2 | Sneha Reddy    | Senior Vice President
        6 |      1 | Ananya Reddy   | Chief Executive Officer
(7 rows)

```

Note the join condition: `ON m.emp_id = c.manager_id`. Downward you match *the employee's
manager id to the current row's id*; upward you match *the current row's manager id to the
employee's id*. Getting these the wrong way round is the single most common mistake with
hierarchical CTEs, and it does not error — it returns one row, the anchor, because nothing
matches on the first iteration.

The walk terminates because `manager_id` is NULL at the CEO, so the join finds nothing.
That termination is a property of the **data**, not of the query. If somebody sets the
CEO's manager to one of their own reports, this query runs forever. Session 12.2's dataset
has no cycles; production data eventually will.

**5 — direct reports versus everybody beneath.**

```sql
WITH RECURSIVE chart AS (
    SELECT emp_id, full_name, job_title, manager_id,
           1 AS depth, ARRAY[emp_id] AS path
    FROM   employees
    WHERE  manager_id IS NULL
  UNION ALL
    SELECT e.emp_id, e.full_name, e.job_title, e.manager_id,
           c.depth + 1, c.path || e.emp_id
    FROM   employees e
    JOIN   chart c ON e.manager_id = c.emp_id
)
SELECT m.emp_id, m.full_name, m.depth,
       (SELECT count(*) FROM employees d WHERE d.manager_id = m.emp_id) AS direct,
       (SELECT count(*) FROM chart s
        WHERE  m.emp_id = ANY (s.path) AND s.emp_id <> m.emp_id)        AS total_below
FROM   chart m
WHERE  m.depth <= 2
ORDER  BY total_below DESC;
```

```text
 emp_id |     full_name     | depth | direct | total_below 
--------+-------------------+-------+--------+-------------
      1 | Ananya Reddy      |     1 |      5 |        2773
      5 | Lakshmi Gupta     |     2 |      6 |        1197
      4 | Fatima Chatterjee |     2 |      6 |        1009
      3 | Nisha Kulkarni    |     2 |      2 |         244
      2 | Sneha Reddy       |     2 |      3 |         206
      6 | Vikram Singh      |     2 |      1 |         112
(6 rows)

```

**The two counts need different machinery because they are different relations.** `direct`
is a one-step relationship, answerable by a single equality against `manager_id` — no
recursion required, and cheap. `total_below` is the transitive closure of that
relationship, and there is no way to compute it without walking the tree.

Having walked it once, though, you do not need to walk it again per manager. The `path`
array already encodes every ancestor of every row, so `m.emp_id = ANY (s.path)` asks *is
this manager anywhere above that employee* with an array containment test. `s.emp_id <>
m.emp_id` excludes the manager from their own count, since a row's path includes itself.

The CEO's 2,773 is `count(*) - 1`, which is the arithmetic check that the tree is fully
connected. And notice how badly `direct` predicts `total_below`: Lakshmi Gupta and Fatima
Chatterjee both have six direct reports and differ by 188 people underneath. An
organisational report that counts direct reports and calls it span of control is measuring
the wrong thing.

## Practice Session 12.3 — Generate a date series to fill gaps

**Goal.** Produce a monthly report over a fixed period in which every month appears,
including the months where nothing happened, and decide deliberately what an empty month
should display.

**Setup.** The small `retail` dataset.

```bash
psql -d retail
```

```sql
SELECT min(placed_at), max(placed_at) FROM orders;
\pset null '(null)'
```

Orders run from January 2024 to 1 September 2026. The reporting period for this session is
the nine months **January to September 2026**.

**Task.**

1. Report the count and revenue of orders over 4000, by month, for the reporting period.
   How many rows come back, and how many should?
2. Produce the nine months of the period as a result set, using `generate_series`.
3. Combine the two so that every month in the period appears. Leave the empty months as
   NULL first, then decide what they should show and justify it.
4. Build the same nine-month series with a recursive CTE instead, and say where the
   termination condition lives.
5. Deliberately join the two the wrong way round and explain what you see.

**Solution.**

**1 — the report with gaps in it.**

```sql
SELECT date_trunc('month', placed_at)::date AS month,
       count(*)          AS orders,
       sum(total_amount) AS revenue
FROM   orders
WHERE  total_amount > 4000
  AND  placed_at >= DATE '2026-01-01'
  AND  placed_at <  DATE '2026-10-01'
GROUP  BY 1
ORDER  BY 1;
```

```text
   month    | orders | revenue 
------------+--------+---------
 2026-03-01 |      1 | 4825.24
 2026-04-01 |      2 | 8489.60
 2026-05-01 |      1 | 4196.31
 2026-06-01 |      1 | 4077.56
(4 rows)

```

Four rows where the period has nine months. `GROUP BY` emits one row per group **present
in the input**, and five of the months contain no order over 4000, so they produce no
group at all. This is the limitation Chapter 8 set up: `coalesce` cannot help, because
there is no row to coalesce. The missing months have to come from somewhere other than
`orders`.

Note also the half-open range
`placed_at >= DATE '2026-01-01' AND placed_at < DATE '2026-10-01'`. Writing
`<= DATE '2026-09-30'` would silently drop anything placed during the last day, because
`placed_at` is a `timestamptz` and `2026-09-30 14:22:00+00` is greater than
`2026-09-30 00:00:00+00`. Half-open ranges on timestamps, always.

**2 — the months.**

```sql
SELECT generate_series(DATE '2026-01-01',
                       DATE '2026-09-01',
                       INTERVAL '1 month')::date AS month;
```

```text
   month    
------------
 2026-01-01
 2026-02-01
 2026-03-01
 2026-04-01
 2026-05-01
 2026-06-01
 2026-07-01
 2026-08-01
 2026-09-01
(9 rows)

```

`generate_series` is a set-returning function: three arguments, start, stop and step, and
it emits one row per step with the stop value **included**. The `::date` cast matters,
because `generate_series` over dates with an `interval` step returns `timestamptz`, and
comparing a `timestamptz` to the `date` produced by `date_trunc(...)::date` on the other
side of the join would force a cast on every row and could mismatch at time-zone
boundaries. Cast once, in the series.

**3 — the two combined.**

```sql
WITH months AS (
    SELECT generate_series(DATE '2026-01-01',
                           DATE '2026-09-01',
                           INTERVAL '1 month')::date AS month
),
large_orders AS (
    SELECT date_trunc('month', placed_at)::date AS month,
           count(*)          AS orders,
           sum(total_amount) AS revenue
    FROM   orders
    WHERE  total_amount > 4000
      AND  placed_at >= DATE '2026-01-01'
      AND  placed_at <  DATE '2026-10-01'
    GROUP  BY 1
)
SELECT m.month, l.orders, l.revenue
FROM   months m
LEFT   JOIN large_orders l ON l.month = m.month
ORDER  BY m.month;
```

```text
   month    | orders | revenue 
------------+--------+---------
 2026-01-01 | (null) |  (null)
 2026-02-01 | (null) |  (null)
 2026-03-01 |      1 | 4825.24
 2026-04-01 |      2 | 8489.60
 2026-05-01 |      1 | 4196.31
 2026-06-01 |      1 | 4077.56
 2026-07-01 | (null) |  (null)
 2026-08-01 | (null) |  (null)
 2026-09-01 | (null) |  (null)
(9 rows)

```

Nine rows. The `months` CTE is the **driving side** of the `LEFT JOIN`: every month
survives, and the aggregate columns are NULL where no group matched.

Now the decision. Wrapping both in `coalesce` gives:

```sql
SELECT m.month,
       coalesce(l.orders, 0)  AS orders,
       coalesce(l.revenue, 0) AS revenue
FROM   months m
LEFT   JOIN large_orders l ON l.month = m.month
ORDER  BY m.month;
```

```text
   month    | orders | revenue 
------------+--------+---------
 2026-01-01 |      0 |       0
 2026-02-01 |      0 |       0
 2026-03-01 |      1 | 4825.24
 2026-04-01 |      2 | 8489.60
 2026-05-01 |      1 | 4196.31
 2026-06-01 |      1 | 4077.56
 2026-07-01 |      0 |       0
 2026-08-01 |      0 |       0
 2026-09-01 |      0 |       0
(9 rows)

```

**Zero is right here, and it is not always right.** The measure is *count and value of
large orders placed in the month*, an event count over a window. No matching events means
the count is genuinely zero, and a chart that plots zero is telling the truth.

It would be wrong for a *stock* measure — closing inventory level, headcount, account
balance. There, a month with no rows means the value did not change, and writing zero
invents a collapse that did not happen. The fix for that shape is to carry the last known
value forward, which is a window function (Chapter 25), not a `coalesce`.

The test: ask what a missing row means in the source system. *No events occurred* →
`coalesce(..., 0)`. *Nothing was recorded because nothing changed* → carry forward. *We do
not know* → leave it NULL and label it, because a fabricated zero is worse than an honest
gap.

One more thing about the September row. The dataset ends on 1 September 2026, so September
is a partial month. Here it happens to be empty anyway, but in a report over all orders it
would show a real number that is not comparable with the eight full months before it.
Ragged final buckets are read as trends by everyone who did not build the report.

**4 — the series by recursion.**

```sql
WITH RECURSIVE months AS (
    SELECT DATE '2026-01-01' AS month
  UNION ALL
    SELECT (month + INTERVAL '1 month')::date
    FROM   months
    WHERE  month < DATE '2026-09-01'
)
SELECT count(*) AS rows, min(month) AS first, max(month) AS last FROM months;
```

```text
 rows |   first    |    last    
------+------------+------------
    9 | 2026-01-01 | 2026-09-01
(1 row)

```

The termination condition is **`WHERE month < DATE '2026-09-01'` inside the recursive
term**, and nowhere else. When the working table holds only the row for September, that
predicate is false, the recursive term returns zero rows, and the loop ends. Delete the
`WHERE` and this query generates months until the session is killed — there is no implicit
limit.

Use `generate_series` in real code when the step is a fixed interval; it is shorter,
faster and cannot run away. Reach for the recursive form when the next value is not a
fixed offset from the previous one — the next working day, the next billing anniversary,
the next value of a balance that depends on the one before it.

**5 — the join the wrong way round.**

`months` and `large_orders` are CTEs, not tables, so both definitions have to come along
for the ride — only the final `SELECT` changes:

```sql
WITH months AS (
    SELECT generate_series(DATE '2026-01-01',
                           DATE '2026-09-01',
                           INTERVAL '1 month')::date AS month
),
large_orders AS (
    SELECT date_trunc('month', placed_at)::date AS month,
           count(*)          AS orders,
           sum(total_amount) AS revenue
    FROM   orders
    WHERE  total_amount > 4000
      AND  placed_at >= DATE '2026-01-01'
      AND  placed_at <  DATE '2026-10-01'
    GROUP  BY 1
)
SELECT l.month, l.orders
FROM   large_orders l
LEFT   JOIN months m ON m.month = l.month
ORDER  BY l.month;
```

```text
   month    | orders 
------------+--------
 2026-03-01 |      1
 2026-04-01 |      2
 2026-05-01 |      1
 2026-06-01 |      1
(4 rows)

```

Four rows again. A `LEFT JOIN` preserves every row of its **left** input, and the left
input here is the aggregate, which never had the five missing months to begin with. The
series has to drive: `FROM months LEFT JOIN data`, or equivalently
`FROM data RIGHT JOIN months`. This is an easy thing to get backwards during a refactor,
and the symptom is not an error — it is a chart that quietly loses its quiet months.

Your absolute timings will differ from the ones below, and will move between runs on the
same machine. Run each query two or three times before believing a number. The ratios and
the plan shapes are the point.

**Task.**

1. Write a CTE selecting the delivered orders, and an outer query restricting to
   `id BETWEEN 100000 AND 100010`. Get `EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)`. Where
   did the CTE go?
2. Add `MATERIALIZED` and get the plan again. Account for every row count in it.
3. Reference the same CTE twice and get the plan. What changed, and why?
4. Add `NOT MATERIALIZED` to the twice-referenced version. Is it faster?
5. In `ch12_scratch`, write a CTE that computes `slow_score(i)` over 500 rows and an outer
   query filtering on the result with two conditions. Compare with and without
   `MATERIALIZED`, and explain the difference from the `Filter:` line alone.

**Solution.**

**1 — the CTE disappears.**

```sql
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)
WITH delivered AS (
    SELECT id, customer_id, placed_at, total_amount
    FROM   orders
    WHERE  status = 'delivered'
)
SELECT * FROM delivered WHERE id BETWEEN 100000 AND 100010;
```

```text
 Index Scan using orders_pkey on orders (actual rows=5 loops=1)
   Index Cond: ((id >= 100000) AND (id <= 100010))
   Filter: (status = 'delivered'::text)
   Rows Removed by Filter: 6
 Planning Time: 0.174 ms
 Execution Time: 0.050 ms
```

There is no `CTE` node and no `CTE Scan`. PostgreSQL **inlined** `delivered` into the
outer query, exactly as though you had written it as a subquery in `FROM`. Having done so,
it could see the `id` predicate and the table together, so it pushed
`id BETWEEN 100000 AND 100010` down as an `Index Cond` on the primary key and used the
index.

Read the row counts: eleven index tuples fetched, `Rows Removed by Filter: 6` for the ones
whose status is not `delivered`, five rows out. The `status` test is a `Filter` rather
than an `Index Cond` because there is no index on `status` — the sample datasets ship with
no indexes beyond primary keys, deliberately (Chapter 33).

**2 — `MATERIALIZED` restores the fence.**

```sql
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)
WITH delivered AS MATERIALIZED (
    SELECT id, customer_id, placed_at, total_amount
    FROM   orders
    WHERE  status = 'delivered'
)
SELECT * FROM delivered WHERE id BETWEEN 100000 AND 100010;
```

```text
 CTE Scan on delivered (actual rows=5 loops=1)
   Filter: ((id >= 100000) AND (id <= 100010))
   Rows Removed by Filter: 799981
   CTE delivered
     ->  Seq Scan on orders (actual rows=799986 loops=1)
           Filter: (status = 'delivered'::text)
           Rows Removed by Filter: 1200014
 Planning Time: 0.132 ms
 Execution Time: 168.002 ms

```

0.050 ms against 168.002 ms, for the same rows, from one keyword.

Every number in that plan follows from the fence:

- `Seq Scan on orders ... Rows Removed by Filter: 1200014` — **no `id` condition anywhere
  on the scan.** The outer query's predicate could not reach inside, so all 2,000,000 rows
  were read. 1,200,014 were not delivered and 799,986 were.
- `CTE delivered` — those 799,986 rows were materialised into a tuplestore.
- `CTE Scan ... Rows Removed by Filter: 799981` — the `id` predicate was applied
  *afterwards*, discarding 799,981 of the 799,986 rows the scan had just produced, to keep
  5.
- 799,986 − 799,981 = 5. The arithmetic closes.

This is exactly what PostgreSQL 11 and earlier did to every CTE, without asking. That is
why advice from before 2019 tells you `WITH` is an optimisation fence, and why following
that advice today produces the opposite of what it promises.

**3 — two references, and the fence comes back on its own.**

```sql
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)
WITH delivered AS (
    SELECT id, total_amount FROM orders WHERE status = 'delivered'
)
SELECT (SELECT count(*) FROM delivered)          AS n,
       (SELECT sum(total_amount) FROM delivered) AS revenue;
```

```text
 Result (actual rows=1 loops=1)
   CTE delivered
     ->  Seq Scan on orders (actual rows=799986 loops=1)
           Filter: (status = 'delivered'::text)
           Rows Removed by Filter: 1200014
   InitPlan 2 (returns $1)
     ->  Aggregate (actual rows=1 loops=1)
           ->  CTE Scan on delivered (actual rows=799986 loops=1)
   InitPlan 3 (returns $2)
     ->  Aggregate (actual rows=1 loops=1)
           ->  CTE Scan on delivered delivered_1 (actual rows=799986 loops=1)
 Planning Time: 0.222 ms
 Execution Time: 180.263 ms
```

The `CTE delivered` node is back, and there are now **two** `CTE Scan` nodes reading it.
One scan of `orders`, one materialised result, two consumers.

Inlining requires the CTE to be referenced **exactly once**. With two references, inlining
would mean substituting the subquery into both places and executing it twice, so
PostgreSQL computes it once and stores it instead. You did not ask for this and you did
not need to — the default is the sensible one.

**4 — forcing inlining on the twice-referenced version.**

```sql
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)
WITH delivered AS NOT MATERIALIZED (
    SELECT id, total_amount FROM orders WHERE status = 'delivered'
)
SELECT (SELECT count(*) FROM delivered)          AS n,
       (SELECT sum(total_amount) FROM delivered) AS revenue;
```

```text
 Result (actual rows=1 loops=1)
   InitPlan 1 (returns $1)
     ->  Finalize Aggregate (actual rows=1 loops=1)
           ->  Gather (actual rows=3 loops=1)
                 Workers Planned: 2
                 Workers Launched: 2
                 ->  Partial Aggregate (actual rows=1 loops=3)
                       ->  Parallel Seq Scan on orders (actual rows=266662 loops=3)
                             Filter: (status = 'delivered'::text)
                             Rows Removed by Filter: 400005
   InitPlan 2 (returns $3)
     ->  Finalize Aggregate (actual rows=1 loops=1)
           ->  Gather (actual rows=3 loops=1)
                 Workers Planned: 2
                 Workers Launched: 2
                 ->  Partial Aggregate (actual rows=1 loops=3)
                       ->  Parallel Seq Scan on orders orders_1 (actual rows=266662 loops=3)
                             Filter: (status = 'delivered'::text)
                             Rows Removed by Filter: 400005
 Planning Time: 0.441 ms
 Execution Time: 93.135 ms
```

**Faster — about twice as fast**, 93 ms against 180 ms, and it should not be. Read what
the plan is doing: two independent `Parallel Seq Scan`s over `orders`, the table read
twice, 1.6 million delivered rows produced instead of 800,000. Inlining did strictly more
I/O and still won.

It won because a `CTE Scan` **cannot be parallelised**. Materialising forces the whole
800,000-row filter through one process and then drags the result back out of a tuplestore
twice; inlining hands each half of the query to two workers and a leader. Three processes
doing double work beat one process doing single work, comfortably.

Do not take that as the new rule either. Over twenty alternating runs the inlined form had
a median of 124 ms against 178 ms and won 16 of the 20 pairs — a real effect, but one that
narrowed to nothing when something else was busy on the machine, because the moment you
cannot have three processes the second scan is no longer free. Run it yourself, on your
own hardware, with the concurrency you actually have.

**That is the point of the exercise, and it is worth more than either number.**
`NOT MATERIALIZED` on a multiply-referenced CTE is a *measurement, not an optimisation*.
It trades one scan plus a tuplestore for N scans with pushdown and parallelism, and the
trade goes different ways on the same query, on the same data, on the same machine,
depending on how busy that machine is. You cannot read the answer off the SQL, and a
plausible story about which way it should go — the one in the paragraph above, which
sounds convincing and predicted the wrong winner — is not a substitute for `EXPLAIN
(ANALYZE)`.

One more thing worth knowing: `NOT MATERIALIZED` is a **request**. Put a volatile function
in the CTE and PostgreSQL ignores it, because inlining a volatile expression could change
how many times it is evaluated and therefore what the query returns:

```sql
EXPLAIN (COSTS OFF)
WITH sampled AS NOT MATERIALIZED (
    SELECT id, random() AS r FROM orders
)
SELECT * FROM sampled WHERE id = 5;
```

```text
 CTE Scan on sampled
   Filter: (id = 5)
   CTE sampled
     ->  Seq Scan on orders
```

Still a `CTE` node, still a sequential scan of two million rows to return one. No warning,
no error. The same happens for a recursive CTE, which can never be inlined.

**5 — where `MATERIALIZED` is the right answer.**

In `ch12_scratch`:

```sql
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)
WITH scored AS (
    SELECT i, slow_score(i) AS score FROM generate_series(1, 500) i
)
SELECT count(*) FROM scored WHERE score > 10 AND score < 20;
```

```text
 Aggregate (actual rows=1 loops=1)
   ->  Function Scan on generate_series i (actual rows=90 loops=1)
         Filter: ((slow_score(i) > 10) AND (slow_score(i) < 20))
         Rows Removed by Filter: 410
 Planning Time: 0.041 ms
 Execution Time: 2090.683 ms
```

```sql
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)
WITH scored AS MATERIALIZED (
    SELECT i, slow_score(i) AS score FROM generate_series(1, 500) i
)
SELECT count(*) FROM scored WHERE score > 10 AND score < 20;
```

```text
 Aggregate (actual rows=1 loops=1)
   CTE scored
     ->  Function Scan on generate_series i (actual rows=500 loops=1)
   ->  CTE Scan on scored (actual rows=90 loops=1)
         Filter: ((score > 10) AND (score < 20))
         Rows Removed by Filter: 410
 Planning Time: 0.042 ms
 Execution Time: 1103.871 ms
```

2,091 ms against 1,104 ms — inlining is roughly twice as slow — and the answer is on one
line of the first plan:

```text
Filter: ((slow_score(i) > 10) AND (slow_score(i) < 20))
```

The column `score` no longer exists in the inlined plan. Inlining substituted the
*expression* into both halves of the predicate, so `slow_score(i)` is called **up to twice
per row** instead of once. The materialised plan's filter reads
`((score > 10) AND (score < 20))`: the function was evaluated once per row into the
tuplestore, and the predicate then tested a stored value.

Count the calls rather than inferring them, because the obvious inference — 500 rows times
two predicates is 1,000 calls — is wrong:

```sql
SET track_functions = 'all';
SELECT pg_stat_reset();

WITH scored AS (SELECT i, slow_score(i) AS score FROM generate_series(1, 500) i)
SELECT count(*) FROM scored WHERE score > 10 AND score < 20;

SELECT funcname, calls FROM pg_stat_user_functions;
```

```text
  funcname  | calls
------------+-------
 slow_score |   890
(1 row)

```

**890, not 1,000.** `AND` short-circuits: the second `slow_score(i)` is only evaluated for
the rows that got past `> 10`, and 390 of the 500 do. So the inlined form does 890 calls
against the materialised form's 500 — a ratio of 1.78, which together with the per-call
overhead is the 1.9× you measured. Statistics collection is asynchronous, so allow a
second before reading `pg_stat_user_functions`.

PostgreSQL is entitled to do this because `slow_score` is declared `IMMUTABLE`, so calling
it twice is guaranteed to give the same answer. The planner's cost model has no idea it is
expensive; the default cost assumption for a function is 100 times `cpu_operator_cost`,
which here is wildly optimistic. Declaring `COST 10000` on the function tells the planner
the truth and is the more principled fix, but `MATERIALIZED` is the one you can apply to a
query you are debugging at the time.

So the practical rule for `MATERIALIZED` on a single-reference CTE: reach for it when the
CTE body is expensive per row and the outer query mentions its output columns more than
once. Otherwise leave the default alone.
