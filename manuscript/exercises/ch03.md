# Chapter 3 Exercises — Databases, Schemas, and the Cluster

## Practice Session 3.1 — Schemas and `search_path`

**Goal.** Understand name resolution well enough to predict which table a query will hit.

**Setup.**

```bash
createdb ch3_demo
psql ch3_demo
```

```sql
CREATE SCHEMA app;
CREATE SCHEMA staging;

CREATE TABLE public.widgets  (id int, origin text DEFAULT 'public');
CREATE TABLE app.widgets     (id int, origin text DEFAULT 'app');
CREATE TABLE staging.widgets (id int, origin text DEFAULT 'staging');

INSERT INTO public.widgets  (id) VALUES (1);
INSERT INTO app.widgets     (id) VALUES (2);
INSERT INTO staging.widgets (id) VALUES (3);
```

Three tables, same name, three schemas.

**Task.** Without running anything yet, predict the output of each step. Then run them.

1. `SHOW search_path;` then `SELECT * FROM widgets;`
2. `SET search_path TO app;` then `SELECT * FROM widgets;`
3. `SET search_path TO staging, app;` then `SELECT * FROM widgets;`
4. Still on that path: `CREATE TABLE gadgets (id int);` — which schema does it land in?
5. `SET search_path TO app;` then `SELECT * FROM public.widgets;`
6. `SET search_path TO '';` then `SELECT * FROM widgets;`

**Solution.**

1. Path is `"$user", public`. No schema matches your username, so `public` wins →
   `origin = public`.
2. → `origin = app`.
3. First match wins, and `staging` is first → `origin = staging`.
4. `staging`. New objects go in the **first** schema in the path. Confirm with `\dt *.*`.
5. → `origin = public`. An explicit qualification ignores `search_path` entirely. This is
   why qualifying names in application code eliminates a class of bug.
6. `ERROR: relation "widgets" does not exist`. An empty path resolves nothing. The table
   is right there and unreachable by that name.

Step 6 is the one worth sitting with. "Relation does not exist" very often does not mean
the table is missing — it means it is not on your path. Before concluding a deployment
failed, check `\dt *.*` and `SHOW search_path`.

```bash
dropdb ch3_demo
```

## Practice Session 3.2 — Collation, and why your index cares

**Goal.** See two collations produce different orderings, and understand why an index
built under one cannot serve a query under the other.

**Setup.**

```bash
createdb ch3_collate
psql ch3_collate
```

```sql
CREATE TABLE words (w text);

INSERT INTO words (w) VALUES
    ('apple'), ('Apple'), ('APPLE'),
    ('banana'), ('Banana'),
    ('ápex'), ('zebra'), ('Zebra');
```

**Task.**

1. Order by `w` with the database default. Note where the capitals land.
2. Order by `w COLLATE "C"`. Note what changed.
3. Explain, in one sentence, why `'Banana' < 'apple'` under `C` but not under `en_US`.
   Then find `ápex` in both outputs and explain why it moved from one end to the other.
4. Build an index using the `C` collation. Then `EXPLAIN` two equality lookups — one
   asking under `C`, one under the database default — and find the single word in each
   plan that tells you whether the index was actually searched.

**Solution.**

```sql
SELECT w FROM words ORDER BY w;                 -- linguistic
SELECT w FROM words ORDER BY w COLLATE "C";     -- bytewise
```

```text
ápex apple Apple APPLE banana Banana zebra Zebra     -- en_US.UTF-8
APPLE Apple Banana Zebra apple banana zebra ápex     -- C
```

Under `C`, comparison is by byte value. Every uppercase ASCII letter (65–90) is
numerically below every lowercase one (97–122), so `'B'` (66) precedes `'a'` (97) and
`Banana` sorts before `apple`. `en_US` applies dictionary rules in which case is a
tiebreaker rather than the primary sort key — which is why its output groups
`apple/Apple/APPLE` together and `C` scatters them.

Watch `ápex` in particular. Under `en_US` it sorts **first**, next to `apple`, because
linguistically `á` is an `a`. Under `C` it sorts **last**, after `zebra`, because its
UTF-8 encoding begins with byte 0xC3 — higher than every ASCII letter. Same string, same
table, opposite ends of the result.

Now the part that matters. Build an index under one collation and query under another:

```sql
CREATE INDEX words_w_c_idx ON words (w COLLATE "C");

SET enable_seqscan = off;   -- tiny table; force the planner to consider the index

EXPLAIN SELECT w FROM words WHERE w COLLATE "C" = 'apple';
EXPLAIN SELECT w FROM words WHERE w = 'apple';        -- database default collation
```

```text
 Index Only Scan using words_w_c_idx on words  (cost=0.13..8.15 rows=1 width=32)
   Index Cond: (w = 'apple'::text)

 Index Only Scan using words_w_c_idx on words  (cost=0.13..12.27 rows=1 width=32)
   Filter: (w = 'apple'::text)
```

Both plans name the same index, and a careless reading concludes both are fine. They are
not, and the difference is the two words `Index Cond` and `Filter`.

**`Index Cond`** means the condition was pushed into the index. Because the index is
sorted under `C` and the query asked under `C`, PostgreSQL can descend the B-tree
directly to the matching entries. It reads almost nothing.

**`Filter`** means the index was read as a convenient source of rows and then *every one
of them was checked*. The sort order was unusable, so there was nothing to search — the
index degenerated into a sequential scan wearing an index's clothes. Note the cost: 12.27
against 8.15 for the matching-collation lookup — and a plain sequential scan of this table
costs **1.10**, which is why we had to forbid it to see the index at all. The mismatched
index is the most expensive of the three. At eight million rows that gap is the difference
between a query and an outage.

That distinction — condition pushed into the index versus applied after the fact — is one
of the most important things to recognise in a query plan, and Chapter 34 returns to it at
length. Here it is enough to see that **a collation mismatch does not produce an error. It
silently produces a worse plan.**

And this is the mechanism behind the glibc problem. When the operating system changes its
rules, the index is still physically sorted the old way while the database believes the
new rules apply. The index has not become corrupt in the sense of damaged bytes; it has
become *sorted according to rules nobody follows any more* — so searches descend the tree
using the wrong comparisons and miss rows that are genuinely there. Wrong answers, no
error message.

> **On `SET enable_seqscan = off` —** this does not forbid sequential scans; it makes the
> planner price them absurdly high so it prefers almost anything else. It is a diagnostic
> tool for asking *what would you do if you could not scan?*, and it is invaluable on
> small tables where the planner is right that scanning eight rows beats any index. Never
> set it in application code. Chapter 34 covers the planner flags properly.

```bash
dropdb ch3_collate
```

## Practice Session 3.3 — Read the catalog

**Goal.** Get comfortable asking the database about itself. Every diagnostic in Part VIII
is a catalog query.

**Setup.** Connect to `retail` from Practice Session 2.3.

**Task.** Write queries answering:

1. What encoding and collation is this database using, and what version of the collation
   provider built it?
2. How large is each database in the cluster, in human-readable units?
3. Which schemas exist here, excluding PostgreSQL's own?
4. Which tables are in `public`, and how much disk does each occupy?

**Solution.**

```sql
-- 1
SELECT datname,
       pg_encoding_to_char(encoding) AS encoding,
       datcollate,
       datlocprovider,
       datcollversion
FROM   pg_database
WHERE  datname = current_database();
```

`datlocprovider` is `c` for glibc, `i` for ICU. If it is `c`, you are exposed to the
problem in section 3.5.

```sql
-- 2
SELECT datname,
       pg_size_pretty(pg_database_size(datname)) AS size
FROM   pg_database
ORDER  BY pg_database_size(datname) DESC;

-- 3
SELECT nspname
FROM   pg_namespace
WHERE  nspname NOT LIKE 'pg_%'
AND    nspname <> 'information_schema'
ORDER  BY nspname;

-- 4
SELECT relname AS table_name,
       pg_size_pretty(pg_total_relation_size(oid)) AS total_size,
       pg_size_pretty(pg_relation_size(oid))       AS table_only
FROM   pg_class
WHERE  relnamespace = 'public'::regnamespace
AND    relkind = 'r'
ORDER  BY pg_total_relation_size(oid) DESC;
```

The last query shows two numbers, and the gap between them is the lesson.
`pg_relation_size` is the table's own heap. `pg_total_relation_size` includes its indexes
and TOAST storage. On a mature table the indexes frequently exceed the data, and that is a
cost people forget they are paying — in disk, in memory, and in write throughput on every
`INSERT`. Chapter 33 returns to this when we discuss the real price of an index.

> **On `regnamespace` —** `'public'::regnamespace` casts the name to its catalog OID,
> which is far more readable than joining to `pg_namespace` every time. There is a family
> of these: `regclass` for tables, `regproc` for functions, `regtype` for types. They make
> catalog queries legible, and Appendix E uses them throughout.
