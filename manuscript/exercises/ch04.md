# Chapter 4 Exercises — Creating and Altering Tables

## Practice Session 4.1 — Build the `retail` core tables

**Goal.** Write a small schema from scratch, applying the defaults from section 4.1, and
confirm the constraints actually fire.

**Setup.**

```bash
createdb ch04_practice
psql ch04_practice
```

**Task.** Create three tables — `products`, `customers`, `orders` — such that:

- every table has a `bigint` identity primary key and a `created_at timestamptz` defaulting
  to now
- `products` has a unique `sku`, a `name`, and a `price` that cannot be negative
- `customers` has a unique `email` and an optional `country`
- `orders` references `customers`, has a `status` restricted to `placed`, `shipped` or
  `cancelled`, and a `total_amount` that cannot be negative
- deleting a customer who has orders must be **prevented**, not cascaded

Then prove all four constraints reject bad data.

**Solution.**

```sql
CREATE TABLE products (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku         text          NOT NULL UNIQUE,
    name        text          NOT NULL,
    price       numeric(10,2) NOT NULL CHECK (price >= 0),
    created_at  timestamptz   NOT NULL DEFAULT now()
);

CREATE TABLE customers (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email       text        NOT NULL UNIQUE,
    country     text,
    created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE orders (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id   bigint        NOT NULL REFERENCES customers(id) ON DELETE RESTRICT,
    status        text          NOT NULL CHECK (status IN ('placed','shipped','cancelled')),
    total_amount  numeric(10,2) NOT NULL CHECK (total_amount >= 0),
    created_at    timestamptz   NOT NULL DEFAULT now()
);
```

Now prove each one:

```sql
INSERT INTO products (sku, name, price) VALUES ('A1', 'Widget', 10.00);
INSERT INTO products (sku, name, price) VALUES ('A1', 'Other', 5.00);
-- ERROR:  duplicate key value violates unique constraint "products_sku_key"

INSERT INTO products (sku, name, price) VALUES ('A2', 'Bad', -1);
-- ERROR:  new row for relation "products" violates check constraint "products_price_check"

INSERT INTO customers (email) VALUES ('a@example.com');
INSERT INTO orders (customer_id, status, total_amount) VALUES (1, 'pending', 5);
-- ERROR:  new row for relation "orders" violates check constraint "orders_status_check"

INSERT INTO orders (customer_id, status, total_amount) VALUES (1, 'placed', 5);
DELETE FROM customers WHERE id = 1;
-- ERROR:  update or delete on table "customers" violates foreign key constraint
```

Four rejections, four different mechanisms. Note that the error messages name the
constraint — `products_price_check` — which is why letting PostgreSQL generate constraint
names is acceptable for small things but a liability for anything an application needs to
catch by name. Chapter 21 covers naming conventions.

`ON DELETE RESTRICT` is the deliberate choice here. The default if you omit it is
`NO ACTION`, which behaves almost identically but can be deferred; `CASCADE` would have
silently deleted the orders along with the customer. Chapter 15 works through when each is
right. The general rule: `CASCADE` on a true parent-child relationship where the child is
meaningless alone, `RESTRICT` on a reference to something with independent existence. An
order without a customer is a data integrity problem, not a tidy-up.

```bash
dropdb ch04_practice
```

## Practice Session 4.2 — Time an instant `ALTER` against a rewriting one

**Goal.** Measure the three tiers yourself, and learn the `relfilenode` test so you never
have to take anyone's word for it again.

**Setup.**

```bash
createdb ch04_rewrite
psql ch04_rewrite
```

```sql
CREATE TABLE big (
    id     int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    code   varchar(20) NOT NULL,
    label  text,
    amount numeric(10,2)
);

INSERT INTO big (code, label, amount)
SELECT 'C' || g, 'label ' || g, (g % 1000)::numeric
FROM   generate_series(1, 2000000) g;

\timing on
```

That takes a few seconds and produces about 158 MB.

**Task.** For each operation below, record the relfilenode before, run it with timing on,
and record the relfilenode after. Predict the answer before you run it.

1. `ALTER TABLE big ADD COLUMN c1 text;`
2. `ALTER TABLE big ADD COLUMN c2 int NOT NULL DEFAULT 42;`
3. `ALTER TABLE big ADD COLUMN c3 uuid DEFAULT gen_random_uuid();`
4. `ALTER TABLE big ALTER COLUMN code TYPE varchar(50);`
5. `ALTER TABLE big ALTER COLUMN id TYPE bigint;`
6. `ALTER TABLE big ALTER COLUMN label SET NOT NULL;`

Then explain why 2 and 3 differ so enormously, and why 6 sits between the two groups.

**Solution.**

```sql
SELECT relfilenode FROM pg_class WHERE relname = 'big';
```

Measured on PostgreSQL 15.10:

| # | Operation | Time | relfilenode |
|---|---|---:|---|
| 1 | `ADD COLUMN c1 text` | 1.055 ms | unchanged |
| 2 | `ADD COLUMN c2 int NOT NULL DEFAULT 42` | 0.891 ms | unchanged |
| 3 | `ADD COLUMN c3 uuid DEFAULT gen_random_uuid()` | 2,694 ms | **changed** |
| 4 | `ALTER COLUMN code TYPE varchar(50)` | 1.279 ms | unchanged |
| 5 | `ALTER COLUMN id TYPE bigint` | 1,037 ms | **changed** |
| 6 | `ALTER COLUMN label SET NOT NULL` | 136.9 ms | unchanged |

**Why 2 and 3 differ by a factor of three thousand.** Both add a column with a default.
But `42` is the same for every row, so PostgreSQL stores it once in the catalog and
synthesises it when a row is read — no row is touched. `gen_random_uuid()` is volatile and
must produce a *different* value per row, so every row must be written, which means a full
rewrite. The syntax is nearly identical; the cost is not remotely.

**Why 4 is free and 5 is not.** Widening `varchar(20)` to `varchar(50)` cannot invalidate
any existing value and does not change how the data is stored, so it is a catalog edit.
Changing `int` to `bigint` changes the physical width of every value from four bytes to
eight. Every row must be rewritten.

**Why 6 is in the middle.** `SET NOT NULL` writes nothing, so no rewrite — but it must
*verify* that no existing row is NULL, and the only way to know is to read all two million
of them. That is the scan tier: no new file, but real work proportional to table size, all
of it under an `ACCESS EXCLUSIVE` lock.

Now the part that matters more than the timings. Open a second terminal:

```sql
-- session 1
BEGIN;
SELECT count(*) FROM big;
-- leave the transaction open, do not commit
```

```sql
-- session 2
ALTER TABLE big ADD COLUMN blocked_demo int;
```

```sql
-- session 3
SELECT 1 FROM big LIMIT 1;
```

Session 2 hangs, which you might expect. Session 3 also hangs, which you might not —
`SELECT` does not conflict with `SELECT`. From a fourth session:

```sql
SELECT pid, wait_event_type, left(query, 45) AS query, pg_blocking_pids(pid) AS blocked_by
FROM   pg_stat_activity
WHERE  datname = current_database() AND pid <> pg_backend_pid();
```

```text
  pid  | wait_event_type |                    query                     | blocked_by 
-------+-----------------+----------------------------------------------+------------
 13336 | Client          | SELECT count(*) FROM big;                    | {}
 13347 | Lock            | ALTER TABLE big ADD COLUMN blocked_demo int; | {13336}
 13357 | Lock            | SELECT 1 FROM big LIMIT 1;                   | {13347}
```

The chain is the lesson. The `ALTER` waits for the open transaction. The innocent `SELECT`
waits for the `ALTER` — not because they conflict, but because PostgreSQL's lock queue is
ordered and it will not let a weak request overtake a waiting strong one. In the measured
run, the `ALTER` took 13.2 seconds and the trivial `SELECT` took 11.2.

Commit session 1 and watch both clear at once.

Now do it again with a guard:

```sql
SET lock_timeout = '3s';
ALTER TABLE big ADD COLUMN guarded int;
-- ERROR:  canceling statement due to lock timeout
```

It fails in three seconds and nothing queues behind it. **That error is the success
case.** Make it a habit: every DDL statement you run against a live system sets
`lock_timeout` first.

```bash
dropdb ch04_rewrite
```
