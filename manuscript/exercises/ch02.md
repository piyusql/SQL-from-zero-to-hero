# Chapter 2 Exercises — Setting Up PostgreSQL 15+ on macOS and Linux

## Practice Session 2.1 — Install, and confirm you have a server

**Goal.** A running PostgreSQL 15+ server you can connect to, and certainty that it is a
server and not just a client.

**Setup.** Follow whichever installation route from section 2.2 matches your machine.

**Task.** Answer all five, from the command line:

1. Is there a server binary on this machine, or only a client?
2. What major version is the **server** running?
3. Where is its data directory?
4. Which port is it listening on?
5. How many databases exist, and what are they?

**Solution.**

```bash
postgres -V          # server present? "command not found" means client-only
psql --version       # client version — not the answer to question 2
```

Questions 2 through 5 require a connection, which is the point — server facts come from
the server:

```sql
SELECT version();
```

```text
                                             version
--------------------------------------------------------------------------------------------------
 PostgreSQL 15.10 on aarch64-unknown-linux-gnu, compiled by gcc (Debian 12.2.0-14) 12.2.0, 64-bit
(1 row)
```

`version()` is the full build string. When you only want the number, and especially when a
script wants it, the settings are easier to parse:

```sql
SHOW server_version;
SHOW data_directory;
SHOW port;
```

```text
 server_version
----------------
 15.10
(1 row)

      data_directory
--------------------------
 /bitnami/postgresql/data
(1 row)

 port
------
 5432
(1 row)
```

Your `data_directory` will differ — it is wherever your install put the cluster, so
`/opt/homebrew/var/postgresql@17` on Homebrew, `/var/lib/postgresql/17/main` on Debian,
and something under `/bitnami` or `/var/lib/postgresql/data` in a container. That the
value is *not* the same as your neighbour's is the point of asking the server rather than
guessing.

And the databases:

```bash
psql -l
```

Three exist on a fresh cluster: `postgres`, `template0`, `template1`.

If `SHOW server_version` reports anything below 15, stop and install a newer one before
continuing. Several things later in this book do not exist on older releases, and you will
waste time discovering that one error message at a time.

> **If you got "connection refused" or "no such file or directory":** the server is not
> running. On Homebrew, `brew services list`. On Debian, `pg_lsclusters`. On Docker,
> `docker ps` — and if the container is missing, `docker start pgbook`.

## Practice Session 2.2 — A tour of `psql`

**Goal.** Fluency with the dozen meta-commands you will use for the rest of the book.

**Setup.**

```bash
createdb psql_tour
psql psql_tour
```

Then, inside `psql`:

```sql
CREATE TABLE tour_demo (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    label       text NOT NULL,
    note        text,
    created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX tour_demo_label_idx ON tour_demo (label);

INSERT INTO tour_demo (label, note) VALUES
    ('first',  'has a note'),
    ('second', NULL),
    ('third',  '');
```

**Task.**

1. Turn on timing, and make NULLs visible.
2. List the tables in this database.
3. Describe `tour_demo`. Find its index without running a separate query.
4. Select all three rows. Tell the NULL apart from the empty string on screen.
5. Switch to expanded display and select again.
6. Open your last query in an editor, add an `ORDER BY`, save, and watch it run.
7. Get the syntax for `INSERT` without leaving `psql` or opening a browser.

**Solution.**

```text
\timing on
\pset null '(null)'
\dt
\d tour_demo
```

`\d tour_demo` gives you columns, types, nullability, defaults, the primary key and the
index in one view:

```text
                                  Table "public.tour_demo"
   Column   |           Type           | Collation | Nullable |           Default
------------+--------------------------+-----------+----------+------------------------------
 id         | bigint                   |           | not null | generated always as identity
 label      | text                     |           | not null |
 note       | text                     |           |          |
 created_at | timestamp with time zone |           | not null | now()
Indexes:
    "tour_demo_pkey" PRIMARY KEY, btree (id)
    "tour_demo_label_idx" btree (label)
```

Then:

```sql
SELECT * FROM tour_demo;
```

```text
 id | label  |    note    |          created_at
----+--------+------------+-------------------------------
  1 | first  | has a note | 2026-09-14 12:15:51.309589+00
  2 | second | (null)     | 2026-09-14 12:15:51.309589+00
  3 | third  |            | 2026-09-14 12:15:51.309589+00
(3 rows)
```

Row 2 holds NULL — *no value*. Row 3 holds an empty string — *a value, of length zero*.
Without `\pset null` those two rows are pixel-identical, and this is the setting's entire
justification. Chapter 7 shows how differently the two behave in a `WHERE` clause; you
cannot debug that if you cannot see it.

Then `\x` and re-select, `\e` to edit and run, `\h INSERT` for syntax.

Note that all three rows share a `created_at` to the microsecond. `now()` returns the time
the **transaction** started, not the moment the row was written, so every row inserted by
one statement — or one transaction — gets the same timestamp. That is usually what you
want. When it is not, `clock_timestamp()` gives you the real wall clock. Chapter 14 covers
the full family.

Clean up:

```bash
dropdb psql_tour
```

## Practice Session 2.3 — Load the sample datasets

**Goal.** The `retail`, `hr` and `telemetry` datasets loaded and verified. Every chapter
after this one assumes they are present.

**Setup.** Get the book's companion files, then:

```bash
cd datasets
./load.sh all sm
```

The script creates one database per dataset, applies the schema, loads the data and prints
the row counts. It is safe to re-run — it drops and recreates cleanly, so if you make a
mess of a table during an exercise, re-running it is the fix.

It honours the standard libpq environment variables, so if your server is not on
`localhost:5432` as your own user:

```bash
PGHOST=localhost PGPORT=5432 PGUSER=postgres ./load.sh all sm
```

**Task.**

1. Load all three small datasets.
2. Connect to `retail` and list its tables.
3. For each table, get a row count.
4. Find the foreign keys on `order_items` — which tables does it reference?
5. Confirm `hr` has a self-referencing hierarchy, and find how deep it goes.

**Solution.**

```bash
./load.sh all sm
psql retail
```

```text
\dt
```

Row counts for every table at once, from the statistics the database already keeps, rather
than by counting each table by hand:

```sql
SELECT relname AS table_name,
       n_live_tup AS approx_rows
FROM   pg_stat_user_tables
ORDER  BY n_live_tup DESC;
```

> **Trap —** `n_live_tup` is an *estimate*, maintained by the statistics collector. It is
> perfect for "roughly how big is this", instant even on huge tables, and wrong if
> autovacuum has not run recently. When you need an exact number, `count(*)` is the only
> answer — and on a large table it reads every row. Knowing which of the two a question
> deserves is a real skill; Chapter 37 explains where these numbers come from.

Foreign keys:

```text
\d order_items
```

The `Foreign-key constraints:` section at the bottom lists what this table references, and
`Referenced by:` lists what references it. Reading both before altering a table is a habit
worth forming now.

For the `hr` hierarchy, `\d employees` shows `manager_id` referencing `employees(id)` —
a table pointing at itself. To find the depth you need recursion, which is Chapter 12, so
here is the answer with the promise that it will make sense later:

```sql
WITH RECURSIVE chain AS (
    SELECT id, manager_id, 1 AS depth
    FROM   employees
    WHERE  manager_id IS NULL

    UNION ALL

    SELECT e.id, e.manager_id, c.depth + 1
    FROM   employees e
    JOIN   chain c ON e.manager_id = c.id
)
SELECT max(depth) AS hierarchy_depth FROM chain;
```

If that query returns a number, your `hr` dataset is intact and Chapter 12 will have
something interesting to walk.

> **The large datasets —** you do not need them yet. `telemetry lg` is ten million events,
> takes about a minute to generate and occupies roughly 2.4 GB; all three large variants
> together are about 3.5 GB. Generate them when you reach Part VIII, where the entire
> point is that small tables cannot teach you anything about performance:
>
> ```bash
> ./load.sh telemetry lg
> ```
