# Chapter 30 Exercises — MVCC Internals

## Practice Session 30.1 — Inspect `xmin`/`xmax` across sessions

**Goal.** Predict, from `xmin`, `xmax` and the transaction's status, which row version a
second session sees while the first is mid-update, after it rolls back, and while it holds
only a lock, and prove each prediction on the page.

**Setup.** A scratch database and a three-row table. Use `psql -q`, and open two terminals
(Session A and Session B) both connected to `ch30_ws1`. Transaction ids will differ from the
ones printed; compare them with each other, not with the printed values.

```bash
createdb ch30_ws1
```

```sql
\c ch30_ws1
\pset null '(null)'
CREATE EXTENSION pageinspect;
CREATE TABLE stock (sku int PRIMARY KEY, item text, qty int) WITH (autovacuum_enabled = false);
INSERT INTO stock VALUES (1, 'Basmati rice 5kg', 40), (2, 'Filter coffee 500g', 25), (3, 'Masala chai 250g', 60);
```

**Task.**

1. In A, start a transaction, reduce `qty` of `sku` 1 by 10, and print `txid_current()`. Do
   not commit. In B, select `ctid, xmin, xmax, qty` for `sku` 1, plus
   `pg_xact_status(xmax::text::xid8)`. Before you run it, predict which quantity B sees and
   what `xmax` will be. Is B blocked?
2. Roll back in A. Run B's query again. Predict whether `xmax` goes back to 0. Then list
   every tuple on page 0 with `t_xmin`, `t_xmax`, `t_ctid` and the status of both ids. How
   many physical tuples now exist for `sku` 1, and which is dead?
3. In A, start a transaction and `SELECT ... FOR SHARE` on `sku` 2. In B, read `sku` 2's
   `xmax`. Is the row deleted? Prove what the `xmax` means from the infomask flags. Then
   roll back A.
4. In B, open a `REPEATABLE READ` transaction and read `sku` 3. In A, add 5 to `sku` 3
   (autocommit). In B, read `sku` 3 again together with
   `pg_visible_in_snapshot(xmax::text::xid8, pg_current_snapshot())`. Explain the result,
   then end B's transaction.

**Solution.**

Step 1. B sees the old quantity, and is not blocked:

```sql
-- Session A
BEGIN;
UPDATE stock SET qty = qty - 10 WHERE sku = 1;
SELECT txid_current() AS a_xid;
```

```text
 a_xid
--------
 202729
(1 row)
```

```sql
-- Session B
SELECT ctid, xmin, xmax, qty, pg_xact_status(xmax::text::xid8) AS xmax_status
FROM stock WHERE sku = 1;
```

```text
 ctid  |  xmin  |  xmax  | qty | xmax_status
-------+--------+--------+-----+-------------
 (0,1) | 202728 | 202729 |  40 | in progress
(1 row)
```

`xmax` is A's id, and its status is `in progress`, so the deletion does not count: B's
snapshot cannot see it, the row is live, and 40 is returned. Readers never wait on a writer.

Step 2. `xmax` does **not** go back to 0:

```sql
-- Session A
ROLLBACK;
```

```sql
-- Session B
SELECT ctid, xmin, xmax, qty, pg_xact_status(xmax::text::xid8) AS xmax_status
FROM stock WHERE sku = 1;
SELECT lp, t_xmin, t_xmax, t_ctid,
       pg_xact_status(t_xmin::text::xid8) AS xmin_status,
       CASE WHEN t_xmax <> 0 THEN pg_xact_status(t_xmax::text::xid8) END AS xmax_status
FROM heap_page_items(get_raw_page('stock', 0)) WHERE lp <= 4 ORDER BY lp;
```

```text
 ctid  |  xmin  |  xmax  | qty | xmax_status
-------+--------+--------+-----+-------------
 (0,1) | 202728 | 202729 |  40 | aborted
(1 row)

 lp | t_xmin | t_xmax | t_ctid | xmin_status | xmax_status
----+--------+--------+--------+-------------+-------------
  1 | 202728 | 202729 | (0,4)  | committed   | aborted
  2 | 202728 |      0 | (0,2)  | committed   | (null)
  3 | 202728 |      0 | (0,3)  | committed   | (null)
  4 | 202729 |      0 | (0,4)  | aborted     | (null)
(4 rows)
```

Rollback writes nothing to the tuples. The old version still carries A's id in `xmax`, but
that transaction `aborted`, so the `xmax` is ignored. Two physical tuples exist for `sku` 1:
slot 1 is live, and slot 4, created by the aborted transaction, is dead on arrival (its
`xmin` aborted). A non-zero `xmax` therefore has three possible meanings, and only the
transaction's status (with the infomask bits) tells you which.

Step 3. A lock, not a deletion:

```sql
-- Session A
BEGIN;
SELECT sku FROM stock WHERE sku = 2 FOR SHARE;
```

```text
 sku
-----
   2
(1 row)
```

```sql
-- Session B
SELECT sku, xmax <> 0 AS xmax_set, pg_xact_status(xmax::text::xid8) AS xmax_status, qty
FROM stock WHERE sku = 2;
SELECT lp, t_ctid,
       'HEAP_XMAX_LOCK_ONLY' = ANY(f.raw_flags) AS lock_only,
       'HEAP_XMAX_SHR_LOCK' = ANY(f.raw_flags) AS shared_lock
FROM heap_page_items(get_raw_page('stock', 0)),
     LATERAL heap_tuple_infomask_flags(t_infomask, t_infomask2) f
WHERE lp = 2;
```

```text
 sku | xmax_set | xmax_status | qty
-----+----------+-------------+-----
   2 | t        | in progress |  25
(1 row)

 lp | t_ctid | lock_only | shared_lock
----+--------+-----------+-------------
  2 | (0,2)  | t         | f
(1 row)
```

The row is visible and unchanged; `xmax` belongs to a transaction still in progress, but the
`HEAP_XMAX_LOCK_ONLY` bit says it is a lock, and `t_ctid` points at itself (no new version).

```sql
-- Session A
ROLLBACK;
```

Step 4. A committed change that B cannot see:

```sql
-- Session B
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT ctid, qty FROM stock WHERE sku = 3;
```

```text
 ctid  | qty
-------+-----
 (0,3) |  60
(1 row)
```

```sql
-- Session A
UPDATE stock SET qty = qty + 5 WHERE sku = 3;
```

```sql
-- Session B
SELECT ctid, xmin, xmax, qty,
       pg_visible_in_snapshot(xmax::text::xid8, pg_current_snapshot()) AS updater_visible
FROM stock WHERE sku = 3;
COMMIT;
```

```text
 ctid  |  xmin  |  xmax  | qty | updater_visible
-------+--------+--------+-----+-----------------
 (0,3) | 202728 | 202731 |  60 | f
(1 row)
```

The updater has committed, yet `pg_visible_in_snapshot` says its id is not visible to B's
snapshot (it was taken before that transaction finished), so the old version, 60, is still the
row B sees. After `COMMIT` B's next statement takes a new snapshot and reads 65.

```bash
dropdb ch30_ws1
```

## Practice Session 30.2 — Watch dead tuples accumulate

**Goal.** Count dead row versions exactly as updates pile up, show that `VACUUM` reclaims
space without shrinking the file, and show an idle transaction stopping it from reclaiming
anything.

**Setup.** A table of 5,000 web sessions with autovacuum switched off for that table (never
do this in production; here it makes the counts deterministic). Two terminals, A and B, both on
`ch30_ws2`. Use `psql -q`.

```bash
createdb ch30_ws2
```

```sql
\c ch30_ws2
\pset null '(null)'
CREATE EXTENSION pgstattuple;
CREATE TABLE web_session (sid int PRIMARY KEY, user_name text, last_page text, hits int)
  WITH (autovacuum_enabled = false);
INSERT INTO web_session
SELECT g, (ARRAY['Meera Banerjee','Arjun Iyer','Harpreet Singh','Fatima Sheikh','Rajesh Kumar'])[1 + g % 5],
       '/home', 0
FROM generate_series(1, 5000) g;
```

**Task.**

1. Record the baseline with `pgstattuple`: heap pages (`pg_relation_size / 8192`), live
   tuples, dead tuples.
2. In one transaction, run `UPDATE web_session SET hits = hits + 1` three times. Predict
   the live and dead counts and the page count, then check.
3. Run `VACUUM web_session`. Predict dead tuples, pages, and `free_percent`.
4. In B, open a `REPEATABLE READ` transaction and read one row, leaving it open. In A,
   update every row twice as separate statements, run `VACUUM`, and count dead tuples.
   Find B's session in `pg_stat_activity`.
5. Commit B, run `VACUUM` again, and count. Then run one more full-table update: does the
   file grow?
6. Compare `pg_stat_user_tables.n_dead_tup` with the exact count at the end of step 2 (wait
   two seconds for statistics to flush). Which would you page on, and which would you
   assert on in a test?

**Solution.**

```sql
-- Session A
SELECT pg_relation_size('web_session') / 8192 AS pages, tuple_count, dead_tuple_count
FROM pgstattuple('web_session');
```

```text
 pages | tuple_count | dead_tuple_count
-------+-------------+------------------
    37 |        5000 |                0
(1 row)
```

Step 2, three updates in one transaction, so nothing can be pruned in between:

```sql
BEGIN;
UPDATE web_session SET hits = hits + 1;
UPDATE web_session SET hits = hits + 1;
UPDATE web_session SET hits = hits + 1;
COMMIT;
SELECT pg_relation_size('web_session') / 8192 AS pages, tuple_count, dead_tuple_count
FROM pgstattuple('web_session');
```

```text
 pages | tuple_count | dead_tuple_count
-------+-------------+------------------
   148 |        5000 |            15000
(1 row)
```

Live stays at 5,000; dead is 3 × 5,000 = 15,000; the file is four times the size, because every
version is a complete row. Step 6 first, while the counts are fresh:

```sql
SELECT pg_sleep(2) \g /dev/null
SELECT n_live_tup, n_dead_tup FROM pg_stat_user_tables WHERE relname = 'web_session';
```

```text
 n_live_tup | n_dead_tup
------------+------------
       5000 |      15000
(1 row)
```

Here the estimate agrees with the exact count. It is maintained from update counters and
lags by the statistics flush, so it is the right thing to graph and alert on for a table
of any size, and the wrong thing to assert on in a test, where you want `pgstattuple`
(exact, but it reads the whole table, so keep it to small tables).

Step 3:

```sql
VACUUM web_session;
SELECT pg_relation_size('web_session') / 8192 AS pages, tuple_count, dead_tuple_count,
       round(free_percent) AS free_pct
FROM pgstattuple('web_session');
```

```text
 pages | tuple_count | dead_tuple_count | free_pct
-------+-------------+------------------+----------
   148 |        5000 |                0 |       75
(1 row)
```

No dead tuples, but the page count is unchanged: `VACUUM` made the space reusable and did
not return it to the operating system. About three quarters of the file is free space.

Step 4, an idle transaction in B:

```sql
-- Session B
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM web_session WHERE sid = 1;
```

```text
 count
-------
     1
(1 row)
```

```sql
-- Session A
UPDATE web_session SET hits = hits + 1;
UPDATE web_session SET hits = hits + 1;
VACUUM web_session;
SELECT pg_relation_size('web_session') / 8192 AS pages, tuple_count, dead_tuple_count
FROM pgstattuple('web_session');
SELECT state, backend_xmin IS NOT NULL AS holds_horizon
FROM pg_stat_activity
WHERE datname = 'ch30_ws2' AND pid <> pg_backend_pid() AND backend_xmin IS NOT NULL;
```

```text
 pages | tuple_count | dead_tuple_count
-------+-------------+------------------
   148 |        5000 |            10000
(1 row)

        state        | holds_horizon
---------------------+---------------
 idle in transaction | t
(1 row)
```

`VACUUM` ran and removed nothing: B's snapshot may still need the old versions. The file did
not grow only because step 3 left it three quarters empty; keep updating and it will.
`pg_stat_activity` names the culprit, `idle in transaction`, and its `backend_xmin` is the
horizon.

Step 5:

```sql
-- Session B
COMMIT;
```

```sql
-- Session A
VACUUM web_session;
SELECT pg_relation_size('web_session') / 8192 AS pages, tuple_count, dead_tuple_count
FROM pgstattuple('web_session');
UPDATE web_session SET hits = hits + 1;
SELECT pg_relation_size('web_session') / 8192 AS pages, dead_tuple_count
FROM pgstattuple('web_session');
```

```text
 pages | tuple_count | dead_tuple_count
-------+-------------+------------------
   148 |        5000 |                0
(1 row)

 pages | dead_tuple_count
-------+------------------
   148 |             5000
(1 row)
```

Once B ended, `VACUUM` removed all 10,000 dead versions, and the next full-table update reused
the freed space: the file stayed at 148 pages. Four times the fresh table's 37 is what a
table that rewrites every row between vacuums costs, and it is where bloat comes from.
Repair and tuning are Chapter 37.

```bash
dropdb ch30_ws2
```

## Practice Session 30.3 — Tune `fillfactor` for HOT updates

**Goal.** Choose a `fillfactor` for a job-state table by measuring the share of HOT updates,
heap size and index size under a fixed update workload, and show what an index on the updated
column does to the result.

**Setup.** Four copies of a 6,000-row `jobs` table: three differing only in `fillfactor`,
plus one at 70 with an extra index on `state`, the column the workload updates. Run this on
a quiet server: an open write transaction anywhere in the cluster switches off the page pruning
that HOT depends on, and lowers every percentage. Use `psql -q`.

```bash
createdb ch30_ws3
```

```sql
\c ch30_ws3
\pset null '(null)'
SELECT format('CREATE TABLE %s (id int PRIMARY KEY, worker text, state text, attempts int)
               WITH (fillfactor = %s, autovacuum_enabled = false)', t, f)
FROM (VALUES ('jobs_ff100', 100), ('jobs_ff85', 85), ('jobs_ff70', 70), ('jobs_ff70_idx', 70)) v(t, f) \gexec
SELECT format('CREATE INDEX ON %s (worker)', t)
FROM unnest(ARRAY['jobs_ff100', 'jobs_ff85', 'jobs_ff70', 'jobs_ff70_idx']) t \gexec
CREATE INDEX ON jobs_ff70_idx (state);
SELECT format($q$INSERT INTO %s SELECT g, (ARRAY['Pune','Kochi','Indore','Jaipur'])[1 + g %% 4] || '-w' || (g %% 20), 'queued', 0
               FROM generate_series(1, 6000) g$q$, t)
FROM unnest(ARRAY['jobs_ff100', 'jobs_ff85', 'jobs_ff70', 'jobs_ff70_idx']) t \gexec
```

**Task.**

1. Record heap pages and total index pages for each table at load.
2. Predict the ranking of the first three tables by HOT percentage after the workload
   below, then run it: 30 rounds, where round *r* runs
   `UPDATE t SET state = 'r<r>', attempts = attempts + 1 WHERE id % 10 = r % 10` as its own
   statement, on every table.
3. Report heap pages, index pages and HOT percentage. Which `fillfactor` would you pick for
   a table like this, and what does it cost?
4. Explain the result for `jobs_ff70_idx`, which has the same `fillfactor` as `jobs_ff70`.
5. Set `fillfactor = 70` on `jobs_ff100` with `ALTER TABLE`. Does its size change? What would
   it take to get the benefit on an existing table?

**Solution.**

```sql
SELECT c.relname, pg_relation_size(c.oid) / 8192 AS heap_at_load,
       (SELECT sum(pg_relation_size(i.indexrelid) / 8192) FROM pg_index i WHERE i.indrelid = c.oid) AS index_at_load
FROM pg_class c WHERE c.relname ~ '^jobs_' AND c.relkind = 'r' ORDER BY c.relname;
```

```text
    relname    | heap_at_load | index_at_load
---------------+--------------+---------------
 jobs_ff100    |           42 |            28
 jobs_ff70     |           60 |            28
 jobs_ff70_idx |           60 |            35
 jobs_ff85     |           50 |            28
(4 rows)
```

The lower the fillfactor, the more pages at load: the free space is the reserve for new
versions. Now the workload:

```sql
\o /dev/null
SELECT format('UPDATE %s SET state = %L, attempts = attempts + 1 WHERE id %% 10 = %s', t, 'r' || r, r % 10)
FROM generate_series(1, 30) r, unnest(ARRAY['jobs_ff100', 'jobs_ff85', 'jobs_ff70', 'jobs_ff70_idx']) t
ORDER BY r, t \gexec
\o
SELECT pg_sleep(2) \g /dev/null
SELECT c.relname, pg_relation_size(c.oid) / 8192 AS heap_pages,
       round(100.0 * s.n_tup_hot_upd / s.n_tup_upd) AS hot_pct,
       (SELECT sum(pg_relation_size(i.indexrelid) / 8192) FROM pg_index i WHERE i.indrelid = c.oid) AS index_pages
FROM pg_class c JOIN pg_stat_user_tables s ON s.relid = c.oid
WHERE c.relname ~ '^jobs_' ORDER BY c.relname;
```

```text
    relname    | heap_pages | hot_pct | index_pages
---------------+------------+---------+-------------
 jobs_ff100    |         53 |      90 |          29
 jobs_ff70     |         60 |     100 |          28
 jobs_ff70_idx |        118 |       0 |          90
 jobs_ff85     |         50 |     100 |          28
(4 rows)
```

Reading it. At 100, 90% of updates were HOT (pruning does the rest of the work on these
narrow rows) but each non-HOT one extended the file, 42 to 53 pages. At 85 every update was
HOT and the table ended at 50 pages, *smaller* than the 100 table, for 19% more space at
load. At 70 the extra room bought nothing more: 60 pages, 100% HOT, over-provisioned. The
pick here is 85, and the lesson is that lower is not better; measure on your own row width
and update pattern rather than copying a number.

`jobs_ff70_idx` has the same `fillfactor` and the same free space, but every update
changes an indexed column, so none can be HOT and each adds an entry to both indexes: 118
heap pages and 90 index pages, against 60 and 28. `fillfactor` cannot help updates that HOT
is not allowed to do. If a column is updated constantly, do not index it (or keep it out of
the table); leaving more room does not fix it.

```sql
ALTER TABLE jobs_ff100 SET (fillfactor = 70);
SELECT pg_relation_size('jobs_ff100') / 8192 AS pages_after_alter;
```

```text
 pages_after_alter
-------------------
                53
(1 row)
```

The size is unchanged, because `ALTER` only affects pages written from now on. An existing
table has to be rewritten (`VACUUM FULL`, or `pg_repack` online) to leave the space in the
old pages: a Chapter 37 job, and a reason to set `fillfactor` when you create a hot table.

```bash
dropdb ch30_ws3
```
