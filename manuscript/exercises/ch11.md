# Chapter 11 Exercises — Set Operations

## Practice Session 11.1 — Reconcile two sources with `EXCEPT`

**Goal.** Produce a two-directional row-level difference report between two systems that
claim to hold the same customer master, and understand why `EXCEPT` gets nullable columns
right where a column-by-column join does not.

**Setup.** This session builds two small snapshot tables, so it uses a scratch database
rather than touching the `retail` database the other sessions rely on. The data is the
small `retail` seed, which is deterministic — derived from `md5()` of the row number, not
from `random()` — so every number below is a number you will see.

```bash
cd path/to/sql-from-my-heart/datasets

createdb ch11_recon
psql -d ch11_recon -v ON_ERROR_STOP=1 -f retail/schema.sql
psql -d ch11_recon -v ON_ERROR_STOP=1 -f retail/seed-sm.sql

psql -d ch11_recon
```

Set the NULL marker before you run anything — a NULL and an empty string are
indistinguishable otherwise, and this session turns on telling them apart:

```sql
\pset null '(null)'
```

Now build the two snapshots. `billing_customers` is what the billing system holds;
`warehouse_customers` is what the warehouse system holds. They overlap but have drifted:

```sql
CREATE TABLE billing_customers   AS SELECT id, name, city FROM customers WHERE id BETWEEN 1 AND 20;
CREATE TABLE warehouse_customers AS SELECT id, name, city FROM customers WHERE id BETWEEN 3 AND 22;

UPDATE warehouse_customers SET city = 'Pune' WHERE id = 7;
```

```sql
SELECT count(*) FROM billing_customers;     -- expect 20
SELECT count(*) FROM warehouse_customers;   -- expect 20
```

Twenty rows each. Equal counts, which is exactly the reassurance that lets a broken feed
run for a month.

**Task.**

1. List the rows present in `billing_customers` and absent from `warehouse_customers`.
2. List the rows present in `warehouse_customers` and absent from `billing_customers`.
   Explain why customer 7 appears in both answers.
3. Combine the two directions into one labelled report, so a reader can tell which side a
   row came from.
4. Write the same reconciliation as a `LEFT JOIN` with `IS NULL`, comparing all three
   columns in the join condition. Compare its answer to step 1 and explain the difference.
   Then fix the join.
5. Duplicate one warehouse row with
   `INSERT INTO warehouse_customers SELECT * FROM warehouse_customers WHERE id = 12;` and
   re-run step 2. Then find the duplicate.

**Solution.**

**1 — billing, not warehouse.**

```sql
SELECT id, name, city FROM billing_customers
EXCEPT
SELECT id, name, city FROM warehouse_customers
ORDER  BY id;
```

```text
 id |     name     |  city
----+--------------+--------
  1 | Imran Reddy  | Kochi
  2 | Rohit Kumar  | Mysuru
  7 | Vikram Menon | Indore
(3 rows)

```

`EXCEPT` compares **whole rows**, not keys. A row survives only if no row on the right
side is identical in every selected column, which is why the comparison is worth writing
this way: one operator covers all three columns and you cannot forget one.

**2 — warehouse, not billing.**

```sql
SELECT id, name, city FROM warehouse_customers
EXCEPT
SELECT id, name, city FROM billing_customers
ORDER  BY id;
```

```text
 id |     name     |   city
----+--------------+-----------
  7 | Vikram Menon | Pune
 21 | Rajesh Joshi | Kochi
 22 | Sneha Singh  | Ahmedabad
(3 rows)

```

Customer 7 is in both answers because **a modification looks like a deletion plus an
insertion.** `EXCEPT` has no concept of a key, so `(7, Vikram Menon, Indore)` and
`(7, Vikram Menon, Pune)` are two different rows, each missing from the other side.

This is a feature rather than a limitation: it means one query finds inserts, deletes
*and* updates without you deciding in advance which you are looking for. The cost is that
the report needs interpreting — an `id` appearing on both sides is a change, an `id`
appearing on one side only is an insert or a delete.

Note also that running only step 1 would have told you nothing useful. `EXCEPT` is
directional. Three rows one way does not imply three rows the other, and zero rows one way
certainly does not mean the sources agree. **Always run both directions.**

**3 — one labelled report.**

```sql
SELECT 'billing only' AS side, id, name, city
FROM  (SELECT id, name, city FROM billing_customers
       EXCEPT
       SELECT id, name, city FROM warehouse_customers) b
UNION ALL
SELECT 'warehouse only', id, name, city
FROM  (SELECT id, name, city FROM warehouse_customers
       EXCEPT
       SELECT id, name, city FROM billing_customers) w
ORDER  BY id, side;
```

```text
      side      | id |     name     |   city
----------------+----+--------------+-----------
 billing only   |  1 | Imran Reddy  | Kochi
 billing only   |  2 | Rohit Kumar  | Mysuru
 billing only   |  7 | Vikram Menon | Indore
 warehouse only |  7 | Vikram Menon | Pune
 warehouse only | 21 | Rajesh Joshi | Kochi
 warehouse only | 22 | Sneha Singh  | Ahmedabad
(6 rows)

```

Three things are doing work here.

Each `EXCEPT` is wrapped in a derived table so the literal label can be attached. You
cannot write `SELECT 'billing only', id, ... EXCEPT SELECT ...` and get what you want,
because the label would become part of the row being compared and every row would then
differ.

The outer operator is `UNION ALL`, not `UNION`. The two sides are disjoint by construction
— their labels differ — so a `UNION` here would sort the whole result to remove duplicates
that cannot exist. That is the chapter's default in miniature.

And `ORDER BY id, side` is attached to the combined result, not to the second branch.
Sorting by `id` puts both halves of the customer 7 change next to each other, which is
what makes the report readable; sorted by `side` first, the two halves of every change end
up pages apart.

**4 — the same thing as a join, and why it is wrong.**

```sql
SELECT b.id, b.name, b.city
FROM   billing_customers b
LEFT   JOIN warehouse_customers w
       ON  w.id = b.id AND w.name = b.name AND w.city = b.city
WHERE  w.id IS NULL
ORDER  BY b.id;
```

```text
 id |       name       |  city
----+------------------+--------
  1 | Imran Reddy      | Kochi
  2 | Rohit Kumar      | Mysuru
  7 | Vikram Menon     | Indore
 20 | Lakshmi Banerjee | (null)
(4 rows)

```

Four rows against three. Customer 20 is a **false positive**, and this is the bug this
exercise exists for.

Lakshmi Banerjee has no city on file. The row is byte-for-byte identical in both
snapshots. But the join condition contains `w.city = b.city`, which for two NULLs
evaluates to `unknown` rather than to true, so the `LEFT JOIN` finds no match, so
`w.id IS NULL` holds, so the row is reported as a difference. Nothing errors. You would
chase a discrepancy that does not exist — and worse, on a column that was NULL in one
snapshot and populated in the other, the same logic hides a real difference.

`EXCEPT` does not use `=`. It compares with the *not distinct from* relation, under which
two NULLs are the same value. That is inconsistent with the three-valued logic that
governs `WHERE` and `ON`, and here the inconsistency is the thing you want.

The fix, if you must use a join:

```sql
SELECT b.id, b.name, b.city
FROM   billing_customers b
LEFT   JOIN warehouse_customers w
       ON  w.id = b.id
       AND w.name IS NOT DISTINCT FROM b.name
       AND w.city IS NOT DISTINCT FROM b.city
WHERE  w.id IS NULL
ORDER  BY b.id;
```

```text
 id |     name     |  city
----+--------------+--------
  1 | Imran Reddy  | Kochi
  2 | Rohit Kumar  | Mysuru
  7 | Vikram Menon | Indore
(3 rows)

```

Three rows, agreeing with `EXCEPT`. `IS NOT DISTINCT FROM` is `=` with NULLs treated as
equal — precisely the comparison a set operation performs for you.

Which to write? The join, once corrected, lets you return columns from both sides at once
— old city beside new city — which the `EXCEPT` report cannot do. But it needs one
`IS NOT DISTINCT FROM` per compared column, every one of them a chance to slip back to `=`
during a later edit, and it cannot use a hash join on those conditions. For a plain *what
differs* report, `EXCEPT` is shorter and cannot be got wrong.

**5 — a duplicated row, and the `ALL` variant.**

```sql
INSERT INTO warehouse_customers SELECT * FROM warehouse_customers WHERE id = 12;
```

The warehouse now holds 21 rows to billing's 20, with customer 12 recorded twice. Re-run
step 2:

```sql
SELECT id, name, city FROM warehouse_customers
EXCEPT
SELECT id, name, city FROM billing_customers
ORDER  BY id;
```

```text
 id |     name     |   city
----+--------------+-----------
  7 | Vikram Menon | Pune
 21 | Rajesh Joshi | Kochi
 22 | Sneha Singh  | Ahmedabad
(3 rows)

```

Unchanged. The reconciliation now passes over a real data-quality fault in silence,
because plain `EXCEPT` works on *sets*: the duplicate collapses into the one copy that
matches billing, and the row disappears from the difference.

`EXCEPT ALL` works on multisets and subtracts occurrences:

```sql
SELECT id, name, city FROM warehouse_customers
EXCEPT ALL
SELECT id, name, city FROM billing_customers
ORDER  BY id;
```

```text
 id |       name       |   city
----+------------------+-----------
  7 | Vikram Menon     | Pune
 12 | Rohit Chatterjee | Guwahati
 21 | Rajesh Joshi     | Kochi
 22 | Sneha Singh      | Ahmedabad
(4 rows)

```

Customer 12 appears once: two occurrences on the left minus one on the right leaves one.
Row 12 is not *different* from billing's copy; there is one too many of it.

**Use `EXCEPT ALL` for reconciliation as the default, and plain `EXCEPT` only when you
have decided that duplicates are uninteresting.** A duplicate row is one of the commonest
results of a retried load or a broken merge key, and it is precisely the fault a set-based
reconciliation hides from you.

**Clean up.**

```sql
DROP TABLE billing_customers, warehouse_customers;
```

```bash
dropdb ch11_recon
```

## Practice Session 11.2 — What `UNION` costs against `UNION ALL`

**Goal.** Measure the deduplication `UNION` performs, identify the plan nodes that do it,
confirm from the plan that it removed nothing, and find out that raising `work_mem` does
not rescue it.

**Setup.** This session needs the large `retail` variant — about two million orders —
because at 2,500 rows every plan finishes in a millisecond and the dedup is invisible.

`load.sh` builds a database named after the dataset, so `./load.sh retail lg` would
replace your small `retail`. Build the large one beside it, as Practice Session 8.2 did:

```bash
cd path/to/sql-from-my-heart/datasets

createdb retail_lg
psql -d retail_lg -v ON_ERROR_STOP=1 -f retail/schema.sql
psql -d retail_lg -v ON_ERROR_STOP=1 -f retail/generate-lg.sql
```

About a minute, and 749 MB. If you still have it from Chapter 8, reuse it.

```bash
psql -d retail_lg
```

```sql
SELECT count(*) FROM orders;   -- 2000000
SHOW work_mem;                 -- 4MB on a default install
```

```sql
SELECT status, count(*) FROM orders GROUP BY status ORDER BY 1;
```

```text
  status   | count
-----------+--------
 cancelled | 199605
 delivered | 799986
 paid      | 200187
 pending   | 200525
 returned  | 200105
 shipped   | 399592
(6 rows)

```

The `lg` variant uses `random()`, so your per-status counts and every row count below will
be close to these rather than equal to them. Nothing in this session depends on the exact
figures. Run each query two or three times before believing a timing, so the table is in
cache and you are measuring CPU rather than your disk; absolute times depend on your
hardware, and it is the ratio that reproduces.

**Task.**

1. Stack the `delivered` orders on the `shipped` orders with `UNION ALL`, selecting `id`,
   `customer_id` and `total_amount`. Count the result. Do the same with `UNION`. How many
   duplicates did `UNION` remove, and how do you know before running it?
2. Get `EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)` for both. Name every node that appears
   in one plan and not the other, and say what each is for.
3. Re-run the `UNION` plan with `BUFFERS`. Quantify the temporary I/O.
4. `SET work_mem = '256MB'` and re-run the `UNION` plan. Predict the effect first, then
   explain what actually happened.
5. Construct a pair of branches that *do* overlap, and show that `UNION ALL` and `UNION`
   then return different numbers of rows.

**Solution.**

**1 — the counts.**

```sql
SELECT count(*) FROM (
  SELECT id, customer_id, total_amount FROM orders WHERE status = 'delivered'
  UNION ALL
  SELECT id, customer_id, total_amount FROM orders WHERE status = 'shipped') t;
```

```text
  count
---------
 1199578
(1 row)

```

Swap `UNION ALL` for `UNION` and the answer is identical:

```text
  count
---------
 1199578
(1 row)

```

Zero duplicates removed, and you could have said so without running either query.
`orders.status` holds one value per row, so an order is `delivered` or `shipped` and never
both; the two branches are disjoint by construction, and `id` is the primary key, so no
row can repeat within a branch either. **The branches were disjoint because you wrote the
predicates that made them disjoint** — which is the situation in the large majority of
real `UNION` queries.

**2 — the two plans.**

```sql
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)
SELECT id, customer_id, total_amount FROM orders WHERE status = 'delivered'
UNION ALL
SELECT id, customer_id, total_amount FROM orders WHERE status = 'shipped';
```

```text
 Append (actual rows=1199578 loops=1)
   ->  Seq Scan on orders (actual rows=799986 loops=1)
         Filter: (status = 'delivered'::text)
         Rows Removed by Filter: 1200014
   ->  Seq Scan on orders orders_1 (actual rows=399592 loops=1)
         Filter: (status = 'shipped'::text)
         Rows Removed by Filter: 1600408
 Planning Time: 0.141 ms
 Execution Time: 232.644 ms
```

```sql
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)
SELECT id, customer_id, total_amount FROM orders WHERE status = 'delivered'
UNION
SELECT id, customer_id, total_amount FROM orders WHERE status = 'shipped';
```

```text
 Unique (actual rows=1199578 loops=1)
   ->  Sort (actual rows=1199578 loops=1)
         Sort Key: orders.id, orders.customer_id, orders.total_amount
         Sort Method: external merge  Disk: 29352kB
         ->  Append (actual rows=1199578 loops=1)
               ->  Seq Scan on orders (actual rows=799986 loops=1)
                     Filter: (status = 'delivered'::text)
                     Rows Removed by Filter: 1200014
               ->  Seq Scan on orders orders_1 (actual rows=399592 loops=1)
                     Filter: (status = 'shipped'::text)
                     Rows Removed by Filter: 1600408
 Planning Time: 0.144 ms
 Execution Time: 457.429 ms
```

Two nodes are new, and the scans below them are unchanged:

- **`Sort`** — the deduplication needs equal rows adjacent, so all 1,199,578 rows are
  sorted on *every selected column*, not on a key. `Sort Key:` lists all three. Widen the
  select list and this node gets more expensive.
- **`Unique`** — walks the sorted stream and drops each row equal to its predecessor.
  Cheap in itself; it is the `Sort` underneath that costs.

`Sort Method: external merge  Disk: 29352kB` is the finding. The default `work_mem` is 4
MB, 1.2 million three-column rows are not, so the sort ran on disk.

Approximately 230 ms against approximately 460 ms on the machine this book was written on,
and repeated runs sit at roughly 210 ms and roughly 440 ms. Twice the work, in that order
every time.

Then read the row counts again. `actual rows=1199578` on the `Append`, and
`actual rows=1199578` on the `Unique`. **The deduplication removed nothing.** Everything
above the `Append` was pure loss.

**3 — the temporary I/O.**

```sql
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF)
SELECT id, customer_id, total_amount FROM orders WHERE status = 'delivered'
UNION
SELECT id, customer_id, total_amount FROM orders WHERE status = 'shipped';
```

```text
 Unique (actual rows=1199578 loops=1)
   Buffers: shared hit=16223 read=51197, temp read=7333 written=7356
   ->  Sort (actual rows=1199578 loops=1)
         Sort Key: orders.id, orders.customer_id, orders.total_amount
         Sort Method: external merge  Disk: 29352kB
         Buffers: shared hit=16223 read=51197, temp read=7333 written=7356
         ->  Append (actual rows=1199578 loops=1)
               Buffers: shared hit=16217 read=51197
               ->  Seq Scan on orders (actual rows=799986 loops=1)
                     Filter: (status = 'delivered'::text)
                     Rows Removed by Filter: 1200014
                     Buffers: shared hit=8120 read=25587
               ->  Seq Scan on orders orders_1 (actual rows=399592 loops=1)
                     Filter: (status = 'shipped'::text)
                     Rows Removed by Filter: 1600408
                     Buffers: shared hit=8097 read=25610
 Planning:
   Buffers: shared hit=88
 Planning Time: 0.152 ms
 Execution Time: 2013.329 ms
```

The execution time there is from a run competing with other work on the machine, which is
a reminder of why the next paragraph does not use it. `temp read=7333 written=7356` counts
8 kB blocks, so roughly 57 MB written to temporary files and 57 MB read back — the merge
passes, of which `Disk: 29352kB` is the peak tape size. The `Append` node below carries no
`temp` counters at all: the `UNION ALL` plan does none of this.

Unlike timings, these counters do not move between runs. When you need to prove a cost to
somebody, quote the buffer numbers rather than the clock.

**4 — more `work_mem`.**

The natural prediction is that the spill disappears and the query gets faster.

```sql
SET work_mem = '256MB';

EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)
SELECT id, customer_id, total_amount FROM orders WHERE status = 'delivered'
UNION
SELECT id, customer_id, total_amount FROM orders WHERE status = 'shipped';
```

```text
 HashAggregate (actual rows=1199578 loops=1)
   Group Key: orders.id, orders.customer_id, orders.total_amount
   Batches: 1  Memory Usage: 106513kB
   ->  Append (actual rows=1199578 loops=1)
         ->  Seq Scan on orders (actual rows=799986 loops=1)
               Filter: (status = 'delivered'::text)
               Rows Removed by Filter: 1200014
         ->  Seq Scan on orders orders_1 (actual rows=399592 loops=1)
               Filter: (status = 'shipped'::text)
               Rows Removed by Filter: 1600408
 Planning Time: 0.141 ms
 Execution Time: 729.989 ms
```

Half the prediction came true. The spill is gone: `Sort` and `Unique` have been replaced
by a single `HashAggregate` with `Batches: 1`, meaning the whole hash table fitted in
memory, and no `Disk Usage:` line appears.

The other half did not. Across repeated runs this lands around 500 ms against around 430
ms for the spilling sort — measurably *slower*. Building a 106 MB hash table over 1.2
million three-column rows, hashing all three columns of every row, costs more here than an
external merge sort of the same data on a machine whose page cache absorbs the temporary
files. The absolute numbers depend on your hardware and this comparison is close enough
that it may invert on yours; what will not change is that neither is remotely close to the
210 ms the `UNION ALL` plan takes.

Two lessons. First, `work_mem` changes *which algorithm the planner picks*, not only how
much memory it is allowed — sort-and-unique became hash-aggregate — so raising it can
change a plan's shape in ways that are not automatically improvements. Second, 106 MB is
per hash node per backend. Setting `work_mem = '256MB'` cluster-wide to fix this one query
gives fifty concurrent sessions permission to allocate that much each, which is Chapter
45, *Configuration and Resource Tuning*. The real fix costs nothing:

```sql
RESET work_mem;
```

and write `UNION ALL`.

**5 — branches that genuinely overlap.**

The dedup is only free of consequence when there is nothing to dedup. Make the branches
overlap by filtering on different columns, so a large delivered order satisfies both:

```sql
SELECT count(*) FROM (
  SELECT id, customer_id, total_amount FROM orders WHERE status = 'delivered'
  UNION ALL
  SELECT id, customer_id, total_amount FROM orders WHERE total_amount > 5900) t;
```

```text
 count
--------
 800375
(1 row)

```

```sql
SELECT count(*) FROM (
  SELECT id, customer_id, total_amount FROM orders WHERE status = 'delivered'
  UNION
  SELECT id, customer_id, total_amount FROM orders WHERE total_amount > 5900) t;
```

```text
 count
--------
 800231
(1 row)

```

144 rows differ on this generated dataset — the delivered orders over 5,900, counted twice
by `UNION ALL` and once by `UNION`. Your figure will differ, since `lg` uses `random()`.

Here `UNION ALL` would be a bug if you wanted distinct orders, and `UNION` is correct.
That is the whole of the decision rule, and it is a semantic question, not a performance
one: **can a row be produced by more than one branch?** If no, `UNION ALL` — always, and
the cost of getting it wrong is zero. If yes, decide whether you want it once or twice,
and if you want it once, consider whether restructuring the predicates so the branches are
disjoint beats paying for a sort over the combined result.
