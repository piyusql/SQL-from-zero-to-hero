# Chapter 9 Exercises — Joins

## Practice Session 9.1 — Inner joining `orders` to `customers`

**Goal.** Attach every order to the customer who placed it, and learn to state — before
running anything — how many rows the join will return and which rows it will silently
drop.

**Setup.** The small `retail` dataset from Practice Session 2.3.

```bash
psql -d retail
```

```sql
\pset null '(null)'
SELECT count(*) FROM orders;      -- expect 2500
SELECT count(*) FROM customers;   -- expect 1000
```

An inner join keeps only the pairs of rows that satisfy its `ON` condition. `orders`
carries `customer_id`, declared `NOT NULL` with a foreign key to `customers.id`, which is
the fact every question below turns on.

**Task.**

1. Before writing anything: how many rows will `orders JOIN customers` return? Write the
   number down, then check it.
2. List the ten largest orders with the customer's name, city and loyalty tier. Label a
   missing city rather than leaving it blank.
3. Count the distinct customers appearing in the join result, and explain the number.
4. Produce per-customer totals — order count and revenue — with the customer's name, city
   and signup date beside them, for the top five customers by revenue. Do it without
   listing all four customer columns in `GROUP BY`.
5. Run `SELECT id FROM orders JOIN customers ON customers.id = orders.customer_id` and
   explain the result.
6. Count `FROM orders o, customers c` with no predicate. Then decide whether
   `ON c.id = o.customer_id AND c.city = 'Kochi'` and
   `ON c.id = o.customer_id WHERE c.city = 'Kochi'` give the same answer, and say why.

**Solution.**

**1 — the row count, predicted.**

2,500. Every order has exactly one customer, because `orders.customer_id` is `NOT NULL`
and a foreign key guarantees the referenced row exists, so each `orders` row finds exactly
one partner. One match per left row means the join neither multiplies nor filters.

```sql
SELECT count(*) AS joined_rows
FROM   orders o JOIN customers c ON c.id = o.customer_id;
```

```text
 joined_rows
-------------
        2500
(1 row)

```

That reasoning is the important part, not the number. **The guarantee comes from the
schema, not from the data.** Drop the `NOT NULL`, or drop the foreign key, and the same
join starts losing rows on the day the first orphan appears — with no error.

**2 — the ten largest orders, with customer attributes.**

```sql
SELECT o.id AS order_id, o.placed_at::date AS placed, o.total_amount,
       c.name AS customer, coalesce(c.city, '(unknown)') AS city, c.loyalty_tier
FROM   orders o
JOIN   customers c ON c.id = o.customer_id
ORDER  BY o.total_amount DESC, o.id
LIMIT  10;
```

```text
 order_id |   placed   | total_amount |     customer     |    city    | loyalty_tier
----------+------------+--------------+------------------+------------+--------------
     2070 | 2024-10-09 |      5982.78 | Harpreet Shetty  | Ahmedabad  | silver
      712 | 2025-03-01 |      5620.14 | Rohit Iyer       | (unknown)  | silver
     1065 | 2025-08-03 |      5507.72 | Vikram Gupta     | Kolkata    | silver
     1126 | 2025-03-08 |      5447.92 | Harpreet Rao     | (unknown)  | bronze
     2404 | 2025-09-12 |      5087.55 | Harpreet Verma   | Pune       | silver
     1612 | 2025-07-07 |      5077.60 | Farhan Patel     | (unknown)  | silver
      601 | 2024-02-03 |      5076.01 | Karthik Desai    | (unknown)  | (null)
     1294 | 2024-08-09 |      5044.99 | Meera Joshi      | Kolkata    | (null)
      711 | 2026-03-28 |      4825.24 | Imran Pillai     | Chandigarh | silver
     1074 | 2024-03-05 |      4813.92 | Arjun Chatterjee | Kolkata    | gold
(10 rows)

```

Two details worth pointing at. The `coalesce` on `city` turns a NULL into a visible
label; `loyalty_tier` was deliberately left alone so you can see what the other treatment
looks like with `\pset null '(null)'` in force. One of those renders as a blank cell in
every BI tool on the market and the other does not.

And `ORDER BY o.total_amount DESC, o.id` carries a tiebreaker. Without it, two orders of
equal value swap places between executions, because a relation is a set and a join result
has no inherent order (Chapter 1).

**3 — distinct customers in the result.**

```sql
SELECT count(DISTINCT c.id) AS customers_represented
FROM   orders o JOIN customers c ON c.id = o.customer_id;
```

```text
 customers_represented
-----------------------
                   803
(1 row)

```

803 out of 1,000. The join did not lose any *orders* — it lost 197 *customers*, because
an inner join keeps a row only if it finds a partner, and 197 customers have never
ordered. Write a "customers by city" report on top of this join and those 197 vanish from
it, with no warning and a total that still looks sensible. Practice Session 9.2 is
entirely about getting them back.

**4 — per-customer totals with customer attributes.**

```sql
SELECT c.id, c.name, coalesce(c.city, '(unknown)') AS city, c.signup_date,
       count(*)            AS orders,
       sum(o.total_amount) AS revenue
FROM   customers c
JOIN   orders o ON o.customer_id = c.id
GROUP  BY c.id
ORDER  BY revenue DESC
LIMIT  5;
```

```text
 id  |      name       |   city    | signup_date | orders | revenue
-----+-----------------+-----------+-------------+--------+----------
 530 | Harpreet Shetty | Ahmedabad | 2023-04-08  |      9 | 22888.39
 848 | Rajesh Menon    | Bengaluru | 2021-08-31  |      8 | 16324.01
 426 | Aditya Kumar    | Nagpur    | 2023-01-20  |     10 | 15608.09
 399 | Rohit Iyer      | (unknown) | 2025-10-25  |      6 | 14388.00
 219 | Farhan Verma    | Delhi     | 2021-11-28  |      7 | 13555.26
(5 rows)

```

`GROUP BY c.id` alone, while selecting `c.name`, `c.city` and `c.signup_date`, is the
functional-dependency exception from Chapter 8: `c.id` is the primary key of `customers`,
so each group holds at most one customer row and the other columns have exactly one
possible value. PostgreSQL reasons from the *declared* primary key — group by
`c.email` instead and the same query fails, even though email is unique in the data.

This is the payoff for that rule. Without it you maintain a four-column `GROUP BY` list
forever, and every column somebody adds to the select list has to be added there too.

Note also that `count(*)` is correct here and would not be in Session 9.2. This is an
inner join, so every row in every group is a real order.

**5 — the ambiguous column.**

```sql
SELECT id FROM orders JOIN customers ON customers.id = orders.customer_id;
```

```text
ERROR:  column reference "id" is ambiguous
LINE 1: SELECT id FROM orders JOIN customers ON customers.id = order...
               ^
```

Both tables have a column called `id` and PostgreSQL refuses to guess which you meant.
This is the good case. The bad case is the query that *is* unambiguous today because only
one table has the column — and becomes ambiguous, or silently starts reading the other
table's column, when someone runs an `ALTER TABLE`. **Alias every table and qualify every
column**, in anything you commit.

**6 — the comma, and `ON` versus `WHERE` on an inner join.**

```sql
SELECT count(*) AS cartesian FROM orders o, customers c;
```

```text
 cartesian
-----------
   2500000
(1 row)

```

2,500 × 1,000. The comma is `CROSS JOIN`; forgetting the predicate does not raise an
error, it raises a row count. At this size it returns instantly, which is exactly why the
mistake survives into a query that later runs against two million orders.

```sql
SELECT count(*) FROM orders o JOIN customers c ON c.id = o.customer_id AND c.city = 'Kochi';
SELECT count(*) FROM orders o JOIN customers c ON c.id = o.customer_id WHERE c.city = 'Kochi';
```

```text
 count
-------
   126
(1 row)

 count
-------
   126
(1 row)

```

Identical, and for an inner join they always are: there is no NULL-extension step between
the two, so filtering during the join and filtering after it remove the same rows. **Do
not generalise this.** On a `LEFT JOIN` the two forms give different answers, which is the
first trap in Session 9.2. My habit is to keep join conditions in `ON` and business
filters in `WHERE` even on inner joins, so that changing `JOIN` to `LEFT JOIN` later
changes the meaning in exactly one predictable way.

## Practice Session 9.2 — `LEFT JOIN` and the customers with no orders

**Goal.** Find the 197 customers who have never placed an order, and learn the three ways
the standard `LEFT JOIN` anti-join pattern goes wrong.

**Setup.** The small `retail` dataset.

```bash
psql -d retail
```

```sql
\pset null '(null)'
SELECT count(*) FROM customers;   -- expect 1000
SELECT count(*) FROM orders;      -- expect 2500
```

The `\pset` line is not optional for this session. Every result below turns on telling a
NULL apart from a zero or an empty string, and stock `psql` prints all three identically.

A `LEFT JOIN` keeps every row of the left table. Where the right table has no matching
row, the join emits the left row once with every right-hand column set to NULL — a
*NULL-extended* row.

**Task.**

1. Join `customers` to `orders` with a `LEFT JOIN` and count the result. Explain the
   number before reading on.
2. Look at customers 16 to 19 in that join and identify the NULL-extended rows.
3. Find the customers who have never ordered. There should be 197.
4. Now three ways to get it wrong, each of which returns a plausible number:
   a. use `o.shipped_at IS NULL` as the sentinel instead of `o.id IS NULL`;
   b. count orders per customer with `count(*)` and keep the customers with zero;
   c. add `WHERE o.status = 'delivered'` to the `LEFT JOIN` to look at delivered orders
      only.
   Run each, get the wrong number, and explain it.
5. Profile the 197: which loyalty tiers are they in?
6. Get `EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)` for the query in step 3 and read the
   top node. Is PostgreSQL executing an anti-join?

**Solution.**

**1 — the row count.**

```sql
SELECT count(*) AS left_join_rows
FROM   customers c LEFT JOIN orders o ON o.customer_id = c.id;
```

```text
 left_join_rows
----------------
           2697
(1 row)

```

2,697 = 2,500 + 197. Every order still matches exactly one customer, contributing its
2,500 rows, and the 197 customers with no orders each contribute one NULL-extended row.

Note what a `LEFT JOIN` does *not* do: it does not stop the fan-out. A customer with four
orders is still four rows here. `LEFT JOIN` adds rows that inner join would have dropped;
it never removes rows that inner join would have kept.

**2 — the NULL-extended rows.**

```sql
SELECT c.id, c.name, o.id AS order_id, o.status, o.total_amount
FROM   customers c
LEFT   JOIN orders o ON o.customer_id = c.id
WHERE  c.id BETWEEN 16 AND 19
ORDER  BY c.id, o.id;
```

```text
 id |      name       | order_id |  status   | total_amount
----+-----------------+----------+-----------+--------------
 16 | Karthik Sheikh  |     1575 | shipped   |      1789.74
 16 | Karthik Sheikh  |     2088 | shipped   |       467.52
 16 | Karthik Sheikh  |     2214 | paid      |      1034.50
 16 | Karthik Sheikh  |     2341 | delivered |       402.06
 17 | Aditya Banerjee |   (null) | (null)    |       (null)
 18 | Anita Singh     |   (null) | (null)    |       (null)
 19 | Ananya Rao      |     1850 | pending   |       148.80
(7 rows)

```

Customers 17 and 18 are the NULL-extended rows: present, with every `orders` column NULL.
Customer 16 shows the fan-out surviving the outer join.

**3 — the anti-join.**

```sql
SELECT count(*) AS customers_with_no_orders
FROM   customers c
LEFT   JOIN orders o ON o.customer_id = c.id
WHERE  o.id IS NULL;
```

```text
 customers_with_no_orders
--------------------------
                      197
(1 row)

```

And the rows themselves:

```sql
SELECT c.id, c.name, coalesce(c.city, '(unknown)') AS city, c.signup_date,
       coalesce(c.loyalty_tier, '(none)') AS tier
FROM   customers c
LEFT   JOIN orders o ON o.customer_id = c.id
WHERE  o.id IS NULL
ORDER  BY c.id
LIMIT  8;
```

```text
 id |      name       |     city      | signup_date |  tier
----+-----------------+---------------+-------------+--------
 11 | Rohit Kulkarni  | Bengaluru     | 2023-03-26  | silver
 17 | Aditya Banerjee | Bengaluru     | 2024-11-28  | bronze
 18 | Anita Singh     | Mumbai        | 2024-09-01  | (none)
 33 | Divya Patel     | Chandigarh    | 2022-11-28  | gold
 40 | Suresh Kulkarni | Chennai       | 2023-04-27  | gold
 48 | Sneha Pillai    | Delhi         | 2024-10-05  | bronze
 49 | Anita Kulkarni  | Visakhapatnam | 2022-02-02  | gold
 51 | Arjun Rao       | Bhubaneswar   | 2022-11-13  | (none)
(8 rows)

```

Why this works: `WHERE o.id IS NULL` can only be true for a NULL-extended row, because
`orders.id` is the primary key of `orders` and a primary key is `NOT NULL`. Any row that
came from a real order has a non-NULL `o.id`. So the filter keeps exactly the left rows
that found no partner.

**The sentinel column must be one that cannot be NULL in the data.** That is the whole
trick, and it is where 4a goes wrong.

**4a — the wrong sentinel.**

```sql
SELECT count(*) AS wrong
FROM   customers c
LEFT   JOIN orders o ON o.customer_id = c.id
WHERE  o.shipped_at IS NULL;
```

```text
 wrong
-------
   964
(1 row)

```

964, not 197, and 964 is a believable number. `orders.shipped_at` is nullable and
genuinely NULL for the 767 orders that have not shipped. The filter therefore keeps two
different populations at once: 197 customers who never ordered *plus* 767 rows for orders
that exist but have not shipped. 197 + 767 = 964.

Nothing in the output says which row is which. A report built on this would list a
customer who ordered six times yesterday as "no orders".

**4b — `count(*)` on an outer join.**

```sql
SELECT count(*) AS zero_order_customers
FROM   (SELECT c.id, count(*) AS n
        FROM   customers c LEFT JOIN orders o ON o.customer_id = c.id
        GROUP  BY c.id) t
WHERE  t.n = 0;
```

```text
 zero_order_customers
----------------------
                    0
(1 row)

```

Zero, which is the worst possible wrong answer: it says the problem does not exist.
`count(*)` counts *rows*, and a NULL-extended row is a row, so a customer with no orders
has `count(*) = 1`. There is no group anywhere in this query with a count of zero.

Swap in `count(o.id)` and it is right:

```sql
SELECT count(*) AS zero_order_customers
FROM   (SELECT c.id, count(o.id) AS n
        FROM   customers c LEFT JOIN orders o ON o.customer_id = c.id
        GROUP  BY c.id) t
WHERE  t.n = 0;
```

```text
 zero_order_customers
----------------------
                  197
(1 row)

```

This is Chapter 8's rule arriving where it matters. `count(*)` counts rows;
`count(column)` counts known values and skips NULLs. On an inner join the two agree and
the distinction looks academic. On an outer join they differ by exactly the number of
unmatched rows, which is usually the number you were trying to find.

**4c — the predicate that deletes the outer join.**

```sql
SELECT count(*) AS rows
FROM   customers c
LEFT   JOIN orders o ON o.customer_id = c.id
WHERE  o.status = 'delivered';
```

```text
 rows
------
  963
(1 row)

```

963 — which is precisely the number of delivered orders, and exactly what a plain inner
join returns. The `LEFT` has been undone. A NULL-extended row has `o.status` NULL,
`NULL = 'delivered'` evaluates to unknown rather than true (Chapter 7), and `WHERE`
discards it along with every customer who never ordered.

Put the condition in `ON` and the outer join survives:

```sql
SELECT count(*) AS rows
FROM   customers c
LEFT   JOIN orders o ON o.customer_id = c.id AND o.status = 'delivered';
```

```text
 rows
------
 1393
(1 row)

```

1,393 = 963 delivered orders + 430 customers with no delivered order, each NULL-extended.
This is the query you want behind "delivered revenue per customer, including customers
with none".

> **Trap —** on an outer join, a `WHERE` condition on the optional table silently converts
> it to an inner join. There is no error, no warning, and the reviewer sees the word
> `LEFT` and assumes it is doing something. The only exception is `IS NULL` on a
> guaranteed-non-null column, which is the anti-join of step 3 and is deliberate.

**5 — profiling the 197.**

```sql
SELECT coalesce(c.loyalty_tier, '(none)') AS tier, count(*) AS customers
FROM   customers c
LEFT   JOIN orders o ON o.customer_id = c.id
WHERE  o.id IS NULL
GROUP  BY 1
ORDER  BY 2 DESC;
```

```text
  tier  | customers
--------+-----------
 (none) |        79
 bronze |        51
 gold   |        35
 silver |        32
(4 rows)

```

Thirty-five enrolled gold customers have never placed an order. Whether that is a data
problem or a marketing finding is not an SQL question, but it is the sort of thing that
only exists in a query somebody wrote as an outer join.

**6 — the plan, confirming what Chapter 7 told you.**

```sql
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)
SELECT c.id, c.name
FROM   customers c
LEFT   JOIN orders o ON o.customer_id = c.id
WHERE  o.id IS NULL;
```

```text
 Hash Right Join (actual rows=197 loops=1)
   Hash Cond: (o.customer_id = c.id)
   Filter: (o.id IS NULL)
   Rows Removed by Filter: 2500
   ->  Seq Scan on orders o (actual rows=2500 loops=1)
   ->  Hash (actual rows=1000 loops=1)
         Buckets: 1024  Batches: 1  Memory Usage: 57kB
         ->  Seq Scan on customers c (actual rows=1000 loops=1)
 Planning Time: 0.231 ms
 Execution Time: 0.255 ms
(10 rows)

```

No — and Chapter 7, section 7.5, already warned you it would not be. On 15.10 this is a
`Hash Right Join` with a separate `Filter`, not an anti-join node. The plan builds all
2,697 joined rows and then throws away `Rows Removed by Filter: 2500` of them. The pattern
is correct and it is the standard way to write an anti-join with joins alone, but the
planner is not recognising the intent — it is executing the join you asked for and
applying your filter afterwards.

What is new here is the *scale* at which that stops being free. At 2,500 orders it costs
nothing. Point the same pattern at `order_items` and it builds and discards one row per
line item; at five million line items it costs exactly what building and discarding five
million rows costs. Session 9.4 runs that query.

> **Chapter 10 —** the direct way to ask this question is
> `WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id)`, which returns
> the same 197 rows and which PostgreSQL plans as a single `Hash Anti Join` node with no
> filter above it. Chapter 10 measures what the planner's *row estimates* do to each of
> these forms, which is the half neither Chapter 7 nor this session covers.

## Practice Session 9.3 — Self-joining the management hierarchy

**Goal.** Walk the `hr` reporting tree with self-joins, establish that it is exactly seven
levels deep, and understand why a fixed number of joins can never answer an
arbitrary-depth question.

**Setup.** The small `hr` dataset from Practice Session 2.3.

```bash
psql -d hr
```

```sql
\pset null '(null)'
SELECT count(*) FROM employees;   -- expect 2774
```

`employees.manager_id` is a nullable foreign key back to `employees.emp_id`. It is NULL
for exactly one row — the chief executive — and non-NULL for everybody else. There are no
cycles and no orphans.

A self-join is an ordinary join in which both sides are the same table. Nothing special is
required beyond two aliases, because the aliases are what let the two copies be
distinguished.

**Task.**

1. List each employee with their manager's name, for employees 1 to 6.
2. Do it again with `JOIN` instead of `LEFT JOIN`. Count both. Which employee disappeared,
   and why does that matter?
3. Add the skip-level manager — the manager's manager.
4. Establish the depth of the tree. Chain enough self-joins to assign every employee a
   level, and prove that seven is the maximum rather than assuming it.
5. Show the full reporting chain for employee 2,774, from them up to the chief executive.
6. Find employees paid more than their own manager. Then look at the names in that result
   and say what they tell you about joining on names.
7. Count direct reports per manager, including people who manage nobody.

**Solution.**

**1 — employee and manager.**

```sql
SELECT e.emp_id, e.full_name AS employee, e.job_title, m.full_name AS manager
FROM   employees e
LEFT   JOIN employees m ON m.emp_id = e.manager_id
ORDER  BY e.emp_id
LIMIT  6;
```

```text
 emp_id |     employee      |        job_title        |   manager
--------+-------------------+-------------------------+--------------
      1 | Ananya Reddy      | Chief Executive Officer | (null)
      2 | Sneha Reddy       | Senior Vice President   | Ananya Reddy
      3 | Nisha Kulkarni    | Senior Vice President   | Ananya Reddy
      4 | Fatima Chatterjee | Senior Vice President   | Ananya Reddy
      5 | Lakshmi Gupta     | Senior Vice President   | Ananya Reddy
      6 | Vikram Singh      | Senior Vice President   | Ananya Reddy
(6 rows)

```

The aliases `e` and `m` are the entire mechanism. `m.emp_id = e.manager_id` reads as
*the row whose employee id is this row's manager id*, and the direction of that equality
is the only thing distinguishing "my manager" from "my reports". Swap the sides and you
get the other question.

**2 — the inner version, and the employee it loses.**

```sql
SELECT count(*) AS inner_rows
FROM   employees e JOIN employees m ON m.emp_id = e.manager_id;

SELECT count(*) AS left_rows
FROM   employees e LEFT JOIN employees m ON m.emp_id = e.manager_id;
```

```text
 inner_rows
------------
       2773
(1 row)

 left_rows
-----------
      2774
(1 row)

```

The inner join returns 2,773 of 2,774. The missing row is employee 1, the chief executive,
whose `manager_id` is NULL and who therefore matches nothing.

Why this matters more than one row: the lost row is always the **root**. Any hierarchy
self-joined inwards drops its root, and the root is usually the row a head-count total,
an org chart or a cost rollup most needs. The bug appears as a total that is short by one
person, or by one department's entire budget if the root happens to own it, and a test
that asserts "about 2,774 employees" passes.

**3 — the skip-level manager.**

```sql
SELECT e.emp_id, e.full_name AS employee,
       m.full_name AS manager,
       g.full_name AS skip_level
FROM   employees e
LEFT   JOIN employees m ON m.emp_id = e.manager_id
LEFT   JOIN employees g ON g.emp_id = m.manager_id
ORDER  BY e.emp_id
LIMIT  6;
```

```text
 emp_id |     employee      |   manager    | skip_level
--------+-------------------+--------------+------------
      1 | Ananya Reddy      | (null)       | (null)
      2 | Sneha Reddy       | Ananya Reddy | (null)
      3 | Nisha Kulkarni    | Ananya Reddy | (null)
      4 | Fatima Chatterjee | Ananya Reddy | (null)
      5 | Lakshmi Gupta     | Ananya Reddy | (null)
      6 | Vikram Singh      | Ananya Reddy | (null)
(6 rows)

```

The second join hangs off `m`, not off `e`. Every `LEFT` in the chain is load-bearing: the
first keeps the CEO, and the second keeps everybody who reports directly to the CEO, since
their manager has no manager. Make the second one an inner join and you lose all six rows
shown here.

**4 — the depth of the tree.**

Chain seven left self-joins and label each employee by the first level at which the chain
runs out:

```sql
SELECT CASE WHEN l1.emp_id IS NULL THEN 1
            WHEN l2.emp_id IS NULL THEN 2
            WHEN l3.emp_id IS NULL THEN 3
            WHEN l4.emp_id IS NULL THEN 4
            WHEN l5.emp_id IS NULL THEN 5
            WHEN l6.emp_id IS NULL THEN 6
            WHEN l7.emp_id IS NULL THEN 7
            ELSE 8 END AS level,
       count(*) AS employees
FROM   employees e
LEFT   JOIN employees l1 ON l1.emp_id = e.manager_id
LEFT   JOIN employees l2 ON l2.emp_id = l1.manager_id
LEFT   JOIN employees l3 ON l3.emp_id = l2.manager_id
LEFT   JOIN employees l4 ON l4.emp_id = l3.manager_id
LEFT   JOIN employees l5 ON l5.emp_id = l4.manager_id
LEFT   JOIN employees l6 ON l6.emp_id = l5.manager_id
LEFT   JOIN employees l7 ON l7.emp_id = l6.manager_id
GROUP  BY level
ORDER  BY level;
```

```text
 level | employees
-------+-----------
     1 |         1
     2 |         5
     3 |        18
     4 |        70
     5 |       280
     6 |      1100
     7 |      1300
(7 rows)

```

1 + 5 + 18 + 70 + 280 + 1,100 + 1,300 = 2,774, so every employee is accounted for. **The
absence of a `level = 8` row is the proof.** The `ELSE 8` branch fires whenever the chain
is still live after seven hops, and it fired for nobody, so no employee is more than seven
levels from the root.

That is the right way to establish a depth: add one more join than you expect to need and
check that the extra one finds nothing. Chaining exactly seven and finding a full bottom
level tells you nothing about whether there is an eighth.

Also notice the shape — 1, 5, 18, 70, 280, 1,100, 1,300. Branching is uneven and the
bottom two levels hold 86% of the company. Uniform test data would have hidden that, and
the "rank within manager" windows in Chapter 25 need it.

**5 — the full chain for one employee.**

```sql
SELECT e.full_name AS employee, e.job_title,
       l1.full_name AS mgr1, l2.full_name AS mgr2, l3.full_name AS mgr3,
       l4.full_name AS mgr4, l5.full_name AS mgr5, l6.full_name AS mgr6
FROM   employees e
LEFT   JOIN employees l1 ON l1.emp_id = e.manager_id
LEFT   JOIN employees l2 ON l2.emp_id = l1.manager_id
LEFT   JOIN employees l3 ON l3.emp_id = l2.manager_id
LEFT   JOIN employees l4 ON l4.emp_id = l3.manager_id
LEFT   JOIN employees l5 ON l5.emp_id = l4.manager_id
LEFT   JOIN employees l6 ON l6.emp_id = l5.manager_id
```

`\gx` runs the statement with expanded output, which is how you read a wide single row in

This is also where the technique runs out. The chain is six joins because the tree is
seven deep *today*. Hire one more layer of management and this query silently starts
truncating — every deep employee's chain ends one manager short of the CEO, no error.

The query that does not have this problem is a recursive CTE:

```sql
WITH RECURSIVE chain AS (...)
```

which walks upward until it runs out of rows, whatever the depth. That is Chapter 12,
*CTEs and Recursive Queries*. Having written the fixed version by hand, the recursive one
reads as the obvious simplification rather than as new syntax to memorise.

## Practice Session 9.4 — Diagnosing a fan-out that inflated a `SUM`

**Goal.** Reproduce the three-fold revenue inflation caused by joining `orders` to
`order_items`, find the cause from the data rather than from the query text, repair it two
different ways, and compare what the repairs cost.

**Setup.** The small `retail` dataset for the diagnosis, and the large `retail_lg`
database built in Practice Session 8.2 for the cost comparison at the end.

```bash
psql -d retail
```

```sql
\pset null '(null)'
SELECT count(*) FROM orders;        -- expect 2500
SELECT count(*) FROM order_items;   -- expect 6250
SELECT sum(total_amount) FROM orders;   -- expect 3678982.61
```

`orders.total_amount` is denormalised in this dataset and kept exactly consistent with the
sum over its line items, so there is a correct answer to reconcile against. Practice
Session 6.3 met this bug from the row-count side; this session is about the money and the
repair.

**Task.**

1. Reproduce the inflation: sum `orders.total_amount` alone, then sum it across a join to
   `order_items`. Both are single queries and they disagree by millions.
2. Do not accept "the join duplicated rows" as the diagnosis. Work out *exactly* where the
   7,459,806.78 of excess comes from, and prove the arithmetic.
3. The row count inflated 2.50× and the money inflated 3.03×. Explain the gap. Then say
   whether you can recover the true total by dividing.
4. Build the report that makes this bug reach production: revenue and units sold per city,
   in one query, joining `customers` → `orders` → `order_items`. Identify which of the two
   measures is wrong.
5. Try `sum(DISTINCT o.total_amount)` as the fix. Find out why it is worse than the bug.
6. Fix it properly, twice:
   a. collapse the child table to one row per order *before* joining;
   b. aggregate each grain separately and join the two results.
   Confirm both agree with step 4's correct figures, and find the trap in (b).
7. Compare `EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)` for the broken query and for fix
   (a), first on `retail` and then on `retail_lg`. The answer at scale is not the one you
   expect.

**Solution.**

**1 — the inflation.**

```sql
SELECT sum(total_amount) AS revenue FROM orders;

SELECT sum(o.total_amount) AS revenue
FROM   orders o
JOIN   order_items oi ON oi.order_id = o.id;
```

```text
  revenue
------------
 3678982.61
(1 row)

   revenue
-------------
 11138789.39
(1 row)

```

One join, three times the money, no error and no warning. The second query returns a
figure of entirely plausible magnitude for a business of this shape, which is why this bug
is usually discovered by someone outside engineering.

**2 — where the excess comes from.**

The join emits one row per line item, and each of those rows carries its parent order's
`total_amount`. So an order with *n* lines contributes `total_amount × n` instead of
`total_amount`, and its excess contribution is `total_amount × (n − 1)`.

That is a claim. Test it:

```sql
SELECT sum(t.total_amount * t.n_items)       AS joined_sum,
       sum(t.total_amount)                   AS true_sum,
       sum(t.total_amount * (t.n_items - 1)) AS excess
FROM   (SELECT o.id, o.total_amount, count(*) AS n_items
        FROM   orders o JOIN order_items oi ON oi.order_id = o.id
        GROUP  BY o.id, o.total_amount) t;
```

```text
 joined_sum  |  true_sum  |   excess
-------------+------------+------------
 11138789.39 | 3678982.61 | 7459806.78
(1 row)

```

`joined_sum` reproduces the broken figure to the paisa from order-level data alone, which
confirms the mechanism exactly: nothing is wrong with the data, and no row of
`order_items` is a duplicate. The query asked for one row per line item and then summed a
column that describes the order.

This is the diagnostic worth keeping. **When two aggregates disagree, reproduce the wrong
one from first principles.** If you can predict the wrong number, you understand it; if
you can only describe it as "duplicates", you will fix it with `DISTINCT` and be wrong
again next quarter.

**3 — why 3.03 and not 2.50.**

```sql
SELECT n_items, count(*) AS orders, round(avg(total_amount), 2) AS avg_order
FROM   (SELECT o.id, o.total_amount, count(*) AS n_items
        FROM   orders o JOIN order_items oi ON oi.order_id = o.id
        GROUP  BY o.id, o.total_amount) t
GROUP  BY n_items
ORDER  BY n_items;
```

```text
 n_items | orders | avg_order
---------+--------+-----------
       1 |    644 |    569.28
       2 |    611 |   1158.12
       3 |    596 |   1781.99
       4 |    649 |   2377.02
(4 rows)

```

Rows inflated by 6250 / 2500 = 2.50, the mean line count. Money inflated by
11138789.39 / 3678982.61 = 3.03. The two differ because **the duplication factor is
correlated with the measure being summed**: a four-line order is worth four times as much
as a one-line order *and* is duplicated four times, so large orders are over-weighted in
the inflated total.

So: no, you cannot divide. `11138789.39 / 2.5` is 4,455,515.76, which is 776,533.15 too
high and would look every bit as plausible as the original error. The only correct
response is to fix the query.

That correlation is the general case, not a quirk of this dataset. Child-row counts
usually correlate with parent size — bigger orders have more lines, bigger accounts have
more transactions, busier devices emit more events — so the naive correction is almost
always wrong, and wrong in the direction of still being too high.

**4 — the report that ships.**

```sql
SELECT coalesce(c.city, '(unknown)') AS city,
       sum(o.total_amount) AS revenue,
       sum(oi.quantity)    AS units
FROM   customers c
JOIN   orders o       ON o.customer_id = c.id
JOIN   order_items oi ON oi.order_id = o.id
GROUP  BY c.city
ORDER  BY revenue DESC
LIMIT  5;
```

```text
    city     |  revenue   | units
-------------+------------+-------
 (unknown)   | 1399283.37 |  2289
 Bhubaneswar |  724762.30 |  1148
 Hyderabad   |  603743.31 |  1069
 Nagpur      |  601848.15 |   984
 Kochi       |  589514.74 |   982
(5 rows)

```

Here is what makes this the dangerous shape. **`units` is correct and `revenue` is wrong,
in the same row of the same query.** `oi.quantity` is a line-level fact being summed at
line level, so the fan-out does not touch it. `o.total_amount` is an order-level fact
being summed at line level, so it is counted once per line.

Compare against the true per-city revenue, which Practice Session 8.1 also produced:

```sql
SELECT coalesce(c.city, '(unknown)') AS city, sum(o.total_amount) AS revenue
FROM   customers c
JOIN   orders o ON o.customer_id = c.id
GROUP  BY c.city
ORDER  BY revenue DESC
LIMIT  5;
```

```text
    city     |  revenue
-------------+-----------
 (unknown)   | 465684.20
 Bhubaneswar | 242128.87
 Hyderabad   | 204241.20
 Nagpur      | 191715.08
 Kochi       | 185669.59
(5 rows)

```

Same cities, same ranking, every number wrong by about three. The ranking surviving is
what kills you: a reviewer checks that Bhubaneswar is still on top, sees that it is, and
approves.

**The general rule this gives you.** A query joins tables at several grains. Every
aggregate in the select list is computed at the *finest* grain in the `FROM` clause —
here, the line item. An aggregate over a column belonging to a coarser grain is inflated
by the fan-out between the two. Before you write `sum(x)`, ask which table `x` lives on
and whether the join has made that table's rows repeat.

**5 — the fix that is worse than the bug.**

```sql
SELECT sum(DISTINCT o.total_amount) AS revenue
FROM   orders o
JOIN   order_items oi ON oi.order_id = o.id;
```

```text
  revenue
------------
 3667689.66
(1 row)

```

3,667,689.66 against a true 3,678,982.61 — wrong by 11,292.95, or 0.3%. That is far more
dangerous than being wrong by 200%, because nobody notices 0.3% and nothing reconciles.

`sum(DISTINCT x)` deduplicates *values*, not rows, and two different orders that happen
to have the same total are one value:

```sql
SELECT count(*) - count(DISTINCT total_amount) AS colliding_amounts FROM orders;
```

```text
 colliding_amounts
-------------------
                13
(1 row)

```

Read that number carefully: it is the count of *excess* rows, not of orders. Thirteen
amounts in this table are shared, by 26 orders in 13 pairs, and `sum(DISTINCT ...)` counts
each shared amount once — so thirteen orders' revenue silently vanishes from the total:

```sql
SELECT count(*) AS shared_amounts, sum(n) AS orders_involved,
       sum((n - 1) * total_amount) AS money_dropped
FROM   (SELECT total_amount, count(*) AS n FROM orders GROUP BY 1 HAVING count(*) > 1) t;
```

```text
 shared_amounts | orders_involved | money_dropped
----------------+-----------------+---------------
             13 |              26 |      11292.95
(1 row)

```

11,292.95 — exactly the shortfall, to the paisa. On a bigger dataset, or on a column with
coarse values like a monthly fee, the collision rate goes up and so does the error.

`DISTINCT` and `sum(DISTINCT ...)` are the two standard responses to a fan-out and both
are wrong for the same reason: they operate on the output of a join that should not have
produced those rows. Remove the cause.

**6a — collapse the child before joining.**

```sql
SELECT coalesce(c.city, '(unknown)') AS city,
       sum(o.total_amount) AS revenue,
       sum(li.units)       AS units
FROM   customers c
JOIN   orders o ON o.customer_id = c.id
JOIN   (SELECT order_id, sum(quantity) AS units
        FROM   order_items
        GROUP  BY order_id) li ON li.order_id = o.id
GROUP  BY c.city
ORDER  BY revenue DESC
LIMIT  5;
```

```text
    city     |  revenue  | units
-------------+-----------+-------
 (unknown)   | 465684.20 |  2289
 Bhubaneswar | 242128.87 |  1148
 Hyderabad   | 204241.20 |  1069
 Nagpur      | 191715.08 |   984
 Kochi       | 185669.59 |   982
(5 rows)

```

Revenue now matches the true figures and `units` is unchanged, because summing a sum of
quantities gives the same total as summing the quantities.

The principle: `order_items` was aggregated to **one row per order** before it met
`orders`, so the join is one-to-one and nothing is replicated. This is the fix to reach
for first. It generalises to any number of child tables — pre-aggregate each one to the
parent's grain and join them all in, which is the only way to attach two different
children without their fan-outs multiplying together.

**6b — aggregate each grain separately, then join.**

```sql
SELECT coalesce(rev.city, '(unknown)') AS city, rev.revenue, u.units
FROM   (SELECT c.city, sum(o.total_amount) AS revenue
        FROM   customers c JOIN orders o ON o.customer_id = c.id
        GROUP  BY c.city) rev
JOIN   (SELECT c.city, sum(oi.quantity) AS units
        FROM   customers c
        JOIN   orders o       ON o.customer_id = c.id
        JOIN   order_items oi ON oi.order_id = o.id
        GROUP  BY c.city) u
       ON u.city IS NOT DISTINCT FROM rev.city
ORDER  BY rev.revenue DESC
LIMIT  5;
```

```text
    city     |  revenue  | units
-------------+-----------+-------
 (unknown)   | 465684.20 |  2289
 Bhubaneswar | 242128.87 |  1148
 Hyderabad   | 204241.20 |  1069
 Nagpur      | 191715.08 |   984
 Kochi       | 185669.59 |   982
(5 rows)

```

Same answers. Each measure is computed in its own query at its own grain, and the two
results — one row per city each — are joined together.

**The trap is the join key.** `city` is nullable, and `NULL = NULL` is not true, so an
ordinary equality join drops the NULL city entirely:

```sql
SELECT count(*) AS with_is_not_distinct FROM
  (SELECT c.city, sum(o.total_amount) r FROM customers c JOIN orders o ON o.customer_id = c.id
   GROUP BY c.city) a
  JOIN (SELECT c.city, sum(oi.quantity) u FROM customers c
        JOIN orders o ON o.customer_id = c.id
        JOIN order_items oi ON oi.order_id = o.id GROUP BY c.city) b
    ON b.city IS NOT DISTINCT FROM a.city;

SELECT count(*) AS with_equals FROM
  (SELECT c.city, sum(o.total_amount) r FROM customers c JOIN orders o ON o.customer_id = c.id
   GROUP BY c.city) a
  JOIN (SELECT c.city, sum(oi.quantity) u FROM customers c
        JOIN orders o ON o.customer_id = c.id
        JOIN order_items oi ON oi.order_id = o.id GROUP BY c.city) b
    ON b.city = a.city;
```

```text
 with_is_not_distinct
----------------------
                   21
(1 row)

 with_equals
-------------
          20
(1 row)

```

Twenty cities instead of twenty-one, and the missing one is `(unknown)` — the largest row
in the report, 465,684.20 of revenue. `IS NOT DISTINCT FROM` treats two NULLs as equal,
which is the same *grouping equivalence* `GROUP BY` uses (Chapter 8) and not the same as
`=`. Any time you join two aggregate results on a nullable grouping key, you need it — or
you need to `coalesce` the key to a sentinel inside both subqueries before joining, which
is often clearer and lets an equality join use an index.

Between (a) and (b): prefer (a). It reads the fact tables once, it extends to more
children without another pass, and it does not need the NULL-key treatment.

Raising `work_mem` removes the spill. Rewriting fix (a) as a CTE, or filtering the orders
before the join so the pre-aggregate is smaller, changes the shape entirely. Chapter 34
reads plans like this one line by line and Chapter 45 sizes `work_mem` properly.

The conclusion to carry out of this session is not about performance at all:

> **The wrong answer was the faster one, and it will usually be the faster one**, because

> join one-to-one. Correctness is not a tuning outcome you can measure your way to. Decide
> what one row of your result means, build the query that produces exactly that, and
> *then* make it fast.
