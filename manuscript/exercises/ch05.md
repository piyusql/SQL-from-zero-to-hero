## Practice Session 5.1 — `COPY` against row-by-row `INSERT`

**Goal.** Measure the three bulk-loading methods yourself and see the two orders of
magnitude between the slowest and the fastest.

**Setup.**

```sql
CREATE TABLE t (id int, label text, amount numeric(10,2));
\timing on
```

Generate twenty thousand rows three ways. From a shell, in another window:

```bash
python3 -c "
print('BEGIN;')
for i in range(1, 20001):
    print(f\"INSERT INTO t VALUES ({i}, 'label {i}', {i%1000}.50);\")
print('COMMIT;')" > /tmp/rows.sql

python3 -c "
print('BEGIN;')
for b in range(0, 20000, 1000):
    vals = ','.join(f\"({i},'label {i}',{i%1000}.50)\" for i in range(b+1, b+1001))
    print(f'INSERT INTO t VALUES {vals};')
print('COMMIT;')" > /tmp/multi.sql

python3 -c "
for i in range(1, 20001):
    print(f'{i}\tlabel {i}\t{i%1000}.50')" > /tmp/rows.tsv
```

**Task.**

1. Load `/tmp/rows.sql`, time it, then `TRUNCATE t`.
2. Load `/tmp/multi.sql`, time it, then `TRUNCATE t`.
3. Load `/tmp/rows.tsv` with `\copy`, time it.
4. Confirm all three produced 20,000 rows.
5. Explain why the first is so much slower, given that all three run inside a single
   transaction and write identical data.
6. Predict what happens to the first number if you remove the `BEGIN`/`COMMIT` wrapper,
   then try it.

**Solution.**

```bash
psql ch05_practice -f /tmp/rows.sql
psql ch05_practice -c "TRUNCATE t;"
psql ch05_practice -f /tmp/multi.sql
psql ch05_practice -c "TRUNCATE t;"
psql ch05_practice -c "\copy t FROM '/tmp/rows.tsv'"
psql ch05_practice -c "SELECT count(*) FROM t;"
```

Measured on PostgreSQL 15.10:

| Method | Time | Relative |
|---|---:|---:|
| 20,000 single-row `INSERT`s | 3.99 s | 1× |
| 1,000 rows per `INSERT` | 0.06 s | 66× faster |
| `\copy` | 0.03 s | 133× faster |

Your absolute numbers will differ; the ratios should not.

**Why.** The cost is per *statement*, not per row. Each statement is parsed, rewritten,
planned and executed, and carries a protocol round trip. Twenty thousand statements pay
that twenty thousand times; twenty statements pay it twenty times; `COPY` skips the
statement machinery altogether and streams rows into the table. The work of physically
writing 20,000 rows is nearly identical in all three — it is the overhead around it that
differs by two orders of magnitude.

**Step 6.** Without the wrapper each `INSERT` becomes its own transaction and must flush
the WAL to durable storage before returning. Measured on the same machine:

| 20,000 single-row `INSERT`s | Time |
|---|---:|
| inside one transaction | 3.81 s |
| autocommit | 5.88 s |

About **1.5×** — real, but far less than the folklore promises, because this container's
storage has a cheap `fsync`. On hardware where a flush costs milliseconds the gap is much
larger. Wrapping an existing row-at-a-time import in one transaction is still usually the
cheapest available speed-up before changing any code; just do not expect it to rescue an
import that is slow for the reason this session is actually about.

> **Before you conclude `COPY` always wins:** it is all-or-nothing. One malformed row
> aborts the whole load. For input you do not control, stage it first — see the note in
> section 5.3.

## Practice Session 5.2 — An upsert you can safely run twice

**Goal.** Write an import that is *idempotent* — running it again changes nothing it
should not — and understand where `ON CONFLICT` stops protecting you.

**Setup.**

```sql
CREATE TABLE inv (
    sku        text PRIMARY KEY,
    qty        int NOT NULL,
    updated_at timestamptz NOT NULL DEFAULT now()
);
```

**Task.**

1. Write one statement that inserts `A-1`/10, `A-2`/5, `A-3`/8, or updates the quantity
   if the SKU already exists. Have it report which rows were inserted and which updated.
2. Run it twice. Confirm the table still holds three rows and the second run reports all
   three as updates.
3. Change the statement so the quantity *accumulates* rather than replaces, and add 3 to
   `A-1`.
4. Try to write the same upsert using `ON CONFLICT (qty)`. Explain the error.
5. Run an upsert of `A-1` and a new `A-9` using `DO NOTHING` with `RETURNING`. Count the
   returned rows. What has the statement not told you?

**Solution.**

```sql
INSERT INTO inv (sku, qty) VALUES ('A-1',10), ('A-2',5), ('A-3',8)
ON CONFLICT (sku) DO UPDATE
SET qty = EXCLUDED.qty, updated_at = now()
RETURNING sku, CASE WHEN xmax = 0 THEN 'inserted' ELSE 'updated' END AS action;
```

First run:

```text
 sku |  action
-----+----------
 A-1 | inserted
 A-2 | inserted
 A-3 | inserted
(3 rows)
```

Run the identical statement again:

```text
 sku | action
-----+---------
 A-1 | updated
 A-2 | updated
 A-3 | updated
(3 rows)
```

Three rows either way. That is what idempotent means here: re-running converges on the
same state rather than duplicating or failing.

`xmax` is a system column holding the transaction that deleted or locked a row version.
On a row your statement just inserted it is `0`; on one it updated, it is not. `RETURNING`
alone cannot tell the two apart — both come back looking identical.

**Step 3 — accumulate instead of replace.** Inside `DO UPDATE`, the table name means the
existing row and `EXCLUDED` means the row you tried to insert:

```sql
INSERT INTO inv (sku, qty) VALUES ('A-1', 3)
ON CONFLICT (sku) DO UPDATE SET qty = inv.qty + EXCLUDED.qty
RETURNING sku, qty;
```

```text
 sku | qty
-----+-----
 A-1 |  13
(1 row)
```

10 + 3. Whether you want `EXCLUDED.qty` or `inv.qty + EXCLUDED.qty` is a business
question — "this is the new count" versus "this is a delivery" — and the two are one
character apart in the diff. Say which you mean in a comment.

**Step 4.**

```text
ERROR:  there is no unique or exclusion constraint matching the ON CONFLICT specification
```

The conflict target must be backed by a unique constraint or index, because that index is
the mechanism the conflict is detected with. `qty` has no such constraint, and PostgreSQL
will not guess.

**Step 5 — the silent gap.**

```sql
INSERT INTO inv (sku, qty) VALUES ('A-1', 1), ('A-9', 4)
ON CONFLICT (sku) DO NOTHING
RETURNING sku, qty;
```

```text
 sku | qty
-----+-----
 A-9 |   4
(1 row)
```

Two rows submitted, one returned. `A-1` conflicted and was skipped, and it is *absent*
from the output — indistinguishable from a row you never sent. Any code that upserts a
batch and counts `RETURNING` rows to confirm success will under-report every time a row
already existed. If you need to account for every row, use `DO UPDATE` — even a trivial
`SET sku = EXCLUDED.sku` — so nothing is silently dropped.

`DO NOTHING` also does not lock the conflicting row, which matters under concurrency: see
section 5.7.

## Practice Session 5.3 — Capturing what you changed with `RETURNING`

**Goal.** Use `RETURNING` to avoid a second round trip, and to move rows between tables
in a single statement.

**Setup.** Continue in `ch05_practice` with the `inv` table from Session 5.2, and add:

```sql
CREATE TABLE inv_archive (LIKE inv);
```

**Task.**

1. Insert a new SKU and get its `updated_at` back without issuing a second query.
2. *Preview* which rows have `qty < 8`, without deleting anything. (Section 5.4 makes
   this a habit: write the `WHERE` clause as a `SELECT` first.)
3. Now move exactly those rows into `inv_archive` in **one statement**, and report what
   moved.
4. Confirm the counts on both tables.
5. Explain why doing this as `SELECT`, then `INSERT`, then `DELETE` is not equivalent.

**Solution.**

```sql
INSERT INTO inv (sku, qty) VALUES ('B-7', 22)
RETURNING sku, qty, updated_at;
```

```text
 sku | qty |          updated_at
-----+-----+-------------------------------
 B-7 |  22 | 2026-09-14 13:34:03.192273+00
(1 row)
```

One statement, one round trip, and you have the server-generated `updated_at` without
guessing at it or re-reading the row.

Preview first — this is the habit from section 5.4, and here it also protects the next
step, because a `DELETE` would consume the very rows you are about to move:

```sql
SELECT sku, qty FROM inv WHERE qty < 8 ORDER BY sku;
```

```text
 sku | qty
-----+-----
 A-2 |   5
 A-9 |   4
(2 rows)
```

Now the move, as a single statement using a data-modifying CTE:

```sql
WITH removed AS (
    DELETE FROM inv WHERE qty < 8 RETURNING *
)
INSERT INTO inv_archive SELECT * FROM removed
RETURNING sku, qty;
```

```text
 sku | qty
-----+-----
 A-2 |   5
 A-9 |   4
(2 rows)
```

```sql
SELECT (SELECT count(*) FROM inv) AS inv, (SELECT count(*) FROM inv_archive) AS archive;
```

```text
 inv | archive
-----+---------
   3 |       2
(1 row)
```

**Why the three-statement version is not equivalent.** `SELECT`, then `INSERT`, then
`DELETE` leaves two windows in which the world can change. A row can be modified between
your `SELECT` and your `DELETE`, so you archive a stale copy and delete the current one.
A row can be inserted that matches your predicate after the `SELECT` but before the
`DELETE`, so you delete a row you never archived. Wrapping all three in a transaction
narrows the window but does not close it under `READ COMMITTED` — Chapter 31 shows
exactly why.

The CTE form has no window. The `DELETE` and the `INSERT` see the same snapshot and
succeed or fail together.

> **One subtlety for later:** all parts of a data-modifying CTE see the same snapshot, so
> the `INSERT` cannot observe the `DELETE`'s effect. That is what makes this safe, and it
> also means you cannot chain modifications that depend on each other's results.
> Chapter 12 covers the rules.
