# Chapter 1 Exercises — The Relational Model and Why PostgreSQL

Chapter 1 has no database yet — you install one in Chapter 2. These two sessions are
deliberately pen-and-paper, because the thinking they exercise is the part people skip,
and skipping it is what produces the kind of schema Chapter 1 opens with: columns named
`flag_2`, a table called `user_data_new`, and a `status` column holding eleven values
nobody can define.

## Practice Session 1.1 — Find the relations

**Goal.** Extract a relational structure from a description written in business language.

**Setup.** None. Paper, or a text file.

**Task.** Read the following, as though a client had said it to you.

> "We run a small chain of bookshops. Each shop has a name and an address. We stock books
> — every book has a title, an author, an ISBN and a price, and the same book can be
> stocked by several shops with different quantities. Customers have an account with us;
> they give us a name and an email. When a customer buys something, we record the sale:
> which shop, which customer, the date, and which books they bought and how many of each.
> A sale can include several different books."

Write down the relations you would create. For each one, list its attributes, mark which
attribute identifies a row, and mark which attributes point at another relation. Then
write in plain English the single fact that one row of each relation asserts.

Do not write SQL. Do not worry about data types. The exercise is the structure.

**Solution.**

Six relations. The count itself is the first thing to get right.

```text
shops        (shop_id, name, address)
                 ↑ identifies

books        (isbn, title, author, price)
                 ↑ identifies

customers    (customer_id, name, email)
                 ↑ identifies

stock        (shop_id → shops, isbn → books, quantity)
                 ↑ the pair identifies

sales        (sale_id, shop_id → shops, customer_id → customers, sold_at)
                 ↑ identifies

sale_items   (sale_id → sales, isbn → books, quantity)
                 ↑ the pair identifies
```

And the facts:

- **shops** — *there is a shop with this ID, at this address.*
- **books** — *there is a book with this ISBN, by this author, at this price.*
- **customers** — *there is a customer with this ID and this email.*
- **stock** — *this shop currently holds this many copies of this book.*
- **sales** — *this customer bought something from this shop at this moment.*
- **sale_items** — *this sale included this many copies of this book.*

Two things in there are the actual lesson.

**`stock` exists because "the same book in several shops with different quantities" is a
many-to-many relationship, and the quantity belongs to the pairing rather than to either
side.** It is not an attribute of the book and not an attribute of the shop. Every time
you find yourself wanting to put a value on a relationship, you have found a table. If you
tried to solve this by adding columns to `books` — `quantity_shop_1`, `quantity_shop_2` —
you have designed something that requires a schema migration every time the chain opens a
branch.

**`sales` and `sale_items` are separate because a sale is one event and the items are
several facts about it.** The date and the customer belong to the sale; they are stated
once. The quantities belong to the individual lines. Collapsing these into one table means
repeating the customer and date on every line, and then nothing stops the third line of a
sale from disagreeing with the first about who bought it.

If your answer had four or five relations, look at which of these two you merged, and
write out what happens when the data disagrees with itself. That question — *what stops
this from becoming inconsistent?* — is the one that produces good schemas, and we
formalise it as normalization in Chapter 18.

## Practice Session 1.2 — Stop thinking in loops

**Goal.** Convert imperative, step-by-step reasoning into a declarative description of a
result set.

**Setup.** None.

**Task.** Below are three descriptions of work, written the way a programmer thinks about
it. For each, write one or two sentences describing *the set of rows in the answer*,
without any reference to order of operations, iteration, or intermediate variables.

1. "Go through every customer. For each one, look at all their sales. Add up the total.
   If the total is over a thousand, remember that customer. At the end, return the list of
   remembered customers."

2. "Take the list of books. For each book, check whether any shop has it in stock. Keep a
   counter. If the counter is zero, add it to the out-of-stock list."

3. "For each shop, find its sales. Sort them by date. Take the most recent one. Put the
   shop and that date in the results."

**Solution.**

1. *The customers whose sales total more than one thousand.*

2. *The books for which no stock row exists with a quantity above zero.*

3. *For each shop, the shop and the date of its most recent sale.*

Notice what disappeared. Iteration, counters, accumulators, sorting-in-order-to-pick,
and the word "then". None of those are part of the answer; they were all part of one
particular strategy for computing it, and the database is going to choose its own
strategy anyway.

Notice too what survived. Number two became a statement about *non-existence* — the
absence of a matching row — which in SQL is `NOT EXISTS` and which we cover in Chapter 10.
Number three became *the maximum per group*, a shape so common it has several idioms; the
cleanest uses window functions in Chapter 25. Number one is a simple aggregate with a
condition applied after grouping, which is Chapter 8.

You have just described all three in the language the query planner thinks in. The syntax
is the easy part from here.

> **Why this matters —** almost every genuinely slow query written by a competent
> programmer is a loop that was translated into SQL one step at a time instead of being
> restated as a set. The N+1 problem in Chapter 36 is exactly this mistake, committed by a
> framework on your behalf, several thousand times per page load.
