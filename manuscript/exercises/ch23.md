# Chapter 23 Exercises — The Column Design Checklist

## Practice Session 23.1 — Audit a table column by column

**Goal.** Take an unreviewed table, audit every column against the checklist with catalog queries and data probes, and migrate it to a design where every rewrite, default and constraint is a decision.

**Setup.** A scratch database and a deliberately sloppy vendor table with 500 deterministic rows. Nothing here touches `retail`.

```bash
createdb ch23_ws1
psql -d ch23_ws1
```

```sql
\pset null '(null)'
CREATE TABLE vendor_sloppy (
    id        serial PRIMARY KEY,
    name      text,
    gstin     text,
    phone     bigint,
    state     text,
    active    char(1),
    rating    float8,
    onboarded timestamp,
    status    text,
    notes     text
);
INSERT INTO vendor_sloppy (name, gstin, phone, state, active, rating, onboarded, status, notes)
SELECT CASE WHEN g % 50 = 0 THEN '  ' ELSE 'Vendor ' || g END,
       CASE WHEN g % 10 = 0 THEN NULL ELSE '27' || upper(substr(md5(g::text), 1, 10)) || '1Z5' END,
       CASE WHEN g % 7 = 0 THEN NULL ELSE 9000000000 + g END,
       (ARRAY['Maharashtra','Karnataka','Tamil Nadu','Gujarat','Delhi','maharashtra','KARNATAKA'])[g % 7 + 1],
       (ARRAY['Y','N','y'])[g % 3 + 1],
       (g % 50) / 10.0,
       timestamp '2025-01-01' + g * interval '3 hours',
       CASE WHEN g % 4 = 0 THEN NULL ELSE (ARRAY['active','on_hold','closed'])[g % 3 + 1] END,
       CASE WHEN g % 3 = 0 THEN '' ELSE 'ok' END
FROM generate_series(1, 500) g;
ANALYZE vendor_sloppy;
```

**Task.**

1. Write one catalog query that lists each column with its type, nullability, default and the share of NULLs. Which columns are nullable that should not be?
2. Write one data probe that counts: names that are blank or whitespace, NULL and blank values in `gstin` and `notes`, NULL `status`, distinct spellings of `state` against distinct `lower(state)`, and distinct values of `active`.
3. For each of the ten columns decide *keep*, *change type*, *add constraint*, or *make NOT NULL*, with a one-line reason tied to a checklist item. One of the decisions is a guess about what NULL means; say which, and how you would confirm it.
4. Write the target `vendor` table and the `INSERT ... SELECT` that migrates the clean rows.
5. Prove the new table rejects three bad rows: an unknown status, a blank name and a malformed GSTIN.

**Solution.**

Step 1. `null_frac` is exact here because `ANALYZE` reads every row of a 500-row table.

```sql
SELECT a.attnum AS n, a.attname AS column, format_type(a.atttypid, a.atttypmod) AS type,
       CASE WHEN a.attnotnull THEN 'NOT NULL' ELSE 'nullable' END AS nulls,
       coalesce(pg_get_expr(d.adbin, d.adrelid), '') AS default,
       round(s.null_frac::numeric, 3) AS null_frac
FROM pg_attribute a
LEFT JOIN pg_attrdef d ON (d.adrelid, d.adnum) = (a.attrelid, a.attnum)
LEFT JOIN pg_stats s ON (s.schemaname, s.tablename, s.attname) = ('public','vendor_sloppy', a.attname)
WHERE a.attrelid = 'vendor_sloppy'::regclass AND a.attnum > 0 AND NOT a.attisdropped
ORDER BY a.attnum;
```

```text
 n  |  column   |            type             |  nulls   |                  default                  | null_frac
----+-----------+-----------------------------+----------+-------------------------------------------+-----------
  1 | id        | integer                     | NOT NULL | nextval('vendor_sloppy_id_seq'::regclass) |     0.000
  2 | name      | text                        | nullable |                                           |     0.000
  3 | gstin     | text                        | nullable |                                           |     0.100
  4 | phone     | bigint                      | nullable |                                           |     0.142
  5 | state     | text                        | nullable |                                           |     0.000
  6 | active    | character(1)                | nullable |                                           |     0.000
  7 | rating    | double precision            | nullable |                                           |     0.000
  8 | onboarded | timestamp without time zone | nullable |                                           |     0.000
  9 | status    | text                        | nullable |                                           |     0.250
 10 | notes     | text                        | nullable |                                           |     0.000
(10 rows)
```

Only `id` is `NOT NULL`. `name` has zero NULLs and every other column carries its own problem, which the catalog cannot see. That is what step 2 is for.

Step 2.

```sql
SELECT count(*) FILTER (WHERE btrim(name) = '') AS blank_names,
       count(*) FILTER (WHERE gstin IS NULL) AS null_gstin,
       count(*) FILTER (WHERE notes = '') AS blank_notes,
       count(*) FILTER (WHERE status IS NULL) AS null_status,
       count(DISTINCT state) AS state_spellings,
       count(DISTINCT lower(state)) AS states,
       count(DISTINCT active) AS active_spellings
FROM vendor_sloppy;
```

```text
 blank_names | null_gstin | blank_notes | null_status | state_spellings | states | active_spellings
-------------+------------+-------------+-------------+-----------------+--------+------------------
          10 |         50 |         166 |         125 |               7 |      5 |                3
(1 row)
```

Ten vendors have a blank name that a `NOT NULL` would have accepted. There are seven spellings of five states. `active` has three spellings of two values, and 166 blank `notes` are missing values written as empty strings.

Step 3. The decisions:

| Column | Decision | Why |
|---|---|---|
| `id serial` | `bigint GENERATED ALWAYS AS IDENTITY` | Checklist 1; overflow later is a rewrite |
| `name` | `NOT NULL` + `CHECK (btrim(name) <> '')` | 7: blank strings are NULLs in disguise |
| `gstin` | keep nullable + shape `CHECK` | 2: some vendors are unregistered, so NULL means not applicable |
| `phone bigint` | `text` + E.164 `CHECK` | 1: never added, and the leading `+` is data |
| `state` | `NOT NULL` + normalised `CHECK`; clean the case on load | 6 |
| `active char(1)` | `is_active boolean NOT NULL DEFAULT true` | 1: `char(1)` `Y`/`y`/`N` is three spellings of a flag |
| `rating float8` | `numeric(2,1)` + `CHECK (BETWEEN 0 AND 5)` | 6; the range is a rule |
| `onboarded timestamp` | `onboarded_at timestamptz NOT NULL DEFAULT now()` | 1: an event is an instant |
| `status` | `NOT NULL DEFAULT 'active'` + `CHECK IN (...)` | 2 and 3, and this is the guess |
| `notes` | nullable, `CHECK (notes IS NULL OR btrim(notes) <> '')` | 7: store absence as NULL |

The guess is that a NULL `status` means "active". 125 vendors (25%) have it, and treating them as `active` is only defensible if you confirm it with whoever owns the vendor process. If NULL meant "not yet reviewed", the right design adds a fourth status instead. Also assumed: `onboarded` values were Kolkata wall-clock time.

Step 4.

```sql
CREATE TABLE vendor (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name          text NOT NULL CONSTRAINT vendor_name_present CHECK (btrim(name) <> ''),
    gstin         text CONSTRAINT vendor_gstin_shape
                  CHECK (gstin ~ '^[0-9]{2}[0-9A-Z]{10}[0-9A-Z]Z[0-9A-Z]$'),
    phone         text CONSTRAINT vendor_phone_e164 CHECK (phone ~ '^\+[1-9][0-9]{7,14}$'),
    state         text NOT NULL CONSTRAINT vendor_state_normalised
                  CHECK (state = btrim(state) AND state <> ''),
    is_active     boolean NOT NULL DEFAULT true,
    rating        numeric(2,1) CONSTRAINT vendor_rating_range CHECK (rating BETWEEN 0 AND 5),
    onboarded_at  timestamptz NOT NULL DEFAULT now(),
    status        text NOT NULL DEFAULT 'active'
                  CONSTRAINT vendor_status_known CHECK (status IN ('active','on_hold','closed')),
    notes         text CONSTRAINT vendor_notes_nonblank CHECK (notes IS NULL OR btrim(notes) <> '')
);
SET TIME ZONE 'Asia/Kolkata';
INSERT INTO vendor (name, gstin, phone, state, is_active, rating, onboarded_at, status, notes)
SELECT btrim(name), gstin, '+' || phone, initcap(lower(state)), upper(active) = 'Y',
       rating::numeric(2,1), onboarded AT TIME ZONE 'Asia/Kolkata',
       coalesce(status, 'active'), nullif(btrim(notes), '')
FROM vendor_sloppy WHERE btrim(name) <> '';
SELECT (SELECT count(*) FROM vendor_sloppy) AS old_rows, (SELECT count(*) FROM vendor) AS new_rows;
```

```text
 old_rows | new_rows
----------+----------
      500 |      490
(1 row)
```

The 10 blank-name vendors were not migrated: 490 rows. Dropping them is a decision too; in real life they go to a quarantine table for a human. Checking the cleaned data:

```sql
SELECT status, count(*) FROM vendor GROUP BY 1 ORDER BY 1;
SELECT count(*) FILTER (WHERE gstin IS NULL) AS null_gstin,
       count(*) FILTER (WHERE notes IS NULL) AS null_notes,
       count(DISTINCT state) AS states
FROM vendor;
```

```text
 status  | count
---------+-------
 active  |   243
 closed  |   123
 on_hold |   124
(3 rows)

 null_gstin | null_notes | states
------------+------------+--------
         40 |        163 |      5
(1 row)
```

`status` no longer has a NULL bucket (the 125 NULLs became `active`, which is why `active` grew from 125 to 243 after the blank-name rows were dropped), the blank notes are now NULL, and the seven state spellings are five states.

```sql
INSERT INTO vendor (name, state, onboarded_at)

INSERT INTO vendor (name, state, gstin, onboarded_at)

```


## Practice Session 23.2 — Reorder columns, measure on-disk size

**Goal.** Predict the alignment padding of a nine-column table from the catalog, then confirm the prediction in bytes and in relation size at one million rows, and find which reorderings change nothing.

**Setup.** A scratch database with `pageinspect`, and a one-million-row parcel table with columns in the order a person would write them. The extension needs a superuser, which the test container gives you.

```bash
createdb ch23_ws2
psql -d ch23_ws2
```

```sql
\pset null '(null)'
CREATE EXTENSION pageinspect;
CREATE TABLE parcel_a (
    is_priority boolean, parcel_id bigint, is_fragile boolean, dispatched_at timestamptz,
    items smallint, pincode int, is_insured boolean, weight_kg float8, declared_value numeric(12,2));
INSERT INTO parcel_a
SELECT g % 2 = 0, g, g % 9 = 0, timestamptz '2026-01-01' + g * interval '20 seconds',
       1 + g % 6, 100000 + g % 899999, g % 4 = 0, (g % 5000) / 100.0, 100 + (g % 20000)
FROM generate_series(1, 1000000) g;
```

**Task.**

1. Query `pg_attribute` for each column's `attlen` and `attalign`.
2. From those, work out by hand where each column of row 1 starts (the heap header is 24 bytes; a `numeric` in a short value uses a one-byte header and needs no alignment) and predict the row's stored length. Then read the real length with `heap_page_items`.
3. Build three rebuilt copies with `CREATE TABLE ... AS SELECT`: `parcel_b` with the fixed-width columns widest first and `numeric` in the middle, `parcel_e` with `numeric` last, and `parcel_f` which is `parcel_e` with its three 8-byte columns permuted. Compare relation sizes and rows on page 0.
4. Explain why `parcel_e` and `parcel_f` are the same size, and why `parcel_b` is larger than `parcel_e`.
5. Build two indexes over `(is_priority, parcel_id, is_fragile)` and `(parcel_id, is_priority, is_fragile)` and compare sizes.

**Solution.**

Step 1.

```sql
SELECT attnum, attname, format_type(atttypid, atttypmod) AS type, attlen, attalign
FROM pg_attribute WHERE attrelid = 'parcel_a'::regclass AND attnum > 0 ORDER BY attnum;
```

```text
 attnum |    attname     |           type           | attlen | attalign
--------+----------------+--------------------------+--------+----------
      1 | is_priority    | boolean                  |      1 | c
      2 | parcel_id      | bigint                   |      8 | d
      3 | is_fragile     | boolean                  |      1 | c
      4 | dispatched_at  | timestamp with time zone |      8 | d
      5 | items          | smallint                 |      2 | s
      6 | pincode        | integer                  |      4 | i
      7 | is_insured     | boolean                  |      1 | c
      8 | weight_kg      | double precision         |      8 | d
      9 | declared_value | numeric(12,2)            |     -1 | i
(9 rows)
```

Step 2. Offsets for `parcel_a`, row 1: header 24; `is_priority` at 24; `parcel_id` needs 8-alignment, so 7 bytes of padding and it occupies 32 to 40; `is_fragile` at 40; `dispatched_at` pads to 48 and occupies 48 to 56; `items` at 56 to 58; `pincode` needs 4-alignment so pads to 60 and occupies 60 to 64; `is_insured` at 64; `weight_kg` pads to 72 and occupies 72 to 80; `declared_value` (101, a five-byte short `numeric`) at 80 to 85. Predicted length: **85**, which the page rounds up to 88.

```sql
SELECT lp_len, t_hoff, ((lp_len + 7) / 8) * 8 AS on_page
FROM heap_page_items(get_raw_page('parcel_a', 0)) WHERE lp = 1;
```

```text
 lp_len | t_hoff | on_page
--------+--------+---------
     85 |     24 |      88
(1 row)
```

The prediction holds. Of the 61 bytes after the header, 23 are padding (7 + 7 + 2 + 7).

Step 3.

```sql
CREATE TABLE parcel_b AS
SELECT parcel_id, dispatched_at, weight_kg, pincode, declared_value, items,
       is_priority, is_fragile, is_insured FROM parcel_a;
CREATE TABLE parcel_e AS
SELECT parcel_id, dispatched_at, weight_kg, pincode, items,
       is_priority, is_fragile, is_insured, declared_value FROM parcel_a;
CREATE TABLE parcel_f AS
SELECT weight_kg, parcel_id, dispatched_at, pincode, items,
       is_priority, is_fragile, is_insured, declared_value FROM parcel_a;

SELECT relname, pg_relation_size(oid) AS bytes,
       round(pg_relation_size(oid)::numeric / 1000000, 1) AS bytes_per_row
FROM pg_class WHERE relname LIKE 'parcel\_%' AND relkind = 'r' ORDER BY 2 DESC, 1;
```

```text
 relname  |  bytes   | bytes_per_row
----------+----------+---------------
 parcel_a | 93093888 |          93.1
 parcel_b | 72458240 |          72.5
 parcel_e | 68272128 |          68.3
 parcel_f | 68272128 |          68.3
(4 rows)
```

```sql
SELECT 'a' AS tbl, count(*) AS rows_on_page0 FROM heap_page_items(get_raw_page('parcel_a', 0))
UNION ALL SELECT 'b', count(*) FROM heap_page_items(get_raw_page('parcel_b', 0))
UNION ALL SELECT 'e', count(*) FROM heap_page_items(get_raw_page('parcel_e', 0))
UNION ALL SELECT 'f', count(*) FROM heap_page_items(get_raw_page('parcel_f', 0));
```

```text
 tbl | rows_on_page0
-----+---------------
 a   |            88
 b   |           120
 e   |           120
 f   |           120
(4 rows)
```

`parcel_e` is 27% smaller than `parcel_a` (68.3 against 93.1 bytes per row, 120 against 88 rows per page).

Step 4. `parcel_e` and `parcel_f` differ only by permuting three columns of the same alignment class (`d`, 8 bytes), and nothing between them changes an offset, so the sizes are identical to the byte. `parcel_b` is 4.2 MB larger than `parcel_e` even though its first page holds the same 120 rows, because `declared_value` (a `numeric` whose length varies with the value) now sits before the 2-byte `smallint`. Depending on the value, the `smallint` needs 0 or 1 byte of padding, and on some rows that pushes the tuple over an 8-byte boundary. Row 1 shows the mechanism: `parcel_b` stores it in 63 bytes and `parcel_e` in 62, which both round to 64. The rule is widest fixed-width first and variable-length last, because a variable-length column's padding cannot be predicted per row.

Step 5.

```sql
CREATE INDEX ix_a ON parcel_a (is_priority, parcel_id, is_fragile);
CREATE INDEX ix_b ON parcel_a (parcel_id, is_priority, is_fragile);
SELECT 'ix_a' AS idx, pg_relation_size('ix_a') AS bytes
UNION ALL SELECT 'ix_b', pg_relation_size('ix_b');
```

```text
 idx  |  bytes
------+----------
 ix_a | 40583168
 ix_b | 31522816
(2 rows)
```

Same three columns, 29% larger with the boolean leading. Whether the index should lead with `is_priority` is a question about the queries (Chapter 33); where the queries do not care, lead with the wide column.

## Practice Session 23.3 — Watch TOAST engage

**Goal.** Watch a value cross from inline to compressed to out-of-line as it grows, see the toast table fill up, and measure how many buffers a query touches with and without the large column.

**Setup.** A scratch database, `pageinspect`, a generator for incompressible text, and a five-row ticket table.

```bash
createdb ch23_ws3
psql -d ch23_ws3
```

```sql
\pset null '(null)'
CREATE EXTENSION pageinspect;
CREATE FUNCTION noise(n int) RETURNS text LANGUAGE sql IMMUTABLE AS
  $$ SELECT substr(string_agg(md5(g::text), ''), 1, n) FROM generate_series(1, n/32 + 1) g $$;
CREATE TABLE ticket (
    id int PRIMARY KEY, customer_id int NOT NULL, status text NOT NULL,
    reopened int NOT NULL DEFAULT 0, description text NOT NULL);
INSERT INTO ticket (id, customer_id, status, description) VALUES
 (1, 11, 'open', noise(500)),
 (2, 12, 'open', noise(1500)),
 (3, 13, 'open', noise(2500)),
 (4, 14, 'open', noise(8000)),
 (5, 15, 'open', repeat('Order delayed. ', 6000));
```

**Task.**

1. For each ticket show the raw size of `description`, its stored size, the compression method (`pg_column_compression`) and the size of the whole row on its heap page (`lp_len`). Which rows are inline, which out of line, which compressed?
2. Count the values and chunks in the ticket's toast table.
3. Copy the table with `description` set to `STORAGE EXTERNAL` using `INSERT ... SELECT *`. Does the stored size of ticket 5 change? Then try again so that it does, and explain the difference.
4. Reload the table with 5,000 tickets whose description is 3,200 bytes of incompressible text. Compare the buffers touched by a query that ignores `description`, one that reads it (`length(description)`), and `EXPLAIN` of `SELECT *`. Pin parallelism off and warm the cache first.
5. Update the small `reopened` column on all rows, then `description` on 1,000. What happens to the toast table each time?

**Solution.**

Step 1.

```sql
SELECT t.id, octet_length(t.description) AS raw_bytes, pg_column_size(t.description) AS stored_bytes,
       pg_column_compression(t.description) AS compression, i.lp_len AS row_bytes
FROM ticket t
JOIN heap_page_items(get_raw_page('ticket', 0)) i ON i.t_ctid = t.ctid
ORDER BY t.id;
```

```text
 id | raw_bytes | stored_bytes | compression | row_bytes
----+-----------+--------------+-------------+-----------
  1 |       500 |          504 | (null)      |       548
  2 |      1500 |         1504 | (null)      |      1548
  3 |      2500 |         2500 | (null)      |        62
  4 |      8000 |         8000 | (null)      |        62
  5 |     90000 |         1057 | pglz        |      1101
(5 rows)
```

Rows 1 and 2 are inline and uncompressed. The 500-byte value adds a 4-byte header (504 stored) and the row is 548 bytes. Rows 3 and 4 are out of line: the row is 62 bytes on the page whatever the description size, and `stored_bytes` reports the raw length because nothing was compressed (the text is MD5 noise). Row 5 is 90,000 bytes of repeated text stored as 1,057 with `pglz`, so it stays inline at 1,101 bytes for the row. Compression is tried first, and a value that shrinks below the threshold never leaves the heap page.

Step 2.

```sql
SELECT c.reltoastrelid::regclass::text AS toast FROM pg_class c WHERE oid = 'ticket'::regclass \gset
SELECT count(DISTINCT chunk_id) AS toasted_values, count(*) AS chunks, sum(length(chunk_data)) AS bytes
FROM :toast;
```

```text
 toasted_values | chunks | bytes
----------------+--------+-------
              2 |      7 | 10500
(1 row)
```

Two values (rows 3 and 4), 10,500 bytes: 2,500 plus 8,000, so out-of-line uncompressed values are stored byte for byte.

Step 3.

```sql
CREATE TABLE ticket_ext (LIKE ticket INCLUDING ALL);
ALTER TABLE ticket_ext ALTER COLUMN description SET STORAGE EXTERNAL;
INSERT INTO ticket_ext SELECT * FROM ticket;
SELECT t.id, pg_column_size(t.description) AS default_stored,
       pg_column_size(e.description) AS copied_external
FROM ticket t JOIN ticket_ext e USING (id) ORDER BY 1;
```

```text
 id | default_stored | copied_external
----+----------------+-----------------
  1 |            504 |             504
  2 |           1504 |            1504
  3 |           2500 |            2500
  4 |           8000 |            8000
  5 |           1057 |            1057
(5 rows)
```

No change: ticket 5 is still 1,057 bytes. `INSERT ... SELECT *` copies the already-compressed datum as it is, and `SET STORAGE` applies to values the server has to form. Forcing a new value:

```sql
INSERT INTO ticket_ext (id, customer_id, status, description)
SELECT id + 100, customer_id, status, description || '' FROM ticket WHERE id = 5;
SELECT id, pg_column_size(description) AS stored FROM ticket_ext WHERE id IN (5, 105) ORDER BY 1;
```

```text
 id  | stored
-----+--------
   5 |   1057
 105 |  90000
(2 rows)
```

`description || ''` builds a new, uncompressed value, and under `EXTERNAL` it is stored at its raw 90,000 bytes. `EXTERNAL` is for large incompressible values you slice with `substr()`; for prose it costs storage.

Step 4.

```sql
TRUNCATE ticket;
INSERT INTO ticket (id, customer_id, status, description)
SELECT g, g % 300, 'open', substr((SELECT string_agg(md5(g::text || i), '') FROM generate_series(1, 100) i), 1, 3200)
FROM generate_series(1, 5000) g;
VACUUM ANALYZE ticket;
SELECT c.reltoastrelid::regclass::text AS toast FROM pg_class c WHERE oid = 'ticket'::regclass \gset
SELECT pg_relation_size('ticket') AS heap_bytes, pg_relation_size(:'toast') AS toast_bytes,
       (SELECT count(*) FROM :toast) AS toast_chunks;
```

```text
 heap_bytes | toast_bytes | toast_chunks
------------+-------------+--------------
     344064 |    20480000 |        10000
(1 row)
```

The heap is 0.34 MB and the descriptions are in a 20.5 MB toast table, two chunks each.

```sql
SET max_parallel_workers_per_gather = 0;
\o /dev/null
SELECT sum(customer_id), sum(length(description)) FROM ticket;
SELECT sum(customer_id), sum(length(description)) FROM ticket;
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF) SELECT sum(customer_id), max(status) FROM ticket;
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF) SELECT sum(customer_id), sum(length(description)) FROM ticket;
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF) SELECT * FROM ticket;
\o
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF) SELECT sum(customer_id), max(status) FROM ticket;
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF) SELECT sum(customer_id), sum(length(description)) FROM ticket;
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF) SELECT * FROM ticket;
```

```text
                     QUERY PLAN
-----------------------------------------------------

   Buffers: shared hit=42
   ->  Seq Scan on ticket (actual rows=5000 loops=1)
         Buffers: shared hit=42
(4 rows)

                     QUERY PLAN
-----------------------------------------------------
 Aggregate (actual rows=1 loops=1)
   Buffers: shared hit=15042
   ->  Seq Scan on ticket (actual rows=5000 loops=1)

                  QUERY PLAN
```

The narrow query touches the heap pages only. Reading `description` adds the toast reads, charged to the aggregate node, and the seq scan is the same in every plan. The third plan reports the same buffers as the first because `EXPLAIN` never sends the rows, and so never detoasts: a real `SELECT *` costs the second plan's buffers. To measure a wide select, consume the column.

Step 5.

```sql
SELECT pg_relation_size(:'toast') AS toast_before \gset
UPDATE ticket SET reopened = reopened + 1;
SELECT pg_relation_size(:'toast') = :toast_before AS toast_unchanged, pg_relation_size('ticket') AS heap_after;
UPDATE ticket SET description = description || '!' WHERE id <= 1000;
SELECT pg_relation_size(:'toast') > :toast_before AS toast_grew,
       pg_relation_size(:'toast') - :toast_before AS growth_bytes;
```

```text
UPDATE 5000
 toast_unchanged | heap_after
-----------------+------------
 t               |     688128
(1 row)

UPDATE 1000
 toast_grew | growth_bytes
------------+--------------
 t          |      4096000
(1 row)
```

The first update rewrote every heap row (the heap roughly doubled) but left the toast table alone: the new row versions point at the existing chunks. The second wrote new chunks for 1,000 values and grew the toast table by 4,096,000 bytes, and the old chunks stay until vacuum. The cost of a large column comes from changing it, not from updating its neighbours.
