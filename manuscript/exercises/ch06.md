# Chapter 6 Exercises — Querying Fundamentals

All three sessions run against the `retail` database loaded in Chapter 2. They are
read-only and require no DDL.

## Practice Session 6.1 — Build a query one clause at a time

**Goal.** Assemble a realistic reporting query from a bare `SELECT`, adding one clause at
a time, and be able to say what each addition changed.

**Setup.**

```bash
psql -d retail
```

No DDL. The `orders` table as loaded is all you need.

**Task.** Work through these in order, running each one before moving on.

1. Select every column of `orders`, first three rows by `id`.
2. Replace `*` with just `id`, `customer_id`, `placed_at`, `status`, `total_amount`.
3. Keep only orders with status `delivered`.
4. Narrow further to orders placed on or after 1 January 2026. Count them before you
   list them.
5. Order by `total_amount` descending, with `id` as a tiebreaker, and take the top ten.
6. Drop `status` from the output (the filter already pins it), rename `customer_id` to
   `customer` and `total_amount` to `net`, and add two computed columns: `gross` at 19%
   VAT rounded to two decimals, and `hours_to_ship` — the time between `placed_at` and
   `shipped_at` in hours, to one decimal place.
7. Sort by `gross` rather than `net`. Then ask yourself why that worked, and predict what
   happens if you write `WHERE gross > 4000` instead.

**Solution.**

Steps 1 and 2:

```sql
SELECT * FROM orders ORDER BY id LIMIT 3;
```

```text
 id | customer_id |       placed_at        |       shipped_at       |  status   | discount_code | total_amount 
----+-------------+------------------------+------------------------+-----------+---------------+--------------
  1 |         610 | 2026-06-04 15:50:29+00 | 2026-06-07 00:50:29+00 | returned  | (null)        |       622.51
  2 |         232 | 2026-06-11 21:50:39+00 | 2026-06-13 00:50:39+00 | delivered | WELCOME10     |      1973.12
  3 |         737 | 2024-03-28 14:32:52+00 | (null)                 | paid      | (null)        |      2673.55
(3 rows)
```

The `*` told you the shape of the table, which is what it is for. Order 3 has not shipped
and carries no discount code, and you can read that off the output because Chapter 2 had
you set `\pset null '(null)'`. Stock `psql` does not. Turn the setting off and run the
identical query:

```sql
\pset null ''
SELECT * FROM orders ORDER BY id LIMIT 3;
```

```text
 id | customer_id |       placed_at        |       shipped_at       |  status   | discount_code | total_amount 
----+-------------+------------------------+------------------------+-----------+---------------+--------------
  1 |         610 | 2026-06-04 15:50:29+00 | 2026-06-07 00:50:29+00 | returned  |               |       622.51
  2 |         232 | 2026-06-11 21:50:39+00 | 2026-06-13 00:50:39+00 | delivered | WELCOME10     |      1973.12
  3 |         737 | 2024-03-28 14:32:52+00 |                        | paid      |               |      2673.55
(3 rows)
```

Same three rows, and now a missing `shipped_at` is rendered exactly as a `discount_code`
that is genuinely the empty string would be — two different facts, one appearance. Put it
back with `\pset null '(null)'` and leave it there for the rest of the book. Chapter 7 is
the argument for why that one line earns its place in your `~/.psqlrc`.

Steps 3 and 4:

```sql
SELECT count(*)
FROM   orders
WHERE  status = 'delivered'
AND    placed_at >= DATE '2026-01-01';
```

```text
 count 
-------
   265
(1 row)
```

Counting before listing is a habit worth building. It costs one statement and tells you
whether the filter did what you meant — 265 out of 2,500 is plausible; 0 or 2,500 would
have meant the predicate was wrong, and you would have found out now rather than after
scrolling through output.

Steps 5, 6 and 7 together:

```sql
SELECT id,
       customer_id                   AS customer,
       total_amount                  AS net,
       round(total_amount * 1.19, 2) AS gross,
       round(extract(epoch FROM shipped_at - placed_at) / 3600.0, 1) AS hours_to_ship
FROM   orders
WHERE  status = 'delivered'
AND    placed_at >= DATE '2026-01-01'
ORDER  BY gross DESC, id
LIMIT  10;
```

```text
  id  | customer |   net   |  gross  | hours_to_ship 
------+----------+---------+---------+---------------
 1146 |       76 | 4228.50 | 5031.92 |          46.0
  847 |      566 | 4077.56 | 4852.30 |          14.0
  446 |       96 | 3819.60 | 4545.32 |          62.0
 2180 |      361 | 3736.04 | 4445.89 |           5.0
 2143 |      530 | 3583.87 | 4264.81 |           9.0
  248 |       59 | 3531.77 | 4202.81 |          54.0
  442 |      358 | 3504.17 | 4169.96 |          86.0
 2385 |      166 | 3498.02 | 4162.64 |          74.0
 1936 |      103 | 3486.62 | 4149.08 |          55.0
  130 |      460 | 3272.54 | 3894.32 |          14.0
(10 rows)
```

Four things in that query are worth saying out loud.

**`ORDER BY gross` works** because `ORDER BY` is evaluated after `SELECT`. `WHERE gross >
4000` would fail with `column "gross" does not exist`, because `WHERE` runs before the
select list is computed. Same identifier, same query, two different answers about whether
it exists — and the pipeline in section 6.2 is the only thing that predicts which.

**`status` disappeared from the output but the filter still holds.** `WHERE` operates on
input columns; it does not care what you project. A column you filter on and a column you
select are independent choices.

**The tiebreaker is doing real work.** Two orders with identical `gross` would otherwise
swap places between executions, and if this query became page one of a report, section
6.5's duplicate-and-skip behaviour would follow.

**`hours_to_ship` is timezone-independent by construction.** Subtracting two `timestamptz`
values gives an absolute interval; casting either to `date` first would have produced a
different answer depending on the session's `TimeZone`. Part IV is about that class of
bug. It is also `NULL` for unshipped orders — which cannot appear here, since only
`delivered` rows survive the filter, but it would matter if the filter changed.

## Practice Session 6.2 — The parts of `ORDER BY` that surprise people

**Goal.** Predict, before running each query, exactly which rows come back and in which
order — including the ones involving `NULL` and ties.

**Setup.**

```bash
psql -d retail
```

Two facts about the data: `customers.loyalty_tier` is `NULL` for 392 of 1,000 customers,
and `orders.shipped_at` is `NULL` for 767 of 2,500 orders.

**Task.** For each of the following, write down your prediction first.

1. Return the three orders with the most recent `shipped_at`. Then look at the result and
   decide whether it answered the question.
2. Fix it so that unshipped orders cannot appear at the top.
3. Return `id` and `loyalty_tier` for the five most recently signed-up customers, without
   putting `signup_date` in the output. Then add `DISTINCT loyalty_tier` to the same query
   and explain the error.
4. Select `id` and `upper(status) AS tag` from `orders`, and sort by the *length* of
   `tag`. Then make it work.
5. Take page one and page two of `customers ORDER BY loyalty_tier`, five rows each. Check
   whether the two pages are disjoint. Then fix it.

**Solution.**

**1 and 2 — null placement.**

```sql
SELECT id, shipped_at FROM orders ORDER BY shipped_at DESC, id LIMIT 3;
```

```text
 id | shipped_at 
----+------------
  3 | (null)
 10 | (null)
 15 | (null)
(3 rows)
```

Three orders that have never shipped, returned by a query asking for the most recently
shipped. `NULL` sorts high in PostgreSQL, and `DESC` therefore puts it first. The default
is not wrong — it is consistent with `NULL` being treated as greater than every value —
but it is almost never what the question meant.

```sql
SELECT id, shipped_at FROM orders ORDER BY shipped_at DESC NULLS LAST, id LIMIT 3;
```

```text
  id  |       shipped_at       
------+------------------------
 2362 | 2026-09-04 21:44:44+00
  828 | 2026-09-02 10:07:31+00
  479 | 2026-09-02 09:05:47+00
(3 rows)
```

`NULLS LAST` is one clause and it makes the intent auditable. The alternative — adding
`WHERE shipped_at IS NOT NULL` — is a *different query* with a different meaning: it
excludes the unshipped orders entirely rather than ranking them last. Which you want
depends on the question, and the fact that they are different is the point.

**3 — sorting by a hidden column, and what `DISTINCT` does to it.**

```sql
SELECT id, loyalty_tier
FROM   customers
ORDER  BY signup_date DESC, id
LIMIT  5;
```

```text
 id  | loyalty_tier 
-----+--------------
 793 | silver
 819 | bronze
 966 | bronze
 469 | (null)
 774 | silver
(5 rows)
```

`signup_date` is not in the select list and sorts the result anyway, because `ORDER BY`
can see the input columns from `FROM` as well as the output columns from `SELECT`. Add
`DISTINCT` and it stops:

```sql
SELECT DISTINCT loyalty_tier
FROM   customers
ORDER  BY signup_date DESC;
```

```text
ERROR:  for SELECT DISTINCT, ORDER BY expressions must appear in select list
LINE 3: ORDER  BY signup_date DESC;
                  ^
```

`DISTINCT` runs between `SELECT` and `ORDER BY`. After it, four rows remain, each standing
for hundreds of customers with hundreds of different signup dates — there is no
`signup_date` left to sort by, and PostgreSQL says so rather than picking one arbitrarily.
The error is the pipeline telling you the truth about itself.

**4 — bare alias versus expression.**

```sql
SELECT id, upper(status) AS tag FROM orders ORDER BY length(tag), id LIMIT 3;
```

```text
ERROR:  column "tag" does not exist
LINE 1: ... upper(status) AS tag FROM orders ORDER BY length(tag), id L...
                                                             ^
```

A bare `ORDER BY tag` would have worked. Wrapping it in `length()` makes the whole thing
an expression, and expressions in `ORDER BY` are resolved against the input columns, where
`tag` does not exist. Repeat the definition:

```sql
SELECT id, upper(status) AS tag
FROM   orders
ORDER  BY length(upper(status)), id
LIMIT  3;
```

```text
 id | tag  
----+------
  3 | PAID
 15 | PAID
 20 | PAID
(3 rows)
```

The rule is narrow and worth stating precisely: **`ORDER BY` accepts an output alias only
as the entire sort key.** Everything else is an input-column expression.

**5 — ties.**

```sql
SELECT id, loyalty_tier FROM customers ORDER BY loyalty_tier LIMIT 5;
SELECT id, loyalty_tier FROM customers ORDER BY loyalty_tier LIMIT 5 OFFSET 5;
```

```text
 id | loyalty_tier 
----+--------------
 32 | bronze
 17 | bronze
  2 | bronze
 20 | bronze
 36 | bronze
(5 rows)

 id | loyalty_tier 
----+--------------
 47 | bronze
  2 | bronze
 17 | bronze
 36 | bronze
 54 | bronze
(5 rows)
```

Customers 2, 17 and 36 are on both pages. `ORDER BY loyalty_tier` specifies an ordering
over four distinct values and says nothing about the 225 bronze customers relative to each
other, so the engine is free to return them in any order — and it uses a different one for
`LIMIT 5` than for `LIMIT 10`, because the bounded top-N heapsort's internal state depends
on the bound.

```sql
SELECT id, loyalty_tier FROM customers ORDER BY loyalty_tier, id LIMIT 5;
SELECT id, loyalty_tier FROM customers ORDER BY loyalty_tier, id LIMIT 5 OFFSET 5;
```

```text
 id | loyalty_tier 
----+--------------
  2 | bronze
 17 | bronze
 20 | bronze
 32 | bronze
 36 | bronze
(5 rows)

 id | loyalty_tier 
----+--------------
 38 | bronze
 45 | bronze
 47 | bronze
 48 | bronze
 54 | bronze
(5 rows)
```

Adding the primary key makes the ordering **total** — no two rows tie on the full key, so
there is exactly one correct answer and every plan must produce it. This is not a
performance tweak or a style preference. Without it the query has more than one correct
result and you are relying on luck to get the same one twice.

## Practice Session 6.3 — Why `DISTINCT` is usually a symptom

**Goal.** Reproduce a duplicate-row result caused by a join fan-out, watch `DISTINCT`
hide it, and see what the correct fixes cost instead.

**Setup.**

```bash
psql -d retail
```

`order_items` holds 6,250 rows against 2,500 orders — an average of 2.5 lines per order.
Joins are Chapter 9's subject; the one-line `JOIN` here is deliberately the simplest form,
because the point is what happens to the row count, not the join syntax.

**Task.**

1. Count the rows in `orders`. Then count the rows produced by joining `orders` to
   `order_items`. Explain the difference before reading on.
2. List `id`, `status` and `total_amount` from that join, ordered by `id`, first eight
   rows. Confirm the duplicates with your own eyes.
3. Sum `total_amount` over the join and compare it to the sum over `orders` alone. This is
   the version of the bug that reaches a finance dashboard.
4. "Fix" the duplicate rows with `DISTINCT`. Verify the row count is right again.
5. Now find the fix that does not need `DISTINCT`, and compare `EXPLAIN (ANALYZE)` for
   both.
6. Finally, handle the case where the filter genuinely lives on `order_items`: orders
   containing a line of exactly five units. Compare `DISTINCT` against a semi-join.

**Solution.**

**1 and 2 — the fan-out.**

```sql
SELECT count(*) AS orders FROM orders;
SELECT count(*) AS joined_rows FROM orders o JOIN order_items oi ON oi.order_id = o.id;
```

```text
 orders 
--------
   2500
(1 row)

 joined_rows 
-------------
        6250
(1 row)
```

The join did not filter, it *multiplied*. Each order row is paired with each of its line
items, so an order with three lines becomes three rows. 6,250 is not a coincidence — it is
exactly the row count of `order_items`, because every line item has exactly one parent
order.

```sql
SELECT o.id, o.status, o.total_amount
FROM   orders o
JOIN   order_items oi ON oi.order_id = o.id
ORDER  BY o.id
LIMIT  8;
```

```text
 id |  status   | total_amount 
----+-----------+--------------
  1 | returned  |       622.51
  1 | returned  |       622.51
  1 | returned  |       622.51
  2 | delivered |      1973.12
  2 | delivered |      1973.12
  2 | delivered |      1973.12
  3 | paid      |      2673.55
  3 | paid      |      2673.55
(8 rows)
```

Order 1 three times, order 2 three times. Nothing is duplicated in the data; the *query*
asks for one row per line item and then declines to display anything from the line item.

**3 — the damage.**

```sql
SELECT sum(o.total_amount) AS inflated
FROM   orders o JOIN order_items oi ON oi.order_id = o.id;

SELECT sum(total_amount) AS correct FROM orders;
```

```text
  inflated   
-------------
 11138789.39
(1 row)

  correct   
------------
 3678982.61
(1 row)
```

Revenue overstated threefold. No error, no warning, a number of exactly the right shape
and magnitude to look believable in a dashboard. This is the shape of the bug that gets
discovered in a board meeting. Chapter 9 dissects it as Practice Session 9.4.

**4 — the bandage.**

```sql
SELECT DISTINCT o.id, o.status, o.total_amount
FROM   orders o
JOIN   order_items oi ON oi.order_id = o.id;
```

2,500 rows. Correct output. And this is precisely what makes it dangerous: the reviewer
sees the right row count, the right values, and a one-word diff.

```sql
EXPLAIN (ANALYZE, TIMING OFF)
SELECT DISTINCT o.id, o.status, o.total_amount
FROM   orders o
JOIN   order_items oi ON oi.order_id = o.id;
```

```text
                                                QUERY PLAN                                                
----------------------------------------------------------------------------------------------------------
 HashAggregate  (cost=265.05..290.05 rows=2500 width=18) (actual rows=2500 loops=1)
   Group Key: o.id, o.status, o.total_amount
   Batches: 1  Memory Usage: 369kB
   ->  Hash Join  (cost=99.25..218.18 rows=6250 width=18) (actual rows=6250 loops=1)
         Hash Cond: (oi.order_id = o.id)
         ->  Seq Scan on order_items oi  (cost=0.00..102.50 rows=6250 width=4) (actual rows=6250 loops=1)
         ->  Hash  (cost=68.00..68.00 rows=2500 width=18) (actual rows=2500 loops=1)
               Buckets: 4096  Batches: 1  Memory Usage: 159kB
               ->  Seq Scan on orders o  (cost=0.00..68.00 rows=2500 width=18) (actual rows=2500 loops=1)
 Planning Time: 0.219 ms
 Execution Time: 1.343 ms
(11 rows)
```

Read it bottom-up and the waste is explicit. Scan both tables. Build a 159 kB hash. Join
to produce 6,250 rows. Build a *second* hash of 369 kB to reduce those 6,250 back to the
2,500 you started with. Every row of `order_items` was read to contribute nothing.

**5 — the actual fix.**

Look at the select list. It contains `o.id`, `o.status`, `o.total_amount` and nothing
else. No column from `order_items` appears anywhere — not in the output, not in a filter.
The join has no purpose.

```sql
EXPLAIN (ANALYZE, TIMING OFF)
SELECT o.id, o.status, o.total_amount
FROM   orders o;
```

```text
                                       QUERY PLAN                                       
----------------------------------------------------------------------------------------
 Seq Scan on orders o  (cost=0.00..68.00 rows=2500 width=18) (actual rows=2500 loops=1)
 Planning Time: 0.009 ms
 Execution Time: 0.089 ms
(3 rows)
```

Cost 290.05 down to 68.00; execution 1.343 ms down to 0.089 ms, a factor of fifteen. One
node instead of five, no hash tables, no temporary 6,250-row intermediate.

This is the usual ending. Someone joined a child table for a reason that no longer exists
— the query was edited, the column it needed was dropped from the output — the duplicates
appeared, and `DISTINCT` made the symptom go away. The join survived because nobody asked
what it was for.

**6 — when the child table does matter.**

Now the filter genuinely requires `order_items`: orders containing a line of exactly five
units. The naive version:

```sql
EXPLAIN (ANALYZE, TIMING OFF)
SELECT DISTINCT o.id, o.status, o.total_amount
FROM   orders o JOIN order_items oi ON oi.order_id = o.id
WHERE  oi.quantity = 5;
```

```text
                                                QUERY PLAN                                                
----------------------------------------------------------------------------------------------------------
 HashAggregate  (cost=229.96..242.39 rows=1243 width=18) (actual rows=1018 loops=1)
   Group Key: o.id, o.status, o.total_amount
   Batches: 1  Memory Usage: 193kB
   ->  Hash Join  (cost=99.25..220.64 rows=1243 width=18) (actual rows=1243 loops=1)
         Hash Cond: (oi.order_id = o.id)
         ->  Seq Scan on order_items oi  (cost=0.00..118.12 rows=1243 width=4) (actual rows=1243 loops=1)
               Filter: (quantity = 5)
               Rows Removed by Filter: 5007
         ->  Hash  (cost=68.00..68.00 rows=2500 width=18) (actual rows=2500 loops=1)
               Buckets: 4096  Batches: 1  Memory Usage: 159kB
               ->  Seq Scan on orders o  (cost=0.00..68.00 rows=2500 width=18) (actual rows=2500 loops=1)
 Planning Time: 0.045 ms
 Execution Time: 0.527 ms
(13 rows)
```

1,243 qualifying line items collapse to 1,018 orders — 202 orders contained more than one
five-unit line. `DISTINCT` is doing genuine work here, unlike in step 4, but it is doing
it *after* the duplicates have been manufactured.

What you actually want to say is "orders for which such a line **exists**", which is a
semi-join — it stops at the first match and never produces a duplicate to clean up:

```sql
EXPLAIN (ANALYZE, TIMING OFF)
SELECT o.id, o.status, o.total_amount
FROM   orders o
WHERE  EXISTS (SELECT 1 FROM order_items oi
               WHERE oi.order_id = o.id AND oi.quantity = 5);
```

```text
                                                QUERY PLAN                                                
----------------------------------------------------------------------------------------------------------
 Hash Semi Join  (cost=133.66..226.71 rows=1243 width=18) (actual rows=1018 loops=1)
   Hash Cond: (o.id = oi.order_id)
   ->  Seq Scan on orders o  (cost=0.00..68.00 rows=2500 width=18) (actual rows=2500 loops=1)
   ->  Hash  (cost=118.12..118.12 rows=1243 width=4) (actual rows=1243 loops=1)
         Buckets: 2048  Batches: 1  Memory Usage: 60kB
         ->  Seq Scan on order_items oi  (cost=0.00..118.12 rows=1243 width=4) (actual rows=1243 loops=1)
               Filter: (quantity = 5)
               Rows Removed by Filter: 5007
 Planning Time: 0.043 ms
 Execution Time: 0.301 ms
(10 rows)
```

Same 1,018 rows. `Hash Semi Join` instead of `Hash Join` feeding a `HashAggregate`: one
hash table of 60 kB instead of two totalling 253 kB, no deduplication node, and 0.301 ms
against 0.527 ms. The difference grows with the fan-out, and on the `lg` dataset with five
million line items it is not subtle.

`EXISTS` is Chapter 10's material and you are not expected to reach for it yet. What you
*are* expected to take away is the diagnostic:

> **When a query needs `DISTINCT`, find out where the duplicates came from before you
> remove them.** If the answer is "a join to a table nothing in the query uses", delete
> the join. If it is "a join used only to test for existence", it wants `EXISTS`. If
> neither — if the duplicates are real and deduplicating them is the requirement —
> `DISTINCT` is correct and you now know it is correct, which is a different position from
> having guessed.
