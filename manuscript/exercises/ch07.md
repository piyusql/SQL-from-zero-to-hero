# Chapter 7 Exercises — Filtering, Operators, and Three-Valued Logic

## Practice Session 7.1 — Reproduce, diagnose, and fix the `NOT IN` trap

**Goal.** Make a query return a confidently wrong answer, work out why from first
principles, fix it three ways, and read what the planner does with each.

**Setup.** Connect to the `retail` database loaded in Practice Session 2.3. No other
setup — the dataset already contains the bug, because `customers.referred_by` is a
nullable self-reference and most of it is NULL.

```bash
psql retail
```

```sql
\pset null '(null)'
```

**Task.**

1. Count the customers who have **never referred anybody**, using `NOT IN` with a
   subquery over `referred_by`. Note the answer.
2. Ask the same question with `NOT EXISTS`. Note that answer.
3. Before reading on: write one query, against `customers` alone, that proves which of the
   two is wrong and explains why. It should be a single row of output.
4. Show the UNKNOWN directly. Evaluate `NOT IN` against a customer ID that certainly does
   not exist, and display the result — not a count, the raw Boolean.
5. Write two more correct versions: one that keeps `NOT IN` but repairs the subquery, and
   one using a `LEFT JOIN ... IS NULL` anti-join. Confirm all three fixes agree.
6. Run `EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)` on the broken query and on
   all three fixes. Identify which plans contain a genuine join node and which do not.
7. Repeat the comparison against a one-to-many relationship — customers who have never
   *ordered* — this time with costs left **on**. Compare the estimated row count to the
   actual one for both idioms.
8. Decide which fix you would put in production, and be able to defend it on grounds other
   than performance.

**Solution.**

Steps 1 and 2 — the two answers:

```sql
SELECT count(*) FROM customers c WHERE c.id NOT IN (SELECT referred_by FROM customers);
```

```text
 count
-------
     0
(1 row)
```

```sql
SELECT count(*) FROM customers c
WHERE  NOT EXISTS (SELECT 1 FROM customers x WHERE x.referred_by = c.id);
```

```text
 count
-------
   783
(1 row)
```

Step 3 — the diagnosis. One query, and the only column that matters is the last:

```sql
SELECT count(*)                      AS subquery_rows,
       count(referred_by)            AS non_null,
       count(*) - count(referred_by) AS nulls,
       bool_or(referred_by IS NULL)  AS has_null
FROM   customers;
```

```text
 subquery_rows | non_null | nulls | has_null
---------------+----------+-------+----------
          1000 |      274 |   726 | t
(1 row)
```

726 NULLs in the subquery's output column. `x NOT IN (...)` expands to
`x <> v1 AND x <> v2 AND ...`; each NULL contributes an UNKNOWN term, `TRUE AND UNKNOWN`
is UNKNOWN, and `WHERE` keeps only TRUE. Every row is dropped. The zero was structural,
not factual — it would still be zero if the referral programme had never run.

Step 4 — see it with your own eyes:

```sql
SELECT 999999 NOT IN (SELECT referred_by FROM customers) AS definitely_not_referred;
```

```text
 definitely_not_referred
-------------------------
 (null)
(1 row)
```

Customer 999999 does not exist, has certainly never referred anyone, and the database
still will not say `true`. It cannot: 726 of the values it was asked to compare against
are unknown, and one of them might be 999999.

Step 5 — the other two fixes:

```sql
-- repair the subquery
SELECT count(*) FROM customers c
WHERE  c.id NOT IN (SELECT referred_by FROM customers WHERE referred_by IS NOT NULL);

-- anti-join
SELECT count(*) FROM customers c
LEFT   JOIN customers r ON r.referred_by = c.id
WHERE  r.id IS NULL;
```

```text
 count
-------
   783
(1 row)

 count
-------
   783
(1 row)
```

All three agree: 783.

Step 6 — the plans. The broken query:

```text
 Aggregate (actual rows=1 loops=1)
   ->  Seq Scan on customers c (actual rows=0 loops=1)
         Filter: (NOT (hashed SubPlan 1))
         Rows Removed by Filter: 1000
         SubPlan 1
           ->  Seq Scan on customers (actual rows=1000 loops=1)
```

`Rows Removed by Filter: 1000` out of 1,000. Every row thrown away.

`NOT EXISTS`:

```text
 Aggregate (actual rows=1 loops=1)
   ->  Hash Anti Join (actual rows=783 loops=1)
         Hash Cond: (c.id = x.referred_by)
         ->  Seq Scan on customers c (actual rows=1000 loops=1)
         ->  Hash (actual rows=274 loops=1)
               Buckets: 1024  Batches: 1  Memory Usage: 18kB
               ->  Seq Scan on customers x (actual rows=1000 loops=1)
```

**Hash Anti Join** — a first-class join node. It stops probing as soon as it finds one
match, and the planner can cost it, reorder it, and choose hash or merge or nested-loop
for it like any other join.

`NOT IN` with the NULLs filtered out:

```text
 Aggregate (actual rows=1 loops=1)
   ->  Seq Scan on customers c (actual rows=783 loops=1)
         Filter: (NOT (hashed SubPlan 1))
         Rows Removed by Filter: 217
         SubPlan 1
           ->  Seq Scan on customers (actual rows=274 loops=1)
                 Filter: (referred_by IS NOT NULL)
                 Rows Removed by Filter: 726
```

Right answer, but still a **SubPlan** rather than a join — a hash table consulted per row,
which the planner cannot reorder, cannot restrategise, and cannot push anything through.
It also depends on the hash fitting in `work_mem`; when it does not, the plan drops to a
re-scanned `SubPlan` and the cost becomes quadratic.

The `LEFT JOIN` anti-join:

```text
 Aggregate (actual rows=1 loops=1)
   ->  Hash Right Join (actual rows=783 loops=1)
         Hash Cond: (r.referred_by = c.id)
         Filter: (r.id IS NULL)
         Rows Removed by Filter: 274
         ->  Seq Scan on customers r (actual rows=1000 loops=1)
         ->  Hash (actual rows=1000 loops=1)
               Buckets: 1024  Batches: 1  Memory Usage: 44kB
               ->  Seq Scan on customers c (actual rows=1000 loops=1)
```

Note what this is *not*: it is not an Anti Join. PostgreSQL 15 performs the full outer
join, materialises all 1,057 result rows, and then throws 274 of them away with a
post-join `Filter`. The `IS NULL` test is applied after the join, not folded into it.

Exactly one of the four plans contains a real anti-join, and it is the `NOT EXISTS` one.

Step 7 — on this table the outer-join overhead is invisible. On a one-to-many relationship
it is not:

```sql
EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF)
SELECT c.id FROM customers c LEFT JOIN orders o ON o.customer_id = c.id WHERE o.id IS NULL;

EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF)
SELECT c.id FROM customers c WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
```

```text
 Hash Right Join  (cost=34.50..109.08 rows=1 width=4) (actual rows=197 loops=1)
   Hash Cond: (o.customer_id = c.id)
   Filter: (o.id IS NULL)
   Rows Removed by Filter: 2500
   ->  Seq Scan on orders o  (cost=0.00..68.00 rows=2500 width=8) (actual rows=2500 loops=1)
   ->  Hash  (cost=22.00..22.00 rows=1000 width=4) (actual rows=1000 loops=1)
         Buckets: 1024  Batches: 1  Memory Usage: 44kB
         ->  Seq Scan on customers c  (cost=0.00..22.00 rows=1000 width=4) (actual rows=1000 loops=1)

 Hash Anti Join  (cost=99.25..130.76 rows=197 width=4) (actual rows=197 loops=1)
   Hash Cond: (c.id = o.customer_id)
   ->  Seq Scan on customers c  (cost=0.00..22.00 rows=1000 width=4) (actual rows=1000 loops=1)
   ->  Hash  (cost=68.00..68.00 rows=2500 width=4) (actual rows=2500 loops=1)
         Buckets: 4096  Batches: 1  Memory Usage: 120kB
         ->  Seq Scan on orders o  (cost=0.00..68.00 rows=2500 width=4) (actual rows=2500 loops=1)
```

Two things, and the second matters more.

`Rows Removed by Filter: 2500` — the outer join constructed one row per order and threw
every matched one away to answer a question about 1,000 customers. The anti-join
constructed none of them. Scale `orders` to two million rows and that is the difference
between a report and an incident.

Then read the estimates. The `LEFT JOIN` form estimates `rows=1` where the actual is 197.
`NOT EXISTS` estimates `rows=197` where the actual is 197 — **exact, against 197× wrong.**

That is the strongest argument of the three. An estimate of 1 tells everything above this
node that it is joining a single row, and the planner will choose a nested loop on that
basis. Here it costs nothing; on a production query tree it is how you get a nested loop
over millions of rows. Estimated-versus-actual is the master diagnostic of Chapter 34, and
Chapter 35 is about why estimates go wrong.

Step 8 — **`NOT EXISTS`.** The performance case is real, but it is the third-best
argument.

The first is that `NOT EXISTS` is correct *without you having to remember anything*. The
repaired `NOT IN` is one careless edit away from being broken again, and the breakage is
silent. The anti-join is correct only because `r.id` happens to be a primary key; point it
at a nullable column and you have a fresh, equally invisible bug.

The second is that it reads as the sentence you were asked to write. "Customers for whom
no row exists where someone was referred by them" is the requirement, verbatim.

The third is the plan. And note the direction of the trade-off: the most readable form is
also the one that gives the planner the most information. That is not always how it works,
and when it is, take it.

## Practice Session 7.2 — Rewrite NULL-unsafe comparisons

**Goal.** Find three expressions that run cleanly and return wrong answers, work out what
each is actually computing, and rewrite them.

**Setup.** The `retail` database.

```bash
psql retail
```

```sql
\pset null '(null)'
```

**Task.** Below are three queries. Each one executes without error. Each one is wrong.

For each: predict the correct answer, run the query, explain the gap in terms of
three-valued logic, then rewrite it. Do not look at the solution until you have all three
rewrites.

**(a) Comparing two nullable columns.** Referred customers and their referrers both have a
`loyalty_tier`, which is nullable. How many referral pairs have *different* tiers?

```sql
SELECT count(*) AS pairs FROM customers c JOIN customers r ON c.referred_by = r.id;

SELECT count(*) AS differ
FROM   customers c JOIN customers r ON c.referred_by = r.id
WHERE  c.loyalty_tier <> r.loyalty_tier;

SELECT count(*) AS same
FROM   customers c JOIN customers r ON c.referred_by = r.id
WHERE  c.loyalty_tier = r.loyalty_tier;
```

**(b) A `CASE` that falls through.** Classify every order against a three-day shipping SLA.

```sql
SELECT CASE WHEN shipped_at > placed_at + interval '3 days' THEN 'late'
            ELSE 'on time'
       END AS sla,
       count(*)
FROM   orders
GROUP  BY 1
ORDER  BY 1;
```

**(c) Concatenation that swallows the string.** Build a label for every order.

```sql
SELECT count(*) FILTER (WHERE label IS NULL)     AS lost,
       count(*) FILTER (WHERE label IS NOT NULL) AS kept
FROM   (SELECT 'order ' || id || ' / ' || discount_code AS label FROM orders) s;
```

**Solution.**

**(a)** The counts:

```text
 pairs
-------
   274
(1 row)

 differ
--------
     69
(1 row)

 same
------
   31
(1 row)
```

274 pairs go in; 69 + 31 = 100 come out. **174 pairs vanished** — 63% of the data. Every
pair where either tier is NULL produced UNKNOWN for both `<>` and `=`, and `WHERE` dropped
it from both buckets.

The rewrite uses the NULL-safe comparisons:

```sql
SELECT count(*) AS differ
FROM   customers c JOIN customers r ON c.referred_by = r.id
WHERE  c.loyalty_tier IS DISTINCT FROM r.loyalty_tier;

SELECT count(*) AS same
FROM   customers c JOIN customers r ON c.referred_by = r.id
WHERE  c.loyalty_tier IS NOT DISTINCT FROM r.loyalty_tier;
```

```text
 differ
--------
    201
(1 row)

 same
------
   73
(1 row)
```

201 + 73 = 274. Every pair accounted for.

Note the *semantic* decision hidden in that rewrite, and make it consciously:
`IS DISTINCT FROM` counts "gold referrer, unknown referee" as different, and "both
unknown" as the same. That is one defensible reading. Another is that pairs with a missing
tier are unclassifiable and should be reported as a third bucket rather than folded into
either. If that is your business rule, write it out:

```sql
SELECT CASE WHEN c.loyalty_tier IS NULL OR r.loyalty_tier IS NULL THEN 'unknown'
            WHEN c.loyalty_tier = r.loyalty_tier                  THEN 'same'
            ELSE 'different'
       END AS comparison,
       count(*)
FROM   customers c JOIN customers r ON c.referred_by = r.id
GROUP  BY 1 ORDER BY 1;
```

```text
 comparison | count
------------+-------
 different  |    69
 same       |    31
 unknown    |   174
(3 rows)
```

There are the 174 the original query lost, named rather than discarded.

The point is not that `IS DISTINCT FROM` is always right. It is that `<>` silently picked
an answer for you, and it picked "discard the row", which is never anybody's business
rule.

**(b)** The query returns:

```text
   sla   | count
---------+-------
 late    |   394
 on time |  2106
(2 rows)
```

2,500 orders, all classified, nothing missing. It looks completely healthy — which is what
makes this the worst of the three.

767 of those orders have `shipped_at IS NULL`. They have never shipped.
`NULL > placed_at + interval '3 days'` is UNKNOWN, which is not TRUE, so the `WHEN` did
not fire and the `ELSE` caught them. **767 unshipped orders are being reported as meeting
the shipping SLA.** The one category that should alarm somebody is the one being counted
as a success.

A `CASE` evaluates its `WHEN` clauses in order and takes the first that is TRUE. UNKNOWN
is not TRUE, so it falls through — to the next `WHEN`, and finally to `ELSE`, or to NULL
if there is no `ELSE`. Either outcome is a silent misclassification.

Handle NULL explicitly, and put it first:

```sql
SELECT CASE WHEN shipped_at IS NULL                         THEN 'not shipped'
            WHEN shipped_at > placed_at + interval '3 days' THEN 'late'
            ELSE 'on time'
       END AS sla,
       count(*)
FROM   orders
GROUP  BY 1
ORDER  BY 1;
```

```text
     sla     | count
-------------+-------
 late        |   394
 not shipped |   767
 on time     |  1339
(3 rows)
```

The "on time" figure falls from 2,106 to 1,339 — a 36% correction to a headline metric,
from adding one `WHEN`.

The habit worth forming: **in any `CASE` over a nullable column, make `IS NULL` the first
branch.** If the null case genuinely belongs with one of the others, say so in the branch
rather than letting `ELSE` decide by accident.

**(c)** The counts:

```text
 lost | kept
------+------
 2053 |  447
(1 row)
```

2,053 labels are NULL — not "order 42 / " with a missing suffix, but nothing at all. `||`
propagates NULL, so one missing fragment annihilates the entire expression including the
order number, which was never in doubt.

Two rewrites, and they are not equivalent:

```sql
SELECT 'order ' || id || ' / ' || coalesce(discount_code,'none') AS coalesce_label,
       concat_ws(' / ', 'order ' || id, discount_code)           AS concat_ws_label
FROM   orders WHERE id IN (1, 2) ORDER BY id;
```

```text
   coalesce_label    |   concat_ws_label
---------------------+---------------------
 order 1 / none      | order 1
 order 2 / WELCOME10 | order 2 / WELCOME10
(2 rows)
```

Order 1 has no discount code. `coalesce` is right when the reader needs to see that there
was a slot and it was empty. `concat_ws` is right when the label should omit the absent
part entirely — it drops the element *and* the separator that would have preceded it, so
there is no dangling `/`, which is why it beats manual `||` for addresses, names with
optional middle parts, and anything else assembled from optional pieces.

For reference, the three concatenation behaviours side by side:

```sql
SELECT 'total: ' || NULL              AS concat_op,
       concat('total: ', NULL)        AS concat_fn,
       concat_ws('-', 'a', NULL, 'c') AS concat_ws;
```

```text
 concat_op | concat_fn | concat_ws
-----------+-----------+-----------
 (null)    | total:    | a-c
(1 row)
```

`||` propagates. `concat` treats NULL as empty. `concat_ws` treats NULL as absent. Three
different answers from three functions that look interchangeable, and choosing between
them is a decision about what the output means, not a style preference.
