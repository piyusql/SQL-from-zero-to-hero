# Chapter 14 Exercises — Temporal Types

## Practice Session 14.1 — Reproduce a `timestamp` data-loss bug

**Goal.** Make a `timestamp without time zone` column silently record three shipments as
eleven hours apart when they actually spanned one hour, then migrate the column to
`timestamptz` in a way that does not depend on who runs the migration.

**Setup.** A scratch database, because this session writes. Nothing here touches the sample
datasets.

```bash
createdb ch14_lab
psql -d ch14_lab
```

Inside `psql`, make NULLs visible — some output below contains them:

```sql
\pset null '(null)'
```

Two tables, identical except for one word:

```sql
CREATE TABLE shipments_naive (id int, hub text, shipped_at timestamp);
CREATE TABLE shipments_tz    (id int, hub text, shipped_at timestamptz);
```

Three shipments from three hubs. Read these literals as what an HTTP API actually sends —
an ISO-8601 string carrying the sender's UTC offset. Mumbai's 09:30+05:30 and Singapore's
12:00+08 are **the same instant**, 04:00 UTC. New York's 01:00-04 is 05:00 UTC, one hour
*later* than both.

```sql
SET TIME ZONE 'Asia/Kolkata';

INSERT INTO shipments_naive VALUES
  (1, 'Mumbai',    '2026-04-14 09:30:00+05:30'),
  (2, 'Singapore', '2026-04-14 12:00:00+08'),
  (3, 'New York',  '2026-04-14 01:00:00-04');

INSERT INTO shipments_tz VALUES
  (1, 'Mumbai',    '2026-04-14 09:30:00+05:30'),
  (2, 'Singapore', '2026-04-14 12:00:00+08'),
  (3, 'New York',  '2026-04-14 01:00:00-04');
```

Both inserts succeed. Neither raises a warning.

**Task.**

1. Order each table by `shipped_at` and write down the sequence. Which hub shipped last,
   according to each table? Which one is actually right?
2. Compute the spread — `max(shipped_at) - min(shipped_at)` — for each table.
3. Count the distinct values of `shipped_at` in each table. Explain the difference in one
   sentence.
4. Migrate a `timestamp` column to `timestamptz` with a bare `ALTER TABLE ... TYPE`, twice,
   from sessions in two different zones. Show the two migrations produce different data.
   Then write the migration that does not have this property.

**Solution.**

**1 — the ordering.**

```sql
SELECT id, hub, shipped_at FROM shipments_naive ORDER BY shipped_at;
```

```text
 id |    hub    |     shipped_at      
----+-----------+---------------------
  3 | New York  | 2026-04-14 01:00:00
  1 | Mumbai    | 2026-04-14 09:30:00
  2 | Singapore | 2026-04-14 12:00:00
(3 rows)
```

```sql
SELECT id, hub, shipped_at FROM shipments_tz ORDER BY shipped_at;
```

```text
 id |    hub    |        shipped_at         
----+-----------+---------------------------
  1 | Mumbai    | 2026-04-14 09:30:00+05:30
  2 | Singapore | 2026-04-14 09:30:00+05:30
  3 | New York  | 2026-04-14 10:30:00+05:30
(3 rows)
```

The naive table puts New York **first**. It shipped last. Mumbai and Singapore are shown as
two and a half hours apart; they were simultaneous.

Asked directly:

```sql
SELECT (SELECT hub FROM shipments_naive ORDER BY shipped_at DESC LIMIT 1) AS naive_says,
       (SELECT hub FROM shipments_tz    ORDER BY shipped_at DESC LIMIT 1) AS tz_says;
```

```text
 naive_says | tz_says  
------------+----------
 Singapore  | New York
(1 row)
```

The `timestamp` column threw away each sender's offset and kept the digits. Every row is a
wall-clock reading from a different clock, and sorting them is sorting apples against the
idea of apples. The `timestamptz` column converted each literal to an instant on write, so
the two simultaneous shipments are equal and the later one sorts later — and it renders
them in `Asia/Kolkata` because that is the session zone, not because anything about
Mumbai is stored in the rows.

**2 — the spread.**

```sql
SELECT max(shipped_at) - min(shipped_at) AS naive_spread FROM shipments_naive;
```

```text
 naive_spread 
--------------
 11:00:00
(1 row)
```

```sql
SELECT max(shipped_at) - min(shipped_at) AS tz_spread FROM shipments_tz;
```

```text
 tz_spread 
-----------
 01:00:00
(1 row)
```

Eleven hours against one. If this fed an operations SLA dashboard, the naive column would
report a fulfilment window eleven times too wide and nobody would question it, because
eleven hours is a plausible number for a shipping window. That is the danger: the wrong
answer is not absurd.

**3 — distinct values.**

```sql
SELECT count(DISTINCT shipped_at) AS naive_distinct FROM shipments_naive;
```

```text
 naive_distinct 
----------------
              3
(1 row)
```

```sql
SELECT count(DISTINCT shipped_at) AS tz_distinct FROM shipments_tz;
```

```text
 tz_distinct 
-------------
           2
(1 row)
```

Three rows, three distinct wall-clock readings, but only two distinct instants: Mumbai and
Singapore happened at the same moment. `timestamp` cannot see that and `timestamptz` can.
Deduplication, idempotency keys and "did we already process this event" checks built on a
`timestamp` column are all wrong in the same way.

**4 — the migration.**

Start from a single known value.

```sql
CREATE TABLE mig_demo (id int, recorded_at timestamp);
INSERT INTO mig_demo VALUES (1, '2026-04-14 09:30:00');
```

Migrate it from a session in UTC:

```sql
SET TIME ZONE 'UTC';
ALTER TABLE mig_demo ALTER COLUMN recorded_at TYPE timestamptz;
SELECT id, recorded_at FROM mig_demo;
```

```text
 id |      recorded_at       
----+------------------------
  1 | 2026-04-14 09:30:00+00
(1 row)
```

Put it back and do the identical migration from a session in Mumbai:

```sql
ALTER TABLE mig_demo ALTER COLUMN recorded_at TYPE timestamp;
SET TIME ZONE 'Asia/Kolkata';
ALTER TABLE mig_demo ALTER COLUMN recorded_at TYPE timestamptz;
SELECT id, recorded_at FROM mig_demo;
```

```text
 id |        recorded_at        
----+---------------------------
  1 | 2026-04-14 09:30:00+05:30
(1 row)
```

Same DDL, same starting data, **two different instants** — 09:30 UTC in one case, 04:00 UTC
in the other. A bare `ALTER ... TYPE timestamptz` interprets every existing value in
whatever the migrating session's `TimeZone` happens to be. Run it by hand on a laptop set to
`Asia/Kolkata` and it produces one dataset; run it from CI on a container set to `UTC` and
it produces another. The migration file is identical in your repository either way, which is
why this defect survives code review.

The fix is to state the assumption in the SQL:

```sql
ALTER TABLE mig_demo ALTER COLUMN recorded_at TYPE timestamp;
SET TIME ZONE 'America/New_York';
ALTER TABLE mig_demo
  ALTER COLUMN recorded_at TYPE timestamptz
  USING recorded_at AT TIME ZONE 'Asia/Kolkata';
SET TIME ZONE 'UTC';
SELECT id, recorded_at FROM mig_demo;
```

```text
 id |      recorded_at       
----+------------------------
  1 | 2026-04-14 04:00:00+00
(1 row)
```

Run from a New York session and the answer is still 04:00 UTC — 09:30 Mumbai time, the zone
named in the `USING` clause. The migration now carries its own assumption instead of
inheriting one.

> **Trap —** `USING recorded_at AT TIME ZONE 'Asia/Kolkata'` is only correct if every
> existing value really was written in Mumbai local time. If half your rows came from a
> service in Singapore, no single zone in the `USING` clause is right and the data is
> genuinely unrecoverable — you would need a per-row zone you did not store. That is the
> real cost of the original mistake, and it is why the fix belongs in the schema, before
> the first row lands.

This `ALTER` rewrites the whole table and takes `ACCESS EXCLUSIVE` for the duration. On a
large table that is an outage; Chapter 52, *Schema Migrations on Live Systems*, covers the
expand/contract pattern that avoids it.

Keep `ch14_lab`. Session 14.2 works against the sample datasets, but 14.3 comes back here.

## Practice Session 14.2 — Bucket events by local day across zones

**Goal.** Produce a daily event rollup whose answer does not change when a different
connection runs it, and quantify how far a UTC-bucketed report drifts from what customers in
five countries would call "today".

**Setup.** The small `telemetry` and `retail` datasets from Practice Session 2.3. Both are
read-only here.

```bash
psql -d telemetry
```

```sql
\pset null '(null)'
SELECT count(*) FROM device_events;   -- expect 9800
SHOW timezone;                        -- whatever your server was built with
```

`device_events.recorded_at` is `timestamptz` and spans June to early September 2026. The
three-day window used below holds 575 events. The last line matters: this session is about
the fact that your answer depends on that setting, so write it down before you start.

**Task.**

1. Count events per day for 1–3 June 2026 with the session in `UTC`. Then run the identical
   query with the session in `Asia/Kolkata`. Explain why the bucket count changes.
2. Rewrite the query so both sessions return the Mumbai-day answer. Prove it by running it
   from a UTC session.
3. Try the same thing with the three-argument `date_trunc(field, source, zone)` and a
   `::date` cast. Explain the result.
4. Produce a six-hour rollup over 1–2 June, Mumbai time.
5. Switch to `retail`. For customers in `IN`, `SG`, `AE`, `US` and `AU`, count how many
   orders fall on a different calendar day when bucketed in the customer's own zone rather
   than UTC.
6. Still in `retail`, list the days in 1–10 August 2026 where the UTC daily order count and
   the Mumbai daily order count disagree.

**Solution.**

**1 — the same query, two answers.**

```sql
SET TIME ZONE 'UTC';
SELECT date_trunc('day', recorded_at)::date AS day, count(*) AS events
FROM   device_events
WHERE  recorded_at >= TIMESTAMPTZ '2026-06-01 00:00:00+00'
  AND  recorded_at <  TIMESTAMPTZ '2026-06-04 00:00:00+00'
GROUP  BY day ORDER BY day;
```

```text
    day     | events 
------------+--------
 2026-06-01 |    191
 2026-06-02 |    192
 2026-06-03 |    192
(3 rows)
```

```sql
SET TIME ZONE 'Asia/Kolkata';
SELECT date_trunc('day', recorded_at)::date AS day, count(*) AS events
FROM   device_events
WHERE  recorded_at >= TIMESTAMPTZ '2026-06-01 00:00:00+00'
  AND  recorded_at <  TIMESTAMPTZ '2026-06-04 00:00:00+00'
GROUP  BY day ORDER BY day;
```

```text
    day     | events 
------------+--------
 2026-06-01 |    147
 2026-06-02 |    192
 2026-06-03 |    192
 2026-06-04 |     44
(4 rows)
```

The `WHERE` clause selected the same 575 rows both times — its bounds are `timestamptz`
literals with explicit offsets, so they name instants and instants do not move. What moved
is the *bucketing*. `date_trunc('day', ...)` has to decide when a day begins, that is a
local question, and it answers it with the session's `TimeZone`. Mumbai's 1 June began at
18:30 UTC on 31 May, so the window's first 44 events — the ones between 18:30 and midnight
UTC on 3 June — land in a fourth bucket, and 44 events shift out of the first.

Nothing is broken. Both results are correct answers to different questions, and the query
text cannot tell you which one you asked.

**2 — pin the zone.**

```sql
SET TIME ZONE 'UTC';
SELECT (recorded_at AT TIME ZONE 'Asia/Kolkata')::date AS ist_day, count(*) AS events
FROM   device_events
WHERE  recorded_at >= TIMESTAMPTZ '2026-06-01 00:00:00+00'
  AND  recorded_at <  TIMESTAMPTZ '2026-06-04 00:00:00+00'
GROUP  BY ist_day ORDER BY ist_day;
```

```text
  ist_day   | events 
------------+--------
 2026-06-01 |    147
 2026-06-02 |    192
 2026-06-03 |    192
 2026-06-04 |     44
(4 rows)
```

The Mumbai answer, from a UTC session. `recorded_at AT TIME ZONE 'Asia/Kolkata'` converts
each instant to a zone-less `timestamp` holding the Mumbai wall clock, and the `::date` cast
on a `timestamp` just takes its date part — no zone involved, nothing left for the session
to influence.

Setting `TimeZone` on the reporting role achieves the same thing and is worth doing as
defence in depth, but it is not a substitute: a report whose correctness depends on a
`GRANT`-time setting will eventually be run by someone else's connection.

**3 — the three-argument form, and why the cast ruins it.**

```sql
SELECT date_trunc('day', recorded_at, 'Asia/Kolkata')::date AS ist_day, count(*) AS events
FROM   device_events
WHERE  recorded_at >= TIMESTAMPTZ '2026-06-01 00:00:00+00'
  AND  recorded_at <  TIMESTAMPTZ '2026-06-04 00:00:00+00'
GROUP  BY ist_day ORDER BY ist_day;
```

```text
  ist_day   | events 
------------+--------
 2026-05-31 |    147
 2026-06-01 |    192
 2026-06-02 |    192
 2026-06-03 |     44
(4 rows)
```

The group *sizes* are right — 147, 192, 192, 44, exactly as in step 2 — and every *label* is
a day early. `date_trunc(field, source, zone)` truncates in the zone you name but returns a
`timestamptz`: the instant at which that Mumbai day began. Midnight in Mumbai is 18:30 the
previous afternoon in UTC, and `::date` on a `timestamptz` resolves in the session zone, so
it reports 31 May.

Two ways out. Keep the `timestamptz` and let the presentation layer render it, or convert
before casting. The second is what step 2 does, which is why `(x AT TIME ZONE 'zone')::date`
is the form worth memorising: it has no second step that can undo the first.

**4 — six-hour buckets.**

```sql
SET TIME ZONE 'Asia/Kolkata';
SELECT date_bin(INTERVAL '6 hours', recorded_at,
                TIMESTAMPTZ '2026-06-01 00:00:00+05:30') AS bucket_start,
       count(*) AS events
FROM   device_events
WHERE  recorded_at >= TIMESTAMPTZ '2026-06-01 00:00:00+05:30'
  AND  recorded_at <  TIMESTAMPTZ '2026-06-03 00:00:00+05:30'
GROUP  BY bucket_start ORDER BY bucket_start;
```

```text
       bucket_start        | events 
---------------------------+--------
 2026-06-01 00:00:00+05:30 |      3
 2026-06-01 06:00:00+05:30 |     48
 2026-06-01 12:00:00+05:30 |     48
 2026-06-01 18:00:00+05:30 |     48
 2026-06-02 00:00:00+05:30 |     48
 2026-06-02 06:00:00+05:30 |     48
 2026-06-02 12:00:00+05:30 |     48
 2026-06-02 18:00:00+05:30 |     48
(8 rows)
```

`date_bin` slices the timeline into fixed widths measured from the origin you supply, which
is how you get bucket sizes `date_trunc` has no name for. The first bucket holds 3 events
rather than 48 because the dataset itself starts at 00:12 UTC on 1 June — 05:42 in Mumbai —
so most of that six-hour window predates the data. A ragged first or last bucket is almost
always the window, not the traffic.

The origin is load-bearing. Pass `'2026-06-01 00:00:00+00'` instead and every boundary moves
by five and a half hours, which is correct for a UTC report and wrong for a Mumbai one.

> **Trap —** `date_bin` measures elapsed time from the origin and knows nothing about
> daylight saving. In `Asia/Kolkata` that is invisible, because there is none. In a zone
> that shifts, a "6 hours" bucket boundary drifts an hour away from the wall clock after a
> transition and stays there. Right for rate calculations; wrong for anything a human reads
> as a shift or a business hour.

**5 — every customer in their own day.**

```bash
psql -d retail
```

```sql
\pset null '(null)'
SET TIME ZONE 'UTC';

WITH zone_of (country, tz) AS (
  VALUES ('IN','Asia/Kolkata'),     ('SG','Asia/Singapore'),
         ('AE','Asia/Dubai'),       ('US','America/New_York'),
         ('AU','Australia/Sydney')
)
SELECT z.country,
       count(*)                                        AS orders,
       count(*) FILTER (
         WHERE (o.placed_at AT TIME ZONE z.tz)::date
            <> (o.placed_at AT TIME ZONE 'UTC')::date) AS moved_day
FROM   orders o
JOIN   customers c ON c.id = o.customer_id
JOIN   zone_of  z ON z.country = c.country
GROUP  BY z.country
ORDER  BY moved_day DESC;
```

```text
 country | orders | moved_day 
---------+--------+-----------
 IN      |   1568 |       358
 AU      |    103 |        50
 AE      |    248 |        41
 US      |    227 |        35
 SG      |    108 |        35
(5 rows)
```

The zone is an ordinary expression, so a `VALUES` list joined in by country supplies one per
row. 358 of 1,568 Indian orders — 23% — and 50 of 103 Australian ones fall on a different
calendar day depending on which definition you use. Australia is worst because
`Australia/Sydney` sits ten or eleven hours from UTC, so its local day overlaps two UTC days
for most of its length.

`retail` deliberately decouples `country` from `city`: `country` is the billing or
registration country and every `city` is Indian. Treat the country as the zone the customer
reads their invoice in, which is what a billing-period boundary actually turns on.

In production the zone belongs in a column on `customers`, not in a `VALUES` list — country
is a poor proxy for zone the moment you have a customer in a country with more than one, and
`US` and `AU` both have several. `America/New_York` here is a simplification, and a real
system stores the zone the customer chose.

**6 — which days disagree.**

```sql
WITH utc_days AS (
  SELECT (placed_at AT TIME ZONE 'UTC')::date AS day, count(*) AS n
  FROM orders GROUP BY 1),
ist_days AS (
  SELECT (placed_at AT TIME ZONE 'Asia/Kolkata')::date AS day, count(*) AS n
  FROM orders GROUP BY 1)
SELECT coalesce(u.day, i.day) AS day, u.n AS utc_orders, i.n AS ist_orders
FROM   utc_days u FULL JOIN ist_days i ON i.day = u.day
WHERE  coalesce(u.day, i.day) BETWEEN DATE '2026-08-01' AND DATE '2026-08-10'
  AND  u.n IS DISTINCT FROM i.n
ORDER  BY day;
```

```text
    day     | utc_orders | ist_orders 
------------+------------+------------
 2026-08-01 |          1 |     (null)
 2026-08-02 |          1 |          2
 2026-08-04 |          7 |          5
 2026-08-05 |          6 |          5
 2026-08-06 |          2 |          5
 2026-08-07 |          2 |          1
 2026-08-08 |          2 |          3
 2026-08-10 |          5 |          2
(8 rows)
```

Eight of the ten days in the window appear, which means eight of ten disagree; only 3 and
9 August bucketed identically. On 1 August the Mumbai bucketing has **no row at all**,
which is why this needs a `FULL JOIN` rather than an inner one: an inner join hides
exactly the days you are hunting for, because a day present in one bucketing and absent in
the other has no match to join to. Reading `(null)` as zero is correct here, and
`IS DISTINCT FROM` rather than `<>` is what lets the comparison survive it — `1 <> NULL` is
NULL, not true, and the row would have been filtered out. That is Chapter 7's rule doing
real work.

Take the honest summary: across this ten-day window, two perfectly defensible daily
bucketings of the same table agree on two days out of ten. Write the zone into the query
and onto the report.

## Practice Session 14.3 — Handle a DST boundary

**Goal.** Build a daily schedule that survives a daylight-saving transition, find the two
local times the transition makes impossible or ambiguous, and add a constraint that refuses
the impossible one.

**Setup.** `ch14_lab` from Practice Session 14.1, or any scratch database.

```bash
psql -d ch14_lab
```

```sql
\pset null '(null)'
```

Nothing below depends on your server's `TimeZone`, because every step sets the session zone
explicitly. That is deliberate — it is the habit this whole chapter is arguing for.

Two dates to keep in front of you. In `America/New_York`, 2026 clocks go **forward** at
02:00 on Sunday 8 March (02:00 to 03:00, that hour does not exist) and **back** at 02:00 on
Sunday 1 November (02:00 to 01:00, that hour happens twice). `Asia/Kolkata` is UTC+05:30 all
year and does neither, which is why this session has to leave India to show you anything.

**Task.**

1. Generate a five-day run of 09:00 clinic appointments for a New York clinic starting
   6 March 2026, first with `INTERVAL '1 day'` and then with `INTERVAL '24 hours'`. Which
   one keeps the appointment at 09:00?
2. Run the same pair for a Bengaluru clinic. Explain why the two agree.
3. A support ticket is raised at 14:00 on 7 March 2026 in New York. Compute the deadline
   under "same clock time tomorrow" and under "24 hours to respond", and the elapsed hours
   to each. Which is the SLA you actually promised?
4. List the hourly slots on 8 March and on 1 November between midnight and the early
   morning. Count the slots in each full day.
5. Build an `appointments` table storing a local `timestamp` plus an IANA zone name.
   Insert 02:30 on 8 March for both clinics and 01:30 on 1 November for New York. Resolve
   each to an instant, then convert back and find which rows do not round-trip.
6. Add a `CHECK` constraint that refuses a local time which does not exist in its zone, and
   prove it fires.

**Solution.**

**1 — the schedule.**

```sql
SET TIME ZONE 'America/New_York';
SELECT TIMESTAMPTZ '2026-03-06 09:00:00' + (n * INTERVAL '1 day') AS slot
FROM generate_series(0, 4) AS g(n);
```

```text
          slot          
------------------------
 2026-03-06 09:00:00-05
 2026-03-07 09:00:00-05
 2026-03-08 09:00:00-04
 2026-03-09 09:00:00-04
 2026-03-10 09:00:00-04
(5 rows)
```

```sql
SELECT TIMESTAMPTZ '2026-03-06 09:00:00' + (n * INTERVAL '24 hours') AS slot
FROM generate_series(0, 4) AS g(n);
```

```text
          slot          
------------------------
 2026-03-06 09:00:00-05
 2026-03-07 09:00:00-05
 2026-03-08 10:00:00-04
 2026-03-09 10:00:00-04
 2026-03-10 10:00:00-04
(5 rows)
```

`1 day` keeps 09:00. `24 hours` becomes 10:00 from the transition onward and stays wrong
for the rest of the run. An `interval` holds months, days and microseconds as separate
fields, and adding it to a `timestamptz` treats them differently on purpose: the `days`
field means *the same wall-clock time on the next calendar day*, the microseconds field
means *this many elapsed seconds*. On 8 March those differ by an hour.

Note that the two intervals compare as equal — `INTERVAL '1 day' = INTERVAL '24 hours'` is
true, because comparison normalises at 24 hours to the day. Equality and arithmetic
disagree, so you cannot test your way to this and will not be warned.

A clinic schedule wants `1 day`. A machine's "run every 24 hours" watchdog wants
`24 hours`. Write down which one the requirement is before you write the SQL.

**2 — the Bengaluru control.**

```sql
SET TIME ZONE 'Asia/Kolkata';
SELECT TIMESTAMPTZ '2026-03-06 09:00:00' + (n * INTERVAL '1 day')    AS by_day,
       TIMESTAMPTZ '2026-03-06 09:00:00' + (n * INTERVAL '24 hours') AS by_hours
FROM generate_series(0, 3) AS g(n);
```

```text
          by_day           |         by_hours          
---------------------------+---------------------------
 2026-03-06 09:00:00+05:30 | 2026-03-06 09:00:00+05:30
 2026-03-07 09:00:00+05:30 | 2026-03-07 09:00:00+05:30
 2026-03-08 09:00:00+05:30 | 2026-03-08 09:00:00+05:30
 2026-03-09 09:00:00+05:30 | 2026-03-09 09:00:00+05:30
(4 rows)
```

Identical. In a zone with a constant offset every day is exactly 24 hours long, so the two
interval fields coincide and the bug is unobservable. This is why a team working only in
`Asia/Kolkata` can ship `+ INTERVAL '24 hours'` for years, pass every test, and then break
the week the business opens in Sydney. The absence of DST at home is not a property of your
code.

**3 — the SLA.**

```sql
SET TIME ZONE 'America/New_York';
SELECT TIMESTAMPTZ '2026-03-07 14:00:00'                       AS raised,
       TIMESTAMPTZ '2026-03-07 14:00:00' + INTERVAL '1 day'    AS due_same_clock,
       TIMESTAMPTZ '2026-03-07 14:00:00' + INTERVAL '24 hours' AS due_24h;
```

```text
         raised         |     due_same_clock     |        due_24h         
------------------------+------------------------+------------------------
 2026-03-07 14:00:00-05 | 2026-03-08 14:00:00-04 | 2026-03-08 15:00:00-04
(1 row)
```

```sql
SELECT extract(epoch FROM (TIMESTAMPTZ '2026-03-07 14:00:00' + INTERVAL '1 day')
                          - TIMESTAMPTZ '2026-03-07 14:00:00') / 3600 AS hours_same_clock,
       extract(epoch FROM (TIMESTAMPTZ '2026-03-07 14:00:00' + INTERVAL '24 hours')
                          - TIMESTAMPTZ '2026-03-07 14:00:00') / 3600 AS hours_24h;
```

```text
  hours_same_clock   |      hours_24h      
---------------------+---------------------
 23.0000000000000000 | 24.0000000000000000
(1 row)
```

A contract that says "24 hours to respond" means 24 elapsed hours, so `24 hours` is correct
and `1 day` shortens the window to 23 — you would breach an SLA you had actually met. A
contract that says "by close of business the next day" means the wall clock, so `1 day` is
correct. The two agree on 363 days a year, which is exactly why the wrong one survives to
production.

`extract(epoch FROM ...)` is used here rather than printing the interval because
`timestamptz - timestamptz` justifies a whole-day result: the 24-hour difference prints as
`1 day` and the 23-hour one as `23:00:00`, which invites the reader to compare a day against
hours. Epoch seconds are unambiguous.

**4 — the broken hours.**

```sql
SELECT g AS slot
FROM generate_series(TIMESTAMPTZ '2026-03-08 00:00:00',
                     TIMESTAMPTZ '2026-03-08 04:00:00', INTERVAL '1 hour') AS g;
```

```text
          slot          
------------------------
 2026-03-08 00:00:00-05
 2026-03-08 01:00:00-05
 2026-03-08 03:00:00-04
 2026-03-08 04:00:00-04
(4 rows)
```

```sql
SELECT g AS slot
FROM generate_series(TIMESTAMPTZ '2026-11-01 00:00:00',
                     TIMESTAMPTZ '2026-11-01 03:00:00', INTERVAL '1 hour') AS g;
```

```text
          slot          
------------------------
 2026-11-01 00:00:00-04
 2026-11-01 01:00:00-04
 2026-11-01 01:00:00-05
 2026-11-01 02:00:00-05
 2026-11-01 03:00:00-05
(5 rows)
```

March skips 02:00 entirely. November lists 01:00 twice, distinguishable only by the offset
`-04` against `-05`. They are different instants an hour apart and both are genuinely
called "1 a.m.".

Over a full day:

```sql
SELECT (SELECT count(*) FROM generate_series(TIMESTAMPTZ '2026-03-08 00:00:00',
          TIMESTAMPTZ '2026-03-08 23:59:59', INTERVAL '1 hour')) AS mar_08_slots,
       (SELECT count(*) FROM generate_series(TIMESTAMPTZ '2026-11-01 00:00:00',
          TIMESTAMPTZ '2026-11-01 23:59:59', INTERVAL '1 hour')) AS nov_01_slots;
```

```text
 mar_08_slots | nov_01_slots 
--------------+--------------
           23 |           25
(1 row)
```

23 and 25. Anything that hard-codes 24 — a capacity plan, an hourly billing loop, a chart
axis, a "gaps in my metrics" alert — is wrong twice a year. November is the expensive
direction: two bookable 01:00 slots that a naive uniqueness check on the local time will
happily merge into one, double-booking whoever holds the second.

**5 — storing local time plus a zone.**

```sql
CREATE TABLE appointments (
  id          int,
  clinic      text,
  local_when  timestamp NOT NULL,
  zone        text      NOT NULL
);

INSERT INTO appointments VALUES
  (1, 'Bengaluru', '2026-03-08 02:30:00', 'Asia/Kolkata'),
  (2, 'New York',  '2026-03-08 02:30:00', 'America/New_York'),
  (3, 'New York',  '2026-11-01 01:30:00', 'America/New_York');
```

This is the shape Chapter 14 recommends for a booking that is defined by its wall clock: the
local time in a `timestamp`, the zone name beside it in `text`, and the instant computed
when needed rather than stored.

```sql
SET TIME ZONE 'UTC';
SELECT id, clinic, local_when, zone,
       local_when AT TIME ZONE zone AS instant
FROM   appointments ORDER BY id;
```

```text
 id |  clinic   |     local_when      |       zone       |        instant         
----+-----------+---------------------+------------------+------------------------
  1 | Bengaluru | 2026-03-08 02:30:00 | Asia/Kolkata     | 2026-03-07 21:00:00+00
  2 | New York  | 2026-03-08 02:30:00 | America/New_York | 2026-03-08 07:30:00+00
  3 | New York  | 2026-11-01 01:30:00 | America/New_York | 2026-11-01 06:30:00+00
(3 rows)
```

No errors. Now convert back and compare:

```sql
SELECT id, local_when,
       (local_when AT TIME ZONE zone) AT TIME ZONE zone AS round_tripped,
       (local_when AT TIME ZONE zone) AT TIME ZONE zone = local_when AS unchanged
FROM   appointments ORDER BY id;
```

```text
 id |     local_when      |    round_tripped    | unchanged 
----+---------------------+---------------------+-----------
  1 | 2026-03-08 02:30:00 | 2026-03-08 02:30:00 | t
  2 | 2026-03-08 02:30:00 | 2026-03-08 03:30:00 | f
  3 | 2026-11-01 01:30:00 | 2026-11-01 01:30:00 | t
(3 rows)
```

Row 2 booked 02:30 and got 03:30. That local time does not exist in New York on 8 March, and
PostgreSQL resolved it by shifting forward rather than raising an error. The patient turns
up at 02:30, the system says 03:30, and nothing in the database ever complained. Row 1 is
the same wall clock in Bengaluru and round-trips exactly, because `Asia/Kolkata` has no gap
to fall into.

Row 3 round-trips, and that is not the same as being unambiguous:

```sql
SELECT TIMESTAMPTZ '2026-11-01 05:30:00+00' AT TIME ZONE 'America/New_York' AS edt_reading,
       TIMESTAMPTZ '2026-11-01 06:30:00+00' AT TIME ZONE 'America/New_York' AS est_reading;
```

```text
     edt_reading     |     est_reading     
---------------------+---------------------
 2026-11-01 01:30:00 | 2026-11-01 01:30:00
(1 row)
```

Two instants an hour apart, one local reading. Converting to `timestamp` chose 06:30 UTC —
the second, post-transition occurrence — and the first is simply not expressible in this
table. If both 1 a.m. slots must be bookable, the local-time-plus-zone representation is not
enough on its own: store the resolved `timestamptz` as well, and treat the local columns as
what the user typed rather than as the authoritative value.

**6 — refusing the impossible.**

The round-trip test from step 5 is exactly a constraint. Drop the row that already violates
it, then add it:

```sql
DELETE FROM appointments WHERE id = 2;

ALTER TABLE appointments
  ADD CONSTRAINT local_when_exists
  CHECK ((local_when AT TIME ZONE zone) AT TIME ZONE zone = local_when);
```

```sql
INSERT INTO appointments VALUES (4, 'New York', '2026-03-08 02:30:00', 'America/New_York');
```

```text
ERROR:  new row for relation "appointments" violates check constraint "local_when_exists"
DETAIL:  Failing row contains (4, New York, 2026-03-08 02:30:00, America/New_York).
```

Rejected at the door instead of silently moved. The constraint is accepted because
`timezone(text, timestamp)` is marked `IMMUTABLE` on 15.10 — check for yourself with
`SELECT provolatile FROM pg_proc WHERE proname = 'timezone'` — and `CHECK` constraints will
not accept anything weaker. It also catches a nonsense zone name, since an unrecognised zone
raises rather than returning a wrong answer.

> **Trap —** the `IMMUTABLE` marking is a convenient fiction. The IANA time zone database is
> data, it ships with the server or the OS, and governments change the rules: Egypt
> reintroduced DST in 2023, Mexico abolished most of it in 2022. If a future update moves a
> transition, a row that satisfied this constraint when it was written may no longer satisfy
> it, and `ALTER TABLE ... VALIDATE CONSTRAINT` or a restore from `pg_dump` will notice. That
> is a real risk, not a reason to skip the constraint — it is a reason to know it exists
> before a restore fails at 3 a.m. Chapter 15 covers `NOT VALID` and `VALIDATE`.

Had you tried to enforce the same rule against the *ambiguous* November hour, there would be
nothing to catch: 01:30 round-trips perfectly and is still two different moments. Gaps are
detectable and folds are not, which is a good short summary of why DST is worse than it
looks.
