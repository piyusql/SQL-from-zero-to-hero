# Chapter 18 Exercises — Normalization and Deliberate Denormalization

## Practice Session 18.1 — Normalize a flat import to 3NF

**Goal.** Take a spreadsheet-shaped table with no documented rules, discover its functional
dependencies from the data, decompose it to third normal form, and prove the decomposition
lost nothing.

**Setup.** The small `retail` dataset. Everything is built in a scratch database; `retail`
itself is only read.

```bash
createdb ch18_ws1
psql -d retail -Atq -c "\copy (
SELECT 'ORD-'||lpad(o.id::text,5,'0'), o.placed_at::date, c.name, c.email, c.city, o.status,
       (ARRAY['WH-PUN','WH-BLR','WH-DEL','WH-HYD'])[o.id%4+1],
       (ARRAY['Pune','Bengaluru','Delhi','Hyderabad'])[o.id%4+1],
       p.sku, p.name, p.category, oi.unit_price, oi.quantity
FROM orders o JOIN customers c ON c.id = o.customer_id
JOIN order_items oi ON oi.order_id = o.id JOIN products p ON p.id = oi.product_id
ORDER BY oi.id) TO '/tmp/flat.csv' CSV"
psql -d ch18_ws1
```

```sql
\pset null '(null)'
CREATE TABLE flat_import (
    order_no text, order_date date, customer_name text, customer_email text,
    customer_city text, status text, warehouse text, warehouse_city text,
    sku text, product_name text, category text, unit_price numeric(10,2), quantity int);
\copy flat_import FROM '/tmp/flat.csv' CSV

SELECT count(*) FROM flat_import;      -- expect 6250
```

**Task.**

1. For each candidate dependency below, write a query that counts the groups that *violate*
   it. Report which hold: `customer_email → customer_name`, `customer_email → customer_city`,
   `sku → product_name`, `sku → category`, `sku → unit_price`, `order_no → order_date`,
   `order_no → customer_email`, `warehouse → warehouse_city`, `customer_name → customer_email`.
2. One of those failing dependencies is *not* a sign of redundancy. Say which, and why
   normalizing it would be a bug.
3. Test whether `(order_no, sku)` is a key. If not, mint a `line_no` that makes
   `(order_no, line_no)` one, and prove it.
4. Design five tables to 3NF and create them with primary keys, foreign keys and at least
   one `CHECK`. Load them from `flat_import`.
5. Prove the decomposition is lossless: rebuild the flat shape by joining, and compare it to
   `flat_import` with `EXCEPT` in both directions.
6. Pick the customer with the most rows in `flat_import`. Change their city in the flat
   table inside a transaction, but only for the first half of their orders; show the
   inconsistency; roll back. Then make the same change in your normalized schema and count
   the rows touched.
7. **BCNF.** A courier firm records which courier serves each customer from each warehouse.
   Each courier is based at exactly one warehouse, and a customer has one courier per
   warehouse:

   ```sql
   CREATE TABLE delivery_slot (customer text, warehouse text, courier text,
                               PRIMARY KEY (customer, warehouse));
   INSERT INTO delivery_slot VALUES
    ('Anita Rao','WH-PUN','BlueDart'),     ('Anita Rao','WH-BLR','Delhivery'),
    ('Harpreet Singh','WH-PUN','BlueDart'), ('Meera Banerjee','WH-DEL','Ecom Express'),
    ('Fatima Sheikh','WH-BLR','Delhivery');
   ```

   Show that it violates BCNF, decompose it, prove the decomposition lossless, and then
   show one row the decomposed schema accepts that the original would have refused.

**Solution.**

Step 1 — one probe per candidate. Group by the left side; keep the groups with more than
one distinct right side:

```sql
SELECT 'email -> name' AS candidate, count(*) AS violations
FROM (SELECT customer_email FROM flat_import GROUP BY 1
      HAVING count(DISTINCT customer_name) > 1) s
UNION ALL SELECT 'email -> city', count(*)
FROM (SELECT customer_email FROM flat_import GROUP BY 1
      HAVING count(DISTINCT customer_city) > 1) s
UNION ALL SELECT 'sku -> product_name', count(*)
FROM (SELECT sku FROM flat_import GROUP BY 1
      HAVING count(DISTINCT product_name) > 1) s
UNION ALL SELECT 'sku -> category', count(*)
FROM (SELECT sku FROM flat_import GROUP BY 1
      HAVING count(DISTINCT category) > 1) s
UNION ALL SELECT 'sku -> unit_price', count(*)
FROM (SELECT sku FROM flat_import GROUP BY 1
      HAVING count(DISTINCT unit_price) > 1) s
UNION ALL SELECT 'order_no -> order_date', count(*)
FROM (SELECT order_no FROM flat_import GROUP BY 1
      HAVING count(DISTINCT order_date) > 1) s
UNION ALL SELECT 'order_no -> customer_email', count(*)
FROM (SELECT order_no FROM flat_import GROUP BY 1
      HAVING count(DISTINCT customer_email) > 1) s
UNION ALL SELECT 'warehouse -> warehouse_city', count(*)
FROM (SELECT warehouse FROM flat_import GROUP BY 1
      HAVING count(DISTINCT warehouse_city) > 1) s
UNION ALL SELECT 'name -> email', count(*)
FROM (SELECT customer_name FROM flat_import GROUP BY 1
      HAVING count(DISTINCT customer_email) > 1) s;
```

Every dependency holds (zero violations) except two: `sku → unit_price` fails for all 200
SKUs, and `customer_name → customer_email` fails for 238 names. (Do not rely on the row
order of a `UNION ALL` result; read the `candidate` column.)

Step 2 — `sku → unit_price` is the price on the order line: the price *at sale*. It is an
attribute of the line, not of the product. Moving it to `products` would silently rewrite
every historical order the next time a price changed. Repeated values are redundancy only
when they are the same fact. (`customer_name → customer_email` is a different lesson: two
customers can share a name, so a name can never be a key.)

Step 3 — the natural key does not survive contact with the data:

```sql
SELECT count(*) - count(DISTINCT (order_no, sku)) AS duplicate_keys FROM flat_import;   -- 25

ALTER TABLE flat_import ADD COLUMN line_no int;
UPDATE flat_import f SET line_no = n.rn
FROM  (SELECT ctid AS c, row_number() OVER (PARTITION BY order_no ORDER BY ctid) AS rn
       FROM flat_import) n
WHERE  f.ctid = n.c;

SELECT count(*) - count(DISTINCT (order_no, line_no)) AS duplicate_keys FROM flat_import;  -- 0
```

Twenty-five orders carry the same product on two lines. Minting a line number from `ctid`
is acceptable only on a table nobody is writing to; in production the source system
supplies it.

Step 4 — the dependencies fall out as tables. Order attributes depend on `order_no` alone
(2NF); customer, warehouse and product attributes depend on the key only through another
column (3NF):

```sql
CREATE TABLE customers  (customer_id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
                         email text NOT NULL UNIQUE, name text NOT NULL, city text);
CREATE TABLE warehouses (warehouse_code text PRIMARY KEY, city text NOT NULL);
CREATE TABLE products   (sku text PRIMARY KEY, name text NOT NULL, category text NOT NULL);
CREATE TABLE orders     (order_no text PRIMARY KEY, order_date date NOT NULL, status text NOT NULL,
                         customer_id    int  NOT NULL REFERENCES customers,
                         warehouse_code text NOT NULL REFERENCES warehouses);
CREATE TABLE order_lines (order_no text NOT NULL REFERENCES orders, line_no int NOT NULL,
                          sku text NOT NULL REFERENCES products,
                          quantity int NOT NULL CHECK (quantity > 0),
                          unit_price numeric(10,2) NOT NULL,
                          PRIMARY KEY (order_no, line_no));

INSERT INTO customers (email, name, city)
  SELECT DISTINCT customer_email, customer_name, customer_city FROM flat_import ORDER BY 1;
INSERT INTO warehouses SELECT DISTINCT warehouse, warehouse_city FROM flat_import;
INSERT INTO products   SELECT DISTINCT sku, product_name, category FROM flat_import;
INSERT INTO orders
  SELECT DISTINCT f.order_no, f.order_date, f.status, c.customer_id, f.warehouse
  FROM flat_import f JOIN customers c ON c.email = f.customer_email;
INSERT INTO order_lines SELECT order_no, line_no, sku, quantity, unit_price FROM flat_import;
```

Expect 803, 4, 200, 2,500 and 6,250 rows. `email` stays `UNIQUE` but `customer_id` is the key
other tables point at, because people change email addresses and a foreign key should not
have to follow.

Step 5 — subtract in both directions; both counts must be zero. `EXCEPT` treats NULLs as
equal, so rows with a NULL city compare correctly:

```sql
WITH rebuilt AS (
  SELECT o.order_no, o.order_date, c.name AS customer_name, c.email AS customer_email,
         c.city AS customer_city, o.status, w.warehouse_code AS warehouse,
         w.city AS warehouse_city, p.sku, p.name AS product_name, p.category,
         l.unit_price, l.quantity, l.line_no
  FROM   order_lines l JOIN orders o USING (order_no) JOIN customers c USING (customer_id)
         JOIN warehouses w USING (warehouse_code) JOIN products p USING (sku))
SELECT (SELECT count(*) FROM (SELECT * FROM flat_import EXCEPT SELECT * FROM rebuilt) a) AS missing,
       (SELECT count(*) FROM (SELECT * FROM rebuilt EXCEPT SELECT * FROM flat_import) b) AS invented;
```

The column order of `rebuilt` must match `flat_import` (which now ends in `line_no`), or
`EXCEPT` compares the wrong columns and reports nonsense.

Step 6 — the most-repeated customer is `customer426@vyapar.example`, with 26 rows:

```sql
BEGIN;
UPDATE flat_import SET customer_city = 'Kochi'
WHERE  customer_email = 'customer426@vyapar.example' AND order_no < 'ORD-01500';   -- UPDATE 19
SELECT customer_city, count(*) FROM flat_import
WHERE  customer_email = 'customer426@vyapar.example' GROUP BY 1 ORDER BY 1;         -- Kochi 19, Nagpur 7
ROLLBACK;

UPDATE customers SET city = 'Kochi' WHERE email = 'customer426@vyapar.example';    -- UPDATE 1
```

The flat table accepted a state in which one customer lives in two cities and raised no
error. The normalized table has one place to put the fact, so it has no way to disagree
with itself.

Step 7 — every courier appears with exactly one warehouse, so `courier → warehouse` holds,
but `courier` is not a key of `delivery_slot`: a BCNF violation. Decompose on the
dependency:

```sql
SELECT courier, count(DISTINCT warehouse) AS warehouses
FROM delivery_slot GROUP BY courier ORDER BY courier;          -- all 1

CREATE TABLE courier_base (courier text PRIMARY KEY, warehouse text NOT NULL);
INSERT INTO courier_base SELECT DISTINCT courier, warehouse FROM delivery_slot;
CREATE TABLE customer_courier (customer text, courier text REFERENCES courier_base,
                               PRIMARY KEY (customer, courier));
INSERT INTO customer_courier SELECT DISTINCT customer, courier FROM delivery_slot;

WITH rebuilt AS (
  SELECT cc.customer, cb.warehouse, cc.courier
  FROM   customer_courier cc JOIN courier_base cb USING (courier))
SELECT (SELECT count(*) FROM (SELECT * FROM delivery_slot EXCEPT SELECT * FROM rebuilt) a) AS missing,
       (SELECT count(*) FROM (SELECT * FROM rebuilt EXCEPT SELECT * FROM delivery_slot) b) AS invented;
                                                                     -- 0 and 0
```

Now the dependency the split lost, `(customer, warehouse) → courier`:

```sql
INSERT INTO courier_base VALUES ('DTDC','WH-PUN');
INSERT INTO customer_courier VALUES ('Anita Rao','DTDC');     -- accepted

SELECT cc.customer, cb.warehouse, count(*) AS couriers
FROM   customer_courier cc JOIN courier_base cb USING (courier)
GROUP  BY 1,2 HAVING count(*) > 1;                           -- Anita Rao | WH-PUN | 2

INSERT INTO delivery_slot VALUES ('Anita Rao','WH-PUN','DTDC');
-- ERROR:  duplicate key value violates unique constraint "delivery_slot_pkey"
```

Anita Rao now has two couriers from the Pune warehouse in the decomposed schema; the
original refused the same fact through its primary key. Nothing declarative in the new
schema can express it — it would take a trigger. Whether that is acceptable is the actual
design decision: keep the redundancy and the constraint, or drop the redundancy and enforce
the rule elsewhere.

Clean up: `DROP DATABASE ch18_ws1;` (from another database).

## Practice Session 18.2 — Denormalize one hot path and measure both sides

**Goal.** Decide, with numbers from both the read side and the write side, whether one
derived column earns its keep, and build the mechanism that keeps it correct.

**Setup.** The large `retail` dataset, 2,000,000 orders. If you built `retail_lg` in
Practice Session 8.2 it is still there. If not, build it beside the small `retail` (about a
minute, 749 MB). Do not run `./load.sh retail lg`: it names its database `retail` and would
replace the small dataset.

```bash
cd path/to/sql-from-my-heart/datasets
createdb retail_lg
psql -d retail_lg -v ON_ERROR_STOP=1 -f retail/schema.sql
psql -d retail_lg -v ON_ERROR_STOP=1 -f retail/generate-lg.sql
```

Work on a copy so the original stays as loaded:

```bash
createdb -T retail_lg ch18_ws2
psql -d ch18_ws2
```

```sql
\pset null '(null)'
SET max_parallel_workers_per_gather = 0;   -- one process, so buffer totals compare cleanly

VACUUM FULL customers;                     -- start from a repacked heap so sizes mean something
CREATE INDEX customers_city  ON customers (city);
CREATE INDEX orders_customer ON orders (customer_id);
VACUUM (ANALYZE) customers;
ANALYZE orders;

SELECT count(*) AS customers, count(*) FILTER (WHERE city = 'Chennai') AS chennai FROM customers;
-- expect 300000 and 13406
```

The marketing team's hot path: *the twenty best repeat customers in Chennai*, meaning
customers with at least five orders, most orders first.

**Task.**

1. Write that query against the normalized schema. Run it under
   `EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF)` twice and read the
   second run. Record the total buffers (`hit` plus `read`) at the top node.
2. Record the size of `customers` (heap and indexes). Then add `customers.order_count`,
   backfill it, make it `NOT NULL DEFAULT 0`, and build an index that lets the hot path be
   answered from `customers` alone. Repack and record the sizes again.
3. Rewrite the hot path against the new column. Confirm it returns the same twenty rows,
   then record its buffers.
4. Write the trigger that keeps `order_count` correct on `INSERT`, `DELETE` and a change of
   `customer_id` on `orders`.
5. Measure the write side: WAL bytes per inserted order, first with the trigger disabled
   and then enabled, inserting one order for each of 1,000 different customers after a
   `CHECKPOINT`. Also read how many of the trigger's updates to `customers` were HOT.
6. Write a drift query. Then try to break the invariant two ways — delete an order, and move
   an order to another customer with the trigger disabled — and show which one the drift
   query catches. Repair what it finds.
7. Write down your decision in three sentences, using the numbers.

**Solution.**

Step 1 — the normalized form. The join is the cost: every one of the 13,406 Chennai
customers probes `orders`.

```sql
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT c.id, c.name, count(*) AS orders
FROM   customers c JOIN orders o ON o.customer_id = c.id
WHERE  c.city = 'Chennai'
GROUP  BY c.id
HAVING count(*) >= 5
ORDER  BY orders DESC, c.id
LIMIT  20;
```

Expect roughly **52,240 buffers**: a bitmap scan of the Chennai customers (3,579) and then
an index-only scan on `orders_customer` run 13,406 times (about 48,660). The exact count
can differ by a few between runs; the order of magnitude does not.

Step 2 — before, the heap is about 29 MB with 8,672 kB of indexes. Then:

```sql
ALTER TABLE customers ADD COLUMN order_count int;
UPDATE customers c
SET    order_count = (SELECT count(*) FROM orders o WHERE o.customer_id = c.id);
ALTER TABLE customers ALTER COLUMN order_count SET NOT NULL,
                      ALTER COLUMN order_count SET DEFAULT 0;
CREATE INDEX customers_city_orders ON customers (city, order_count DESC);
VACUUM FULL customers;
ANALYZE customers;

SELECT pg_size_pretty(pg_relation_size('customers')) AS heap,
       pg_size_pretty(pg_indexes_size('customers'))  AS indexes;
```

After: 32 MB and 11 MB. Storage cost is about 3 MB of heap and 2 MB of index. Note that
the column alone is not what makes the query fast; the index on `(city, order_count DESC)`
is. Part of the "price" of this denormalization is that index, and every later update of
`order_count` has to maintain it.

Step 3 — same answer from one table:

```sql
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT id, name, order_count AS orders
FROM   customers
WHERE  city = 'Chennai' AND order_count >= 5
ORDER  BY order_count DESC, id
LIMIT  20;
```

**47 buffers** against about 52,240: roughly a thousandfold. Compare the twenty rows from
Step 1 and Step 3 (`EXCEPT` both ways); they are identical, the first being Rajesh Gupta
with 23 orders. This is the shape where denormalization pays: the counter moved a
*filter* into an index, so the query stopped reading almost everything. Contrast the
chapter's dashboard, where the column removed a join but left the scan and won only 2.7×.

Step 4 — the trigger must handle all three ways an order can change customers:

```sql
CREATE FUNCTION bump_order_count() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    UPDATE customers SET order_count = order_count + 1 WHERE id = NEW.customer_id;
  ELSIF TG_OP = 'DELETE' THEN
    UPDATE customers SET order_count = order_count - 1 WHERE id = OLD.customer_id;
  ELSIF NEW.customer_id <> OLD.customer_id THEN
    UPDATE customers SET order_count = order_count - 1 WHERE id = OLD.customer_id;
    UPDATE customers SET order_count = order_count + 1 WHERE id = NEW.customer_id;
  END IF;
  RETURN NULL;
END $$;

CREATE TRIGGER orders_count
AFTER INSERT OR DELETE OR UPDATE OF customer_id ON orders
FOR EACH ROW EXECUTE FUNCTION bump_order_count();
```

A trigger that only handled `INSERT` would pass a quick test and drift the first time
someone reassigned an order. `UPDATE OF customer_id` limits the trigger to updates that can
matter, so a status change does not pay for it.

Step 5 — the write side:

```sql
ALTER TABLE orders DISABLE TRIGGER orders_count;
CHECKPOINT;
SELECT pg_current_wal_insert_lsn() AS start_lsn \gset
INSERT INTO orders (customer_id, placed_at, status, total_amount)
SELECT id, '2026-09-02', 'pending', 100 FROM customers WHERE id % 300 = 1;
SELECT round(pg_wal_lsn_diff(pg_current_wal_insert_lsn(), :'start_lsn') / 1000) AS wal_bytes_per_row;
```

Expect about **14,800** bytes per row, most of it full-page images: the first change to any
page after a checkpoint logs the whole page, and 1,000 scattered inserts touch many pages.
Repair the counts the bypass left stale, re-enable the trigger, wait for statistics to flush
so the reset is clean, and repeat on different customers:

```sql
UPDATE customers c SET order_count = n.k
FROM  (SELECT customer_id, count(*) AS k FROM orders GROUP BY customer_id) n
WHERE  n.customer_id = c.id AND c.order_count <> n.k;
ALTER TABLE orders ENABLE TRIGGER orders_count;
SELECT pg_sleep(2);
SELECT pg_stat_reset();
CHECKPOINT;
SELECT pg_current_wal_insert_lsn() AS start_lsn \gset
INSERT INTO orders (customer_id, placed_at, status, total_amount)
SELECT id, '2026-09-02', 'pending', 100 FROM customers WHERE id % 300 = 2;
SELECT round(pg_wal_lsn_diff(pg_current_wal_insert_lsn(), :'start_lsn') / 1000) AS wal_bytes_per_row;
SELECT pg_sleep(2);
SELECT n_tup_upd, n_tup_hot_upd FROM pg_stat_user_tables WHERE relname = 'customers';
```

Expect about **24,800** bytes per row (1.7×), and `n_tup_upd = 1000`, **`n_tup_hot_upd = 0`**.
Zero HOT updates is not bad luck. `order_count` is a column of `customers_city_orders`, and
a HOT update is only possible when no indexed column changes — so every counter bump writes
a new row version and a new index entry. That is the cost of the index that made Step 3
fast, and it is the reason to prefer a counter column that no index covers where you can.
(`pg_stat_reset()` resets the counters for the whole current database; do it only in a
scratch copy. Without the `pg_sleep` before it, the previous statement's counts can arrive
after the reset and inflate the totals.)

Step 6 — the drift query, and two attempts to break the invariant:

```sql
SELECT count(*) AS drifted FROM customers c
WHERE  c.order_count IS DISTINCT FROM (SELECT count(*) FROM orders o WHERE o.customer_id = c.id);
```

It returns 0 at this point. A delete goes through the trigger, so it stays at 0:

```sql
DELETE FROM orders WHERE id = (SELECT max(id) FROM orders);   -- DELETE 1, drifted stays 0
```

A move made while the trigger is disabled — as a bulk fix-up script might — does not:

```sql
BEGIN;
ALTER TABLE orders DISABLE TRIGGER orders_count;
UPDATE orders SET customer_id = customer_id + 1 WHERE id = (SELECT min(id) FROM orders);
COMMIT;
ALTER TABLE orders ENABLE TRIGGER orders_count;
-- drift query now returns 2: one customer too high, one too low
```

Two customers are wrong, one in each direction, and nothing raised an error. Repair with a
statement that recomputes from the source of truth and touches only the rows that differ
(the `LEFT JOIN` matters: a customer whose count fell to zero has no rows in `orders` and
would be skipped by an inner join):

```sql
UPDATE customers c SET order_count = n.k
FROM  (SELECT c2.id, count(o.id) AS k
       FROM customers c2 LEFT JOIN orders o ON o.customer_id = c2.id GROUP BY c2.id) n
WHERE  n.id = c.id AND c.order_count <> n.k;                  -- UPDATE 2, drifted back to 0
```

Step 7 — a defensible answer: "The Chennai query dropped from about 52,000 buffers to 47,
because the counter plus its index turned a per-customer join into a single index range
scan. The price is 1.7× the WAL per inserted order, no HOT updates on `customers` (the
counter is indexed), and a drift query someone has to run. Worth it if this list is
served often and orders arrive slower than it is read; not worth it for a report run
weekly." The point of the session is not which way you decide; it is that the decision
cites numbers from both sides.

Clean up: `DROP DATABASE ch18_ws2;` (from another database).
