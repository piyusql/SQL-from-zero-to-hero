# Chapter 13 Exercises — Numeric and Character Types

## Practice Session 13.1 — Float rounding error on currency

**Goal.** Reproduce, on real data, the specific way `double precision` breaks money —
then decide for yourself whether the damage is where you expected it.

**Setup.** The small `retail` dataset from Practice Session 2.3. Steps 1 to 4 are
read-only; step 5 needs a scratch database.

```bash
psql -d retail
```

```sql
SELECT count(*) FROM order_items;    -- expect 6250
\pset null '(null)'
```

`order_items.unit_price` is `numeric(10,2)` and `orders.total_amount` is `numeric(12,2)`,
and the dataset keeps `total_amount` equal to the sum over its line items. That gives you
a correct answer to reconcile against, which is the whole point of the exercise.

**Task.**

1. Compute the grand total of `quantity * unit_price` twice: once in `numeric`, once with
   `unit_price` cast to `double precision`. How far apart are they?
2. Count the individual line totals where the float arithmetic does not produce exactly
   the right value.
3. Reconcile per order: how many of the 2,500 orders fail an exact match between the
   stored `total_amount` and a float-computed sum of their line items?
4. Now the question that matters: how many of those orders differ once you round the
   float total to two decimal places? Predict before you run it.
5. In a scratch database, store three float-derived amounts, then migrate the column to
   `numeric(12,2)`. Say what the migration repaired and what it did not.

**Solution.**

**1 — the grand total.**

```sql
SELECT sum(quantity * unit_price)         AS numeric_total,
       sum(quantity * unit_price::float8) AS float_total
FROM   order_items;
```

```text
 numeric_total |    float_total     
---------------+--------------------
    3678982.61 | 3678982.6099999947
(1 row)
```

Five nanorupees apart on a total of three and a half million. Nobody notices that in a
report, and that is exactly why the bug survives to production.

**2 — the line totals that are not exactly right.**

```sql
SELECT count(*) AS lines,
       count(*) FILTER (WHERE quantity * unit_price::float8
                           <> (quantity * unit_price)::float8) AS float_not_exact
FROM   order_items;
```

```text
 lines | float_not_exact 
-------+-----------------
  6250 |             707
(1 row)
```

707 of 6,250 line totals — 11% — are not the value the exact calculation produces. The
comparison is float-to-float, so this is not a casting artefact: the same multiplication
done in binary floating point lands somewhere else than the same multiplication done in
decimal, and then lands there permanently.

**3 — reconciliation per order.**

```sql
SELECT count(*) AS orders,
       count(*) FILTER (WHERE f.float_total <> o.total_amount::float8) AS fail_exact_match
FROM   orders o
JOIN   (SELECT order_id, sum(quantity * unit_price::float8) AS float_total
        FROM   order_items
        GROUP  BY order_id) f ON f.order_id = o.id;
```

```text
 orders | fail_exact_match 
--------+------------------
   2500 |              623
(1 row)
```

**One order in four fails an exact-match reconciliation.** Look at what they look like:

```sql
SELECT o.id, o.total_amount AS stored_numeric, f.float_total
FROM   orders o
JOIN   (SELECT order_id, sum(quantity * unit_price::float8) AS float_total
        FROM   order_items
        GROUP  BY order_id) f ON f.order_id = o.id
WHERE  f.float_total <> o.total_amount::float8
ORDER  BY o.id
LIMIT  5;
```

```text
 id | stored_numeric |    float_total     
----+----------------+--------------------
 10 |         511.05 | 511.04999999999995
 16 |        1514.63 | 1514.6299999999999
 20 |        1052.26 | 1052.2600000000002
 25 |         411.33 | 411.33000000000004
 26 |         1987.86 | 1987.8600000000001
(5 rows)
```

Every one of those renders as the correct rupee amount in any UI that formats to two
decimals. They are wrong only to a machine, and a reconciliation job is a machine.

**4 — and now the honest part.**

```sql
SELECT count(*) AS orders_differing_at_two_decimals
FROM   orders o
JOIN   (SELECT order_id, sum(quantity * unit_price::float8) AS float_total
        FROM   order_items
        GROUP  BY order_id) f ON f.order_id = o.id
WHERE  round(f.float_total::numeric, 2) <> o.total_amount;
```

```text
 orders_differing_at_two_decimals 
----------------------------------
                                0
(1 row)
```

**Zero.** Round to paise and every single order agrees.

If you predicted a few hundred, notice what just happened, because it is the most useful
thing in this session. The float argument is often made as "your totals will be wrong",
and on this data, at this scale, at two decimal places, that claim is false. Arguing it
that way gets you beaten in a design review by someone who runs the query.

The argument that survives contact with the query is narrower and stronger:

- **Exact comparison fails.** 623 of 2,500 orders. Any reconciliation, any
  `WHERE total = ?`, any `GROUP BY amount`, any checksum between two systems.
- **The error is unbounded as the arithmetic deepens.** One multiplication puts you in
  the fifteenth significant digit. Tax, then a discount, then a currency conversion, then
  a sum over ten thousand rows, and the digit creeps left. Two decimal places is not a
  safe margin, it is today's margin.
- **The result is not reproducible.** Chapter 13 showed the same float column summing to
  three different values depending on whether the plan was serial, parallel or sorted.
  `numeric` has no such property.
- **`round()` disagrees between the types**, and this one does move rupees:

```sql
SELECT round(0.5::float8) AS f_half,       round(0.5::numeric) AS n_half,
       round(2.5::float8) AS f_two_half,   round(2.5::numeric) AS n_two_half,
       round(3.5::float8) AS f_three_half, round(3.5::numeric) AS n_three_half;
```

```text
 f_half | n_half | f_two_half | n_two_half | f_three_half | n_three_half 
--------+--------+------------+------------+--------------+--------------
      0 |      1 |          2 |          3 |            4 |            4
(1 row)
```

`round()` on `double precision` rounds halves to the nearest **even** integer — the IEEE
default. On `numeric` it rounds halves **away from zero**. Same function name, same
literal, different answer, and no cast anywhere in the SQL to warn you which one you got.

**5 — migrating a float column, and what it cannot fix.**

```bash
createdb ch13_scratch
psql -d ch13_scratch
```

```sql
CREATE TABLE invoice_f8 (id int, amt double precision);
INSERT INTO invoice_f8 VALUES (1, 1149.99::float8 * 3),
                              (2, 0.1::float8 + 0.2::float8),
                              (3, 2099.99::float8 * 0.5::float8);
SELECT id, amt::text AS as_printed FROM invoice_f8 ORDER BY id;
```

```text
 id |     as_printed      
----+---------------------
  1 | 3449.9700000000003
  2 | 0.30000000000000004
  3 | 1049.995
(3 rows)
```

> **Trap —** the `::text` is load-bearing. Write the `::float8` casts too. `1149.99 * 3`
> with bare literals is computed in `numeric` and gives exactly 3449.97, so a demo
> written without explicit casts silently proves the opposite of what it intended.

Check `relfilenode` before and after, the way Chapter 4 taught:

```sql
SELECT relfilenode FROM pg_class WHERE relname = 'invoice_f8';
```

```text
 relfilenode 
-------------
       39634
(1 row)
```

```sql
ALTER TABLE invoice_f8 ALTER COLUMN amt TYPE numeric(12,2);
SELECT relfilenode FROM pg_class WHERE relname = 'invoice_f8';
```

```text
 relfilenode 
-------------
       39637
(1 row)
```

The number changed, so every row was physically rewritten — under `ACCESS EXCLUSIVE` for
the duration, which on a real invoice table is an outage you schedule rather than a
migration you merge on a Friday.

```sql
SELECT id, amt AS after_migration FROM invoice_f8 ORDER BY id;
```

```text
 id | after_migration 
----+-----------------
  1 |         3449.97
  2 |            0.30
  3 |         1050.00
(3 rows)
```

**What it repaired:** every value is now exact at two decimal places, and every future
calculation on the column is decimal arithmetic. Row 3 is worth staring at — `1049.995`
became `1050.00`, because the cast to `numeric` rounds half away from zero. Had the
application rounded that value in float, it would have produced `1049.99`. The migration
did not just change a type; it changed a rupee.

**What it did not repair:** anything already written elsewhere. Every invoice PDF, every
row in a downstream warehouse, every figure a finance team has already reconciled against
was computed under the old rules and is still there. You can fix the column in one
`ALTER`; you cannot fix the history without knowing which of the two roundings each
downstream consumer applied. That asymmetry is the reason this is a day-one decision.

```bash
dropdb ch13_scratch
```

## Practice Session 13.2 — `ALTER` lock levels compared

**Goal.** Measure the lock mode each type-and-constraint `ALTER TABLE` takes, then watch
one of them block a trivial `SELECT` while another does not.

**Setup.** A scratch database and a table big enough that the scanning operations take
long enough to observe. Chapter 4 covered *which* `ALTER TABLE` operations rewrite and
which are instant metadata changes; this session is about the lock, which is a separate
question and usually the one that takes the service down.

```bash
createdb ch13_scratch
psql -d ch13_scratch
```

```sql
\pset null '(null)'

CREATE TABLE sku_t (id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY, sku text        NOT NULL);
CREATE TABLE sku_v (id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY, sku varchar(20) NOT NULL);
INSERT INTO sku_t (sku) SELECT 'SKU-' || lpad(i::text, 8, '0') FROM generate_series(1,2000000) i;
INSERT INTO sku_v (sku) SELECT 'SKU-' || lpad(i::text, 8, '0') FROM generate_series(1,2000000) i;
ANALYZE;
```

You also want a way to ask what locks *this* backend currently holds on a table. PostgreSQL
releases locks at commit, so the question only has an answer inside an open transaction:

```sql
CREATE FUNCTION locks_held(regclass) RETURNS text LANGUAGE sql AS
$$ SELECT string_agg(DISTINCT mode, ', ' ORDER BY mode)
   FROM   pg_locks
   WHERE  relation = $1 AND locktype = 'relation' AND pid = pg_backend_pid() $$;
```

**Task.**

1. For each of these six operations, run it inside `BEGIN … ROLLBACK` and report the lock
   mode it took: widen `varchar(20)` to `varchar(50)`; narrow `text` to `varchar(20)`; add
   a validated `CHECK`; add the same `CHECK` as `NOT VALID`; `VALIDATE` it; drop it.
2. From your six results, predict which operations a concurrent `SELECT count(*)` can run
   through and which it cannot. Then prove both, using two `psql` sessions and a third to
   watch `pg_locks`.
3. One of the six took *two* lock modes. Explain the second one.
4. Set a `lock_timeout` and make a DDL statement give up rather than queue.

**Solution.**

**1 — the six lock modes.** Each of these is `BEGIN`, the statement, the probe, `ROLLBACK`:

```sql
BEGIN;
ALTER TABLE sku_v ALTER COLUMN sku TYPE varchar(50);
SELECT locks_held('sku_v') AS lock_mode;
ROLLBACK;
```

```text
      lock_mode      
---------------------
 AccessExclusiveLock
(1 row)
```

```sql
BEGIN;
ALTER TABLE sku_t ALTER COLUMN sku TYPE varchar(20);
SELECT locks_held('sku_t') AS lock_mode;
ROLLBACK;
```

```text
           lock_mode            
--------------------------------
 AccessExclusiveLock, ShareLock
(1 row)
```

```sql
BEGIN;
ALTER TABLE sku_t ADD CONSTRAINT sku_len CHECK (length(sku) <= 20);
SELECT locks_held('sku_t') AS lock_mode;
ROLLBACK;
```

```text
      lock_mode      
---------------------
 AccessExclusiveLock
(1 row)
```

```sql
BEGIN;
ALTER TABLE sku_t ADD CONSTRAINT sku_len CHECK (length(sku) <= 20) NOT VALID;
SELECT locks_held('sku_t') AS lock_mode;
ROLLBACK;
```

```text
      lock_mode      
---------------------
 AccessExclusiveLock
(1 row)
```

Now add it for real, so there is something to validate:

```sql
ALTER TABLE sku_t ADD CONSTRAINT sku_len CHECK (length(sku) <= 20) NOT VALID;

BEGIN;
ALTER TABLE sku_t VALIDATE CONSTRAINT sku_len;
SELECT locks_held('sku_t') AS lock_mode;
ROLLBACK;
```

```text
        lock_mode         
--------------------------
 ShareUpdateExclusiveLock
(1 row)
```

```sql
BEGIN;
ALTER TABLE sku_t DROP CONSTRAINT sku_len;
SELECT locks_held('sku_t') AS lock_mode;
ROLLBACK;
```

```text
      lock_mode      
---------------------
 AccessExclusiveLock
(1 row)
```

Five `ACCESS EXCLUSIVE`, one `SHARE UPDATE EXCLUSIVE`. The lock mode is **not** what
distinguishes a cheap `ALTER` from an expensive one — widening a `varchar`, which touches
nothing but a catalog row, takes the same lock as a full rewrite. What distinguishes them
is how long that lock is *held*. A metadata change holds `ACCESS EXCLUSIVE` only long
enough to update a catalog row; the validated `ADD CONSTRAINT` holds it for a scan of two
million rows; the narrowing type change holds it for a rewrite of two million rows.

**2 — prediction, then proof.**

`ACCESS EXCLUSIVE` conflicts with every lock mode there is, including the `ACCESS SHARE`
that a plain `SELECT` takes. `SHARE UPDATE EXCLUSIVE` conflicts with itself and with the
heavier modes, but **not** with `ACCESS SHARE` or `ROW EXCLUSIVE` — so reads and ordinary
writes go straight through. Prediction: the first five block a reader, `VALIDATE` does not.

Step 1 left `sku_len` on the table, so clear it first. Then, in session A, leave the
transaction open:

```sql
ALTER TABLE sku_t DROP CONSTRAINT sku_len;

BEGIN;
ALTER TABLE sku_t ADD CONSTRAINT sku_len CHECK (length(sku) <= 20);
-- do not commit yet
```

Session B:

```sql
SELECT count(*) FROM sku_t;
```

Session C, while B sits there:

```sql
SELECT a.pid, a.state, left(a.query, 46) AS query, l.mode, l.granted
FROM   pg_stat_activity a
JOIN   pg_locks l ON l.pid = a.pid
WHERE  l.relation = 'sku_t'::regclass AND l.locktype = 'relation'
ORDER  BY l.granted DESC, a.pid;
```

```text
  pid  |        state        |                     query                      |        mode         | granted 
-------+---------------------+------------------------------------------------+---------------------+---------
 36675 | idle in transaction | ALTER TABLE sku_t ADD CONSTRAINT sku_len CHECK | AccessExclusiveLock | t
 36685 | active              | SELECT count(*) FROM sku_t;                    | AccessShareLock     | f
(2 rows)
```

`granted | f` on a `SELECT count(*)` that would otherwise finish immediately. Note also
that session A is `idle in transaction` — it has *finished its work* and is still holding
the lock, because locks are released at commit and not a moment earlier. A migration tool
that wraps several statements in one transaction holds the strongest lock any of them took
for the length of all of them.

`ROLLBACK` in A, and B completes.

Now the other one. In session A:

```sql
ALTER TABLE sku_t ADD CONSTRAINT sku_len CHECK (length(sku) <= 20) NOT VALID;

BEGIN;
ALTER TABLE sku_t VALIDATE CONSTRAINT sku_len;
-- do not commit yet
```

Run both a read and a write from other sessions:

```sql
SELECT count(*) FROM sku_t;                             -- returns 2000000
INSERT INTO sku_t (sku) VALUES ('SKU-99999999');        -- INSERT 0 1
```

```text
  pid  |        state        |                     query                      |           mode           | granted 
-------+---------------------+------------------------------------------------+--------------------------+---------
 36735 | idle in transaction | ALTER TABLE sku_t VALIDATE CONSTRAINT sku_len; | ShareUpdateExclusiveLock | t
(1 row)
```

One row. The reader and the writer both finished before the observer query even ran — they
never queued, so they never appeared. That is the entire argument for the
`NOT VALID` + `VALIDATE` split: the expensive half of the work happens under a lock that
your application does not notice.

**3 — the second lock mode.**

`text` → `varchar(20)` reported `AccessExclusiveLock, ShareLock`. The `ShareLock` is the
index rebuild. A type change that rewrites the table must also rebuild every index on it,
and building an index takes `SHARE` on the table (that is what stops writes during a
non-concurrent `CREATE INDEX`). `sku_t` has a primary key, so there is an index to rebuild;
the same statement on a table with no indexes shows only `AccessExclusiveLock`.

It makes no practical difference here — `ACCESS EXCLUSIVE` already excludes everything
`SHARE` would — but it tells you what the statement is actually doing, and it is a good
reminder that a rewrite costs you the indexes as well as the heap.

**4 — failing fast instead of queueing.**

The danger is not a slow `ALTER`. It is a *blocked* `ALTER`: while it waits, every query
that arrives behind it also waits, because PostgreSQL's lock queue is ordered and a
pending exclusive request is not overtaken. Chapter 4 measured that chain.

Session A opens a transaction and just reads:

```sql
BEGIN;
SELECT count(*) FROM sku_t;
-- left open
```

Session B:

```sql
SET lock_timeout = '2s';
ALTER TABLE sku_t ALTER COLUMN sku TYPE varchar(20);
```

```text
ERROR:  canceling statement due to lock timeout
```

Two seconds, then it gives up, and nothing queued behind it. **This is the correct
outcome.** A migration that fails cleanly can be retried in a quieter minute; a migration
that waits indefinitely takes the application with it. Set `lock_timeout` before every DDL
statement on a live system. Chapter 52 builds the full pattern, including the retry loop
and how to find the long-running transaction that is in your way.

```bash
dropdb ch13_scratch
```

## Practice Session 13.3 — Trigger an index-size failure

**Goal.** Find the exact point at which a B-tree refuses a value, discover that the
boundary is not where the column definition says it is, and fix a real table three ways.

**Setup.** A scratch database. You need deterministic, incompressible test data — which
rules out `repeat()`, as step 2 will show — so build it from MD5 output:

```bash
createdb ch13_scratch
psql -d ch13_scratch
```

```sql
\pset null '(null)'

CREATE FUNCTION noise(n int) RETURNS text LANGUAGE sql IMMUTABLE AS
  $$ SELECT substr(string_agg(md5(g::text), ''), 1, n)
     FROM generate_series(1, n/32 + 1) g $$;

CREATE TABLE probe (
    id   int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    body text NOT NULL
);
CREATE INDEX probe_body_idx ON probe (body);
```

`noise(n)` returns exactly `n` characters and is `IMMUTABLE` and deterministic, so your
values match the ones below.

**Task.**

1. Insert `noise(2000)`, then find by bisection the largest `n` that `probe` will accept.
   Read the error message carefully — every number in it means something.
2. Insert `repeat('a', 5000)`. Explain the result.
3. Build a `documents` table with 20,000 rows and a `UNIQUE` index on the body text, then
   insert one oversized document. Fix it three ways, and say what each fix costs you.

**Solution.**

**1 — the boundary.**

```sql
INSERT INTO probe (body) VALUES (noise(2000));   -- INSERT 0 1
INSERT INTO probe (body) VALUES (noise(2692));   -- INSERT 0 1
INSERT INTO probe (body) VALUES (noise(2693));
```

```text
ERROR:  index row size 2712 exceeds btree version 4 maximum 2704 for index "probe_body_idx"
DETAIL:  Index row references tuple (0,3) in relation "probe".
HINT:  Values larger than 1/3 of a buffer page cannot be indexed.
Consider a function index of an MD5 hash of the value, or use full text indexing.
```

The bisection lands between 2,692 and 2,693 characters. Four things in that message earn
their place:

- **`maximum 2704`.** A B-tree page must hold at least three entries so the tree can
  split, which is the `1/3 of a buffer page` in the `HINT`: 8192 / 3, minus page header,
  line pointers and the page's special space, rounded down to an alignment boundary.
- **`index row size 2712`.** The whole entry: the stored value, its varlena length word,
  and 8 bytes of index-tuple header, MAXALIGNed. That is why 2,693 characters of payload
  overflows a 2,704-byte budget.
- **`btree version 4`** is the on-disk format introduced in PostgreSQL 12. The limit is a
  property of the format, not of your table.
- **`Index row references tuple (0,3)`** is the heap location of the offending row, which
  matters when the failure is a `CREATE INDEX` over a table you did not load yourself.

Note that the failure is on `INSERT`. Nothing in `CREATE TABLE` or `CREATE INDEX` warned
you; the column is plain `text` and `text` has no such limit. **The heap will store
values up to 1 GB. The index will not index them.**

**2 — the 5,000-character value that works.**

```sql
INSERT INTO probe (body) VALUES (repeat('a', 5000));
SELECT id, length(body) AS chars, pg_column_size(body) AS stored FROM probe ORDER BY id;
```

```text
 id | chars | stored 
----+-------+--------
  1 |  2000 |   2004
  2 |  2692 |   2692
  4 |  5000 |     69
(3 rows)
```

A 5,000-character value inserted happily while a 2,693-character one was rejected, and the
`stored` column says why: **the limit is enforced against the compressed size.**
`repeat('a', 5000)` is five thousand identical bytes and PGLZ crushes it to 69. The MD5
filler barely compresses at all — 2,000 characters stored in 2,004 bytes, header included.

This is the finding to take away, because it is what makes the failure a production
incident rather than a design-time error. Whether a row can be indexed depends on how well
*that particular value* compresses. You cannot predict it from the column type, you cannot
predict it from a character count, and you cannot rule it out with a representative
sample. It arrives months after launch, from one customer whose document happened to be
high-entropy, on a write path that has worked ten million times.

(`id` 3 is missing: the failed insert consumed an identity value. Sequences are not
transactional — Chapter 20.)

**3 — a real table, and three fixes.**

```sql
CREATE TABLE documents (
    id       int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    doc_ref  text NOT NULL,
    body     text NOT NULL
);
INSERT INTO documents (doc_ref, body)
SELECT 'DOC-' || lpad(i::text, 6, '0'), md5(i::text) || noise(200 + (i % 400))
FROM   generate_series(1, 20000) i;
CREATE UNIQUE INDEX documents_body_key ON documents (body);
ANALYZE documents;
SELECT count(*) AS rows, max(length(body)) AS longest FROM documents;
```

```text
 rows  | longest 
-------+---------
 20000 |     631
(1 row)
```

Twenty thousand rows, longest body 631 characters, unique index built without complaint.
This schema is *fine*, and would stay fine through every test you would think to write.
Then a real document arrives:

```sql
INSERT INTO documents (doc_ref, body) VALUES ('DOC-999999', md5('x') || noise(3000));
```

```text
ERROR:  index row size 3048 exceeds btree version 4 maximum 2704 for index "documents_body_key"
DETAIL:  Index row references tuple (1202,6) in relation "documents".
HINT:  Values larger than 1/3 of a buffer page cannot be indexed.
Consider a function index of an MD5 hash of the value, or use full text indexing.
```

**Fix one: refuse it earlier, with a message somebody can act on.**

```sql
ALTER TABLE documents
  ADD CONSTRAINT documents_body_indexable CHECK (octet_length(body) <= 2600) NOT VALID;
ALTER TABLE documents VALIDATE CONSTRAINT documents_body_indexable;
```

```sql
INSERT INTO documents (doc_ref, body) VALUES ('DOC-999999', md5('x') || noise(3000));
```

```text
ERROR:  new row for relation "documents" violates check constraint "documents_body_indexable"
DETAIL:  Failing row contains (20002, DOC-999999, 9dd4e461268c8034f5c8564e155c67a6c4ca4238a0b923820dcc509a6f75849b...).
```

`octet_length` measures the uncompressed value, so the rule is deterministic where the
index limit is not — no row that passes this `CHECK` can fail the index, whatever it
contains. **Cost:** you have declared that documents over 2,600 bytes do not exist, which
is a product decision dressed as a constraint. It is the right fix when the column really
is a key (an external reference, a natural identifier) and the wrong one when it is a
document that legitimately grows. Note the `NOT VALID` + `VALIDATE` split from Practice
Session 13.2 — the scan runs under `SHARE UPDATE EXCLUSIVE` rather than blocking readers.

**Fix two: index a hash of the value.** Drop fix one first — it would reject the very row
this fix is meant to accept.

```sql
ALTER TABLE documents DROP CONSTRAINT documents_body_indexable;
DROP INDEX documents_body_key;
CREATE UNIQUE INDEX documents_body_key ON documents (md5(body));
```

```sql
INSERT INTO documents (doc_ref, body) VALUES ('DOC-999999', md5('x') || noise(3000));
```

```text
INSERT 0 1
```

It goes in, and uniqueness still holds — on the hash:

```sql
INSERT INTO documents (doc_ref, body) VALUES ('DOC-999998', md5('x') || noise(3000));
```

```text
ERROR:  duplicate key value violates unique constraint "documents_body_key"
DETAIL:  Key (md5(body))=(9b08decfa4f22356cdbb8c960fcba237) already exists.
```

Queries must be written to match the index expression:

```sql
EXPLAIN (COSTS OFF) SELECT doc_ref FROM documents WHERE md5(body) = md5(md5('7') || noise(207));
```

```text
                              QUERY PLAN                              
----------------------------------------------------------------------
 Index Scan using documents_body_key on documents
   Index Cond: (md5(body) = 'ad913c6484b00c75c8bf620f2926a062'::text)
(2 rows)
```

**Cost:** three things. Every caller must remember to write `md5(body) = md5($1)`; a query
that says `WHERE body = $1` gets a sequential scan and no error. You lose range scans,
`ORDER BY` and prefix matching — the index is equality-only. And the uniqueness you are
now enforcing is uniqueness *of the MD5*, not of the text. For a document store that is a
reasonable trade; for anything where a deliberate collision would be worth money, it is
not, and you should be hashing with SHA-256 via `pgcrypto` (Chapter 49) or not hashing.

**Fix three: a hash index.**

```sql
CREATE INDEX documents_body_hash ON documents USING hash (body);
```

```text
CREATE INDEX
```

No error, no size limit, no expression for callers to remember: `WHERE body = $1` uses it
directly. Hash indexes have been crash-safe and WAL-logged since PostgreSQL 10, so the old
advice to avoid them is out of date. **Cost:** equality only, and it cannot back a `UNIQUE`
constraint — so it solves lookup but not the uniqueness requirement the original index
existed for.

**And the fix that is often the real answer.** If what you wanted was to search *inside*
those documents rather than match them whole, none of the three is right: you want a
