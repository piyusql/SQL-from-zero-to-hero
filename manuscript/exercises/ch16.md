# Chapter 16 Exercises — PostgreSQL-Native Types

## Practice Session 16.1 — Tags as array vs junction table

**Goal.** Build the same tagging facts twice — once as a `text[]` column, once as a
junction table — and decide between them on modelling consequences and index support
rather than on taste.

**Setup.** A scratch database. Nothing here touches the sample datasets.

```bash
createdb ch16_tags
psql -d ch16_tags
```

```sql
-- The tag vocabulary, shared by both models.
CREATE TABLE tag (
    name         text    PRIMARY KEY,
    display_name text    NOT NULL,
    retired      boolean NOT NULL DEFAULT false
);

INSERT INTO tag (name, display_name)
SELECT t, initcap(replace(t, '-', ' '))
FROM   unnest(ARRAY['apparel','handloom','cotton','grocery','beverage',
                    'south-indian','home','festive','brass','kitchen',
                    'steel','ayurveda','organic','gifting','clearance',
                    'imported']) AS t;

-- Model A: tags in an array column.
CREATE TABLE catalog_item (
    id   int  PRIMARY KEY,
    name text NOT NULL,
    tags text[] NOT NULL
);

INSERT INTO catalog_item (id, name, tags)
SELECT i, 'Item ' || i,
       ARRAY(SELECT t.name
             FROM   tag t, generate_series(1,1) AS g
             WHERE  (('x' || substr(md5(i || ':' || t.name), 1, 8))::bit(32)::int % 16) = 0)
FROM   generate_series(1, 200000) AS i;

-- Model B: the same facts as a junction table.
CREATE TABLE item (id int PRIMARY KEY, name text NOT NULL);
INSERT INTO item SELECT id, name FROM catalog_item;

CREATE TABLE item_tag (
    item_id int  NOT NULL REFERENCES item(id) ON DELETE CASCADE,
    tag     text NOT NULL REFERENCES tag(name),
    PRIMARY KEY (item_id, tag)
);
INSERT INTO item_tag (item_id, tag)
SELECT c.id, t.tag FROM catalog_item c, unnest(c.tags) AS t(tag);

CREATE INDEX catalog_item_tags_gin ON catalog_item USING gin (tags);
CREATE INDEX item_tag_tag_idx      ON item_tag (tag, item_id);
```

`VACUUM ANALYZE` cannot run inside a transaction block, so give it its own statement:

```sql
VACUUM ANALYZE;
```

Two hundred thousand items, each carrying a hash-chosen subset of sixteen tags. The two
models hold identical facts; the generator is deterministic, so your numbers will match
the ones below.

**Task.**

1. Count the items tagged **both** `handloom` and `cotton`, then the items tagged
   **either**, in each model. Confirm the two models agree.
2. Produce a tag-frequency list from each model.
3. Get `EXPLAIN (COSTS OFF)` for the "both tags" query in each model, and for the array
   model written as `'handloom' = ANY (tags)`. Which access methods are chosen, and why
   does the third one differ?
4. Insert an item tagged `handlooom` — a typo — into each model. What happens?
5. Rename `clearance` to `end-of-season` everywhere, in each model. Count the rows each
   rename had to touch.
6. Mark `end-of-season` as retired and count tag assignments that are still live. Try it
   in each model.
7. Compare total on-disk size.
8. Write down, in two sentences, which model you would ship and what would change your
   mind.

**Solution.**

**1 — the same question, two shapes.**

```sql
SELECT count(*) AS both_tags FROM catalog_item WHERE tags @> ARRAY['handloom','cotton'];
```

```text
 both_tags 
-----------
       734
(1 row)
```

```sql
SELECT count(*) AS both_tags FROM (
  SELECT item_id FROM item_tag WHERE tag IN ('handloom','cotton')
  GROUP  BY item_id HAVING count(*) = 2) x;
```

```text
 both_tags 
-----------
       734
(1 row)
```

The array version says what you mean in one operator. The junction version has to
re-assemble the set per item and count it — `GROUP BY ... HAVING count(*) = 2`, an idiom
called relational division that you will write again every time an AND-of-tags question
comes up. That is the array model's real advantage, and it is about *expression*, not
speed.

"Either tag" is symmetrical and both are easy:

```sql
SELECT count(*) AS either_tag FROM catalog_item WHERE tags && ARRAY['handloom','cotton'];
```

```text
 either_tag 
------------
      24089
(1 row)
```

```sql
SELECT count(DISTINCT item_id) AS either_tag FROM item_tag WHERE tag IN ('handloom','cotton');
```

```text
 either_tag 
------------
      24089
(1 row)
```

**2 — tag frequency.**

```sql
SELECT t.tag, count(*) AS items
FROM   catalog_item c, unnest(c.tags) AS t(tag)
GROUP  BY t.tag
ORDER  BY items DESC
LIMIT  5;
```

```text
    tag    | items 
-----------+-------
 beverage  | 12683
 festive   | 12638
 gifting   | 12605
 home      | 12542
 clearance | 12497
(5 rows)
```

```sql
SELECT tag, count(*) AS items
FROM   item_tag
GROUP  BY tag
ORDER  BY items DESC
LIMIT  5;
```

```text
    tag    | items 
-----------+-------
 beverage  | 12683
 festive   | 12638
 gifting   | 12605
 home      | 12542
 clearance | 12497
(5 rows)
```

Same answer. The array version needs `unnest` to turn the column back into rows first —
you are paying to undo the nesting every time you want to aggregate *across* items. The
junction version is already in that shape.

**3 — the plans.**

```sql
EXPLAIN (COSTS OFF)
SELECT count(*) FROM catalog_item WHERE tags @> ARRAY['handloom','cotton'];
```

```text
                           QUERY PLAN                            
-----------------------------------------------------------------
 Aggregate
   ->  Bitmap Heap Scan on catalog_item
         Recheck Cond: (tags @> '{handloom,cotton}'::text[])
         ->  Bitmap Index Scan on catalog_item_tags_gin
               Index Cond: (tags @> '{handloom,cotton}'::text[])
(5 rows)
```

```sql
EXPLAIN (COSTS OFF)
SELECT count(*) FROM (
  SELECT item_id FROM item_tag WHERE tag IN ('handloom','cotton')
  GROUP  BY item_id HAVING count(*) = 2) x;
```

```text
                             QUERY PLAN                              
---------------------------------------------------------------------
 Aggregate
   ->  HashAggregate
         Group Key: item_tag.item_id
         Filter: (count(*) = 2)
         ->  Index Only Scan using item_tag_tag_idx on item_tag
               Index Cond: (tag = ANY ('{handloom,cotton}'::text[]))
(6 rows)
```

Both are indexed. The GIN index intersects two posting lists and hands up a bitmap of
candidate rows, which the heap then rechecks. The junction index is an ordinary B-tree on
`(tag, item_id)`, and because both columns it needs are in the index, PostgreSQL can
satisfy the scan without touching the table at all — an **index-only scan**. Chapter 33
covers when that is possible and Chapter 34 reads these plans line by line.

Now the version almost everyone writes first:

```sql
EXPLAIN (COSTS OFF)
SELECT count(*) FROM catalog_item WHERE 'handloom' = ANY (tags);
```

```text
                         QUERY PLAN                          
-------------------------------------------------------------
 Finalize Aggregate
   ->  Gather
         Workers Planned: 1
         ->  Partial Aggregate
               ->  Parallel Seq Scan on catalog_item
                     Filter: ('handloom'::text = ANY (tags))
(6 rows)
```

No index, despite `catalog_item_tags_gin` existing and the query asking a containment
question. `= ANY` is a scalar comparison evaluated against each element in turn; GIN
indexes the *array operators* `@>`, `<@` and `&&`, and nothing else. Write
`tags @> ARRAY['handloom']`. This is the single most common way an array column ends up
seq-scanning in production, and it is invisible in code review because the query is
correct.

**4 — the typo.**

```sql
INSERT INTO catalog_item VALUES (200001, 'Jute Shopping Bag', ARRAY['handlooom','eco']);
```

```text
INSERT 0 1
```

```sql
INSERT INTO item VALUES (200001, 'Jute Shopping Bag');
```

```text
INSERT 0 1
```

```sql
INSERT INTO item_tag VALUES (200001, 'handlooom');
```

```text
ERROR:  insert or update on table "item_tag" violates foreign key constraint "item_tag_tag_fkey"
DETAIL:  Key (tag)=(handlooom) is not present in table "tag".
```

The array accepted both `handlooom` and `eco`, neither of which is a tag this business
recognises. There is no foreign key you can put on array elements — PostgreSQL will tell
you so if you try, because `text[]` and `text` are not comparable types — so the
vocabulary is enforced nowhere, or in application code, which is the same thing eighteen
months later. The junction table refused the typo before it existed.

You can approximate the check in the array model with
`CHECK (tags <@ ARRAY[...the whole vocabulary...])`, but now the vocabulary is frozen into
a table constraint and adding a tag is a DDL change under `ACCESS EXCLUSIVE`.

**5 — the global rename.**

```sql
UPDATE catalog_item SET tags = array_replace(tags, 'clearance', 'end-of-season')
WHERE  tags @> ARRAY['clearance'];
```

```text
UPDATE 12497
```

Twelve and a half thousand rows rewritten. Under MVCC each of those is a new row version
plus a GIN index update, and the dead versions wait for autovacuum (Chapters 30 and 37).

```sql
UPDATE tag SET name = 'end-of-season' WHERE name = 'clearance';
```

```text
ERROR:  update or delete on table "tag" violates foreign key constraint "item_tag_tag_fkey" on table "item_tag"
DETAIL:  Key (name)=(clearance) is still referenced from table "item_tag".
```

That error is the junction model telling you it noticed. Declare the intent and the
rename costs one row:

```sql
ALTER TABLE item_tag DROP CONSTRAINT item_tag_tag_fkey;
ALTER TABLE item_tag ADD  CONSTRAINT item_tag_tag_fkey
      FOREIGN KEY (tag) REFERENCES tag(name) ON UPDATE CASCADE;
UPDATE tag SET name = 'end-of-season' WHERE name = 'clearance';
```

```text
ALTER TABLE
ALTER TABLE
UPDATE 1
```

```sql
SELECT count(*) AS rows_carrying_new_name FROM item_tag WHERE tag = 'end-of-season';
```

```text
 rows_carrying_new_name 
------------------------
                  12497
(1 row)
```

`ON UPDATE CASCADE` did update the same 12,497 rows underneath, so the write volume is
comparable. What differs is the *operation*: one statement against one row of a
vocabulary table, atomic and auditable, versus a bulk rewrite of a business table that a
reader of the schema has no way to know is required. And it is better still to use a
surrogate key on `tag` so the display string can change without any cascade at all —
Chapter 20's argument, applied to a lookup table.

**6 — an attribute on a tag.**

```sql
UPDATE tag SET retired = true WHERE name = 'end-of-season';
```

```text
UPDATE 1
```

```sql
SELECT count(*) AS live_tag_assignments
FROM   item_tag jt JOIN tag t ON t.name = jt.tag
WHERE  NOT t.retired;
```

```text
 live_tag_assignments 
----------------------
               186771
(1 row)
```

In the array model there is nowhere to put `retired`. You can keep the `tag` table beside
the array and join to it — which is what the query above does — but the array has no
foreign key to that table, so nothing guarantees every element has a row there, and the
join silently drops the elements that do not. You have built a junction table without the
integrity.

This is the step that decides most real designs. A tag starts as a string and acquires a
display label, a colour, a sort order, an owner and a deprecation date. Each of those is
free in model B and impossible in model A.

**7 — size.**

```sql
SELECT pg_size_pretty(pg_total_relation_size('catalog_item')) AS model_a,
       pg_size_pretty(pg_total_relation_size('item')
                    + pg_total_relation_size('item_tag')
                    + pg_total_relation_size('tag')) AS model_b;
```

```text
 model_a | model_b 
---------+---------
 21 MB   | 35 MB
(1 row)
```

The junction model is about two-thirds larger here, and that is the honest cost: one heap
row plus two index entries per *assignment*, against one inline array per item. At this
scale nobody cares. At a hundred times this scale you would care, and that is when the
array model starts to look like the right answer for genuinely opaque elements.

**8 — the verdict.**

Ship the junction table for anything a human named. Tags, categories, roles, permissions
and labels all acquire attributes, all get renamed, and all need a vocabulary the database
enforces; the array model can do none of that and gives you, in exchange, a nicer
"contains all of" query and a third less disk.

Keep the array for elements that are genuinely opaque to the database and always read with
their row — a captured list of validation warnings, the column headers of an import file,
a fixed set of feature flags your own code owns. The test I use: *if someone asked you to
add a column describing one of these elements, would you have somewhere to put it?* If
not, and you are confident nobody ever will, the array is fine.

Drop the database when you are done:

```bash
dropdb ch16_tags
```

## Practice Session 16.2 — Range types for validity periods

**Goal.** Build a price history in which overlapping validity periods are impossible,
query it as of any date, close and reopen a period safely, and produce a coverage-gap
report with a multirange.

**Setup.** A scratch database. `btree_gist` is a contrib extension shipped with
PostgreSQL; it is what allows the plain-equality `product_id` column to sit in a GiST
exclusion constraint next to the range.

```bash
createdb ch16_ranges
psql -d ch16_ranges
```

```sql
CREATE EXTENSION btree_gist;

CREATE TABLE product_price (
    id         int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_id int           NOT NULL,
    price      numeric(10,2) NOT NULL CHECK (price > 0),
    valid      daterange     NOT NULL,
    CONSTRAINT product_price_no_overlap
        EXCLUDE USING gist (product_id WITH =, valid WITH &&)
);

INSERT INTO product_price (product_id, price, valid) VALUES
 (101,  499.00, daterange('2025-01-01','2025-07-01')),
 (101,  549.00, daterange('2025-07-01','2026-01-01')),
 (101,  599.00, daterange('2026-01-01', NULL)),
 (102, 1299.00, daterange('2025-01-01','2025-04-01')),
 (102, 1149.00, daterange('2025-10-01','2026-03-01')),
 (103,  249.00, daterange('2025-06-01','2025-06-15'));
```

Product 101 has continuous cover and an open-ended current price. Product 102 has a hole.
Product 103 was priced for a fortnight and never since. Multiranges and `range_agg`
require PostgreSQL 14 or newer. Everything here was run on 15.10.

**Task.**

1. Show the stored rows. What happened to the bounds you typed?
2. Which price was in effect for each product on 1 July 2025?
3. Try to insert a price for product 101 covering 15 June to 15 August 2025. Read the
   error carefully.
4. Demonstrate why closed bounds `'[]'` are the wrong default for timestamps.
5. In one transaction, close product 101's open-ended period on 1 April 2026 and open a
   new one at ₹649 from that date.
6. Produce a coverage-gap report for the window 1 Jan 2025 to 1 Mar 2026, one row per gap,
   with the number of days uncovered.
7. Build a 200,000-row price history and show that the index the exclusion constraint
   created answers a point-in-time lookup on its own.

**Solution.**

**1 — canonical bounds.**

```sql
SELECT product_id, price, valid FROM product_price ORDER BY product_id, valid;
```

```text
 product_id |  price  |          valid          
------------+---------+-------------------------
        101 |  499.00 | [2025-01-01,2025-07-01)
        101 |  549.00 | [2025-07-01,2026-01-01)
        101 |  599.00 | [2026-01-01,)
        102 | 1299.00 | [2025-01-01,2025-04-01)
        102 | 1149.00 | [2025-10-01,2026-03-01)
        103 |  249.00 | [2025-06-01,2025-06-15)
(6 rows)
```

You wrote bare two-argument `daterange(...)` calls and PostgreSQL stored `[)` — inclusive
lower bound, exclusive upper. For discrete element types such as `date` and `integer` it
canonicalises every range this way whatever you wrote, so `daterange('2025-01-01','2025-07-01','[]')`
would have been stored as `[2025-01-01,2025-07-02)`. The empty upper bound on row three is
NULL, meaning unbounded: no `9999-12-31` sentinel to filter around, and no risk of someone
comparing against it.

**2 — as of a date.**

```sql
SELECT product_id, price FROM product_price
WHERE  valid @> DATE '2025-07-01'
ORDER  BY product_id;
```

```text
 product_id | price  
------------+--------
        101 | 549.00
(1 row)
```

One row, and it is the new price rather than the old one — 1 July is excluded from
`[2025-01-01,2025-07-01)` and included in `[2025-07-01,2026-01-01)`. That is the whole
reason to prefer half-open periods: the changeover date belongs to exactly one period, by
construction, with no `>= AND <` to get backwards.

Products 102 and 103 are absent because they genuinely had no price that day. With
`valid_from`/`valid_to` columns you would have got the same answer only if the two
predicates were written with matching strictness, and getting one of them wrong returns
either zero rows or two.

**3 — the overlap.**

```sql
INSERT INTO product_price (product_id, price, valid)
VALUES (101, 525.00, daterange('2025-06-15','2025-08-15'));
```

```text
ERROR:  conflicting key value violates exclusion constraint "product_price_no_overlap"
DETAIL:  Key (product_id, valid)=(101, [2025-06-15,2025-08-15)) conflicts with existing key (product_id, valid)=(101, [2025-01-01,2025-07-01)).
```

The `DETAIL` names the row it conflicts with, which is more than most integrity errors
give you. This is the constraint earning its place: "a product has at most one price on
any given day" is now unfalsifiable rather than a convention, and it holds under
concurrency — two sessions inserting overlapping periods at the same moment cannot both
commit, which no application-level check can promise.

**4 — why `'[]'` is the wrong default.**

```sql
SELECT tstzrange('2026-01-01 00:00+05:30','2026-02-01 00:00+05:30','[]')
       && tstzrange('2026-02-01 00:00+05:30','2026-03-01 00:00+05:30','[]') AS closed_bounds,
       tstzrange('2026-01-01 00:00+05:30','2026-02-01 00:00+05:30','[)')
       && tstzrange('2026-02-01 00:00+05:30','2026-03-01 00:00+05:30','[)') AS half_open;
```

```text
 closed_bounds | half_open 
---------------+-----------
 t             | f
(1 row)
```

Two periods that any human would call consecutive **overlap** when written with closed
bounds, because both contain the instant at midnight on 1 February. `tstzrange` is
continuous, so unlike `daterange` it is not canonicalised for you and the bound you wrote
is the bound you got. Under an exclusion constraint the second insert is simply rejected
and you spend an afternoon on it. Write `'[)'`, or omit the argument and take the default,
which is `'[)'`.

**5 — close and reopen atomically.**

```sql
BEGIN;
UPDATE product_price
   SET valid = daterange(lower(valid), DATE '2026-04-01')
 WHERE product_id = 101 AND upper_inf(valid);
INSERT INTO product_price (product_id, price, valid)
VALUES (101, 649.00, daterange('2026-04-01', NULL));
COMMIT;
```

```text
BEGIN
UPDATE 1
INSERT 0 1
COMMIT
```

```sql
SELECT price, valid FROM product_price WHERE product_id = 101 ORDER BY valid;
```

```text
 price  |          valid          
--------+-------------------------
 499.00 | [2025-01-01,2025-07-01)
 549.00 | [2025-07-01,2026-01-01)
 599.00 | [2026-01-01,2026-04-01)
 649.00 | [2026-04-01,)
(4 rows)
```

Three things earn their keep here. `upper_inf(valid)` finds the open-ended row without
hard-coding a date. `lower(valid)` preserves the start rather than restating it. And the
transaction matters more than it looks: run the `INSERT` first and the exclusion
constraint rejects it, because at that instant the old period still runs to infinity. The
constraint is checked per statement, so the order inside the transaction is load-bearing
even though the end state is legal. If you cannot control the order — a bulk load, say —
declare the constraint `DEFERRABLE INITIALLY IMMEDIATE` and `SET CONSTRAINTS ... DEFERRED`
for that transaction (Chapter 15).

**6 — the gap report.**

```sql
SELECT product_id,
       datemultirange(daterange('2025-01-01','2026-03-01')) - range_agg(valid) AS gaps
FROM   product_price
GROUP  BY product_id
ORDER  BY product_id;
```

```text
 product_id |                       gaps                        
------------+---------------------------------------------------
        101 | {}
        102 | {[2025-04-01,2025-10-01)}
        103 | {[2025-01-01,2025-06-01),[2025-06-15,2026-03-01)}
(3 rows)
```

`range_agg` unions a group's ranges into a multirange, merging anything adjacent or
overlapping — which is why product 101's four separate periods collapse to a single
interval and subtracting them from the window leaves `{}`. Product 103 needs two gaps to
describe it, and that is exactly what a multirange is for: the union of disjoint ranges is
not a range, so before PostgreSQL 14 this result had no type to live in.

One row per gap, with `unnest`:

```sql
SELECT g.product_id, lower(u.gap) AS uncovered_from, upper(u.gap) AS uncovered_to,
       upper(u.gap) - lower(u.gap) AS days
FROM  (SELECT product_id,
              datemultirange(daterange('2025-01-01','2026-03-01')) - range_agg(valid) AS gaps
       FROM   product_price GROUP BY product_id) g,
      unnest(g.gaps) AS u(gap)
ORDER BY g.product_id, uncovered_from;
```

```text
 product_id | uncovered_from | uncovered_to | days 
------------+----------------+--------------+------
        102 | 2025-04-01     | 2025-10-01   |  183
        103 | 2025-01-01     | 2025-06-01   |  151
        103 | 2025-06-15     | 2026-03-01   |  259
(3 rows)
```

Subtracting `date` values yields an integer number of days, and because the bounds are
half-open the subtraction is the day count with no off-by-one correction. Write the
equivalent as a window query with `lag()` and you will need twenty lines and three
attempts at the boundaries.

**7 — the index you already have.**

```sql
CREATE TABLE price_history (
    id         int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_id int           NOT NULL,
    price      numeric(10,2) NOT NULL,
    valid      daterange     NOT NULL,
    EXCLUDE USING gist (product_id WITH =, valid WITH &&)
);

INSERT INTO price_history (product_id, price, valid)
SELECT p, 100 + (p % 900) + k,
       daterange(DATE '2024-01-01' + (k * 120), DATE '2024-01-01' + ((k + 1) * 120))
FROM   generate_series(1, 50000) AS p, generate_series(0, 3) AS k;
```

```sql
VACUUM ANALYZE price_history;
```

```sql
SELECT product_id, price, valid
FROM   price_history
WHERE  product_id = 4242 AND valid @> DATE '2024-09-01';
```

```text
 product_id | price  |          valid          
------------+--------+-------------------------
       4242 | 744.00 | [2024-08-28,2024-12-26)
(1 row)
```

```sql
EXPLAIN (COSTS OFF)
SELECT product_id, price FROM price_history
WHERE  product_id = 4242 AND valid @> DATE '2024-09-01';
```

```text
                              QUERY PLAN                               
-----------------------------------------------------------------------
 Index Scan using price_history_product_id_valid_excl on price_history
   Index Cond: ((product_id = 4242) AND (valid @> '2024-09-01'::date))
(2 rows)
```

The index named in the plan is the one the `EXCLUDE` clause created. You declared a
business rule and got the access path for the most common query against this table for
free — both predicates served by one index, no heap scan of the product's history. That
is unusual: most constraints cost you something. This one pays.

It is not free on disk, though:

```sql
SELECT indexname, pg_size_pretty(pg_relation_size(indexname::regclass)) AS size
FROM   pg_indexes WHERE tablename = 'price_history' ORDER BY indexname;
```

```text
              indexname              |  size   
-------------------------------------+---------
 price_history_pkey                  | 4408 kB
 price_history_product_id_valid_excl | 10 MB
(2 rows)
```

A GiST index over `(int, daterange)` is more than twice the size of the B-tree over a
single `int`, and every insert must probe it for conflicts before the row is accepted.

Drop the database when you are done:

```bash
dropdb ch16_ranges
```

## Practice Session 16.3 — A `DOMAIN` for validated email

**Goal.** Build a reusable, self-documenting email type with named constraints, load a
thousand real addresses through it, and find the three places a domain stops protecting
you.

**Setup.** A scratch database, plus the small `retail` dataset from Practice Session 2.3
as a source of real addresses.

```bash
createdb ch16_email
psql -d ch16_email
```

```sql
CREATE DOMAIN email_address AS text
    CONSTRAINT email_address_shape
      CHECK (VALUE ~ '^[^@[:space:]]+@[^@[:space:]]+\.[A-Za-z]{2,}$')
    CONSTRAINT email_address_lowercase
      CHECK (VALUE = lower(VALUE))
    CONSTRAINT email_address_length
      CHECK (length(VALUE) <= 254);

CREATE TABLE app_user (
    id    int  PRIMARY KEY,
    name  text NOT NULL,
    email email_address NOT NULL UNIQUE
);
```

Then pipe the real addresses across from `retail`, from a shell prompt rather than from
inside `psql`:

```bash
psql -d retail -Atc "COPY (SELECT id, name, email FROM customers ORDER BY id) TO STDOUT" \
 | psql -d ch16_email -c "COPY app_user (id, name, email) FROM STDIN"
```

```text
COPY 1000
```

**Task.**

1. Confirm all 1,000 addresses loaded, and list the domain's constraints as the database
   holds them.
2. Find which named constraint rejects each of: an address with a space in it, a
   mixed-case address, an address with no dot in the domain part.
3. Reuse the domain on a second table with no extra code, and try to insert a mixed-case
   address.
4. A colleague proposes validating against a whitelist of known TLDs. Test that idea
   against the loaded data.
5. Ask whether a `NOT NULL` domain guarantees non-null values in query results.
6. Tighten the domain after the fact: forbid plus-addressing (`user+tag@host`), discover
   existing data violates it, apply it with `NOT VALID`, then decide whether the rule was
   a good idea at all.

**Solution.**

**1 — what loaded, and what the rules are.**

```sql
SELECT count(*) AS loaded FROM app_user;
```

```text
 loaded 
--------
   1000
(1 row)
```

Every address passed. `COPY` runs the domain's checks on every value like any other
insert, so a single bad row would have aborted the whole load — which is the behaviour you
want for a validated type, and the reason to validate on the way in rather than
discovering it during a migration two years later.

```sql
SELECT conname, pg_get_constraintdef(oid) AS definition
FROM   pg_constraint
WHERE  contypid = 'email_address'::regtype
ORDER  BY conname;
```

```text
         conname         |                               definition                                
-------------------------+-------------------------------------------------------------------------
 email_address_length    | CHECK ((length(VALUE) <= 254))
 email_address_lowercase | CHECK ((VALUE = lower(VALUE)))
 email_address_shape     | CHECK ((VALUE ~ '^[^@[:space:]]+@[^@[:space:]]+\.[A-Za-z]{2,}$'::text))
(3 rows)
```

Three separately named constraints rather than one big `AND`. That is deliberate: the name
is what the error message carries, so a rejected signup tells you *which* rule it broke
without anyone reading the regex. `\dD email_address` shows the same thing in one line if
you prefer.

**2 — which rule fires.**

```sql
SELECT 'rajesh kumar@delhi-mail.example'::email_address;
```

```text
ERROR:  value for domain email_address violates check constraint "email_address_shape"
```

```sql
SELECT 'Rajesh.Kumar@delhi-mail.example'::email_address;
```

```text
ERROR:  value for domain email_address violates check constraint "email_address_lowercase"
```

```sql
SELECT 'rajesh.kumar@delhi-mail'::email_address;
```

```text
ERROR:  value for domain email_address violates check constraint "email_address_shape"
```

Note that no table is involved in any of these. A domain constrains a *type*, so a bare
cast is checked, and so is every function parameter and return value declared with it.
A column `CHECK` could not do that.

**3 — reuse.**

```sql
CREATE TABLE newsletter_signup (
    id    int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email email_address NOT NULL,
    added timestamptz   NOT NULL DEFAULT now()
);
```

```sql
INSERT INTO newsletter_signup (email) VALUES ('MEERA.BANERJEE@kolkata-mail.example');
```

```text
ERROR:  value for domain email_address violates check constraint "email_address_lowercase"
```

One word in the column definition and the second table has the same three rules, the same
error messages and the same meaning. With column `CHECK`s you would have copied the regex,
and the two copies would have diverged the first time one of them was fixed.

This also exposes the domain's hardest limit: **it rejects, it does not normalise.** There
is no way to make a domain lower-case the value on the way in. If you want
`MEERA.BANERJEE@...` accepted and stored folded, that is a `BEFORE INSERT OR UPDATE`
trigger or a generated column (Chapters 43 and 23), and the domain's job is then to verify
the result rather than to fix the input. Decide which behaviour you want before you write
either — silently rewriting user input has its own failure modes.

**4 — the TLD whitelist.**

```sql
SELECT substring(email FROM '\.([A-Za-z]+)$') AS tld, count(*) AS customers
FROM   app_user GROUP BY 1;
```

```text
   tld   | customers 
---------+-----------
 example |      1000
(1 row)
```

```sql
SELECT count(*) AS rejected_by_a_tld_whitelist
FROM   app_user
WHERE  substring(email FROM '\.([A-Za-z]+)$') NOT IN ('com','org','net','in','co');
```

```text
 rejected_by_a_tld_whitelist 
-----------------------------
                        1000
(1 row)
```

Every single address in the dataset would be rejected. The sample data uses `.example`,
which is reserved by RFC 2606 precisely so that documentation and test fixtures cannot
resolve to a real host — and a five-entry whitelist has never heard of it.

That is the argument in miniature, and it is not about `.example`. There are well over a
thousand TLDs and the list changes; any whitelist you ship is a list of customers you will
turn away, and the people who report it are a self-selecting minority of the ones you
lost. **Validate the shape, not the vocabulary.** The only real proof that an address
works is a message that arrives, so send a confirmation and let the domain stop the
typos — a missing `@`, a trailing comma, a pasted display name.

**5 — the `NOT NULL` hole.**

```sql
SELECT r.id AS requested_id, u.email,
       u.email IS NULL    AS email_is_null,
       pg_typeof(u.email) AS declared_type
FROM   (VALUES (1),(99999)) AS r(id)
LEFT   JOIN app_user u ON u.id = r.id
ORDER  BY r.id;
```

```text
 requested_id |          email           | email_is_null | declared_type 
--------------+--------------------------+---------------+---------------
            1 | customer1@vyapar.example | f             | email_address
        99999 | (null)                   | t             | email_address
(2 rows)
```

`app_user.email` is `NOT NULL`, and the second row is NULL of type `email_address` anyway.
A constraint governs values *stored in a column*; an outer join manufactures a row that was
never stored. The same happens with a scalar subquery over no rows, and with `UNION` against
a nullable column.

This matters for a domain specifically because people declare `CREATE DOMAIN ... NOT NULL`
and then treat the type as non-nullable in generated client code. It is not. Put `NOT NULL`
on the column, where every tool understands it, and keep the domain for value shape.

**6 — tightening a live domain.**

```sql
INSERT INTO app_user (id, name, email) VALUES
 (1001, 'Anita Rao',      'anita.rao+deals@bengaluru-mail.example'),
 (1002, 'Harpreet Singh', 'harpreet.singh@chandigarh-mail.example');
```

```text
INSERT 0 2
```

```sql
ALTER DOMAIN email_address
  ADD CONSTRAINT email_address_no_plus CHECK (VALUE !~ '\+');
```

```text
ERROR:  column "email" of table "app_user" contains values that violate the new constraint
```

Adding a constraint to a domain scans every column of that type in the database and
refuses if any value fails — all or nothing, and the message names the first table it
found rather than listing everything wrong. On a large table that scan is also a long
`ACCESS EXCLUSIVE` hold. The same `NOT VALID` escape hatch you used for foreign keys in
Chapter 15 applies:

```sql
ALTER DOMAIN email_address
  ADD CONSTRAINT email_address_no_plus CHECK (VALUE !~ '\+') NOT VALID;
```

```text
ALTER DOMAIN
```

```sql
INSERT INTO app_user (id, name, email)
VALUES (1003, 'Priya Menon', 'priya.menon+receipts@kochi-mail.example');
```

```text
ERROR:  value for domain email_address violates check constraint "email_address_no_plus"
```

New writes are checked from this moment; history is not. That is the useful asymmetry —
you stop the bleeding immediately and clean up on your own schedule. Running `VALIDATE`
before the cleanup tells you so:

```sql
ALTER DOMAIN email_address VALIDATE CONSTRAINT email_address_no_plus;
```

```text
ERROR:  column "email" of table "app_user" contains values that violate the new constraint
```

**Now the part the task actually asked.** Was the rule a good idea? No. Plus-addressing is
valid under RFC 5321, Gmail and Fastmail both implement it, and users rely on it to tag
where an address was given out. Banning it rejects real customers and teaches them to give
you a throwaway address instead. The right move is to drop the constraint, not to clean
the data:

```sql
ALTER DOMAIN email_address DROP CONSTRAINT email_address_no_plus;
```

```text
ALTER DOMAIN
```

```sql
INSERT INTO app_user (id, name, email)
VALUES (1003, 'Priya Menon', 'priya.menon+receipts@kochi-mail.example');
```

```text
INSERT 0 1
```

Which is the lesson worth keeping from all six steps. A domain makes a rule cheap to
declare, cheap to reuse and cheap to name — and that is exactly why it is easy to encode a
rule that is wrong. Every constraint you add to an `email_address` domain beyond *it has
one `@`, it has a dot after it, and it has no whitespace* is a bet that you know more about
the world's addressing than the people trying to give you money.

Drop the database when you are done:

```bash
dropdb ch16_email
```
