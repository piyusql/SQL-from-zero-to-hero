# Chapter 21 Exercises — Structuring a New Enterprise Database

## Practice Session 21.1 — Lay out a multi-schema database from requirements

**Goal.** Turn a paragraph of business requirements into schemas, roles and privileges, and
prove with real error messages that every role can do what it should and nothing else.

**Setup.** The small `retail` dataset is only read. Roles are cluster-wide, so every role
here is prefixed `ch21_w1_`; the last step drops them.

```bash
psql -d retail -Atq -c "\copy (SELECT name, email, city FROM customers ORDER BY id) TO '/tmp/ch21_ws_customers.csv' CSV"
psql -d retail -Atq -c "\copy (SELECT customer_id, placed_at, total_amount FROM orders ORDER BY id) TO '/tmp/ch21_ws_orders.csv' CSV"
createdb ch21_ws1
psql -d ch21_ws1
```

**The requirements.** Sahyadri Stores, Pune, is moving to a new PostgreSQL 15 database:

1. Customers and orders are operational data. The application reads and writes them, may
   never delete them and must not be able to drop or truncate the tables.
2. Every change is recorded. The application may add audit rows and never alter or remove
   one. Auditors read the audit trail and must not see operational tables.
3. A nightly customer file arrives from a partner. A loader role receives it into a landing
   area and must have no access to operational data.
4. Analysts read a revenue-by-city summary and never the base tables.
5. One role runs schema changes and owns every object except the landing area.

**Task.**

1. On paper, write a table of schemas, roles and the privileges each role holds on each
   schema. Name five roles: owner, application, read-only, ETL, auditor.
2. Create the roles and schemas, the default privileges, and the tables
   `app.customers(id, name, email, city)`, `app.orders(id, customer_id, placed_at,
   total_amount)` and `audit.change_log`. Load the two CSV files as the owner.
3. Close the `TEMP` door: PostgreSQL grants `TEMP` on every database to `PUBLIC`, which
   Chapter 21 uses to hijack an unpinned function. Revoke it.
4. Print a privilege matrix, one row per role and one column per table, from
   `has_table_privilege`.
5. Connect as each role and attempt at least eight actions that must fail. Record the exact
   error for each.
6. Create a table as `postgres` inside `app` and show the application cannot read it. Explain
   why, then fix it the way you would in a migration.
7. Build `reporting.revenue_by_city`. Show the analyst can read it, then switch the view to
   `security_invoker` and show what happens.

**Solution.**

The roles, schemas and grants. `staging` belongs to the loader, everything else to the owner:

```sql
\pset null '(null)'
CREATE ROLE ch21_w1_owner LOGIN;
CREATE ROLE ch21_w1_app   LOGIN;
CREATE ROLE ch21_w1_ro    LOGIN;
CREATE ROLE ch21_w1_etl   LOGIN;
CREATE ROLE ch21_w1_aud   LOGIN;

CREATE SCHEMA app       AUTHORIZATION ch21_w1_owner;
CREATE SCHEMA audit     AUTHORIZATION ch21_w1_owner;
CREATE SCHEMA reporting AUTHORIZATION ch21_w1_owner;
CREATE SCHEMA staging   AUTHORIZATION ch21_w1_etl;

GRANT USAGE ON SCHEMA app        TO ch21_w1_app;
GRANT USAGE ON SCHEMA audit      TO ch21_w1_app, ch21_w1_aud;
GRANT USAGE ON SCHEMA reporting  TO ch21_w1_ro;

ALTER DEFAULT PRIVILEGES FOR ROLE ch21_w1_owner IN SCHEMA app
  GRANT SELECT, INSERT, UPDATE ON TABLES TO ch21_w1_app;
ALTER DEFAULT PRIVILEGES FOR ROLE ch21_w1_owner IN SCHEMA app
  GRANT USAGE ON SEQUENCES TO ch21_w1_app;
ALTER DEFAULT PRIVILEGES FOR ROLE ch21_w1_owner IN SCHEMA audit
  GRANT INSERT ON TABLES TO ch21_w1_app;
ALTER DEFAULT PRIVILEGES FOR ROLE ch21_w1_owner IN SCHEMA audit
  GRANT SELECT ON TABLES TO ch21_w1_aud;
ALTER DEFAULT PRIVILEGES FOR ROLE ch21_w1_owner IN SCHEMA reporting
  GRANT SELECT ON TABLES TO ch21_w1_ro;

REVOKE TEMPORARY ON DATABASE ch21_ws1 FROM PUBLIC;

\c ch21_ws1 ch21_w1_owner
CREATE TABLE app.customers (
    id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL, email text NOT NULL, city text);
CREATE TABLE app.orders (
    id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id  int NOT NULL REFERENCES app.customers,
    placed_at    timestamptz NOT NULL,
    total_amount numeric(12,2) NOT NULL CHECK (total_amount >= 0));
CREATE TABLE audit.change_log (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    table_name text NOT NULL, row_id bigint NOT NULL, action text NOT NULL,
    changed_by name NOT NULL DEFAULT session_user,
    changed_at timestamptz NOT NULL DEFAULT now());
\copy app.customers (name, email, city) FROM '/tmp/ch21_ws_customers.csv' CSV
\copy app.orders (customer_id, placed_at, total_amount) FROM '/tmp/ch21_ws_orders.csv' CSV
SELECT (SELECT count(*) FROM app.customers) AS customers, (SELECT count(*) FROM app.orders) AS orders;
```

```text
 customers | orders
-----------+--------
      1000 |   2500
(1 row)
```

Default privileges were declared **before** the tables existed, so no table needed a
hand-written `GRANT`. The matrix, from a superuser session, with one letter per privilege
(`r` read, `a` append, `w` update, `d` delete, `D` truncate) and `-` for none:

```sql
\c ch21_ws1 postgres
SELECT role,
       max(privs) FILTER (WHERE tbl = 'app.customers')     AS app_customers,
       max(privs) FILTER (WHERE tbl = 'audit.change_log')  AS audit_log
FROM (
  SELECT r.role, t.tbl,
         coalesce(string_agg(p.abbr, '' ORDER BY p.ord)
                  FILTER (WHERE has_table_privilege(r.role, t.tbl, p.priv)), '-') AS privs
  FROM unnest(ARRAY['ch21_w1_owner','ch21_w1_app','ch21_w1_ro','ch21_w1_etl','ch21_w1_aud']) r(role)
  CROSS JOIN unnest(ARRAY['app.customers','audit.change_log']) t(tbl)
  CROSS JOIN (VALUES (1,'SELECT','r'),(2,'INSERT','a'),(3,'UPDATE','w'),(4,'DELETE','d'),(5,'TRUNCATE','D')) p(ord,priv,abbr)
  GROUP BY r.role, t.tbl
) x
GROUP BY role ORDER BY role;
```

```text
     role      | app_customers | audit_log
---------------+---------------+-----------
 ch21_w1_app   | raw           | a
 ch21_w1_aud   | -             | r
 ch21_w1_etl   | -             | -
 ch21_w1_owner | rawdD         | rawdD
 ch21_w1_ro    | -             | -
(5 rows)
```

Read it against the requirements. The application holds `raw` on customers (read, append, update; no delete, no truncate) and only `a` on the audit log: it can add and cannot even read. The auditor holds `r` on the audit log and `-` on customers. The loader and the analyst hold nothing on either. The owner holds everything and is the only role that can change structure. In order: the application's insert works and its `DELETE`, `TRUNCATE`, `DROP` and audit
`UPDATE` are refused, and it cannot read the audit trail it writes. The temp-table attempt
fails because of the `REVOKE TEMPORARY`, and `CREATE SCHEMA` is refused because only
`CREATE` on the database allows it. The auditor reads the audit log and is refused
customers. The loader is refused `app` but can create in its own `staging`. The analyst is
refused `app`.

Default privileges cover objects created **by the owner role, afterwards**. Create a table
as the wrong role:

```sql
\c ch21_ws1 postgres
CREATE TABLE app.made_by_postgres (id int);
\c ch21_ws1 ch21_w1_app
SELECT count(*) FROM app.made_by_postgres;
\c ch21_ws1 postgres
DROP TABLE app.made_by_postgres;
\c ch21_ws1 ch21_w1_owner
CREATE TABLE app.made_by_owner (id int);
\c ch21_ws1 ch21_w1_app
SELECT count(*) FROM app.made_by_owner;
```

```text
ERROR:  permission denied for table made_by_postgres
 count
-------
     0
(1 row)
```

The first fails because the default-privilege rule names `ch21_w1_owner` and `postgres`
is a different creator; the second works. The fix in a migration is not a `GRANT` after
the fact but running the migration as the owner. Now the analyst's view:

```sql
\c ch21_ws1 ch21_w1_owner
CREATE VIEW reporting.revenue_by_city AS
SELECT coalesce(c.city, 'unknown') AS city, count(*) AS orders, sum(o.total_amount) AS revenue
FROM   app.orders o JOIN app.customers c ON c.id = o.customer_id
GROUP  BY 1;

\c ch21_ws1 ch21_w1_ro
SELECT * FROM reporting.revenue_by_city ORDER BY revenue DESC LIMIT 3;

\c ch21_ws1 ch21_w1_owner
ALTER VIEW reporting.revenue_by_city SET (security_invoker = true);
\c ch21_ws1 ch21_w1_ro
SELECT * FROM reporting.revenue_by_city ORDER BY revenue DESC LIMIT 3;
```

```text
    city     | orders |  revenue
-------------+--------+-----------
 unknown     |    307 | 465684.20
 Bhubaneswar |    154 | 242128.87
 Hyderabad   |    136 | 204241.20
(3 rows)

ERROR:  permission denied for table orders
```

A default view runs with its owner's rights, so the analyst reads through it without
touching `app`. With `security_invoker` (PostgreSQL 15) the check moves to the caller and
the same query is refused. Choose deliberately: the default is the narrow door, and
`security_invoker` is for views over row-level-security tables where the policy must see
who is asking.

Clean up, roles included:

```bash
for r in ch21_w1_owner ch21_w1_app ch21_w1_ro ch21_w1_etl ch21_w1_aud; do psql -X -q -d ch21_ws1 -c "DROP OWNED BY $r"; done
dropdb ch21_ws1
for r in ch21_w1_owner ch21_w1_app ch21_w1_ro ch21_w1_etl ch21_w1_aud; do psql -X -q -d postgres -c "DROP ROLE $r"; done
rm -f /tmp/ch21_ws_customers.csv /tmp/ch21_ws_orders.csv
```

## Practice Session 21.2 — Three tenant models compared

**Goal.** Build the same three-table product under shared tables, schema-per-tenant and
database-per-tenant, and compare them on integrity, migration cost, cross-tenant reporting,
lock footprint and physical locality, using only counts and catalog facts.

**Setup.** The small `retail` dataset supplies the rows. Customers are split into three
tenants by `id % 3`. Nothing here times anything.

```bash
psql -d retail -Atq -c "\copy (SELECT id, name, city FROM customers ORDER BY id) TO '/tmp/ch21_ws2_customers.csv' CSV"
psql -d retail -Atq -c "\copy (SELECT id, customer_id, placed_at, total_amount FROM orders ORDER BY id) TO '/tmp/ch21_ws2_orders.csv' CSV"
createdb ch21_ws2
psql -d ch21_ws2
```

**Task.**

1. Shared model: schema `shared` with `tenants`, `customers` and `orders` whose keys and
   foreign key both include `tenant_id`. Tenant of a customer is `1 + id % 3`; an order
   follows its customer.
2. Schema-per-tenant model: schemas `t1`, `t2`, `t3` with `customers` and `orders` each,
   loaded with the same rows.
3. Compare catalog footprint: tables and total relations per schema.
4. Attempt a cross-tenant order in both models. Report both errors.
5. Count the statements to add one column to `orders` in each model, and generate them.
6. Produce revenue per tenant in both models. Which query grows with tenant count?
7. Drop all tenant schemas inside one transaction and count the locks held. Divide by the
   tenant count and use `max_locks_per_transaction * max_connections` to state at what
   tenant count that transaction would run out of lock slots. Label it arithmetic.
8. Show how many heap pages tenant 2's orders occupy in the shared table against a table of
   their own.
9. Create an empty database and report its size and catalog rows.
10. Choose a model for each: (a) 4,000 small tenants, self-serve sign-up; (b) 25 hospital
    groups with contractual data segregation and per-customer restore; (c) 2 very large
    tenants and 300 tiny ones.

**Solution.**

```sql
\pset null '(null)'
CREATE TEMP TABLE raw_c (id int, name text, city text);
CREATE TEMP TABLE raw_o (id int, customer_id int, placed_at timestamptz, total_amount numeric(12,2));
\copy raw_c FROM '/tmp/ch21_ws2_customers.csv' CSV
\copy raw_o FROM '/tmp/ch21_ws2_orders.csv' CSV

CREATE SCHEMA shared;
CREATE TABLE shared.tenants (tenant_id int PRIMARY KEY, name text NOT NULL);
INSERT INTO shared.tenants VALUES (1, 'Tenant One'), (2, 'Tenant Two'), (3, 'Tenant Three');
CREATE TABLE shared.customers (
    tenant_id int NOT NULL REFERENCES shared.tenants, id int NOT NULL, name text NOT NULL, city text,
    PRIMARY KEY (tenant_id, id));
CREATE TABLE shared.orders (
    tenant_id int NOT NULL, id int NOT NULL, customer_id int NOT NULL,
    placed_at timestamptz NOT NULL, total_amount numeric(12,2) NOT NULL,
    PRIMARY KEY (tenant_id, id),
    FOREIGN KEY (tenant_id, customer_id) REFERENCES shared.customers (tenant_id, id));
INSERT INTO shared.customers SELECT 1 + id % 3, id, name, city FROM raw_c;
INSERT INTO shared.orders    SELECT 1 + customer_id % 3, id, customer_id, placed_at, total_amount FROM raw_o;

DO $$ BEGIN
  FOR t IN 1..3 LOOP
    EXECUTE format('CREATE SCHEMA t%s', t);
    EXECUTE format('CREATE TABLE t%s.customers (id int PRIMARY KEY, name text NOT NULL, city text)', t);
    EXECUTE format('CREATE TABLE t%s.orders (id int PRIMARY KEY, customer_id int NOT NULL REFERENCES t%s.customers, placed_at timestamptz NOT NULL, total_amount numeric(12,2) NOT NULL)', t, t);
    EXECUTE format('INSERT INTO t%s.customers SELECT id, name, city FROM raw_c WHERE 1 + id %% 3 = %s', t, t);
    EXECUTE format('INSERT INTO t%s.orders SELECT id, customer_id, placed_at, total_amount FROM raw_o WHERE 1 + customer_id %% 3 = %s', t, t);
  END LOOP;
END $$;

SELECT n.nspname AS schema,
       count(*) FILTER (WHERE c.relkind = 'r') AS tables,
       count(*) AS relations
FROM   pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE  n.nspname IN ('shared', 't1', 't2', 't3') GROUP BY 1 ORDER BY 1;
```

```text
 schema | tables | relations
--------+--------+-----------
 shared |      3 |         6
 t1     |      2 |         4
 t2     |      2 |         4
 t3     |      2 |         4
(4 rows)
```

The tenant schemas together hold 6 tables and 12 relations against the shared schema's 3 and 6 (the shared model has a `tenants` table the others do not), and each further tenant adds 2 tables and 4 relations while the shared model adds none. Now the cross-tenant order. Customer 5 belongs to tenant `1 + 5 % 3 = 3`; try to give tenant 1 an order for them:

```sql
INSERT INTO shared.orders VALUES (1, 900001, 5, now(), 100);
INSERT INTO t1.orders VALUES (900001, 5, now(), 100);
```

```text

DETAIL:  Key (tenant_id, customer_id)=(1, 5) is not present in table "customers".
ERROR:  insert or update on table "orders" violates foreign key constraint "orders_customer_id_fkey"
DETAIL:  Key (customer_id)=(5) is not present in table "customers".
```

Both refuse. The shared model refuses because its foreign key includes `tenant_id`; the
schema model refuses because customer 5 is simply not in `t1.customers`. The shared
model's protection is a design choice you must make, the schema model's is free. Migration
fan-out and cross-tenant reporting:

```sql

FROM   information_schema.tables
WHERE  table_name = 'orders' AND table_schema IN ('t1', 't2', 't3') ORDER BY 1;

SELECT tenant_id, count(*) AS orders, sum(total_amount) AS revenue
FROM   shared.orders GROUP BY 1 ORDER BY 1;

SELECT 1 AS tenant_id, count(*) AS orders, sum(total_amount) AS revenue FROM t1.orders
UNION ALL SELECT 2, count(*), sum(total_amount) FROM t2.orders
UNION ALL SELECT 3, count(*), sum(total_amount) FROM t3.orders;
```

```text
         1 |    816 | 1175449.60
```

The shared model adds a column with one statement and totals with one `GROUP BY`. The
schema model needs one statement per tenant (three shown, five hundred for five hundred
tenants) and a `UNION ALL` with one arm per tenant, which has to be regenerated whenever a
tenant is added. Same totals both ways. Now the lock footprint, measured on a rollback:

```sql
BEGIN;
DROP SCHEMA t1 CASCADE;
DROP SCHEMA t2 CASCADE;
DROP SCHEMA t3 CASCADE;
SELECT count(*) AS locks_held FROM pg_locks WHERE pid = pg_backend_pid() \gset
ROLLBACK;
SELECT :locks_held AS locks_held, :locks_held / 3.0 AS per_tenant,
       current_setting('max_locks_per_transaction')::int * current_setting('max_connections')::int AS slots,
       (current_setting('max_locks_per_transaction')::int * current_setting('max_connections')::int
        / (:locks_held / 3.0))::int AS tenants_at_slot_limit;
```

```text
 locks_held |     per_tenant      | slots | tenants_at_slot_limit
------------+---------------------+-------+-----------------------
         57 | 19.0000000000000000 |  6400 |                   337
(1 row)
```

That last column is **arithmetic, not a measurement**: it assumes the whole lock table is free for one transaction, which on a busy server it is not, and I did not try to exhaust it. The measured part is the per-tenant lock count, 19 for a tenant of two tables and their indexes; I expect it to grow with the tables per tenant, so a realistic schema would reach the limit at far fewer tenants than printed, but I did not measure that. Whole-database operations that take a lock per object, a single-transaction drop or a dump, are what would hit this first. Locality:

```sql
SELECT count(*) AS orders,
       count(DISTINCT (ctid::text::point)[0]) AS heap_pages_touched,
       pg_relation_size('shared.orders') / 8192 AS table_pages
FROM   shared.orders WHERE tenant_id = 2;
SELECT count(*) AS orders, pg_relation_size('t2.orders') / 8192 AS pages_in_own_table FROM t2.orders;
```

```text
 orders | heap_pages_touched | table_pages
--------+--------------------+-------------
    850 |                 19 |          19
(1 row)

 orders | pages_in_own_table
--------+--------------------
    850 |                  6
(1 row)
```

Tenant 2's 850 orders touch all 19 of the shared table's pages, while in a table of their own they occupy 6. This is the physical cost of sharing a heap: reading a small tenant's rows touches pages full of other tenants' data. Partitioning by tenant (Chapter 38) restores the locality inside a shared model. The last model:

```sql
CREATE DATABASE ch21_ws2_probe;

       (SELECT count(*) FROM pg_class) AS pg_class_rows;
\c ch21_ws2

```

```text

----------------+---------------

(1 row)

-------------------------

```

An empty database carries a fixed cost before it holds a row, and needs its own connection
pool. Answers to the scenarios:

- **(a) 4,000 small self-serve tenants:** shared tables with composite keys and row-level
  security. Schemas would be 4,000 fan-out migrations; databases, 4,000 pools.
- **(b) 25 hospital groups with contractual segregation and per-customer restore:**
  database-per-tenant. Twenty-five is well inside its ceiling, and restore-per-customer is
  the whole reason to pay for it. Schema-per-tenant is the fallback if the cluster count
  must stay at one.
- **(c) 2 huge tenants and 300 tiny ones:** hybrid. The two whales get their own
  databases; the 300 share tables. A single shared table would give the whales' scans to
  everyone.

## Practice Session 21.3 — First versioned migration

**Goal.** Build a psql-only migration runner, apply three migrations to two environments,
and prove it is idempotent, atomic, tamper-evident and able to detect drift.

**Setup.** Two empty databases and an empty directory.

```bash
mkdir ch21_ws3 && cd ch21_ws3 && mkdir migrations
createdb ch21_ws3_dev
createdb ch21_ws3_prod
psql -d ch21_ws3_dev
```

**Task.**

1. Write `migrate.sh DBNAME` that keeps an `ops.schema_migrations` table of `version`,
   `checksum`, `applied_at`, applies each `migrations/V###__name.sql` not yet recorded,
   in order, one transaction per migration together with its bookkeeping row, and stops on
   the first error.
2. Write `V001__schemas.sql` (schemas `app`, `audit`), `V002__customers.sql` (a
   `customers` table with **named** primary key and a `CHECK`) and `V003__orders.sql`
   (an `orders` table with a named foreign key). Apply them to dev, then again, then to prod.
3. Write `V004__bad.sql` that creates a table and then fails. Show that the table does not
   exist afterwards and that nothing was recorded.
4. Edit an applied migration and show the runner refuses.
5. Write a schema fingerprint query. Show dev and prod agree, then hotfix prod by hand and
   show they differ.
6. Add `V005__index.sql` containing `CREATE INDEX CONCURRENTLY`. Show what your runner
   does, and extend the runner so that a file named `*.notx.sql` is applied outside a
   transaction.
7. State what your extension gives up.

**Solution.**

The runner and three migrations. `-1` puts the file and the bookkeeping `INSERT` in one
transaction:

```bash
cat > migrate.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
db=${1:?database name}; dir=${2:-migrations}
q() { psql -X -q -v ON_ERROR_STOP=1 -d "$db" "$@"; }

q -c "CREATE SCHEMA IF NOT EXISTS ops" \
  -c "CREATE TABLE IF NOT EXISTS ops.schema_migrations (
        version text PRIMARY KEY, checksum text NOT NULL,
        applied_at timestamptz NOT NULL DEFAULT now())"

for f in "$dir"/V[0-9]*__*.sql; do
  v=$(basename "$f" .sql)
  sum=$(shasum -a 256 "$f" | cut -d' ' -f1)
  old=$(q -At -c "SELECT checksum FROM ops.schema_migrations WHERE version = '$v'")
  if [ -n "$old" ]; then
    [ "$old" = "$sum" ] || { echo "CHECKSUM MISMATCH: $v was edited after it was applied" >&2; exit 1; }
    echo "skip   $v"; continue
  fi
  echo "apply  $v"
  q -1 -f "$f" -c "INSERT INTO ops.schema_migrations (version, checksum) VALUES ('$v', '$sum')"
done
EOF
chmod +x migrate.sh
cat > migrations/V001__schemas.sql <<'EOF'
CREATE SCHEMA app;
CREATE SCHEMA audit;
EOF
cat > migrations/V002__customers.sql <<'EOF'
CREATE TABLE app.customers (
    id    int GENERATED ALWAYS AS IDENTITY,
    name  text NOT NULL,
    email text NOT NULL,
    CONSTRAINT customers_pkey PRIMARY KEY (id),
    CONSTRAINT customers_email_ck CHECK (position('@' in email) > 1));
EOF
cat > migrations/V003__orders.sql <<'EOF'
CREATE TABLE app.orders (
    id           int GENERATED ALWAYS AS IDENTITY,
    customer_id  int NOT NULL,
    total_amount numeric(12,2) NOT NULL,
    CONSTRAINT orders_pkey PRIMARY KEY (id),
    CONSTRAINT orders_customer_id_fkey FOREIGN KEY (customer_id) REFERENCES app.customers (id));
CREATE INDEX orders_customer_id_idx ON app.orders (customer_id);
EOF
./migrate.sh ch21_ws3_dev
echo "--- again"
./migrate.sh ch21_ws3_dev
echo "--- prod"
./migrate.sh ch21_ws3_prod
```

```text
apply  V001__schemas
apply  V002__customers
```

```bash

SELECT md5(string_agg(line, E'\n' ORDER BY line)) AS schema_fingerprint, count(*) AS objects
FROM (
  SELECT 'col ' || table_schema || '.' || table_name || '.' || column_name || ' ' || data_type
         || ' null=' || is_nullable AS line
  FROM information_schema.columns WHERE table_schema IN ('app', 'audit')
  UNION ALL
  SELECT 'con ' || conrelid::regclass || ' ' || conname || ' ' || pg_get_constraintdef(oid)
  FROM pg_constraint WHERE connamespace::regnamespace::text IN ('app', 'audit')
  UNION ALL
  SELECT 'idx ' || schemaname || '.' || indexname || ' ' || indexdef
  FROM pg_indexes WHERE schemaname IN ('app', 'audit')
) s;
EOF
```

`CREATE INDEX CONCURRENTLY` cannot run in a transaction block, and the runner puts every
file in one. The extension applies files ending `.notx.sql` outside a transaction and
records them afterwards:

```bash
mv migrations/V005__index.sql migrations/V005__index.notx.sql
python3 - <<'EOF'
p = 'migrate.sh'
s = open(p).read()
s = s.replace('''  q -1 -f "$f" -c "INSERT INTO ops.schema_migrations (version, checksum) VALUES ('$v', '$sum')"''',
'''  if [[ "$f" == *.notx.sql ]]; then
    q -f "$f"
    q -c "INSERT INTO ops.schema_migrations (version, checksum) VALUES ('$v', '$sum')"
  else
    q -1 -f "$f" -c "INSERT INTO ops.schema_migrations (version, checksum) VALUES ('$v', '$sum')"
  fi''')
s = s.replace('v=$(basename "$f" .sql)', 'v=$(basename "${f%.notx.sql}" .sql)')
open(p, 'w').write(s)
EOF
./migrate.sh ch21_ws3_dev
psql -X -d ch21_ws3_dev -Atc "SELECT version FROM ops.schema_migrations ORDER BY 1"
```

```text
skip   V002__customers
skip   V003__orders

V001__schemas
V002__customers
V003__orders
V005__index
```

What the extension gives up: the migration and its bookkeeping row are no longer atomic. If
the index build succeeds and the process dies before the `INSERT`, the next run tries to
build it again and fails on the existing name, and if the build itself fails it can leave an
`INVALID` index behind that must be dropped by hand. For that reason `.notx` migrations
should hold **one** statement and are the one place I allow `IF NOT EXISTS`. Chapter 52
covers the rest of the online-migration toolkit.
