# Chapter 29 Exercises — Transactions in Practice

## Practice Session 29.1 — Roll back a DDL migration mid-flight

**Goal.** Run a four-step schema migration that fails at step 3, and show that in one
transaction it leaves the database exactly as it found it, while the same file in autocommit
leaves it half-migrated.

**Setup.** A scratch database holding a copy of the small `retail` `customers` table
(1,000 rows, 128 of them with no city). `pg_dump` reads `retail` and changes nothing in it.
(The `grep` drops a `SET transaction_timeout` line that `pg_dump` 17 and later write and
a PostgreSQL 15 server rejects; with a matching `pg_dump` it is harmless.)

```bash
createdb ch29_lab
pg_dump -t customers retail | grep -v '^SET transaction_timeout' | psql -q -X -o /dev/null -d ch29_lab
psql -X -P null='(null)' -d ch29_lab -c "SELECT count(*) AS customers, count(*) FILTER (WHERE city IS NULL) AS no_city FROM customers"
```

```text
 customers | no_city
-----------+---------
      1000 |     128
(1 row)
```

**Task.** The migration adds a `region` column, fills it from `city`, makes it `NOT NULL`,
and indexes it.

1. Save the migration below as `migrate.sql` and run it the way people usually do:
   `psql -f migrate.sql`, with no other options. Report which statements succeeded and
   which failed, then inspect the table: does `region` exist? How many rows have a NULL
   region? Does the index exist?
2. Undo the damage by hand (`DROP INDEX`, `ALTER TABLE ... DROP COLUMN`), and say why you
   had to.
3. Wrap the file in one transaction and stop at the first error:
   `psql -v ON_ERROR_STOP=1 -1 -f migrate.sql`. Inspect the same three things. What state is
   the database in now?
4. Change the index step to `CREATE INDEX CONCURRENTLY` (the choice you would make on a busy
   table) and run the file under `-1` again. Read the error, then read it again: which
   statement raised it, and did the earlier error still occur?
5. Repair the migration so it succeeds: fix the fill step so customers with no city get
   `'unknown'`, keep the transactional steps in `migrate.sql`, and move the concurrent index
   into its own file `index.sql` that you run *after* the first one, outside `-1`.
6. Show that a concurrent build that fails leaves something behind. Try
   `CREATE UNIQUE INDEX CONCURRENTLY` on `customers (loyalty_tier)` and look for the
   leftover with `pg_index.indisvalid`. Then remove it.

```bash
cat > migrate.sql <<'SQL'
ALTER TABLE customers ADD COLUMN region text;
UPDATE customers SET region = CASE
  WHEN city IN ('Mumbai','Pune','Nagpur','Ahmedabad','Surat','Indore')            THEN 'west'
  WHEN city IN ('Chennai','Coimbatore','Kochi','Bengaluru','Mysuru','Hyderabad',
                'Visakhapatnam')                                                   THEN 'south'
  WHEN city IN ('Delhi','Lucknow','Jaipur','Chandigarh')                           THEN 'north'
  WHEN city IN ('Kolkata','Guwahati','Bhubaneswar')                                THEN 'east'
END;
ALTER TABLE customers ALTER COLUMN region SET NOT NULL;
CREATE INDEX customers_region_idx ON customers (region);
SQL
```

**Solution.**

1. Plain `psql -f` runs every statement in autocommit and, on error, carries on to the next:

```bash
psql -X -P null='(null)' -d ch29_lab -f migrate.sql; echo "exit status: $?"
psql -X -P null='(null)' -d ch29_lab -c "SELECT count(*) FILTER (WHERE region IS NULL) AS null_regions FROM customers" -c "SELECT indexname FROM pg_indexes WHERE tablename = 'customers' ORDER BY 1"
```

```text
ALTER TABLE
UPDATE 1000
psql:migrate.sql:9: ERROR:  column "region" of relation "customers" contains null values
CREATE INDEX
exit status: 0
 null_regions
--------------
          128
(1 row)

      indexname
----------------------
 customers_pkey
 customers_region_idx
(2 rows)
```

   Steps 1, 2 and 4 succeeded and step 3 failed, so the table now has a `region` column that
   is NULL for all 128 no-city customers and lacks its `NOT NULL`, and it carries an index
   built over that half-finished state. Nothing in the run said "stop", and the exit status
   is 0, so a deploy pipeline would report success.

2. The steps that succeeded were committed one by one, so nothing rolls them back:

```sql
DROP INDEX customers_region_idx;
ALTER TABLE customers DROP COLUMN region;
```

3. With `ON_ERROR_STOP` and `-1`, the first error ends the script and psql rolls back:

```bash
psql -X -P null='(null)' -d ch29_lab -v ON_ERROR_STOP=1 -1 -f migrate.sql; echo "exit status: $?"
psql -X -P null='(null)' -d ch29_lab -c "SELECT count(*) FILTER (WHERE attname = 'region') AS region_columns FROM pg_attribute WHERE attrelid = 'customers'::regclass" -c "SELECT count(*) AS region_indexes FROM pg_indexes WHERE indexname = 'customers_region_idx'"
```

```text
ALTER TABLE
UPDATE 1000
psql:migrate.sql:9: ERROR:  column "region" of relation "customers" contains null values
exit status: 3
 region_columns
----------------
              0
(1 row)

 region_indexes
----------------
              0
(1 row)
```

   The same error, but the database is untouched: no column, no index, and a non-zero exit
   status a pipeline can act on. Steps 1 and 2 ran, and were undone. This is what
   transactional DDL buys you.

4. Make the index step concurrent and run the file under `-1`:

```bash
sed 's/CREATE INDEX/CREATE INDEX CONCURRENTLY/' migrate.sql > migrate_conc.sql
psql -X -d ch29_lab -v ON_ERROR_STOP=1 -1 -f migrate_conc.sql
```

```text
ALTER TABLE
UPDATE 1000
psql:migrate_conc.sql:9: ERROR:  column "region" of relation "customers" contains null values
```

   The same error as before: the `NOT NULL` step at statement 3 still fails first, and
   `ON_ERROR_STOP` never lets the script reach the index. A concurrent build has a second,
   structural problem that this data problem was hiding. Test that statement alone under
   `-1`:

```bash
psql -X -d ch29_lab -v ON_ERROR_STOP=1 -1 -c "CREATE INDEX CONCURRENTLY customers_region_idx ON customers (city)"
```

```text
ERROR:  CREATE INDEX CONCURRENTLY cannot run inside a transaction block
```

   `-1` opens a transaction block and `CREATE INDEX CONCURRENTLY` cannot run in one. Fixing
   the data would have exposed this error next.

5. Fix the data (`ELSE 'unknown'`), split the file, and run both in order:

```bash
cat > migrate.sql <<'SQL'
ALTER TABLE customers ADD COLUMN region text;
UPDATE customers SET region = CASE
  WHEN city IN ('Mumbai','Pune','Nagpur','Ahmedabad','Surat','Indore')            THEN 'west'
  WHEN city IN ('Chennai','Coimbatore','Kochi','Bengaluru','Mysuru','Hyderabad',
                'Visakhapatnam')                                                   THEN 'south'
  WHEN city IN ('Delhi','Lucknow','Jaipur','Chandigarh')                           THEN 'north'
  WHEN city IN ('Kolkata','Guwahati','Bhubaneswar')                                THEN 'east'
  ELSE 'unknown'
END;
ALTER TABLE customers ALTER COLUMN region SET NOT NULL;
SQL
echo "CREATE INDEX CONCURRENTLY customers_region_idx ON customers (region);" > index.sql
psql -X -d ch29_lab -v ON_ERROR_STOP=1 -1 -f migrate.sql && psql -X -d ch29_lab -v ON_ERROR_STOP=1 -f index.sql
psql -X -P null='(null)' -d ch29_lab -c "SELECT region, count(*) FROM customers GROUP BY 1 ORDER BY 2 DESC" -c "SELECT indexrelid::regclass AS index, indisvalid FROM pg_index WHERE indrelid = 'customers'::regclass ORDER BY 1"
```

```text
ALTER TABLE
UPDATE 1000
ALTER TABLE
CREATE INDEX
 region  | count
---------+-------
 south   |   307
 west    |   260
 north   |   168
 east    |   137
 unknown |   128
(5 rows)

        index         | indisvalid
----------------------+------------
 customers_pkey       | t
 customers_region_idx | t
(2 rows)
```

   The `&&` matters: the concurrent build runs only if the transactional part committed.
   The index step is the one part of this migration that is not atomic, so put it last and
   make it safe to re-run (`CREATE INDEX CONCURRENTLY IF NOT EXISTS`, or drop and retry).

6. A concurrent build that fails part-way cannot roll back, so it leaves its index behind
   marked invalid:

```bash
psql -X -d ch29_lab -c "CREATE UNIQUE INDEX CONCURRENTLY customers_tier_uq ON customers (loyalty_tier)"
psql -X -P null='(null)' -d ch29_lab -c "SELECT indexrelid::regclass AS index, indisvalid FROM pg_index WHERE indrelid = 'customers'::regclass ORDER BY 1"
```

```text
ERROR:  could not create unique index "customers_tier_uq"
DETAIL:  Key (loyalty_tier)=(silver) is duplicated.
        index         | indisvalid
----------------------+------------
 customers_pkey       | t
 customers_region_idx | t
 customers_tier_uq    | f
(3 rows)
```

   The build failed because `loyalty_tier` is not unique, and `customers_tier_uq` is still
   there with `indisvalid = f`. Per the documentation, an invalid index is ignored by queries
   but still updated on every write, so it costs you and gives nothing back. Drop it and retry:
   `DROP INDEX customers_tier_uq;`.

```bash
psql -X -d ch29_lab -c "DROP INDEX customers_tier_uq" -c "DROP INDEX customers_region_idx" -c "ALTER TABLE customers DROP COLUMN region"
```

## Practice Session 29.2 — Create and resolve an idle-in-transaction stall

**Goal.** Reproduce a stall caused by a session that is idle in a transaction, diagnose the
blocker from `pg_stat_activity` and `pg_locks`, clear it, and then make the database refuse
to let it happen again.

**Setup.** The `ch29_lab` database from Session 29.1 (or, if you skipped it, the same two
commands, which give you a copy of the small `retail` `customers` table). You need three
`psql` connections. In the solution they are labelled Session A, B and C; open three
terminals and type the blocks in the order shown. Connect each with a distinct
`PGAPPNAME` so you can tell them apart, for example
`PGAPPNAME=session_a psql -X -d ch29_lab`.

```bash
dropdb --if-exists ch29_lab
createdb ch29_lab
pg_dump -t customers retail | grep -v '^SET transaction_timeout' | psql -q -X -o /dev/null -d ch29_lab
```

**Task.**

1. In Session A, begin a transaction and update customer 1's `loyalty_tier`. Do not commit.
2. In Session B, update a different column of the same row (`city`), returning the row's
   `city` and `loyalty_tier`. It will not return.
3. In Session C, write one query that shows, for the sessions in your database only:
   application name, state, what each is waiting on, and who is blocking it. Identify the
   blocker and its state.
4. Resolve the stall without touching Session B: terminate the *blocker*, from Session C.
   Confirm B completes and A's change did not survive.
5. Set `idle_in_transaction_session_timeout = '1s'` on the database and reproduce the idle
   session. Show the server ending it with no intervention, and read what A sees next. Reset
   the setting.
6. The row lock is only one way an idle session hurts. Have Session A open a transaction and
   merely `SELECT` from `customers`, then idle. Have B run
   `ALTER TABLE customers ADD COLUMN spare int` and C run a plain
   `SELECT count(*) FROM customers`. Show the lock queue in `pg_locks` and say which session
   is blocking C even though it is not the one C is waiting for.

**Solution.**

1 and 2.

```sql
-- Session A
BEGIN;
UPDATE customers SET loyalty_tier = 'gold' WHERE id = 1;
```

```sql
-- Session B
UPDATE customers SET city = 'Mumbai' WHERE id = 1 RETURNING id, city, loyalty_tier;
```

3. `pg_blocking_pids(pid)` returns the pids holding up a session, and a self-join turns
   them into names. Filtering on `datname` keeps other databases' sessions out, and
   `pg_backend_pid()` keeps the diagnostic query itself out:

```sql
-- Session C
SELECT a.application_name AS session, a.state, a.wait_event_type AS waiting_on,
       (SELECT string_agg(b.application_name, ',') FROM pg_stat_activity b
        WHERE b.pid = ANY (pg_blocking_pids(a.pid))) AS blocked_by
FROM pg_stat_activity a
WHERE a.datname = current_database() AND a.pid <> pg_backend_pid()
  AND a.application_name IN ('session_a', 'session_b')
ORDER BY a.application_name;
```

```text
  session  |        state        | waiting_on | blocked_by
-----------+---------------------+------------+------------
 session_a | idle in transaction | Client     | (null)
 session_b | active              | Lock       | session_a
(2 rows)
```

   The blocker, `session_a`, is `idle in transaction` and waiting on `Client`: nothing is
   running, and nothing will until that application sends another command. The victim is
   `session_b`, `active` and waiting on a `Lock`. The blocker is the idle one, which is why
   `WHERE state = 'active'` misses it.

4. Terminate the blocker:

```sql
-- Session C
SELECT pg_terminate_backend(pid) FROM pg_stat_activity
WHERE datname = current_database() AND application_name = 'session_a';
```

```text
 pg_terminate_backend
----------------------
 t
(1 row)
```

```text
 id |  city  | loyalty_tier
----+--------+--------------
  1 | Mumbai | silver
(1 row)
```

   B's update completed, and its `RETURNING` shows a `loyalty_tier` that is not `'gold'`: the
   terminated transaction rolled back, so A's change never became visible. Terminating is an
   emergency measure; the application that owned A has just lost work it believed was in
   progress.

5. Prevention. New connections pick up the database setting:

```sql
ALTER DATABASE ch29_lab SET idle_in_transaction_session_timeout = '1s';
```

```sql
-- Session A
BEGIN;
UPDATE customers SET loyalty_tier = 'gold' WHERE id = 1;
```

   Leave A alone until its backend disappears from `pg_stat_activity` (a `SELECT` in
   Session C, repeated, will show it going). Then:

```sql
-- Session A
SELECT 1;
```

```text
FATAL:  terminating connection due to idle-in-transaction timeout
server closed the connection unexpectedly
	This probably means the server terminated abnormally
	before or while processing the request.
connection to server was lost
```

   The server ended the session itself. `psql` reports the loss on the next command, and the
   update is rolled back. Reset the setting, since the next step does not want it:

```sql
ALTER DATABASE ch29_lab RESET idle_in_transaction_session_timeout;
```

6. An idle session that only *read* still holds `AccessShareLock` on the table until it
   ends:

```sql
-- Session A
BEGIN;
SELECT count(*) FROM customers;
```

```text
 count
-------
  1000
(1 row)
```

```sql
-- Session B
ALTER TABLE customers ADD COLUMN spare int;
```

```sql
-- Session C
SELECT count(*) FROM customers;
```

```sql
-- Session A
SELECT a.application_name AS session, l.mode, l.granted
FROM pg_locks l JOIN pg_stat_activity a USING (pid)
WHERE l.relation = 'customers'::regclass AND a.datname = current_database()
ORDER BY l.granted DESC, a.application_name;
```

```text
  session  |        mode         | granted
-----------+---------------------+---------
 session_a | AccessShareLock     | t
 session_b | AccessExclusiveLock | f
 session_c | AccessShareLock     | f
(3 rows)
```

   `session_a` holds `AccessShareLock`, the weakest lock, and is doing nothing. `session_b`'s
   `ALTER` wants `AccessExclusiveLock`, which conflicts with it, so it waits. `session_c`
   wants only `AccessShareLock`, which does *not* conflict with A's, yet it also waits:
   PostgreSQL queues lock requests in order, so C sits behind B. The idle session that only
   read is what holds up every reader of the table, via the queued `ALTER`. The cure is the
   same, `lock_timeout` on the `ALTER` and `idle_in_transaction_session_timeout` on the
   application role (Chapter 52 builds the full pattern). End A and let the others finish:

```sql
-- Session A
ROLLBACK;
```


```text
 count
-------
  1000
(1 row)
```

Clean up:

```bash
psql -X -d ch29_lab -c "ALTER TABLE customers DROP COLUMN spare"
dropdb ch29_lab
```
