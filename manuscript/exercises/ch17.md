# Chapter 17 Exercises — JSONB in Depth

## Practice Session 17.1 — Query and index a JSONB column

**Goal.** Read values out of a real JSONB column with every extraction operator, get the
casting right, then index it and confirm from the plan that the index is actually used.

**Setup.** The small `telemetry` dataset from Practice Session 2.3. Its `device_events`
table carries a `payload` column of type `jsonb` — nested objects and an array — which is
the only JSONB the sample data ships with.

```bash
psql -d telemetry
```

```sql
\pset null '(null)'
SELECT count(*) FROM device_events;      -- expect 9800
```

Everything below is read-only except two `CREATE INDEX` statements at the end; the last
step drops them, so `telemetry` is left exactly as it was loaded.

**Task.**

1. Show `event_id`, the firmware string, the battery level **as an integer**, the Wi-Fi
   SSID from the nested `net` object, and the raw `tags` array, for the first five events.
2. Count events and average battery per firmware version.
3. Count how many events are tagged `calibrated`, three different ways: containment, key
   existence, and a SQL/JSON path. Confirm all three agree.
4. Find every event where the battery is below 50. Then do it again without casting, and
   explain the difference.
5. Produce a frequency table of every tag across all events. Note that `tags` is an array,
   so one event can contribute several rows.
6. Create a GIN index on `payload` and prove from `EXPLAIN (ANALYZE)` that a containment
   query uses it. Then write a query that *looks* like it should use the same index and
   does not, and say why.
7. Create a B-tree expression index on the firmware key. Compare the planner's row estimate
   before and after. Drop both indexes when you are done.

**Solution.**

**1 — the four extraction operators.**

```sql
SELECT event_id, payload ->> 'fw' AS firmware, (payload ->> 'batt')::int AS battery,
       payload #>> '{net,ssid}' AS ssid, payload -> 'tags' AS tags
FROM device_events ORDER BY event_id LIMIT 5;
```

```text
 event_id | firmware  | battery |  ssid  |              tags              
----------+-----------+---------+--------+--------------------------------
        1 | 2.1.4     |      78 | site-4 | ["retry"]
        2 | 2.1.4     |      77 | site-5 | ["ok"]
        3 | 2.2.0-rc1 |      72 | site-6 | ["ok", "calibrated"]
        4 | 2.1.4     |      74 | site-5 | ["ok"]
        5 | 1.8.2     |     100 | site-2 | ["ok", "indoor", "calibrated"]
(5 rows)
```

`->>` returns `text`, so `batt` needs an explicit `::int` before it is a number. `#>>` takes
a path array and reaches into the nested `net` object in one step — `payload -> 'net' ->>
'ssid'` is the same thing written longhand. `->` returns `jsonb`, which is why `tags` prints
as a JSON array rather than a Postgres array: note the double quotes around the elements.

**2 — grouping on an extracted value.**

```sql
SELECT payload ->> 'fw' AS firmware, count(*) AS events,
       round(avg((payload ->> 'batt')::int), 1) AS avg_battery
FROM device_events GROUP BY 1 ORDER BY 1;
```

```text
 firmware  | events | avg_battery 
-----------+--------+-------------
 1.8.2     |   2450 |        79.6
 2.0.0     |   2520 |        80.0
 2.1.4     |   2411 |        80.4
 2.2.0-rc1 |   2419 |        79.9
(4 rows)
```

Four firmware versions, evenly spread, and battery does not vary meaningfully between them.
The `::int` inside `avg` is load-bearing again: without it, `avg` over `text` raises
`function avg(text) does not exist`, which is at least a loud failure rather than a quiet
wrong answer.

**3 — three ways to ask the same question.**

```sql
SELECT count(*) FILTER (WHERE payload @> '{"tags": ["calibrated"]}')        AS via_containment,
       count(*) FILTER (WHERE payload -> 'tags' ? 'calibrated')             AS via_existence,
       count(*) FILTER (WHERE payload @? '$.tags[*] ? (@ == "calibrated")') AS via_path
FROM device_events;
```

```text
 via_containment | via_existence | via_path 
-----------------+---------------+----------
            4851 |          4851 |     4851
(1 row)
```

All three agree, and they are not interchangeable in every respect:

- `@>` asks *does the whole document contain this fragment*. Containment matches a subset of
  an array, so `{"tags": ["calibrated"]}` matches an event tagged
  `["ok", "indoor", "calibrated"]`.
- `?` applied to a JSON **array** tests string membership. Applied to an object it would
  test for a key instead — the same operator, two meanings, chosen by the type of the left
  operand.
- The path form is the most explicit and the most flexible, and the only one of the three
  you could extend to `@ starts with "cal"` without changing approach.

Prefer `@>` when the shape is fixed. It is the form the index serves best, as step 6 shows.

**4 — the cast that decides the answer.**

```sql
SELECT count(*) FILTER (WHERE payload ->> 'batt' < '50')      AS text_compare,
       count(*) FILTER (WHERE (payload ->> 'batt')::int < 50) AS int_compare,
       min((payload ->> 'batt')::int)                         AS lowest_battery
FROM device_events;
```

```text
 text_compare | int_compare | lowest_battery 
--------------+-------------+----------------
          230 |           0 |             60
(1 row)
```

**No device in this dataset is below 50% battery.** The correct answer is zero.

The uncast comparison returns 230, and those 230 rows are precisely the events reporting
**100%** — a full battery. `->>` returns `text`, so `'100' < '50'` is a string comparison,
and `'1'` sorts before `'5'`. The query does not error, does not warn, and returns a
plausible-looking count of "low battery" events that are in fact the healthiest devices in
the fleet.

This is the single most common JSONB bug I see in review, and it is invisible unless you
already know to look for it. **Cast on extraction, every time.** The habit to build is that
`->>` is never the last thing in a comparison against a number or a date.

**5 — expanding the array.**

```sql
SELECT tag, count(*) AS events
FROM device_events, jsonb_array_elements_text(payload -> 'tags') AS tag
GROUP BY tag ORDER BY events DESC;
```

```text
    tag     | events 
------------+--------
 ok         |   7353
 calibrated |   4851
 retry      |   2447
 indoor     |   2412
(4 rows)
```

`jsonb_array_elements_text` is set-returning, so writing it in the `FROM` clause is an
implicit `LATERAL` join: each event produces one row per tag. The counts therefore sum to
17,063 across 9,800 events, which is correct and is *not* what you want if somebody asks
"how many events are there". The `_text` suffix matters — plain `jsonb_array_elements`
returns `jsonb`, so the tags would come back quoted and group as `"ok"` rather than `ok`.

**6 — the index, and a query that quietly bypasses it.**

```sql
CREATE INDEX device_events_payload_gin ON device_events USING gin (payload);

EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT count(*) FROM device_events WHERE payload @> '{"net": {"ssid": "site-3"}, "fw": "2.0.0"}';
```

```text
                                         QUERY PLAN                                         
--------------------------------------------------------------------------------------------
 Aggregate (actual rows=1 loops=1)
   ->  Bitmap Heap Scan on device_events (actual rows=421 loops=1)
         Recheck Cond: (payload @> '{"fw": "2.0.0", "net": {"ssid": "site-3"}}'::jsonb)
         Heap Blocks: exact=211
         ->  Bitmap Index Scan on device_events_payload_gin (actual rows=421 loops=1)
               Index Cond: (payload @> '{"fw": "2.0.0", "net": {"ssid": "site-3"}}'::jsonb)
(6 rows)
```

The `Bitmap Index Scan` returns 421 rows and the `Bitmap Heap Scan` above it also returns
421, so the recheck eliminated nothing: the index answered the question exactly. GIN
combined both keys of the containment fragment before touching the heap.

Now the query that does not use it — the one from step 3:

```sql
EXPLAIN (COSTS OFF) SELECT count(*) FROM device_events WHERE payload -> 'tags' ? 'calibrated';
```

```text
                            QUERY PLAN                            
------------------------------------------------------------------
 Aggregate
   ->  Seq Scan on device_events
         Filter: ((payload -> 'tags'::text) ? 'calibrated'::text)
(3 rows)
```

The index is on `payload`. The predicate is on `payload -> 'tags'`, which is a *different
expression*, and an index can only serve the exact expression it was built on. PostgreSQL
will not reason that one contains the other.

Two fixes, and they are not equivalent: rewrite the predicate as
`payload @> '{"tags": ["calibrated"]}'`, which the existing index serves; or build a second
index on `((payload -> 'tags'))` if you cannot change the query. Prefer the rewrite — an
index you did not have to create costs nothing to maintain.

**7 — the expression index and what it does to the estimate.**

```sql
EXPLAIN SELECT * FROM device_events WHERE payload ->> 'fw' = '2.2.0-rc1';
```

```text
                            QUERY PLAN                            
------------------------------------------------------------------
 Seq Scan on device_events  (cost=0.00..414.00 rows=49 width=187)
   Filter: ((payload ->> 'fw'::text) = '2.2.0-rc1'::text)
(2 rows)
```

```sql
CREATE INDEX device_events_fw ON device_events ((payload ->> 'fw'));
ANALYZE device_events;
EXPLAIN SELECT * FROM device_events WHERE payload ->> 'fw' = '2.2.0-rc1';
```

```text
                                    QUERY PLAN                                     
-----------------------------------------------------------------------------------
 Bitmap Heap Scan on device_events  (cost=31.03..334.32 rows=2419 width=187)
   Recheck Cond: ((payload ->> 'fw'::text) = '2.2.0-rc1'::text)
   ->  Bitmap Index Scan on device_events_fw  (cost=0.00..30.43 rows=2419 width=0)
         Index Cond: ((payload ->> 'fw'::text) = '2.2.0-rc1'::text)
(4 rows)
```

**`rows=49` became `rows=2419`, and 2,419 is exactly right** — compare step 2. The first
figure was never an estimate at all: 49 is 0.5% of 9,800, PostgreSQL's fixed fallback for a
predicate whose selectivity it cannot compute. There are no statistics for
`payload ->> 'fw'` because there is no column called `payload ->> 'fw'`.

Creating the expression index changes that. `ANALYZE` now samples the expression and files
the result in `pg_stats` under the *index's* name:
`SELECT most_common_vals FROM pg_stats WHERE tablename = 'device_events_fw'`.

That second effect is usually worth more than the access path. A 49-row estimate for a
2,419-row reality is how the planner talks itself into a nested loop; the index fixes the
estimate for every query mentioning that expression, even ones that never scan it.

Restore `telemetry` to its loaded state:

```sql
DROP INDEX device_events_fw, device_events_payload_gin;
```

## Practice Session 17.2 — Compare GIN operator classes

**Goal.** Measure the size difference between `jsonb_ops` and `jsonb_path_ops`, establish
exactly which operators each one can serve, and learn to tell "the index was used" from
"the index helped".

**Setup.** The small `telemetry` dataset from Practice Session 2.3, whose `device_events`
table has a `jsonb` column named `payload`.

```bash
psql -d telemetry
```

```sql
\pset null '(null)'
SELECT count(*) FROM device_events;      -- expect 9800
```

This session creates and drops indexes only; the final step leaves `telemetry` as loaded.

**Task.**

1. Build both GIN operator classes over `payload` and compare their sizes against the
   table's.
2. With both present, confirm the default class serves the key-existence operator `?`.
   Sequential scans are cheap on 9,800 rows, so you will need to stop the planner choosing
   one on cost — otherwise you cannot tell *cannot* from *will not*.
3. Drop the default index and ask the same question of `jsonb_path_ops`. Explain the result.
4. Confirm `jsonb_path_ops` still serves `@>`, and find the rewrite that lets it answer the
   question from step 3.
5. Run two `@@` path predicates against `jsonb_path_ops` — one an equality test, one a
   `<` comparison — with `EXPLAIN (ANALYZE)`. Both plans use the index. Only one benefits.
   Find the line that proves it.
6. State which operator class you would make the default in your own schema.
7. Drop both indexes.

**Solution.**

**1 — the size difference.**

```sql
CREATE INDEX device_events_payload_gin     ON device_events USING gin (payload);
CREATE INDEX device_events_payload_pathops ON device_events USING gin (payload jsonb_path_ops);

SELECT pg_size_pretty(pg_relation_size('device_events'))                 AS table_size,
       pg_size_pretty(pg_relation_size('device_events_payload_gin'))     AS jsonb_ops,
       pg_size_pretty(pg_relation_size('device_events_payload_pathops')) AS jsonb_path_ops;
```

```text
 table_size | jsonb_ops | jsonb_path_ops 
------------+-----------+----------------
 2136 kB    | 352 kB    | 176 kB
(1 row)
```

Exactly half. This is not a property of this dataset — the same two-to-one ratio appears on
a 200,000-row `orders` table with a completely different document shape (Chapter 17,
section 17.4, where the figures are 4000 kB and 1976 kB).

The reason is structural. `jsonb_ops` makes an index entry for **every key and every value
separately**: the document `{"fw": "2.0.0", "batt": 78}` contributes entries for `fw`,
`2.0.0`, `batt` and `78`. `jsonb_path_ops` makes one entry per value, hashing the *whole
path down to it*, so the same document contributes two. Half the entries, half the index.

Those hashed entries are also more selective. Under `jsonb_ops` the value `2.0.0` is one
posting list regardless of which key held it; under `jsonb_path_ops`, `fw → 2.0.0` is its
own entry, so a containment lookup does less work intersecting lists.

**2 — proving what the default class can do.**

```sql
EXPLAIN (COSTS OFF) SELECT count(*) FROM device_events WHERE payload ? 'net';
```

Left alone, this reports a sequential scan — but that tells you nothing, because every one
of the 9,800 rows has a `net` key, so a scan is genuinely the cheaper plan. Cost and
capability look identical in the output. Separate them:

```sql
SET enable_seqscan = off;
EXPLAIN (COSTS OFF) SELECT count(*) FROM device_events WHERE payload ? 'net';
```

```text
                         QUERY PLAN                         
------------------------------------------------------------
 Aggregate
   ->  Bitmap Heap Scan on device_events
         Recheck Cond: (payload ? 'net'::text)
         ->  Bitmap Index Scan on device_events_payload_gin
               Index Cond: (payload ? 'net'::text)
(5 rows)
```

`enable_seqscan = off` does not forbid sequential scans — it applies a large cost penalty,
so the planner will pick any index that *can* serve the predicate. It chose
`device_events_payload_gin`. The default class can answer `?`.

**3 — and what the other class cannot.**

```sql
DROP INDEX device_events_payload_gin;
EXPLAIN (COSTS OFF) SELECT count(*) FROM device_events WHERE payload ? 'net';
```

```text
               QUERY PLAN                
-----------------------------------------
 Aggregate
   ->  Seq Scan on device_events
         Filter: (payload ? 'net'::text)
(3 rows)
```

A sequential scan *with sequential scans penalised*, and an index sitting right there on the
column. That is PostgreSQL telling you plainly that no alternative exists.

The cause is the same structure that made the index small. `jsonb_path_ops` never stores a
bare key — only hashes of complete paths-with-values — so there is nothing in it to look up
when you ask whether a key exists. The whole `?` family goes: `?`, `?|` and `?&`.

**4 — what it does serve, and the rewrite.**

```sql
EXPLAIN (COSTS OFF) SELECT count(*) FROM device_events WHERE payload @> '{"fw": "2.0.0"}';
```

```text
                           QUERY PLAN                            
-----------------------------------------------------------------
 Aggregate
   ->  Bitmap Heap Scan on device_events
         Recheck Cond: (payload @> '{"fw": "2.0.0"}'::jsonb)
         ->  Bitmap Index Scan on device_events_payload_pathops
               Index Cond: (payload @> '{"fw": "2.0.0"}'::jsonb)
(5 rows)
```

Containment works, which is the point of the class. And the existence question from step 3
becomes answerable if you ask it as a path instead of as a key:

```sql
EXPLAIN (COSTS OFF) SELECT count(*) FROM device_events WHERE payload @? '$.net';
```

```text
                           QUERY PLAN                           
----------------------------------------------------------------
 Aggregate
   ->  Bitmap Heap Scan on device_events
         Recheck Cond: (payload @? '$."net"'::jsonpath)
         ->  Bitmap Index Scan on device_events_payload_pathops
               Index Cond: (payload @? '$."net"'::jsonpath)
(5 rows)
```

`attrs ? 'k'` rewrites to `attrs @? '$.k'`, and `?|` / `?&` to `@?` with `||` / `&&` inside
the path. In practice this means the `?` family is rarely a real reason to choose
`jsonb_ops` — only an unchangeable query is.

**5 — used versus helped.**

```sql
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT count(*) FROM device_events WHERE payload @@ '$.fw == "2.0.0"';
```

```text
                                        QUERY PLAN                                         
-------------------------------------------------------------------------------------------
 Aggregate (actual rows=1 loops=1)
   ->  Bitmap Heap Scan on device_events (actual rows=2520 loops=1)
         Recheck Cond: (payload @@ '($."fw" == "2.0.0")'::jsonpath)
         Heap Blocks: exact=267
         ->  Bitmap Index Scan on device_events_payload_pathops (actual rows=2520 loops=1)
               Index Cond: (payload @@ '($."fw" == "2.0.0")'::jsonpath)
(6 rows)
```

```sql
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT count(*) FROM device_events WHERE payload @@ '$.batt < 65';
```

```text
                                        QUERY PLAN                                         
-------------------------------------------------------------------------------------------
 Aggregate (actual rows=1 loops=1)
   ->  Bitmap Heap Scan on device_events (actual rows=1166 loops=1)
         Recheck Cond: (payload @@ '($."batt" < 65)'::jsonpath)
         Rows Removed by Index Recheck: 8634
         Heap Blocks: exact=267
         ->  Bitmap Index Scan on device_events_payload_pathops (actual rows=9800 loops=1)
               Index Cond: (payload @@ '($."batt" < 65)'::jsonpath)
(7 rows)
```

Both plans contain a `Bitmap Index Scan`. Only the first one did any work.

The line to read is `actual rows` on the **index scan node**. In the equality case it is
2,520 — the index found exactly the matching rows. In the comparison case it is **9,800**,
the entire table, and the next line up says `Rows Removed by Index Recheck: 8634`.

GIN indexes *equality of extracted entries*, and nothing else. It has no ordered structure,
so `< 65` cannot be looked up; PostgreSQL falls back to scanning every entry in the index,
building a bitmap of every row, reading all 267 heap blocks and then evaluating the
predicate properly on each row. That is strictly more work than a plain sequential scan —
the same heap reads, plus a full index traversal — and the plan looks like an index scan the
whole time.

`Rows Removed by Index Recheck` is the tell. Treat any nonzero value as a finding: it means
the index narrowed nothing and you are paying for it twice. If you need range predicates on
a JSON value, build a B-tree expression index on `((payload ->> 'batt')::int)` instead;
GIN is the wrong structure for the question.

**6 — the decision.**

**Make `jsonb_path_ops` your default.** Half the size, more selective entries, and it covers
`@>`, `@?` and `@@`, which is every predicate you are likely to write against a document
column. Reach for `jsonb_ops` only when you need `?`/`?|`/`?&` against queries you cannot
rewrite — for example SQL emitted by an ORM or a reporting tool.

Note that it is not either-or in one respect: neither class helps with range comparisons,
and neither gives the planner selectivity statistics. For a single hot scalar key you query
with `=`, `<` or `ORDER BY`, the right answer is a B-tree expression index, or promoting the
key to a column (Practice Session 17.3).

**7 — clean up.**

```sql
DROP INDEX device_events_payload_pathops;
```

## Practice Session 17.3 — Benchmark JSONB vs a normalized column

**Goal.** Put a number on what it costs to leave an attribute inside a JSONB document, by
measuring plan shape, row estimates, index size and query time for the same question asked
both ways over the same 200,000 rows.

**Setup.** This session needs its own database — the sample datasets have no JSONB column
with enough rows to make the comparison honest.

```bash
createdb ch17_scratch
psql -d ch17_scratch
```

```sql
\pset null '(null)'

CREATE FUNCTION _h(t text) RETURNS bigint LANGUAGE sql IMMUTABLE AS
$$ SELECT ('x' || substr(md5(t), 1, 8))::bit(32)::bigint $$;

CREATE TABLE orders (
    id           int PRIMARY KEY,
    customer_id  int NOT NULL,
    placed_at    timestamptz NOT NULL,
    status       text NOT NULL,
    total_amount numeric(12,2) NOT NULL,
    attrs        jsonb NOT NULL
);

INSERT INTO orders (id, customer_id, placed_at, status, total_amount, attrs)
SELECT i,
       1 + (_h('cust' || i) % 40000)::int,
       TIMESTAMPTZ '2026-01-01 00:00:00+05:30' + ((_h('when' || i) % 21600000) || ' seconds')::interval,
       (ARRAY['pending','paid','shipped','delivered','returned','cancelled'])[1 + (_h('st' || i) % 6)::int],
       round((199 + (_h('amt' || i) % 8980000) / 100.0)::numeric, 2),
       jsonb_build_object(
         'channel',  (ARRAY['app','web','partner','store'])[1 + (_h('ch' || i) % 4)::int],
         'payment',  jsonb_build_object(
                       'method', (ARRAY['upi','card','netbanking','cod','wallet'])[1 + (_h('pm' || i) % 5)::int],
                       'bank',   (ARRAY['HDFC','ICICI','SBI','Axis','Kotak'])[1 + (_h('bk' || i) % 5)::int]),
         'delivery', jsonb_build_object(
                       'city', (ARRAY['Mumbai','Delhi','Bengaluru','Hyderabad','Chennai','Kolkata',
                                      'Pune','Ahmedabad','Jaipur','Kochi','Lucknow','Indore'])[1 + (_h('cy' || i) % 12)::int],
                       'slot', (ARRAY['morning','afternoon','evening'])[1 + (_h('sl' || i) % 3)::int]),
         'gift_wrap', (_h('gw' || i) % 10) = 0,
         'promo',    CASE (_h('pr' || i) % 8)
                       WHEN 0 THEN jsonb_build_array('FESTIVE')
                       WHEN 1 THEN jsonb_build_array('FIRSTBUY')
                       WHEN 2 THEN jsonb_build_array('BANKOFF','FREESHIP')
                       WHEN 3 THEN jsonb_build_array('DIWALI')
                       ELSE jsonb_build_array()
                     END)
       || CASE WHEN (_h('cp' || i) % 500) = 0
               THEN jsonb_build_object('po_number', 'PO-' || (700000 + i))
               ELSE '{}'::jsonb
          END
FROM generate_series(1, 200000) AS i;

ANALYZE orders;
```

Every value derives from `md5()` of the row number rather than `random()`, so your figures
will match the ones printed here. This is the same table Chapter 17 uses.

One exception. Above 30,000 rows `ANALYZE` samples instead of reading every row, so the
planner's row *estimates* and cost figures in step 5 will differ from mine in the last two
or three digits. Actual counts, relation sizes and plan shapes will not.

The question throughout is a realistic one: **how many orders were paid by UPI for delivery
in Kochi?** The answer is 3,340 either way.

**Task.**

1. Build a GIN `jsonb_path_ops` index on `attrs` and get `EXPLAIN (ANALYZE)` for the
   question asked by containment.
2. Build a second table that is identical except that the two attributes have been promoted
   to real `text` columns, index those, and get the same plan. Build it with `CREATE TABLE
   ... AS` rather than `ALTER TABLE ... ADD COLUMN` plus `UPDATE`, and say why that matters
   to a size comparison.
3. Compare the two plans node by node. Which one touches the heap?
4. Compare the four relation sizes. What did promoting the columns actually cost on disk?
5. Compare the planner's row estimate in each case against the true 3,340.
6. Now time both, several runs each, and work out the ratio.
7. Decide, and say what would change your mind.

**Solution.**

**1 — the JSONB baseline.**

```sql
CREATE INDEX orders_attrs_pathops ON orders USING gin (attrs jsonb_path_ops);
VACUUM ANALYZE orders;

EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT count(*) FROM orders
WHERE attrs @> '{"payment": {"method": "upi"}, "delivery": {"city": "Kochi"}}';
```

```text
                                                 QUERY PLAN                                                  
-------------------------------------------------------------------------------------------------------------
 Aggregate (actual rows=1 loops=1)
   ->  Bitmap Heap Scan on orders (actual rows=3340 loops=1)
         Recheck Cond: (attrs @> '{"payment": {"method": "upi"}, "delivery": {"city": "Kochi"}}'::jsonb)
         Heap Blocks: exact=2617
         ->  Bitmap Index Scan on orders_attrs_pathops (actual rows=3340 loops=1)
               Index Cond: (attrs @> '{"payment": {"method": "upi"}, "delivery": {"city": "Kochi"}}'::jsonb)
(6 rows)
```

This is GIN working well. The index scan returns exactly 3,340 rows, so the recheck discards
nothing — no `Rows Removed by Index Recheck` line at all. Note `Heap Blocks: exact=2617`;
it will matter in step 3.

**2 — the promoted copy.**

```sql
CREATE TABLE orders_norm AS
SELECT id, customer_id, placed_at, status, total_amount, attrs,
       attrs #>> '{payment,method}' AS payment_method,
       attrs #>> '{delivery,city}'  AS delivery_city
FROM orders;

CREATE INDEX norm_method_city ON orders_norm (payment_method, delivery_city);
VACUUM ANALYZE orders_norm;
```

`CREATE TABLE ... AS` matters for step 4. The obvious alternative —
`ALTER TABLE orders ADD COLUMN ...` followed by `UPDATE orders SET ...` — is correct but
rewrites all 200,000 rows, since under MVCC an `UPDATE` is a delete plus an insert
(Chapter 30). The table roughly doubles to 100 MB and the GIN index quadruples to 7864 kB,
none of which is the cost of the new columns; it is dead tuples awaiting vacuum. Measuring
storage on that table would attribute bloat to normalization and get the answer badly wrong.

In production you would of course use `ALTER`/`UPDATE`/`VACUUM`, or a batched backfill
(Chapter 52). For a size comparison, build clean.

```sql
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT count(*) FROM orders_norm WHERE payment_method = 'upi' AND delivery_city = 'Kochi';
```

```text
                                        QUERY PLAN                                        
------------------------------------------------------------------------------------------
 Aggregate (actual rows=1 loops=1)
   ->  Index Only Scan using norm_method_city on orders_norm (actual rows=3340 loops=1)
         Index Cond: ((payment_method = 'upi'::text) AND (delivery_city = 'Kochi'::text))
         Heap Fetches: 0
(4 rows)
```

**3 — reading the two plans.**

Same 3,340 rows, and the plans have almost nothing in common.

| | JSONB + GIN | columns + B-tree |
|---|---|---|
| Node | Bitmap Heap Scan over Bitmap Index Scan | **Index Only Scan** |
| Heap blocks read | 2,617 | **0** |
| Recheck needed | yes (discarded nothing) | none |

The decisive line is `Heap Fetches: 0`. Both values the query needs — `payment_method` and
`delivery_city` — are *in the index*, and `count(*)` needs nothing else, so PostgreSQL never
visits the table at all. The GIN plan cannot do that: a GIN entry holds a hash, not the
value, so every candidate row must be fetched from the heap and rechecked. 2,617 heap blocks
is roughly 20 MB of pages touched to answer a question the other plan answers without
reading the table.

> **Trap —** an index-only scan needs the visibility map, which only a **plain** `VACUUM`
> maintains. `VACUUM FULL` rewrites the table and leaves the map empty, so the plan above
> silently degrades to a Bitmap Heap Scan until an ordinary `VACUUM` has run. If you are
> reproducing this and see `Bitmap Heap Scan` on `orders_norm`, run `VACUUM ANALYZE
> orders_norm;` and try again. Chapter 33 covers the visibility map properly.

**4 — what the columns cost on disk.**

```sql
SELECT pg_size_pretty(pg_relation_size('orders'))               AS jsonb_table,
       pg_size_pretty(pg_relation_size('orders_attrs_pathops')) AS gin_index,
       pg_size_pretty(pg_relation_size('orders_norm'))          AS promoted_table,
       pg_size_pretty(pg_relation_size('norm_method_city'))     AS btree_index;
```

```text
 jsonb_table | gin_index | promoted_table | btree_index 
-------------+-----------+----------------+-------------
 49 MB       | 1976 kB   | 52 MB          | 1432 kB
(1 row)
```

Two `text` columns over 200,000 rows cost **3 MB**, about 6% — and note that `orders_norm`
still carries the full `attrs` document as well, so this is the genuinely duplicated case,
the worst-case cost of promotion. The B-tree that replaced the GIN index is *smaller*:
1432 kB against 1976 kB.

So the storage argument for leaving the keys in JSONB does not survive contact with a
measurement. You pay 3 MB and get back 544 kB of index, for a plan that never reads the
table.

```text
               Index Cond: (attrs @> '{"payment": {"method": "upi"}, "delivery": {"city": "Kochi"}}'::jsonb)
(5 rows)
```

```sql
EXPLAIN SELECT count(*) FROM orders_norm WHERE payment_method = 'upi' AND delivery_city = 'Kochi';
```

```text
                                            QUERY PLAN                                             
---------------------------------------------------------------------------------------------------
 Aggregate  (cost=85.55..85.56 rows=1 width=8)
   ->  Index Only Scan using norm_method_city on orders_norm  (cost=0.42..77.42 rows=3250 width=0)
         Index Cond: ((payment_method = 'upi'::text) AND (delivery_city = 'Kochi'::text))
```

3,986 against 3,250, with 3,340 the truth. Both are close, and this is worth being honest
about: **containment estimates are not the disaster that extraction estimates are.** GIN
containment has its own selectivity logic, so `@>` is estimated far better than
`attrs #>> '{payment,method}' = 'upi'`, which falls back to the flat 0.5% guess and lands on

artefact: 5,890.45 against 85.55, a factor of 69 in the planner's own units, arrived at from
roughly correct row counts on both sides.

**6 — the timings.**

Cost units are not milliseconds (Chapter 34), so confirm it on the clock. Run each query
three times in a row and take the last, so the comparison is CPU against CPU rather than
against your disk:

```sql
\timing on

SELECT count(*) FROM orders
WHERE attrs @> '{"payment": {"method": "upi"}, "delivery": {"city": "Kochi"}}';

SELECT count(*) FROM orders_norm WHERE payment_method = 'upi' AND delivery_city = 'Kochi';
```

Query A lands at 2.47 ms, query B at 0.37 ms — a factor of about 7. Smaller than the 69×
separating the cost estimates, and that gap is expected: cost units price disk pages
touched, and both plans fit in cache here. The direction agrees; the magnitude does not
have to.

Whatever the ratio turns out to be, compare it against the 69× separating the two cost
estimates in step 5. Cost units are not milliseconds and the two ratios have no reason to
agree; the cost model is a tool for ranking plans, not for predicting latency.

Your absolute figures will differ from anyone else's, and that is fine. What should *not*
differ is the plan shape — `Index Only Scan` with `Heap Fetches: 0` against a bitmap scan
reading 2,617 heap blocks. If you get a different plan, check that `VACUUM ANALYZE` has run
on both tables. That, not the stopwatch, is the durable result of this session.

**7 — the decision, and what would reverse it.**

Promote the key. On this evidence: a plan that never touches the heap, a smaller index, a
better cost, and — the part that does not show up in any single measurement — a column the
planner has statistics for, that a `CHECK` constraint or foreign key can guard, and that
raises an error rather than returning zero rows when somebody misspells it.

What would change the answer:

- **You cannot enumerate the keys.** If `attrs` genuinely holds per-tenant custom fields,
  there is nothing to promote. That is JSONB's real job.
- **The key is queried rarely and written constantly.** Every promoted column is another
  index to maintain on every write; if nobody filters on it, you have added write cost for
  nothing.
- **The document is the unit of retrieval.** If every query fetches the whole `attrs` blob
  and the application picks it apart, no individual key is hot and promoting one buys
  nothing.

None of those apply to `payment_method`. It is a five-value enumeration that every report
filters on, and it was a column all along.
