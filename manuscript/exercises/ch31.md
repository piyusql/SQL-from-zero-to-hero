# Chapter 31 Exercises — Isolation Levels and Anomalies

These sessions need two terminals, both connected to the same scratch database, each run as
`psql -X -P null='(null)' -d ch31_db`. Transcripts show the prompt (`A=>`, `B=>`) and the
order to type things. A `-- B is now waiting for A` line is not typed: it marks a statement
hanging on a lock, and output that follows without a prompt is that statement completing
after A commits. Errors are shown with `\set VERBOSITY verbose` so the SQLSTATE appears.
The `LOCATION:` line is a server source line and process ids will differ on your machine.

## Practice Session 31.1 — Reproduce each anomaly, then eliminate it

**Goal.** Fill in the table of anomaly by isolation level from runs you did yourself, and
name the cheapest way to remove each anomaly that Read Committed allows.

**Setup.** Create the scratch database and the schema. Re-running the file resets every
table.

```bash
createdb ch31_db
psql -X -d ch31_db -f schema.sql
```

```sql
DROP TABLE IF EXISTS tickets, wards, accounts, doctors, control, receipts CASCADE;
CREATE TABLE accounts (id int PRIMARY KEY, owner text NOT NULL, balance numeric(10,2) NOT NULL);
INSERT INTO accounts VALUES (1, 'Anita Rao', 1000), (2, 'Rajesh Kumar', 1000);
CREATE TABLE doctors (name text PRIMARY KEY, ward text NOT NULL, on_call boolean NOT NULL);
INSERT INTO doctors VALUES ('Dr Priya Menon', 'Kochi ICU', true), ('Dr Arjun Iyer', 'Kochi ICU', true);
CREATE TABLE control (id int PRIMARY KEY, batch int NOT NULL);
INSERT INTO control VALUES (1, 1);
CREATE TABLE receipts (id serial PRIMARY KEY, batch int NOT NULL, amount numeric(10,2) NOT NULL);
CREATE OR REPLACE VIEW si_locks AS   -- predicate locks held in this database only
  SELECT locktype, relation::regclass AS rel, count(*)
  FROM pg_locks
  WHERE mode = 'SIReadLock' AND database = (SELECT oid FROM pg_database WHERE datname = current_database())
  GROUP BY 1, 2 ORDER BY 1, 2;
```

**Task.**

1. **Dirty read.** In A, `BEGIN` and set account 1's balance to 700 without committing. In B,
   begin a transaction at each of `READ UNCOMMITTED`, `READ COMMITTED`, `REPEATABLE READ` and
   `SERIALIZABLE` in turn, read account 1, and commit. Which levels see 700? What does that
   say about `READ UNCOMMITTED`? Roll A back.
2. **Non-repeatable read and phantom.** In B, at Read Committed, run
   `SELECT count(*) AS n, sum(balance) AS total FROM accounts WHERE balance >= 500`. In A,
   insert an account with balance 900 and reduce account 1 by 100. Repeat B's query, then
   commit. Do it again at Repeatable Read (delete A's account and restore the balance first).
3. **Lost update.** Both sessions begin at Read Committed. Each reads the same account's
   balance (1000). A writes 1100 and commits; B writes 1050, computed in the application
   from its read. What is the final balance? Then eliminate the problem three
   ways: (a) an `UPDATE` that does its own arithmetic, (b) `SELECT ... FOR UPDATE` before the
   update, (c) Repeatable Read. For each, say what the losing session sees.
4. **Table.** Fill the table of dirty read, non-repeatable read, phantom read and lost
   update at Read Committed, Repeatable Read and Serializable. Note the two cells where
   PostgreSQL is stricter than the SQL standard.

**Solution.**

Step 1. B sees the committed value at every level:

```text
A=> BEGIN;
BEGIN
A=> UPDATE accounts SET balance = 700 WHERE id = 1;
UPDATE 1
B=> BEGIN ISOLATION LEVEL READ UNCOMMITTED;
BEGIN
B=> SELECT balance FROM accounts WHERE id = 1;
 balance
---------
 1000.00
(1 row)
B=> COMMIT;
COMMIT
B=> BEGIN ISOLATION LEVEL READ COMMITTED;
BEGIN
B=> SELECT balance FROM accounts WHERE id = 1;
 balance
---------
 1000.00
(1 row)
B=> COMMIT;
COMMIT
B=> BEGIN ISOLATION LEVEL REPEATABLE READ;
BEGIN
B=> SELECT balance FROM accounts WHERE id = 1;
 balance
---------
 1000.00
(1 row)
B=> COMMIT;
COMMIT
B=> BEGIN ISOLATION LEVEL SERIALIZABLE;
BEGIN
B=> SELECT balance FROM accounts WHERE id = 1;
 balance
---------
 1000.00
(1 row)
B=> COMMIT;
COMMIT
A=> ROLLBACK;
ROLLBACK
```

No level shows 700.00. PostgreSQL implements `READ UNCOMMITTED` as Read Committed.

Step 2. Read Committed sees both changes; Repeatable Read sees neither:

```text
B=> BEGIN ISOLATION LEVEL READ COMMITTED;
BEGIN
B=> SELECT count(*) AS n, sum(balance) AS total FROM accounts WHERE balance >= 500;
 n |  total
---+---------
 2 | 2000.00
(1 row)
A=> INSERT INTO accounts VALUES (3, 'Meera Banerjee', 900);
INSERT 0 1
A=> UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE 1
B=> SELECT count(*) AS n, sum(balance) AS total FROM accounts WHERE balance >= 500;
 n |  total
---+---------
 3 | 2800.00
(1 row)
B=> COMMIT;
COMMIT
-- (reset: row 3 removed, balance restored)
B=> BEGIN ISOLATION LEVEL REPEATABLE READ;
BEGIN
B=> SELECT count(*) AS n, sum(balance) AS total FROM accounts WHERE balance >= 500;
 n |  total
---+---------
 2 | 2000.00
(1 row)
A=> INSERT INTO accounts VALUES (3, 'Meera Banerjee', 900);
INSERT 0 1
A=> UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE 1
B=> SELECT count(*) AS n, sum(balance) AS total FROM accounts WHERE balance >= 500;
 n |  total
---+---------
 2 | 2000.00
(1 row)
B=> COMMIT;
COMMIT
-- (reset: row 3 removed, balance restored)
```

At Read Committed the second query moves from two rows and 2,000.00 to three rows and
2,800.00: a non-repeatable read (account 1 changed) and a phantom (account 3 appeared). At
Repeatable Read the transaction keeps its first snapshot. The standard allows phantoms at
this level; PostgreSQL does not, and that is the first stricter-than-standard cell.

Step 3. The application-side arithmetic loses A's update, and Repeatable Read turns that into
an error:

```text
(1 row)
-- Repeatable Read: the same application-side update

B=> BEGIN ISOLATION LEVEL REPEATABLE READ;

---------

```

The final balance is 1050.00, A's 100 is gone. Elimination (a), arithmetic inside the
statement, waits for the row lock and then adds to the new version:

```text
-- Read Committed: the arithmetic runs inside the UPDATE
A=> BEGIN;
BEGIN
B=> BEGIN;
BEGIN
A=> UPDATE accounts SET balance = balance + 100 WHERE id = 1;
UPDATE 1
B=> UPDATE accounts SET balance = balance + 50 WHERE id = 1;
-- B is now waiting for A
A=> COMMIT;
COMMIT
UPDATE 1
B=> COMMIT;
COMMIT
B=> SELECT balance FROM accounts WHERE id = 1;

---------

(1 row)
```

Elimination (b), a row lock taken before the read, makes B wait at the `SELECT`. B's read
returns the *new* balance after A commits, so its own computation is right:

```text
A=> BEGIN;
BEGIN
B=> BEGIN;
BEGIN
A=> SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
 balance
---------

(1 row)
B=> SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- B is now waiting for A
A=> UPDATE accounts SET balance = 1100 WHERE id = 1;
UPDATE 1
A=> COMMIT;
COMMIT
 balance
---------
 1100.00
(1 row)
B=> UPDATE accounts SET balance = 1150 WHERE id = 1;
UPDATE 1
B=> COMMIT;
COMMIT
B=> SELECT balance FROM accounts WHERE id = 1;
 balance
---------
 1150.00
(1 row)
```

Elimination (c) is the `40001` at the end of the Step 3 transcript; B must be retried from
`BEGIN` (Session 31.3). Prefer (a) whenever the new value is a function of the old one: it
needs no lock choreography and no retry. Use (b) when the application must *look at* the
value to decide, and (c) when you already have a retry loop.

Step 4. Each cell below is the classified result of a driven run like the ones above. The
table adds write skew (Session 31.2) and the read-only anomaly (a three-session case in the
chapter):

```text
---------------------+------------------+----------------+-----------------+--------------
```

The stricter-than-standard cells are phantom reads at Repeatable Read and dirty reads at

## Practice Session 31.2 — Trigger write skew, fix it two ways

**Goal.** Make two doctors on a Kochi ICU rota both go off call, then stop it with
Serializable and with a lock or constraint, and find out which "fixes" do not work.

**Setup.** The schema from Session 31.1 (`psql -X -d ch31_db -f schema.sql` resets it). The
rule to protect: at least one doctor stays on call.

**Task.**

1. In A and B, at Read Committed, each check `SELECT count(*) FROM doctors WHERE on_call`,
   then A takes Dr Priya Menon off call and B takes Dr Arjun Iyer off call. Commit both.
   Count who is on call. Repeat at Repeatable Read.
2. **Fix 1.** Reset, repeat at `SERIALIZABLE`. Which session fails, on which statement, with
   which SQLSTATE? Who is on call afterwards?
3. **Fix 2a.** Reset. At Read Committed, have each session run
   `SELECT name FROM doctors WHERE on_call FOR UPDATE` before deciding. What does the
   second session get back when it unblocks, and what should it decide?
4. **Fix 2b.** Instead, add a `wards` table holding `on_call_count` with
   `CHECK (on_call_count >= 1)` for `'Kochi ICU'` (starting at 2), and have each session
   decrement it in the same transaction as its roster change. What happens to the second
   session?
5. **Non-fix.** Reset. Use `FOR SHARE` instead of `FOR UPDATE` in step 3. What happens?

Step 4. The counter row is a *materialised conflict*: it turns "two rows, one invariant" into
"one row, one `CHECK`". Setup, then the two sessions (`wards` is created here because the

```text
A=> BEGIN;

BEGIN

UPDATE 1
A=> UPDATE doctors SET on_call = false WHERE name = 'Dr Priya Menon';
UPDATE 1

(1 row)
```

A decrements and commits; B waits for the row lock, re-evaluates against the new value
(0), and the `CHECK` rejects it with `23514`. This is not retryable: retrying yields the same
refusal, which is the correct business answer.

Step 5. `FOR SHARE` lets both sessions lock both rows, so each `UPDATE` waits on the other's

The ERROR is A's blocked `UPDATE` being chosen as the deadlock victim (your process and
transaction ids will differ). The invariant holds, but by a deadlock, not by design, and
A's transaction needs a retry.
Which to choose: Serializable when the invariant is spread over rows you cannot lock in
advance; `FOR UPDATE` or a counter row when you know the set.

## Practice Session 31.3 — Serialization-failure retry loop

**Goal.** Run a retry driver that re-executes a whole transaction on `40001` and `40P01`,
bounded, with jitter; watch it succeed, give up, and refuse an error it must not retry.

**Setup.** Reset the schema (`psql -X -d ch31_db -f schema.sql`) and save these four files in
one directory. `leave.sql` has a *test hook* that runs a rival session on attempt 1 so the
conflict is arranged. `transfer.sql` has a hook that fires on every attempt. `bad.sql` can
never succeed.

```sql
-- leave.sql: a doctor asks to leave the on-call rota.  Variables: who, attempt
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) > 1 AS may_leave FROM doctors WHERE on_call \gset
-- test hook: on the first attempt only, a rival commits the same request while we hold our snapshot
SELECT :attempt = 1 AS rival \gset
\if :rival
  \! psql -X -q -d ch31_db -v ON_ERROR_STOP=1 -v who="Dr Arjun Iyer" -v attempt=2 -f leave.sql
\endif
\if :may_leave
  UPDATE doctors SET on_call = false WHERE name = :'who';
  COMMIT;
  \echo :who left the rota
\else
  ROLLBACK;
  \echo :who must stay: last doctor on call
\endif
```

```sql
-- transfer.sql: read-modify-write in the application.  Variable: attempt
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance AS old FROM accounts WHERE id = 1 \gset
-- test hook: a rival commits an update to the same row on EVERY attempt
\! psql -X -q -d ch31_db -c "UPDATE accounts SET balance = balance + 1 WHERE id = 1"
UPDATE accounts SET balance = :old + 50 WHERE id = 1;
COMMIT;
\echo transfer committed
```

```sql
-- bad.sql: a transaction that can never succeed
BEGIN ISOLATION LEVEL SERIALIZABLE;
INSERT INTO accounts VALUES (1, 'Duplicate Id', 0);
COMMIT;
```

```bash
#!/usr/bin/env bash
# usage: retry.sh MAX_ATTEMPTS FILE [psql args]
# Re-runs the WHOLE file on 40001 (serialization_failure) or 40P01 (deadlock_detected).
max=$1; file=$2; shift 2
for ((attempt = 1; attempt <= max; attempt++)); do
  out=$(psql -X -q -d ch31_db -v ON_ERROR_STOP=1 -v VERBOSITY=verbose \
             -v attempt=$attempt "$@" -f "$file" 2>&1)
  status=$?
  echo "$out"
  if [ $status -eq 0 ]; then echo "attempt $attempt: done"; exit 0; fi
  if ! grep -qE 'ERROR:  (40001|40P01):' <<<"$out"; then
    echo "attempt $attempt: not retryable, giving up"; exit 1
  fi
  [ "$attempt" -lt "$max" ] || break
  echo "attempt $attempt: serialization failure, retrying"
  sleep "$(awk -v a="$attempt" 'BEGIN { srand(); printf "%.3f", rand() * 0.05 * 2^a }')"   # exponential backoff, full jitter
done
echo "gave up after $max attempts"; exit 1
```

Make the driver executable with `chmod +x retry.sh`.

**Task.**

1. Run `./retry.sh 5 leave.sql -v who="Dr Priya Menon"`. What happened on attempt 1, and why
   did attempt 2 not repeat the update?
2. Reset. Run `./retry.sh 3 transfer.sql`. Why does it give up, and what should a real
   application do when the cap is reached?
3. Reset. Run `./retry.sh 3 bad.sql`. Why does the driver stop after one attempt?
4. Copy `leave.sql` to `leave_sms.sql` and add `\echo SMS: :who is going off call` on its own
   line before the `UPDATE`. Reset and run it through the driver. What does the log tell
   you about side effects inside a retried transaction?

**Solution.**

Step 1. Attempt 1 read two doctors on call. While it held that snapshot the rival committed
its own leave, so at the `UPDATE` the server aborted it as a dangerous structure. Attempt 2
started from `BEGIN`, read one doctor on call, and refused:

```text
Dr Arjun Iyer left the rota
psql:leave.sql:10: ERROR:  40001: could not serialize access due to read/write dependencies among transactions
DETAIL:  Reason code: Canceled on identification as a pivot, during write.
HINT:  The transaction might succeed if retried.
LOCATION:  OnConflict_CheckForSerializationFailure, predicate.c:4820
attempt 1: serialization failure, retrying
Dr Priya Menon must stay: last doctor on call
attempt 2: done
```

The retry re-ran the read, so the decision changed. Re-issuing only the failed `UPDATE`
would have taken the last doctor off call.

Step 2. The rival updates the same row on every attempt, so every attempt fails with
`40001` at Repeatable Read:

```text
psql:transfer.sql:6: ERROR:  40001: could not serialize access due to concurrent update
LOCATION:  ExecUpdate, nodeModifyTable.c:2378
attempt 1: serialization failure, retrying
psql:transfer.sql:6: ERROR:  40001: could not serialize access due to concurrent update
LOCATION:  ExecUpdate, nodeModifyTable.c:2378
attempt 2: serialization failure, retrying
psql:transfer.sql:6: ERROR:  40001: could not serialize access due to concurrent update
LOCATION:  ExecUpdate, nodeModifyTable.c:2378
gave up after 3 attempts
```

Three attempts, three failures, and the driver returns non-zero. The cap exists because
retrying can spin forever under sustained contention. At the cap, surface the failure
to the caller (an HTTP 409 or 503 that a client can retry), or park the work on a queue,
and alert if the rate is more than a trickle. Do not loop forever.

Step 3. A duplicate key is `23505`, not a serialization failure. Retrying repeats the error,
so the driver exits after one attempt:

```text
psql:bad.sql:3: ERROR:  23505: duplicate key value violates unique constraint "accounts_pkey"
DETAIL:  Key (id)=(1) already exists.
SCHEMA NAME:  public
TABLE NAME:  accounts
CONSTRAINT NAME:  accounts_pkey
LOCATION:  _bt_check_unique, nbtinsert.c:664
attempt 1: not retryable, giving up
```

Step 4. The `SMS:` line is printed on attempt 1, which was rolled back, and attempt 2
refused the request:

```text
Dr Arjun Iyer left the rota
SMS: Dr Priya Menon is going off call
psql:leave_sms.sql:11: ERROR:  40001: could not serialize access due to read/write dependencies among transactions
DETAIL:  Reason code: Canceled on identification as a pivot, during write.
HINT:  The transaction might succeed if retried.
LOCATION:  OnConflict_CheckForSerializationFailure, predicate.c:4820
attempt 1: serialization failure, retrying
Dr Priya Menon must stay: last doctor on call
attempt 2: done
```

The message went out for a leave that never happened. A retry loop re-executes everything
in the transaction, including side effects outside the database. Send after commit, and make
the send idempotent (an idempotency key the receiver de-duplicates on; Chapter 50 covers
the pattern).
