# Chapter 15 Exercises — Constraints and Referential Integrity

## Practice Session 15.1 — A business rule as a `CHECK`

**Goal.** Take a shipped schema that enforces nothing beyond its primary keys, work out
what its data already guarantees, and turn two real business rules into constraints — 
discovering on the way that a `CHECK` does not stop NULLs and that constraint order matters
when you backfill.

**Setup.** The small `retail` dataset from Practice Session 2.3. You will be creating and
altering tables, so work on a copy rather than on `public`. A schema inside `retail` is the
cheapest copy there is, and it goes away in one statement at the end.

```bash
psql -d retail
```

```sql
\pset null '(null)'

CREATE SCHEMA ch15;
CREATE TABLE ch15.customers (LIKE public.customers INCLUDING ALL);
CREATE TABLE ch15.orders    (LIKE public.orders    INCLUDING ALL);
INSERT INTO ch15.customers SELECT * FROM public.customers;
INSERT INTO ch15.orders    SELECT * FROM public.orders;
SELECT setval(pg_get_serial_sequence('ch15.customers','id'), (SELECT max(id) FROM ch15.customers)),
       setval(pg_get_serial_sequence('ch15.orders','id'),    (SELECT max(id) FROM ch15.orders));
```

```text
CREATE SCHEMA
CREATE TABLE
CREATE TABLE
INSERT 0 1000
INSERT 0 2500
 setval | setval 
--------+--------
   1000 |   2500
(1 row)
```

The `setval` calls matter. `LIKE ... INCLUDING ALL` copies the identity column but not the
sequence's current position, so without them your first `INSERT` collides with an existing
primary key.

Then point the session at the copy, so plain table names resolve there:

```sql
SET search_path = ch15, public;
```

**Task.**

1. Ask the copy what it enforces. Then check what `LIKE ... INCLUDING ALL` did *not* bring
   across.
2. `orders.status` is bare `text`. Establish its real domain from the data, constrain it,
   and prove the constraint bites.
3. The business rule: *an order in `shipped`, `delivered` or `returned` must have a
   `shipped_at`, that date must not precede `placed_at`, and an order in any other state
   must not have a `shipped_at` at all.* Before writing any DDL, count how many existing
   rows break it. Then write the naive version, `CHECK (shipped_at >= placed_at)`, and find
   the hole in it.
4. Write the rule properly and prove it rejects both failure directions.
5. `customers.loyalty_tier` is bare, nullable `text`. Constrain it to `bronze`, `silver`,
   `gold` — then explain why 392 rows still hold a value outside that list. Fix it so the
   column genuinely has a domain, and pay attention to the order in which you run the
   statements.
6. Put back the foreign key that step 1 found missing.

**Solution.**

**1 — what is actually enforced.**

```sql
SELECT conrelid::regclass::text AS on_table, conname, contype
FROM   pg_constraint
WHERE  connamespace = 'ch15'::regnamespace
ORDER  BY 1, 2;
```

```text
 on_table  |    conname     | contype 
-----------+----------------+---------
 customers | customers_pkey | p
 orders    | orders_pkey    | p
(2 rows)
```

Two primary keys and nothing else — and the original `retail` schema is barely richer, with
one self-referencing foreign key on `customers.referred_by` and no `CHECK` anywhere.

`LIKE ... INCLUDING ALL` brought over the primary key, the identity column, the defaults
and the `NOT NULL` flags, which `\d orders` confirms:

```text
                                        Table "ch15.orders"
    Column     |           Type           | Collation | Nullable |             Default              
---------------+--------------------------+-----------+----------+----------------------------------
 id            | integer                  |           | not null | generated by default as identity
 customer_id   | integer                  |           | not null | 
 placed_at     | timestamp with time zone |           | not null | 
 shipped_at    | timestamp with time zone |           |          | 
 status        | text                     |           | not null | 
 discount_code | text                     |           |          | 
 total_amount  | numeric(12,2)            |           | not null | 
Indexes:
    "orders_pkey" PRIMARY KEY, btree (id)
```

What it did **not** bring is the foreign key. `LIKE` never copies foreign keys, on any
option. That is worth filing away: a table cloned with `LIKE ... INCLUDING ALL` for a
staging or backfill job looks complete and is not referentially connected to anything.
Step 6 puts it back.

**2 — a domain for `status`.**

Never guess a column's domain from its name. Ask:

```sql
SELECT status, count(*) FROM orders GROUP BY status ORDER BY status;
```

```text
  status   | count 
-----------+-------
 cancelled |   254
 delivered |   963
 paid      |   266
 pending   |   247
 returned  |   272
 shipped   |   498
(6 rows)
```

Six values. Note what is *not* there: no `refunded`, however natural that word sounds for a
retail system.

```sql
ALTER TABLE orders ADD CONSTRAINT orders_status_known
    CHECK (status IN ('pending','paid','shipped','delivered','returned','cancelled'));
```

```text
ALTER TABLE
```

The `ALTER` succeeded, which is itself information: PostgreSQL scanned all 2,500 rows and
every one satisfied the predicate. Had a single row disagreed, the statement would have
failed and named it. Now the constraint bites:

```sql
INSERT INTO orders (customer_id, placed_at, status, total_amount)
VALUES (1, TIMESTAMPTZ '2026-03-01 10:00+05:30', 'refunded', 1499.00);
```

```text
ERROR:  new row for relation "orders" violates check constraint "orders_status_known"
DETAIL:  Failing row contains (2501, 1, 2026-03-01 04:30:00+00, null, refunded, null, 1499.00).
```

Two details in that output. The identity value 2501 was consumed even though the row was
rejected — sequences are not transactional. And the `DETAIL:` line renders the absent
`shipped_at` as the bare word `null`; that is the server's tuple format, not psql's
`\pset null`, so it does not follow the `(null)` you configured for result grids.

**3 — count the violations before writing the constraint.**

This is the habit worth building. An `ALTER TABLE ... ADD CONSTRAINT` that fails halfway
through a migration window is an avoidable outage; a `SELECT` that tells you in advance
whether it will fail costs nothing.

```sql
SELECT count(*) FILTER (WHERE status IN ('shipped','delivered','returned')
                          AND shipped_at IS NULL)     AS shipped_no_date,
       count(*) FILTER (WHERE status NOT IN ('shipped','delivered','returned')
                          AND shipped_at IS NOT NULL) AS unshipped_with_date,
       count(*) FILTER (WHERE shipped_at < placed_at) AS ships_before_placed
FROM   orders;
```

```text
 shipped_no_date | unshipped_with_date | ships_before_placed 
-----------------+---------------------+---------------------
               0 |                   0 |                   0
(1 row)
```

Clean. The rule can be added without a backfill — which is the happy case, and rare enough
in production that you should be suspicious when you see it.

Now the naive constraint:

```sql
ALTER TABLE orders ADD CONSTRAINT orders_ship_after_place
    CHECK (shipped_at >= placed_at);
```

```text
ALTER TABLE
```

And the hole:

```sql
INSERT INTO orders (customer_id, placed_at, shipped_at, status, total_amount)
VALUES (1, TIMESTAMPTZ '2026-03-01 10:00+05:30', NULL, 'shipped', 1499.00)
RETURNING id, status, shipped_at;
```

```text
  id  | status  | shipped_at 
------+---------+------------
 2502 | shipped | (null)
(1 row)

INSERT 0 1
```

An order whose status is `shipped` and which has no shipping date, accepted by a constraint
written specifically to police shipping dates. The expression evaluated to
`NULL >= TIMESTAMPTZ '2026-03-01 10:00+05:30'`, which is NULL, and **a `CHECK` rejects a
row only when its expression is false**. NULL is not false.

This is the single most common way a `CHECK` constraint fails to do its job, and it is
silent: nobody gets an error, the constraint shows up in `\d`, the migration passed review,
and the bad rows accumulate.

**4 — the rule written properly.**

Clean up the bad row, drop the naive constraint, and express both directions of the rule:

```sql
DELETE FROM orders WHERE id = 2502;
ALTER TABLE orders DROP CONSTRAINT orders_ship_after_place;
ALTER TABLE orders ADD CONSTRAINT orders_shipping_consistent CHECK (
    CASE WHEN status IN ('shipped','delivered','returned')
         THEN shipped_at IS NOT NULL AND shipped_at >= placed_at
         ELSE shipped_at IS NULL
    END
);
```

```text
DELETE 1
ALTER TABLE
ALTER TABLE
```

`CASE` is doing real work here. Both branches return true or false and never NULL: the
`THEN` branch is an `AND` of two `IS`-tests and a comparison guarded by one of them, and
the `ELSE` branch is an `IS NULL` test. A `CHECK` you can prove never evaluates to NULL is
a `CHECK` you can trust.

Both failure directions are now caught. Shipped without a date:

```sql
INSERT INTO orders (customer_id, placed_at, shipped_at, status, total_amount)
VALUES (1, TIMESTAMPTZ '2026-03-01 10:00+05:30', NULL, 'shipped', 1499.00);
```

```text
ERROR:  new row for relation "orders" violates check constraint "orders_shipping_consistent"
DETAIL:  Failing row contains (2503, 1, 2026-03-01 04:30:00+00, null, shipped, null, 1499.00).
```

And a cancelled order that somehow acquired one — order 37 is `cancelled`:

```sql
UPDATE orders SET shipped_at = TIMESTAMPTZ '2026-03-05 09:00+05:30' WHERE id = 37;
```

```text
ERROR:  new row for relation "orders" violates check constraint "orders_shipping_consistent"
DETAIL:  Failing row contains (37, 526, 2025-06-26 19:27:43+00, 2026-03-05 03:30:00+00, cancelled, null, 3227.89).
```

Constraints apply to `UPDATE`, not just `INSERT`. That is obvious written down and
routinely forgotten when someone reasons about "the insert path".

A legitimate row still goes in:

```sql
INSERT INTO orders (customer_id, placed_at, shipped_at, status, total_amount)
VALUES (1, TIMESTAMPTZ '2026-03-01 10:00+05:30', TIMESTAMPTZ '2026-03-03 09:00+05:30',
        'shipped', 1499.00)
RETURNING id, status, shipped_at;
```

```text
  id  | status  |       shipped_at       
------+---------+------------------------
 2504 | shipped | 2026-03-03 03:30:00+00
(1 row)

INSERT 0 1
```

(The `+00` is the session's `TimeZone`, not a change to the value — Chapter 14.)

**5 — `loyalty_tier`, and why a `CHECK` is not enough.**

The column's current contents:

```sql
SELECT loyalty_tier, count(*) FROM customers GROUP BY 1 ORDER BY 1 NULLS LAST;
```

```text
 loyalty_tier | count 
--------------+-------
 bronze       |   225
 gold         |   183
 silver       |   200
 (null)       |   392
(4 rows)
```

Add the obvious constraint:

```sql
ALTER TABLE customers ADD CONSTRAINT customers_tier_known
    CHECK (loyalty_tier IN ('bronze','silver','gold'));
```

```text
ALTER TABLE
```

It succeeded despite 392 rows holding a value not in the list, because for those rows the
expression is `NULL IN (...)`, which is NULL, which is not false. Same rule as step 3,
different disguise — and this time it also means the constraint **validated cleanly against
data that violates the intent**, which is the worst possible combination: a green migration
and an unenforced rule.

Prove the hole is still open:

```sql
INSERT INTO customers (name, email, country, signup_date, loyalty_tier)
VALUES ('Rajesh Kumar', 'rajesh.kumar@example.com', 'IN', DATE '2026-03-01', NULL)
RETURNING id, name, loyalty_tier;
```

```text
  id  |     name     | loyalty_tier 
------+--------------+--------------
 1001 | Rajesh Kumar | (null)
(1 row)

INSERT 0 1
```

The fix needs `NOT NULL`, and `NOT NULL` needs the NULLs gone:

```sql
ALTER TABLE customers ALTER COLUMN loyalty_tier SET NOT NULL;
```

```text
ERROR:  column "loyalty_tier" of relation "customers" contains null values
```

So backfill first. And here is the order trap — try the natural sequence, backfill then
adjust the constraint:

```sql
UPDATE customers SET loyalty_tier = 'none' WHERE loyalty_tier IS NULL;
```

```text
ERROR:  new row for relation "customers" violates check constraint "customers_tier_known"
DETAIL:  Failing row contains (3, Sneha Sheikh, customer3@vyapar.example, AE, Ahmedabad, 2024-02-21, none, null).
```

Of course. `none` is not in `('bronze','silver','gold')`, and the constraint you just added
is enforced on every `UPDATE` immediately, row by row — it does not wait to see whether a
later statement in the same transaction is going to widen it. **Drop the constraint, then
backfill, then add the wider constraint, then add `NOT NULL`:**

```sql
ALTER TABLE customers DROP CONSTRAINT customers_tier_known;
UPDATE customers SET loyalty_tier = 'none' WHERE loyalty_tier IS NULL;
ALTER TABLE customers ADD CONSTRAINT customers_tier_known
    CHECK (loyalty_tier IN ('none','bronze','silver','gold'));
ALTER TABLE customers ALTER COLUMN loyalty_tier SET NOT NULL;
```

```text
ALTER TABLE
UPDATE 393
ALTER TABLE
ALTER TABLE
```

393, not 392 — Rajesh Kumar, whom you inserted with a NULL tier two steps ago, is in there
too. Small, and exactly the kind of drift that makes a count you took an hour ago wrong.

```sql
SELECT loyalty_tier, count(*) FROM customers GROUP BY 1 ORDER BY 1;
```

```text
 loyalty_tier | count 
--------------+-------
 bronze       |   225
 gold         |   183
 none         |   393
 silver       |   200
(4 rows)
```

Now the column has a domain, and nothing can get past it:

```sql
INSERT INTO customers (name, email, country, signup_date, loyalty_tier)
VALUES ('Fatima Sheikh', 'fatima.sheikh@example.com', 'IN', DATE '2026-03-02', NULL);
```

```text
ERROR:  null value in column "loyalty_tier" of relation "customers" violates not-null constraint
DETAIL:  Failing row contains (1002, Fatima Sheikh, fatima.sheikh@example.com, IN, null, 2026-03-02, null, null).
```

**Was replacing NULL with `'none'` the right call?** It is a modelling decision, not an SQL
one, and it turns on what the NULL meant. If it meant *not enrolled in the loyalty
programme* — a real, knowable state — then `'none'` names it, and every future
`GROUP BY loyalty_tier` gets a labelled bucket instead of a blank cell that BI tools render
as a glitch. If it had meant *we have not yet imported this customer's tier*, then `'none'`
would be a lie, and the honest schema keeps the column nullable and documents what NULL
means. You cannot make that call from the data. Ask.

**6 — restore the foreign key.**

```sql
ALTER TABLE orders ADD CONSTRAINT orders_customer_id_fkey
    FOREIGN KEY (customer_id) REFERENCES customers(id);
```

```text
ALTER TABLE
```

Clean, because every `orders.customer_id` exists in `customers`. Had it not been, the
statement would have named the first offending value — and finding the rest one error at a
time is the problem Practice Session 15.3 solves.

The finished schema:

```sql
SELECT conrelid::regclass::text AS on_table, conname, contype
FROM   pg_constraint
WHERE  connamespace = 'ch15'::regnamespace
ORDER  BY 1, 2;
```

```text
 on_table  |          conname           | contype 
-----------+----------------------------+---------
 customers | customers_pkey             | p
 customers | customers_tier_known       | c
 orders    | orders_customer_id_fkey    | f
 orders    | orders_pkey                | p
 orders    | orders_shipping_consistent | c
 orders    | orders_status_known        | c
(6 rows)
```

Six constraints where there were two, and the `NOT NULL` on `loyalty_tier` besides — which
does not appear in that list, because on PostgreSQL 15 a `NOT NULL` is a flag on the column
(`pg_attribute.attnotnull`) rather than a row in `pg_constraint`.

**Clean up.**

```sql
DROP SCHEMA ch15 CASCADE;
```

## Practice Session 15.2 — Prevent overlapping bookings

**Goal.** Make it impossible for two confirmed bookings to overlap on the same meeting
room, using an exclusion constraint, and see it hold under two concurrent transactions that
both checked availability and both found the room free.

**Setup.** This session writes, so build a throwaway database. It also needs two terminals
for the last task.

```bash
createdb ch15_scratch
psql -d ch15_scratch
```

First check that `btree_gist` is available. It is a `contrib` extension, shipped with the
standard PostgreSQL packages but not installed into a database until you ask:

```sql
\pset null '(null)'

SELECT name, default_version, installed_version
FROM   pg_available_extensions WHERE name = 'btree_gist';
```

```text
    name    | default_version | installed_version 
------------+-----------------+-------------------
 btree_gist | 1.7             | (null)
(1 row)
```

Available, not yet installed — `installed_version` is NULL. If the row comes back empty
instead, your packaging has split `contrib` out; on Debian and Ubuntu it is
`postgresql-contrib`, on RHEL family `postgresql15-contrib`.

Set an explicit time zone, so the output below matches yours, and create the table with
only the constraint a beginner would reach for:

```sql
SET TimeZone = 'Asia/Kolkata';

CREATE TABLE meeting_booking (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room      text  NOT NULL,
    booked_by text  NOT NULL,
    slot      tstzrange NOT NULL,
    status    text  NOT NULL DEFAULT 'confirmed'
              CHECK (status IN ('confirmed','cancelled')),
    CONSTRAINT meeting_booking_room_slot_key UNIQUE (room, slot)
);
```

**Task.**

1. Show that `UNIQUE (room, slot)` does not prevent double booking.
2. Replace it with an exclusion constraint that does — and notice what happens when you try
   to add it while the table still holds an overlap.
3. Verify three behaviours: an overlap is rejected, a back-to-back booking is allowed, and
   a *cancelled* booking does not block the slot.
4. In two terminals, have both sessions run the "is this room free?" query, both get zero
   conflicts, and both then insert. Explain what happens and why an application-level check
   could never have prevented it.

**Solution.**

**1 — `UNIQUE` cannot express "must not overlap".**

```sql
INSERT INTO meeting_booking (room, booked_by, slot) VALUES
  ('Nilgiri','Anita Rao',      tstzrange('2026-04-13 09:00+05:30','2026-04-13 10:00+05:30')),
  ('Nilgiri','Harpreet Singh', tstzrange('2026-04-13 09:30+05:30','2026-04-13 10:30+05:30'));

SELECT id, room, booked_by, slot FROM meeting_booking ORDER BY id;
```

```text
 id |  room   |   booked_by    |                           slot                            
----+---------+----------------+-----------------------------------------------------------
  1 | Nilgiri | Anita Rao      | ["2026-04-13 09:00:00+05:30","2026-04-13 10:00:00+05:30")
  2 | Nilgiri | Harpreet Singh | ["2026-04-13 09:30:00+05:30","2026-04-13 10:30:00+05:30")
(2 rows)
```

Both accepted. The two rows are genuinely distinct on `(room, slot)` — the ranges are not
equal — and equality is the only question a unique index knows how to ask. Anita and
Harpreet now have the same room at 09:30.

**2 — the exclusion constraint, and the state it refuses to start from.**

Try the constraint before installing anything:

```sql
ALTER TABLE meeting_booking ADD CONSTRAINT meeting_booking_no_overlap
    EXCLUDE USING gist (room WITH =, slot WITH &&) WHERE (status = 'confirmed');
```

```text
ERROR:  data type text has no default operator class for access method "gist"
HINT:  You must specify an operator class for the index or define a default operator class for the data type.
```

GiST knows how to index ranges out of the box but not scalars, and `room` is `text`. That
is precisely the gap `btree_gist` fills:

```sql
CREATE EXTENSION btree_gist;
ALTER TABLE meeting_booking DROP CONSTRAINT meeting_booking_room_slot_key;
```

```text
CREATE EXTENSION
ALTER TABLE
```

```sql
ALTER TABLE meeting_booking ADD CONSTRAINT meeting_booking_no_overlap
    EXCLUDE USING gist (room WITH =, slot WITH &&) WHERE (status = 'confirmed');
```

```text
ERROR:  could not create exclusion constraint "meeting_booking_no_overlap"
DETAIL:  Key (room, slot)=(Nilgiri, ["2026-04-13 09:00:00+05:30","2026-04-13 10:00:00+05:30")) conflicts with key (room, slot)=(Nilgiri, ["2026-04-13 09:30:00+05:30","2026-04-13 10:30:00+05:30")).
```

You cannot add the rule until the data obeys it, and the error names both offenders. That
is the normal shape of this work: the constraint is easy, the cleanup is the project.
Resolve the clash and try again:

```sql
DELETE FROM meeting_booking WHERE id = 2;
```

```text
DELETE 1
```

```sql
ALTER TABLE meeting_booking ADD CONSTRAINT meeting_booking_no_overlap
    EXCLUDE USING gist (room WITH =, slot WITH &&) WHERE (status = 'confirmed');
```

```text
ALTER TABLE
```

Three pieces are doing work in that constraint, and all three are needed:

- **`USING gist`** — overlap (`&&`) is not a B-tree operator. GiST is the access method
  that can answer "does this range overlap any stored range?".
- **`btree_gist`** — it supplies the GiST operator classes for `text`, `integer` and the
  other scalar types, which is what the first attempt was missing.
- **`WHERE (status = 'confirmed')`** — an exclusion constraint takes a predicate, exactly
  like a partial index. Cancelled bookings stay in the table as history and stop competing
  for the slot.

**3 — the three behaviours.**

```sql
INSERT INTO meeting_booking (room, booked_by, slot) VALUES
  ('Nilgiri', 'Harpreet Singh', tstzrange('2026-04-13 10:00+05:30','2026-04-13 11:00+05:30')),
  ('Sahyadri','Meera Banerjee', tstzrange('2026-04-13 09:30+05:30','2026-04-13 11:00+05:30'));

SELECT id, room, booked_by, slot FROM meeting_booking ORDER BY room, slot;
```

```text
 id |   room   |   booked_by    |                           slot                            
----+----------+----------------+-----------------------------------------------------------
  1 | Nilgiri  | Anita Rao      | ["2026-04-13 09:00:00+05:30","2026-04-13 10:00:00+05:30")
  3 | Nilgiri  | Harpreet Singh | ["2026-04-13 10:00:00+05:30","2026-04-13 11:00:00+05:30")
  4 | Sahyadri | Meera Banerjee | ["2026-04-13 09:30:00+05:30","2026-04-13 11:00:00+05:30")
(3 rows)
```

**Back-to-back works.** Booking 1 ends at 10:00 and booking 3 starts at 10:00, and they do
not conflict, because `tstzrange` is half-open by default: the square bracket on the left
includes the lower bound, the parenthesis on the right excludes the upper. Had the
constructor produced `[09:00, 10:00]`, the 10:00 instant would belong to both bookings and
the second insert would have failed. Bound convention is the thing to get right in any
scheduling schema, and the printed value tells you which one you got.

**Overlap is rejected.**

```sql
INSERT INTO meeting_booking (room, booked_by, slot)
VALUES ('Nilgiri', 'Arjun Iyer', tstzrange('2026-04-13 09:30+05:30','2026-04-13 10:30+05:30'));
```

```text
ERROR:  conflicting key value violates exclusion constraint "meeting_booking_no_overlap"
DETAIL:  Key (room, slot)=(Nilgiri, ["2026-04-13 09:30:00+05:30","2026-04-13 10:30:00+05:30")) conflicts with existing key (room, slot)=(Nilgiri, ["2026-04-13 09:00:00+05:30","2026-04-13 10:00:00+05:30")).
```

The message names the booking it clashed with, which is what a user needs to see: not
"that slot is taken" but "Anita Rao has Nilgiri from 09:00".

**A cancelled booking frees the slot.**

```sql
UPDATE meeting_booking SET status = 'cancelled' WHERE id = 1;
```

```text
UPDATE 1
```

```sql
INSERT INTO meeting_booking (room, booked_by, slot)
VALUES ('Nilgiri', 'Arjun Iyer', tstzrange('2026-04-13 09:00+05:30','2026-04-13 10:00+05:30'))
RETURNING id, room, booked_by, slot;
```

```text
 id |  room   | booked_by  |                           slot                            
----+---------+------------+-----------------------------------------------------------
  6 | Nilgiri | Arjun Iyer | ["2026-04-13 09:00:00+05:30","2026-04-13 10:00:00+05:30")
(1 row)

INSERT 0 1
```

Arjun gets the exact slot Anita cancelled, and Anita's row is still there for the audit
trail. `id` jumped to 6 because 2 belonged to the booking you deleted and 5 to the insert
the constraint rejected — identity sequences do not reuse numbers.

**4 — the race the constraint closes.**

This is the part worth doing carefully, because it is the argument for putting the rule in
the database at all. Open two `psql` sessions on `ch15_scratch`, and run
`SET TimeZone = 'Asia/Kolkata';` in both.

**Terminal 1** — the check an application would do, then the insert, and *do not commit*:

```sql
BEGIN;
SELECT count(*) AS conflicts FROM meeting_booking
WHERE  room = 'Nilgiri' AND status = 'confirmed'
AND    slot && tstzrange('2026-04-13 14:00+05:30','2026-04-13 15:00+05:30');
```

```text
 conflicts 
-----------
         0
(1 row)
```

```sql
INSERT INTO meeting_booking (room, booked_by, slot)
VALUES ('Nilgiri', 'Priya Menon', tstzrange('2026-04-13 14:00+05:30','2026-04-13 15:00+05:30'));
```

**Terminal 2** — a different user, an overlapping slot, the same availability check:

```sql
BEGIN;
SELECT count(*) AS conflicts FROM meeting_booking
WHERE  room = 'Nilgiri' AND status = 'confirmed'
AND    slot && tstzrange('2026-04-13 14:30+05:30','2026-04-13 15:30+05:30');
```

```text
 conflicts 
-----------
         0
(1 row)
```

**Zero conflicts, and terminal 1's booking already exists.** Terminal 2 cannot see it,
because it is uncommitted, and no isolation level would help: under Read Committed the row
is invisible, and under Repeatable Read or Serializable terminal 2's snapshot predates it.
Every application-level "is it free?" check has this window. It is not a bug in the
application; it is what the query means.

Now terminal 2 inserts:

```sql
INSERT INTO meeting_booking (room, booked_by, slot)
VALUES ('Nilgiri', 'Rajesh Kumar', tstzrange('2026-04-13 14:30+05:30','2026-04-13 15:30+05:30'));
```

It **blocks**. The exclusion constraint has found a conflicting entry belonging to an
in-flight transaction and must wait to learn its fate. Commit in terminal 1, and terminal 2
resolves immediately:

```text
ERROR:  conflicting key value violates exclusion constraint "meeting_booking_no_overlap"
DETAIL:  Key (room, slot)=(Nilgiri, ["2026-04-13 14:30:00+05:30","2026-04-13 15:30:00+05:30")) conflicts with existing key (room, slot)=(Nilgiri, ["2026-04-13 14:00:00+05:30","2026-04-13 15:00:00+05:30")).
```

Had terminal 1 rolled back instead, terminal 2's insert would have succeeded. Either way
exactly one booking survives, with no application coordination, no advisory lock, and no
`SELECT ... FOR UPDATE` on a row that does not exist yet.

The application still has work to do — it must catch the error and present it as *"someone
just took that slot"* rather than a stack trace, and under load it should expect it. But
the correctness is not its problem any more. That is the whole point of a constraint: it
converts a race into an error, and an error is something you can handle.

> **Trap —** the blocking above means a long-running transaction that has inserted a
> booking holds every overlapping booking attempt hostage until it ends. Keep transactions
> that write to a constrained table short. Chapter 32 covers lock waits and how to find
> them.

**Clean up.** Keep the database if you are going straight on to Practice Session 15.3;
otherwise `\q` and `dropdb ch15_scratch`.

## Practice Session 15.3 — Add a foreign key to a large table without a long lock

**Goal.** Add a foreign key to a three-million-row table while writes to it continue, by
reading the exact lock mode each step takes out of `pg_locks` and splitting the operation
into `NOT VALID` plus `VALIDATE CONSTRAINT`.

**Setup.** A throwaway database and two terminals. If you still have `ch15_scratch` from
Practice Session 15.2 you can reuse it; the table names below do not collide.

```bash
createdb ch15_scratch     # skip if it already exists
psql -d ch15_scratch
```

```sql
\pset null '(null)'

CREATE TABLE depot (
    id   int  PRIMARY KEY,
    code text NOT NULL UNIQUE,
    city text NOT NULL
);
INSERT INTO depot
SELECT g, 'DEP-' || lpad(g::text, 4, '0'),
       (ARRAY['Mumbai','Delhi','Bengaluru','Hyderabad','Chennai',
              'Kolkata','Pune','Ahmedabad','Jaipur','Kochi'])[1 + g % 10]
FROM   generate_series(1, 400) g;

CREATE TABLE shipment_leg (
    id       bigint PRIMARY KEY,
    depot_id int  NOT NULL,
    leg_on   date NOT NULL,
    km       numeric(8,1) NOT NULL
);
INSERT INTO shipment_leg
SELECT g, 1 + (g % 400), DATE '2025-01-01' + (g % 400), (g % 1800) / 2.0
FROM   generate_series(1, 3000000) g;

ANALYZE depot;
ANALYZE shipment_leg;
```

That produces about 214 MB. Confirm:

```sql
SELECT (SELECT count(*) FROM depot) AS depots, (SELECT count(*) FROM shipment_leg) AS legs;
```

```text
 depots |  legs   
--------+---------
    400 | 3000000
(1 row)
```

`shipment_leg.depot_id` is logically a foreign key and is not declared as one. That is a
very common state for a table that predates its own schema discipline, and your job is to
declare it without taking the application down.

**Task.**

1. Find out which lock the naive `ALTER TABLE ... ADD FOREIGN KEY` takes, on which tables,
   by reading `pg_locks` from inside the transaction that took it. Roll back.
2. Prove what that lock mode does to a concurrent writer, and to a concurrent reader.
3. Someone has already inserted a leg pointing at a depot that does not exist. Simulate
   that, then perform the two-step: `NOT VALID`, then find and fix the bad data, then
   `VALIDATE CONSTRAINT`. Read the lock at each step.
4. You are not finished when the constraint is valid. Work out what else the child table
   needs and add it without taking a lock either.

**Solution.**

**1 — the lock the obvious statement takes.**

You do not need to guess and you do not need documentation. Take the lock inside a
transaction and ask the server:

```sql
BEGIN;
ALTER TABLE shipment_leg ADD CONSTRAINT shipment_leg_depot_fk
    FOREIGN KEY (depot_id) REFERENCES depot(id);
SELECT c.relname, l.mode
FROM   pg_locks l JOIN pg_class c ON c.oid = l.relation
WHERE  l.pid = pg_backend_pid()
AND    c.relname IN ('shipment_leg', 'depot')
ORDER  BY c.relname, l.mode;
ROLLBACK;
```

```text
   relname    |         mode          
--------------+-----------------------
 depot        | AccessShareLock
 depot        | RowShareLock
 depot        | ShareRowExclusiveLock
 shipment_leg | AccessShareLock
 shipment_leg | ShareRowExclusiveLock
(5 rows)
```

`ShareRowExclusiveLock` on **both** tables. The `RowShareLock` on `depot` is the validation
scan reading it, and the two `AccessShareLock` rows are the `pg_locks` query itself touching
the tables it is reporting on.

The important line is the one people do not expect: the *parent* table is locked too. A
foreign key is a rule about a pair of tables, so adding it takes a write lock on a table
that has nothing wrong with it and may be far busier than the child.

Note that the statement completed — the transaction scanned all three million rows before
you ran the `SELECT` — and that the `ROLLBACK` undid it. Transactional DDL is one of
PostgreSQL's genuine advantages, and it is what makes this measurement safe to take on a
system you care about.

**2 — what `ShareRowExclusiveLock` costs.**

Simulate the lock without doing the DDL. **Terminal 1:**

```sql
BEGIN;
LOCK TABLE shipment_leg IN SHARE ROW EXCLUSIVE MODE;
```

Leave it open. **Terminal 2**, a writer, with a timeout so you are not stuck:

```sql
SET lock_timeout = '3s';
INSERT INTO shipment_leg VALUES (3000001, 12, DATE '2026-03-01', 118.5);
```

```text
ERROR:  canceling statement due to lock timeout
LINE 1: INSERT INTO shipment_leg VALUES (3000001, 12, DATE '2026-03-...
                    ^
```

Blocked. A reader is not:

```sql
SELECT count(*) FROM shipment_leg WHERE depot_id = 12;
```

```text
 count 
-------
  7500
(1 row)
```

So the naive `ADD FOREIGN KEY` lets the site keep serving pages and stops it taking orders,
for as long as the scan runs. That asymmetry is why this variant of the mistake survives
code review: a smoke test that only reads passes.

Now compare against the lock `VALIDATE CONSTRAINT` will turn out to take. `ROLLBACK` in
terminal 1 and instead:

```sql
BEGIN;
LOCK TABLE shipment_leg IN SHARE UPDATE EXCLUSIVE MODE;
```

**Terminal 2**, same insert:

```sql
SET lock_timeout = '3s';
INSERT INTO shipment_leg VALUES (3000002, 12, DATE '2026-03-01', 118.5);
```

```text
INSERT 0 1
```

Straight through. Remember that result; it is the whole reason for the two-step.

`ROLLBACK` in terminal 1, and tidy up in terminal 2:

```sql
DELETE FROM shipment_leg WHERE id > 3000000;
```

**3 — the two-step.**

First create the mess you will actually find in production — one leg pointing at a depot
that no longer exists:

```sql
INSERT INTO shipment_leg VALUES (3000001, 777, DATE '2026-03-01', 118.5);
```

```text
INSERT 0 1
```

Step one, `NOT VALID`. Set `lock_timeout` first: the statement still needs
`ShareRowExclusiveLock`, so if a long-running transaction is holding the table it will
queue — and everything arriving behind it will queue behind *that*. Failing fast and
retrying is almost always better than joining the queue.

```sql
SET lock_timeout = '3s';
ALTER TABLE shipment_leg ADD CONSTRAINT shipment_leg_depot_fk
    FOREIGN KEY (depot_id) REFERENCES depot(id) NOT VALID;
```

```text
SET
ALTER TABLE
```

It succeeded despite the bad row, which is exactly what `NOT VALID` means: *record this
rule, do not check what is already here.*

```sql
SELECT conname, convalidated FROM pg_constraint
WHERE  conrelid = 'shipment_leg'::regclass ORDER BY conname;
```

```text
        conname        | convalidated 
-----------------------+--------------
 shipment_leg_depot_fk | f
 shipment_leg_pkey     | t
(2 rows)
```

`convalidated = f`. But — and this is the part that makes the technique valuable rather
than merely clever — **new writes are enforced immediately**:

```sql
INSERT INTO shipment_leg VALUES (3000002, 888, DATE '2026-03-02', 40.0);
```

```text
ERROR:  insert or update on table "shipment_leg" violates foreign key constraint "shipment_leg_depot_fk"
DETAIL:  Key (depot_id)=(888) is not present in table "depot".
```

The table stops getting worse the moment the constraint exists. Whatever is already broken
can be repaired on a schedule you choose rather than inside a migration window.

Step two, validate — which fails, because of the row you planted:

```sql
ALTER TABLE shipment_leg VALIDATE CONSTRAINT shipment_leg_depot_fk;
```

```text
ERROR:  insert or update on table "shipment_leg" violates foreign key constraint "shipment_leg_depot_fk"
DETAIL:  Key (depot_id)=(777) is not present in table "depot".
```

One value per attempt. On a table with thousands of orphans that is thousands of round
trips, so do not iterate — ask for the whole set at once with an anti-join:

```sql
SELECT s.id, s.depot_id
FROM   shipment_leg s
LEFT   JOIN depot d ON d.id = s.depot_id
WHERE  d.id IS NULL
ORDER  BY s.id;
```

```text
   id    | depot_id 
---------+----------
 3000001 |      777
(1 row)
```

What you do with them is a business decision, not a technical one: delete them, point them
at a placeholder depot, or create the missing depots. Here, delete:

```sql
DELETE FROM shipment_leg WHERE id = 3000001;
```

```text
DELETE 1
```

Now validate, and read the lock while you hold it:

```sql
BEGIN;
ALTER TABLE shipment_leg VALIDATE CONSTRAINT shipment_leg_depot_fk;
SELECT c.relname, l.mode
FROM   pg_locks l JOIN pg_class c ON c.oid = l.relation
WHERE  l.pid = pg_backend_pid()
AND    c.relname IN ('shipment_leg', 'depot')
ORDER  BY c.relname, l.mode;
COMMIT;
```

```text
   relname    |           mode           
--------------+--------------------------
 depot        | AccessShareLock
 depot        | RowShareLock
 shipment_leg | AccessShareLock
 shipment_leg | ShareUpdateExclusiveLock
(4 rows)
```

**That is the answer to the exercise.** `ShareUpdateExclusiveLock` on the child, and only
`RowShareLock` on the parent — the same mode an ordinary `SELECT ... FOR KEY SHARE` takes.
Neither conflicts with `INSERT`, `UPDATE` or `DELETE`. Step 2 proved that: an insert sailed
through a held `SHARE UPDATE EXCLUSIVE` lock. The three-million-row scan now runs against a
live, writable table.

```sql
SELECT conname, convalidated FROM pg_constraint WHERE conname = 'shipment_leg_depot_fk';
```

```text
        conname        | convalidated 
-----------------------+--------------
 shipment_leg_depot_fk | t
(1 row)
```

Two cautions on `ShareUpdateExclusiveLock`. It conflicts with **itself**, and with `VACUUM`,
`ANALYZE`, `CREATE INDEX CONCURRENTLY` and most other `ALTER TABLE` forms — so run one at a
time, and expect autovacuum to be pushed aside on a table you are validating. And the
`NOT VALID` step in the middle still needed `ShareRowExclusiveLock`; the two-step shortens
that window to a metadata change, it does not remove it.

**4 — the thing that is still missing.**

The foreign key is valid, and the child table is still unindexed on the referencing column.
PostgreSQL indexes the *referenced* side for you — it has to, a foreign key requires a
unique index on the parent — but never the referencing side. Every time a depot row is
deleted or its key updated, the server runs this:

```sql
EXPLAIN SELECT 1 FROM shipment_leg WHERE depot_id = 12 FOR KEY SHARE;
```

```text
                                QUERY PLAN                                
--------------------------------------------------------------------------
 LockRows  (cost=0.00..56683.63 rows=7463 width=10)
   ->  Seq Scan on shipment_leg  (cost=0.00..56609.00 rows=7463 width=10)
         Filter: (depot_id = 12)
(3 rows)
```

A sequential scan of three million rows, per deleted parent row. Delete a hundred
decommissioned depots in one statement and you have a hundred of those.

Fix it, and keep the theme of the session by not taking a blocking lock:

```sql
CREATE INDEX CONCURRENTLY shipment_leg_depot_id_idx ON shipment_leg (depot_id);
```

```text
CREATE INDEX
```

```sql
EXPLAIN SELECT 1 FROM shipment_leg WHERE depot_id = 12 FOR KEY SHARE;
```

```text
                                            QUERY PLAN                                            
--------------------------------------------------------------------------------------------------
 LockRows  (cost=86.27..14522.48 rows=7463 width=10)
   ->  Bitmap Heap Scan on shipment_leg  (cost=86.27..14447.85 rows=7463 width=10)
         Recheck Cond: (depot_id = 12)
         ->  Bitmap Index Scan on shipment_leg_depot_id_idx  (cost=0.00..84.40 rows=7463 width=0)
               Index Cond: (depot_id = 12)
(5 rows)
```

`CREATE INDEX CONCURRENTLY` takes `ShareUpdateExclusiveLock` too — watch it from a second
terminal while the first builds the index and `pg_locks` will show exactly that — so writes
continue here as well. It does two passes over the table instead of one, and cannot run
inside a transaction block. Its failure mode is worth knowing before you use it in anger:
if it aborts, it leaves an invalid index behind that you must find and drop by hand.
Chapter 33 covers it, and Chapter 52 covers the whole family of online-migration techniques
this session belongs to.

**The recipe, for your migration checklist.**

```sql
SET lock_timeout = '3s';
ALTER TABLE child ADD CONSTRAINT child_parent_fk
    FOREIGN KEY (parent_id) REFERENCES parent(id) NOT VALID;   -- ShareRowExclusive, momentary

-- find and repair orphans with an anti-join, at your leisure

ALTER TABLE child VALIDATE CONSTRAINT child_parent_fk;         -- ShareUpdateExclusive, writes continue
CREATE INDEX CONCURRENTLY child_parent_id_idx ON child (parent_id);
```

**Clean up.**

```bash
dropdb ch15_scratch
```
