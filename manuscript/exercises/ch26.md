# Chapter 26 Exercises — Advanced Aggregation

## Practice Session 26.1 — Multi-level report with `ROLLUP`

**Goal.** Produce revenue by product category and customer loyalty tier, with a subtotal
per category and a grand total, from one query, and label every row so a reader cannot
mistake a subtotal for missing data.

**Setup.** The small `retail` dataset, read only. Run everything with `psql -q`.

```sql
\c retail
\pset null '(null)'
SET max_parallel_workers_per_gather = 0;

SELECT count(*) AS lines, count(*) FILTER (WHERE c.loyalty_tier IS NULL) AS lines_without_tier
FROM order_items oi JOIN orders o ON o.id = oi.order_id
JOIN customers c ON c.id = o.customer_id;
```

```text
 lines | lines_without_tier
-------+--------------------
  6250 |               2439
(1 row)
```

**Task.**

1. Write a `ROLLUP (category, loyalty_tier)` query over `order_items`, `orders`,
   `customers` and `products`, computing `sum(quantity * unit_price)` as `revenue`, the
   line count, and `grouping(category, loyalty_tier)`. Restrict to the `kitchen` and
   `lighting` categories to keep it readable.
2. Find the two rows that show `(null)` in `loyalty_tier` for the same category. Say which
   is the subtotal and which is customers with no tier, and how `grouping()` tells you.
3. Rewrite it for all categories with human labels: `ALL categories`, `ALL tiers`,
   `(none)` for the real NULL. Order subtotals directly after their category.
4. Prove the report reconciles: the grand total must equal `sum(quantity * unit_price)`
   over `order_items` alone, and the `kitchen` subtotal must equal the same figure computed
   with a plain `WHERE category = 'kitchen'`.
5. Predict, then count, the output rows of `CUBE (category, loyalty_tier, country,
   status)` over the same join. How many grouping sets is that?

**Solution.**

```sql
SELECT p.category, c.loyalty_tier, sum(oi.quantity * oi.unit_price) AS revenue,
       count(*) AS lines, grouping(p.category, c.loyalty_tier) AS g
FROM order_items oi JOIN orders o ON o.id = oi.order_id
JOIN customers c ON c.id = o.customer_id JOIN products p ON p.id = oi.product_id
WHERE p.category IN ('kitchen', 'lighting')
GROUP BY ROLLUP (p.category, c.loyalty_tier)
ORDER BY grouping(p.category), p.category, grouping(c.loyalty_tier), c.loyalty_tier;
```

set because `loyalty_tier` was rolled up. Nothing in the two visible columns separates
them. The last row, `g = 3`, is the grand total.

```sql
SELECT CASE WHEN grouping(p.category) = 1 THEN 'ALL categories' ELSE p.category END AS category,
       CASE WHEN grouping(c.loyalty_tier) = 1 THEN 'ALL tiers'

       sum(oi.quantity * oi.unit_price) AS revenue
FROM order_items oi JOIN orders o ON o.id = oi.order_id
JOIN customers c ON c.id = o.customer_id JOIN products p ON p.id = oi.product_id
GROUP BY ROLLUP (p.category, c.loyalty_tier)
ORDER BY grouping(p.category), p.category, grouping(c.loyalty_tier), c.loyalty_tier;

SELECT sum(quantity * unit_price) AS all_lines FROM order_items;

SELECT sum(oi.quantity * oi.unit_price) AS kitchen_only
FROM order_items oi JOIN products p ON p.id = oi.product_id

```

The first figure matches the `ALL categories | ALL tiers` row (3,678,982.61) and the second
matches the kitchen subtotal (753,526.36). A rollup you have not reconciled to an
independent total is a rollup you are guessing about.

```sql
SELECT count(DISTINCT g) AS grouping_sets, count(*) AS output_rows
FROM (SELECT grouping(p.category, c.loyalty_tier, c.country, o.status) AS g
      FROM order_items oi JOIN orders o ON o.id = oi.order_id
      JOIN customers c ON c.id = o.customer_id JOIN products p ON p.id = oi.product_id
      GROUP BY CUBE (p.category, c.loyalty_tier, c.country, o.status)) s;
```

```text

---------------+-------------
            16 |        1503
(1 row)
```

Four dimensions is 2⁴ = 16 sets and 1,503 output rows, from 6,250 input lines. The
`CUBE` did not reduce the data, it multiplied the ways of looking at it. Write the
`GROUPING SETS` the report needs instead.

## Practice Session 26.2 — Replace `CASE`-in-`SUM` with `FILTER`

**Goal.** Convert a legacy pivot report from `CASE` expressions to `FILTER`, and find the
two columns that were silently wrong.

**Setup.** The small `retail` dataset, read only. The legacy query below was written by
someone who, understandably, believed every `CASE` did the same thing.

```sql
\c retail
\pset null '(null)'

SELECT c.city,
       count(CASE WHEN o.status = 'delivered' THEN 1 ELSE 0 END)         AS delivered_orders,
       sum(CASE WHEN o.status = 'delivered' THEN o.total_amount END)     AS delivered_revenue,
       avg(CASE WHEN o.status = 'returned' THEN o.total_amount ELSE 0 END) AS avg_returned,
       sum(CASE WHEN o.status = 'cancelled' THEN 1 ELSE 0 END)           AS cancelled_orders
FROM orders o JOIN customers c ON c.id = o.customer_id
WHERE c.city IN ('Pune', 'Kochi', 'Indore')
GROUP BY c.city ORDER BY c.city;
```

```text
  city  | delivered_orders | delivered_revenue |     avg_returned     | cancelled_orders
--------+------------------+-------------------+----------------------+------------------
 Indore |               90 |          55701.37 | 127.2723333333333333 |                8
 Kochi  |              126 |          94529.37 | 123.2047619047619048 |               17
 Pune   |               96 |          38799.19 | 284.6935416666666667 |                8
(3 rows)
```

**Task.**

1. Rewrite the query with `FILTER`, one aggregate for one aggregate.
2. Compare the two versions column by column in a single query, using a join on `city`
   and `IS NOT DISTINCT FROM`. Which columns agree?
3. For each column that disagrees, say what the legacy expression computed instead. Check
   your explanation against a plain `GROUP BY` with a `WHERE status = 'delivered'`.
4. Show that `FILTER` does not remove the need for `coalesce`: build a case where a
   group has no matching rows.
5. Show that the `CASE` and `FILTER` forms read the table the same way, using
   `EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF)`. Do not time them.

**Solution.**

```sql
WITH legacy AS (
  SELECT c.city,
         count(CASE WHEN o.status = 'delivered' THEN 1 ELSE 0 END)         AS delivered_orders,
         sum(CASE WHEN o.status = 'delivered' THEN o.total_amount END)     AS delivered_revenue,
         avg(CASE WHEN o.status = 'returned' THEN o.total_amount ELSE 0 END) AS avg_returned,
         sum(CASE WHEN o.status = 'cancelled' THEN 1 ELSE 0 END)           AS cancelled_orders
  FROM orders o JOIN customers c ON c.id = o.customer_id
  WHERE c.city IN ('Pune', 'Kochi', 'Indore') GROUP BY c.city
), fixed AS (
  SELECT c.city,
         count(*) FILTER (WHERE o.status = 'delivered')                    AS delivered_orders,
         sum(o.total_amount) FILTER (WHERE o.status = 'delivered')         AS delivered_revenue,
         avg(o.total_amount) FILTER (WHERE o.status = 'returned')          AS avg_returned,
         count(*) FILTER (WHERE o.status = 'cancelled')                    AS cancelled_orders
  FROM orders o JOIN customers c ON c.id = o.customer_id
  WHERE c.city IN ('Pune', 'Kochi', 'Indore') GROUP BY c.city
)
SELECT bool_and(l.delivered_orders  IS NOT DISTINCT FROM f.delivered_orders)  AS orders_agree,
       bool_and(l.delivered_revenue IS NOT DISTINCT FROM f.delivered_revenue) AS revenue_agree,
       bool_and(l.avg_returned      IS NOT DISTINCT FROM f.avg_returned)      AS avg_agree,
       bool_and(l.cancelled_orders  IS NOT DISTINCT FROM f.cancelled_orders)  AS cancelled_agree
FROM legacy l JOIN fixed f USING (city);
```

```text
 orders_agree | revenue_agree | avg_agree | cancelled_agree
--------------+---------------+-----------+-----------------
 f            | t             | f         | t
(1 row)
```

Two columns disagree. `delivered_orders` used `count(CASE ... ELSE 0 END)`: `count`
counts non-NULL values and `0` is not NULL, so it counted every order in the city (Pune 96,
Kochi 126, Indore 90) instead of the delivered ones. `avg_returned` averaged in a `0` for
every non-returned order, so the denominator was all orders, not returned ones. The two
columns that agree, `sum(CASE ... END)` with no `ELSE` and `sum(CASE ... THEN 1 ELSE 0
END)`, are the two forms that happen to be correct.

```sql
SELECT c.city,
       count(*) AS all_orders,
       count(*) FILTER (WHERE o.status = 'delivered') AS delivered,
       round(avg(o.total_amount) FILTER (WHERE o.status = 'returned'), 2) AS avg_returned
FROM orders o JOIN customers c ON c.id = o.customer_id
WHERE c.city IN ('Pune', 'Kochi', 'Indore') GROUP BY c.city ORDER BY c.city;
```

```text
  city  | all_orders | delivered | avg_returned
--------+------------+-----------+--------------
 Indore |         90 |        35 |      1431.81
 Kochi  |        126 |        61 |      1940.48
 Pune   |         96 |        31 |      1708.16
(3 rows)
```

The legacy `delivered_orders` equals `all_orders` in every row. The correct delivered count
is 31 for Pune, and the legacy `avg_returned` for Pune was 284.69 against a true 1,708.16.

```sql
SELECT sum(o.total_amount) FILTER (WHERE o.status = 'delivered') AS s,
       coalesce(sum(o.total_amount) FILTER (WHERE o.status = 'delivered'), 0) AS s_zero,
       count(*) FILTER (WHERE o.status = 'delivered') AS c
FROM orders o WHERE o.id < 0;
```

```text
   s    | s_zero | c
--------+--------+---
 (null) |      0 | 0
(1 row)
```

A `sum` over zero qualifying rows is NULL with `FILTER` exactly as with `CASE`. `count` is
0. Use `coalesce` for the sums a report must show as zero.

```sql
SET max_parallel_workers_per_gather = 0;

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT count(*) FILTER (WHERE status = 'paid'), sum(total_amount) FILTER (WHERE status = 'shipped')
FROM orders;

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT sum(CASE WHEN status = 'paid' THEN 1 ELSE 0 END),
       sum(CASE WHEN status = 'shipped' THEN total_amount END)
FROM orders;
```

```text
                     QUERY PLAN
-----------------------------------------------------
 Aggregate (actual rows=1 loops=1)
   Buffers: shared hit=43
   ->  Seq Scan on orders (actual rows=2500 loops=1)
         Buffers: shared hit=43
(4 rows)

                     QUERY PLAN
-----------------------------------------------------
 Aggregate (actual rows=1 loops=1)
   Buffers: shared hit=43
   ->  Seq Scan on orders (actual rows=2500 loops=1)
         Buffers: shared hit=43
(4 rows)
```

Both plans are one `Aggregate` over one `Seq Scan` of `orders`. Compare their `Buffers`
lines: they are equal. `FILTER` buys correctness and readability, not I/O.

## Practice Session 26.3 — p95 with `percentile_cont`

**Goal.** Report the 50th, 95th and 99th percentile of each telemetry metric, compare the
continuous and discrete definitions, find the events above their own metric's p95, and read
what the plan says the exactness costs.

**Setup.** The small `telemetry` dataset, read only.

```sql
\c telemetry
\pset null '(null)'
SET max_parallel_workers_per_gather = 0;

SELECT metric_name, count(*) AS n FROM device_events GROUP BY 1 ORDER BY 1;
```

```text
 metric_name  |  n
--------------+------
 battery_v    | 1999
 humidity_pct | 1974
 pressure_hpa | 1973
 rssi_dbm     | 1888
 temp_c       | 1966
(5 rows)
```

**Task.**

1. For each `metric_name`, report `n`, p50, p95, p99 and the mean, rounded to two
   decimals. Note where the mean and median disagree.
2. Compute the largest gap between `percentile_cont` and `percentile_disc` for the
   fractions 0.5, 0.9, 0.95 and 0.99, per metric.
3. For `temp_c`, report the three devices with the highest per-device p95, considering only
   devices with at least 20 `temp_c` readings. Say why the threshold is there.
4. Count the events whose `metric_value` exceeds their own metric's p95. You cannot use
   `OVER`. Predict roughly what fraction of rows you expect first.
5. Compare `p95` over all events with `p95` over only the events that have a `severity`.
6. Count the rows a per-day p95 summary table would hold, and say what you would do with it.
7. Read the `EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF)` of the p95 query
   and of an `avg`/`max` query. Which node type differs, and why?

**Solution.**

```sql
SELECT metric_name, count(*) AS n,
       round(percentile_cont(0.5)  WITHIN GROUP (ORDER BY metric_value)::numeric, 2) AS p50,
       round(percentile_cont(0.95) WITHIN GROUP (ORDER BY metric_value)::numeric, 2) AS p95,
       round(percentile_cont(0.99) WITHIN GROUP (ORDER BY metric_value)::numeric, 2) AS p99,
       round(avg(metric_value), 2) AS mean
FROM device_events GROUP BY 1 ORDER BY 1;
```

```text
 metric_name  |  n   |   p50   |   p95   |   p99   |  mean
--------------+------+---------+---------+---------+---------
 battery_v    | 1999 |    3.60 |    4.24 |    4.29 |    3.61
 humidity_pct | 1974 |   51.78 |   93.40 |   97.95 |   51.09
 pressure_hpa | 1973 | 1006.43 | 1045.21 | 1048.77 | 1005.90
 rssi_dbm     | 1888 |  -64.87 |  -38.35 |  -35.49 |  -65.02
 temp_c       | 1966 |   17.44 |   42.38 |   44.46 |   17.38
(5 rows)
```

The cast to `numeric` is needed for `round(x, 2)`, because `percentile_cont` returns
`double precision`. The mean and median are close for every metric on this data, which is
roughly uniform within each metric's range. On latency-shaped data they would not be, and
p95 is what tells you.

```sql
SELECT metric_name, max(abs(c - d)) AS max_gap
FROM (SELECT metric_name,
             percentile_cont(f) WITHIN GROUP (ORDER BY metric_value) AS c,
             percentile_disc(f) WITHIN GROUP (ORDER BY metric_value)::float8 AS d
      FROM device_events, unnest(ARRAY[0.5, 0.9, 0.95, 0.99]) AS f
      GROUP BY metric_name, f) s
GROUP BY 1 ORDER BY 1;
```

```text
 metric_name  |       max_gap
--------------+----------------------
 battery_v    |                    0
 humidity_pct |  0.09562999999999988
 pressure_hpa | 0.051839999999856445
 rssi_dbm     |  0.02099999999999369
 temp_c       |  0.01950000000000074
(5 rows)
```

The gap is at most a tenth of a unit on values in the thousands or tens, because each
metric has around 2,000 readings and neighbouring values are close. `battery_v` shows exactly 0 at
these fractions, meaning interpolation landed on an existing value each time. On a group of
ten rows the gap would be much larger.

```sql
SELECT device_id, count(*) AS n,
       round(percentile_cont(0.95) WITHIN GROUP (ORDER BY metric_value)::numeric, 2) AS p95
FROM device_events WHERE metric_name = 'temp_c'
GROUP BY 1 HAVING count(*) >= 20
ORDER BY p95 DESC, device_id LIMIT 3;
```

```text
 device_id | n  |  p95
-----------+----+-------
         5 | 31 | 44.03
        20 | 21 | 43.61
        11 | 27 | 43.42
(3 rows)
```

With few readings, a percentile is close to the maximum and dominated by one value. Without
the `HAVING`, a device with three readings could top this list. Seventeen devices pass the
threshold of 20.

```sql
SELECT e.metric_name, count(*) AS above_p95
FROM device_events e
JOIN (SELECT metric_name,
             percentile_cont(0.95) WITHIN GROUP (ORDER BY metric_value) AS p95
      FROM device_events GROUP BY 1) t USING (metric_name)
WHERE e.metric_value > t.p95
GROUP BY 1 ORDER BY 1;
```

```text
 metric_name  | above_p95
--------------+-----------
 battery_v    |        99
 humidity_pct |        99
 pressure_hpa |        99
 rssi_dbm     |        95
 temp_c       |        99
(5 rows)
```

About 5% of each metric's roughly 2,000 rows is roughly 100, and the counts are 99, 99, 99,
95 and 99. `rssi_dbm` is lowest at 95, and it has the fewest readings (1,888). Aggregating in a
subquery and joining back is the substitute for `OVER`, which is refused for ordered-set
aggregates.

```sql
SELECT metric_name,
       round(percentile_cont(0.95) WITHIN GROUP (ORDER BY metric_value)::numeric, 2) AS p95_all,
       round(percentile_cont(0.95) WITHIN GROUP (ORDER BY metric_value)
             FILTER (WHERE severity IS NOT NULL)::numeric, 2) AS p95_flagged
FROM device_events GROUP BY 1 ORDER BY 1;
```

```text
 metric_name  | p95_all | p95_flagged
--------------+---------+-------------
 battery_v    |    4.24 |        4.22
 humidity_pct |   93.40 |       93.18
 pressure_hpa | 1045.21 |     1046.45
 rssi_dbm     |  -38.35 |      -44.05
 temp_c       |   42.38 |       42.35
(5 rows)
```

`FILTER` sits after `WITHIN GROUP`. For `rssi_dbm` the flagged events have a p95 of -44.05
against -38.35 overall: the upper tail of the flagged readings is weaker.

```sql
SELECT count(*) AS summary_rows
FROM (SELECT metric_name, recorded_at::date AS day,
             percentile_cont(0.95) WITHIN GROUP (ORDER BY metric_value)
      FROM device_events GROUP BY 1, 2) s;
```

```text
 summary_rows
--------------
          470
(1 row)
```

Five metrics over the three months of the sample give 470 rows, one per metric per day.
That is the shape of the table to precompute, and a dashboard reading 470 rows never sorts a
raw event. Refresh it on a schedule, or with a materialized view (Chapter 41).

```sql
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT metric_name, percentile_cont(0.95) WITHIN GROUP (ORDER BY metric_value)
FROM device_events GROUP BY 1;

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT metric_name, max(metric_value), avg(metric_value)
FROM device_events GROUP BY 1;
```

   Group Key: metric_name
   Buffers: shared hit=267
   ->  Sort (actual rows=9800 loops=1)

         Sort Method: quicksort  Memory: 967kB

The percentile query is a `GroupAggregate` fed by a `Sort` of all 9,800 rows. The
`max`/`avg` query is a `HashAggregate` with no sort. Ordered-set aggregates cannot be

sort on `metric_value` happens inside the aggregate and does not appear as a plan node.
