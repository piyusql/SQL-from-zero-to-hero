# Chapter 24 Exercises — Design Anti-Patterns and Safe Refactoring

## Practice Session 24.1 — Refactor EAV into a typed schema

**Goal.** Take an entity-attribute-value table that has accumulated dirty data, inventory
what is really in it, migrate the clean rows into a typed table with constraints, quarantine
the rest instead of guessing, and prove that nothing was lost.

**Setup.** Everything is generated; no dataset is read. The damage is deliberate and
counted: 10 weights that say `N/A`, 4 prices with a thousands separator, 5 attribute names
in the wrong case, 8 missing warranties, and two misspelt attribute names.

```bash
createdb ch24_ws1
psql -d ch24_ws1
```

```sql
\pset null '(null)'
CREATE TABLE item_attr (item_id int NOT NULL, attr_name text NOT NULL, attr_value text,
                        PRIMARY KEY (item_id, attr_name));
INSERT INTO item_attr
SELECT g, a.k, a.v
FROM generate_series(1, 5000) g
CROSS JOIN LATERAL (VALUES
    ('colour',          (ARRAY['Teak','Indigo','Saffron','Ivory'])[g % 4 + 1]),
    ('weight_g',        (200 + (g * 37) % 4800)::text),
    ('warranty_months', (ARRAY[0,6,12,24])[g % 4 + 1]::text),
    ('price',           round((99 + (g * 53) % 9900)::numeric, 2)::text)) AS a(k, v);
UPDATE item_attr SET attr_value = 'N/A'      WHERE attr_name = 'weight_g' AND item_id % 500 = 0;
UPDATE item_attr SET attr_value = '1,299.00' WHERE attr_name = 'price'    AND item_id % 1250 = 7;
UPDATE item_attr SET attr_name  = 'Colour'   WHERE attr_name = 'colour'   AND item_id % 1000 = 3;
DELETE FROM item_attr WHERE attr_name = 'warranty_months' AND item_id % 700 = 1;
INSERT INTO item_attr VALUES (1, 'colur', 'Teak'), (2, 'wieght_g', '900');
```

**Task.**

1. Inventory the attribute names: for each, how many cells and how many distinct items. Which
   names are legitimate, which are spellings of a legitimate one, and which are strays?
2. For the three numeric attributes, count the cells whose value does not parse as a number
   (integers for weight and warranty, at most two decimals for price).
3. Design `item_typed` with a primary key, `NOT NULL` on every attribute and a `CHECK` on
   each (colour from the four known values, non-negative numbers), and an `item_quarantine`
   table `(item_id, reason)`.
4. Migrate in **one statement**: pivot the EAV rows (treating `Colour` as `colour`), insert
   the clean items into `item_typed` and the rest into `item_quarantine` with a reason, and
   return both counts. Do not repair values by guessing.
5. Prove nothing was lost: typed plus quarantined must equal the number of distinct items.
   Then prove the values agree with the source for every migrated item.
6. Write a compatibility view that presents `item_typed` in the old EAV shape, so a reader
   not yet migrated keeps working, and check its row count.
7. Answer in a sentence: why quarantine rather than coerce `'N/A'` to NULL or drop the row?

**Solution.**

```sql
SELECT attr_name, count(*) AS cells, count(DISTINCT item_id) AS items
FROM item_attr GROUP BY 1 ORDER BY 2 DESC, 1;

SELECT attr_name, count(*) AS not_a_number
FROM item_attr
WHERE (attr_name IN ('weight_g', 'warranty_months') AND attr_value !~ '^\d+$')
   OR (attr_name = 'price' AND attr_value !~ '^\d+(\.\d{1,2})?$')
GROUP BY 1 ORDER BY 1;
```

```text
    attr_name    | cells | items
-----------------+-------+-------
 price           |  5000 |  5000
 weight_g        |  5000 |  5000
 colour          |  4995 |  4995
 warranty_months |  4992 |  4992
 Colour          |     5 |     5
 colur           |     1 |     1
 wieght_g        |     1 |     1
(7 rows)

 attr_name | not_a_number
-----------+--------------
 price     |            4
 weight_g  |           10
(2 rows)
```

`Colour` is the legitimate `colour` with the wrong case; `colur` and `wieght_g` are strays
that belong to one item each. Only a person can say whether `wieght_g = 900` on item 2 is a
real second weight or a typo for the row that already has one, which is the argument for
inventorying before migrating. The 4 prices with a comma and the 10 `N/A` weights are the
14 cells that would have broken the first `::numeric` cast.

```sql
CREATE TABLE item_typed (
    item_id int PRIMARY KEY,
    colour  text NOT NULL CHECK (colour IN ('Teak', 'Indigo', 'Saffron', 'Ivory')),
    weight_g int NOT NULL CHECK (weight_g > 0),
    warranty_months int NOT NULL CHECK (warranty_months >= 0),
    price numeric(10,2) NOT NULL CHECK (price >= 0));
CREATE TABLE item_quarantine (item_id int PRIMARY KEY, reason text NOT NULL);

WITH piv AS (
  SELECT item_id,
         max(attr_value) FILTER (WHERE lower(attr_name) = 'colour')   AS colour,
         max(attr_value) FILTER (WHERE attr_name = 'weight_g')        AS weight_g,
         max(attr_value) FILTER (WHERE attr_name = 'warranty_months') AS warranty_months,
         max(attr_value) FILTER (WHERE attr_name = 'price')           AS price
  FROM item_attr GROUP BY item_id),
checked AS (
  SELECT *, CASE
      WHEN colour IS NULL OR weight_g IS NULL OR warranty_months IS NULL OR price IS NULL
           THEN 'missing attribute'
      WHEN weight_g !~ '^\d+$' OR warranty_months !~ '^\d+$' OR price !~ '^\d+(\.\d{1,2})?$'
           THEN 'not a number'
      END AS reason
  FROM piv),
good AS (
  INSERT INTO item_typed
  SELECT item_id, colour, weight_g::int, warranty_months::int, price::numeric
  FROM checked WHERE reason IS NULL
  RETURNING 1),
bad AS (
  INSERT INTO item_quarantine SELECT item_id, reason FROM checked WHERE reason IS NOT NULL
  RETURNING 1)
SELECT (SELECT count(*) FROM good) AS migrated, (SELECT count(*) FROM bad) AS quarantined;

SELECT reason, count(*) FROM item_quarantine GROUP BY 1 ORDER BY 1;
```

```text
 migrated | quarantined
----------+-------------
     4978 |          22
(1 row)

      reason       | count
-------------------+-------
 missing attribute |     8
 not a number      |    14
(2 rows)
```

The pivot is `max(...) FILTER`, one row per item, and the `CASE` classifies before any cast
runs, so the casts in the `good` branch only ever see clean text. That ordering matters: a
cast placed anywhere the planner may evaluate it early is the same time bomb as in the
chapter. `SELECT` in the final line reads the `RETURNING` counts, which is the only way to
report from a data-modifying CTE. Check the two totals and the values:

```sql
SELECT (SELECT count(DISTINCT item_id) FROM item_attr) AS eav_items,
       (SELECT count(*) FROM item_typed) + (SELECT count(*) FROM item_quarantine) AS typed_plus_quarantine;

SELECT count(*) AS mismatches
FROM item_typed t
WHERE t.weight_g::text IS DISTINCT FROM
        (SELECT attr_value FROM item_attr a WHERE a.item_id = t.item_id AND a.attr_name = 'weight_g')
   OR t.warranty_months::text IS DISTINCT FROM
        (SELECT attr_value FROM item_attr a WHERE a.item_id = t.item_id AND a.attr_name = 'warranty_months')
   OR t.price::text IS DISTINCT FROM
        (SELECT attr_value FROM item_attr a WHERE a.item_id = t.item_id AND a.attr_name = 'price')
   OR lower(t.colour) IS DISTINCT FROM
        (SELECT lower(attr_value) FROM item_attr a WHERE a.item_id = t.item_id AND lower(a.attr_name) = 'colour');
```

```text
 eav_items | typed_plus_quarantine
-----------+-----------------------
      5000 |                  5000
(1 row)

 mismatches
------------
          0
(1 row)
```

Reconciliation is two questions: did every item land somewhere, and does each landed value
equal its source. The comparison casts the *typed* side to text rather than the source to a
number, so it cannot fail on dirty input. Finally the bridge for readers that still expect
EAV, which is also what lets you contract the old table safely:

```sql
CREATE VIEW item_attr_v AS
SELECT t.item_id, a.k AS attr_name, a.v AS attr_value
FROM item_typed t
CROSS JOIN LATERAL (VALUES ('colour', t.colour), ('weight_g', t.weight_g::text),
    ('warranty_months', t.warranty_months::text), ('price', t.price::text)) AS a(k, v);

SELECT count(*) AS view_rows, (SELECT count(*) FROM item_typed) * 4 AS expected FROM item_attr_v;
```

```text
 view_rows | expected
-----------+----------
     19912 |    19912
(1 row)
```

**Why quarantine.** Turning `'N/A'` into NULL would either violate `NOT NULL` or force you to
drop the constraint that was the point of the exercise; dropping the row destroys evidence;
guessing (`'1,299.00'` is obviously 1299, but is `'N/A'` zero?) puts your judgement into the
data with nobody's signature on it. A quarantine table keeps the row, names the reason and
hands the decision to whoever owns the data.

## Practice Session 24.2 — Split a column with zero downtime

**Goal.** Split `contact.phone` into `country_code` and `national_number` on a live table
using expand and contract, proving the lock taken at each step, showing what happens if you
skip the dual write, and showing why the backfill is batched.

**Setup.** A generated table of 100,000 contacts. Most numbers are `+91-` followed by ten
digits; some are Singapore or UAE numbers; a few are bare ten-digit domestic numbers with no
country code.

```bash
createdb ch24_ws2
psql -d ch24_ws2
```

```sql
\pset null '(null)'
CREATE TABLE contact (id int PRIMARY KEY, name text NOT NULL, phone text NOT NULL);
INSERT INTO contact
SELECT g, 'Contact ' || g,
       CASE WHEN g % 50 = 0  THEN '9' || lpad((g::bigint * 7919 % 1000000000)::text, 9, '0')
            WHEN g % 20 = 1  THEN '+65-8' || lpad((g::bigint * 104729 % 10000000)::text, 7, '0')
            WHEN g % 33 = 2  THEN '+971-50' || lpad((g::bigint * 15485863 % 10000000)::text, 7, '0')
            ELSE '+91-9' || lpad((g::bigint * 7919 % 1000000000)::text, 9, '0') END
FROM generate_series(1, 100000) g;
CREATE INDEX contact_name ON contact (name);
ANALYZE contact;
SELECT count(*) FROM contact;      -- expect 100000
```

**Task.**

1. Write the split rule as two `IMMUTABLE` SQL functions, `phone_cc(text)` and
   `phone_nn(text)`. A number with a `+` prefix has its country code between `+` and the
   first `-`; a bare number is assumed to be domestic (`91`). Show them on one number of each
   shape.
2. **Expand.** Add `country_code` and `national_number` as nullable text with no default,
   inside a transaction with `lock_timeout`, and print the lock modes held on `contact` from
   `pg_locks`. Prove with `pg_relation_filenode` that the table was not rewritten.
3. **Dual write.** Create a `BEFORE INSERT OR UPDATE OF phone` trigger that fills both new
   columns. Print the lock mode `CREATE TRIGGER` takes.
4. **Skipping it.** On a copy with the columns but no trigger, run the batched backfill in
   two halves with an insert of 500 rows and an update of 300 phone numbers between them.
   Count the rows the reconcile query flags.
5. **Backfill for real** on `contact` with the same interleaved traffic, in 25,000-row
   batches, each its own transaction. Run the reconcile query.
6. **Blast radius.** With two `psql` sessions, hold an open `UPDATE` of one 10,000-row batch
   and try to update a row inside and a row outside it; then repeat with the update covering
   the whole table. Use `lock_timeout`, not the clock, to decide the outcome.
7. Add `NOT NULL` to `country_code` without a long exclusive lock (`NOT VALID`, `VALIDATE`,
   `SET NOT NULL`) and print the lock mode of each step.
8. **Contract.** Drop the trigger and the `phone` column. Show the lock, and show that the
   heap did not shrink.

**Solution.**

```sql
CREATE FUNCTION phone_cc(p text) RETURNS text LANGUAGE sql IMMUTABLE AS
$$ SELECT CASE WHEN p LIKE '+%' THEN substring(p FROM '^\+(\d+)-') ELSE '91' END $$;
CREATE FUNCTION phone_nn(p text) RETURNS text LANGUAGE sql IMMUTABLE AS
$$ SELECT regexp_replace(CASE WHEN p LIKE '+%' THEN substring(p FROM '^\+\d+-(.*)$') ELSE p END,
                         '\D', '', 'g') $$;

SELECT p, phone_cc(p) AS cc, phone_nn(p) AS nn
FROM (VALUES ('+91-9820012345'), ('+65-81234567'), ('9820012345')) v(p);
```

```text
       p        | cc |     nn
----------------+----+------------
 +91-9820012345 | 91 | 9820012345
 +65-81234567   | 65 | 81234567
 9820012345     | 91 | 9820012345
(3 rows)
```

Writing the rule once, in functions, means the trigger, the backfill and the reconcile cannot
disagree. The assumption that a bare number is domestic is a *business* decision; write it
where a reviewer will see it.

```sql
SELECT pg_relation_filenode('contact') AS filenode_before \gset

BEGIN;
SET LOCAL lock_timeout = '2s';
ALTER TABLE contact ADD COLUMN country_code text, ADD COLUMN national_number text;
SELECT mode, granted FROM pg_locks
WHERE  relation = 'contact'::regclass AND pid = pg_backend_pid() ORDER BY mode;
COMMIT;

SELECT pg_relation_filenode('contact') = :filenode_before AS same_file;
```

```text
        mode         | granted
---------------------+---------
 AccessExclusiveLock | t
(1 row)

 same_file
-----------
 t
(1 row)
```

`ACCESS EXCLUSIVE`, held briefly, no rewrite. If another session had an open transaction on
`contact` at this moment, the `ALTER` would wait and every query behind it would wait too;
`lock_timeout` turns that into an error you can retry.

```sql
CREATE FUNCTION contact_split_phone() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  NEW.country_code    := phone_cc(NEW.phone);
  NEW.national_number := phone_nn(NEW.phone);
  RETURN NEW;
END $$;

CREATE PROCEDURE backfill_phones(tbl regclass, lo bigint, hi bigint, batch int DEFAULT 25000)
LANGUAGE plpgsql AS $$
DECLARE cur bigint := lo; n bigint;
BEGIN
  WHILE cur < hi LOOP
    EXECUTE format(
      'UPDATE %s SET country_code = phone_cc(phone), national_number = phone_nn(phone)
       WHERE id > %s AND id <= %s AND country_code IS NULL', tbl, cur, least(cur + batch, hi));
    GET DIAGNOSTICS n = ROW_COUNT;
    RAISE NOTICE 'ids % to %: % rows', cur + 1, least(cur + batch, hi), n;
    COMMIT;
    cur := cur + batch;
  END LOOP;
END $$;

-- a copy that has the new columns but, deliberately, no trigger
CREATE TABLE contact_naive AS
  SELECT id, name, phone, NULL::text AS country_code, NULL::text AS national_number FROM contact;
ALTER TABLE contact_naive ADD PRIMARY KEY (id);

BEGIN;
SET LOCAL lock_timeout = '2s';
CREATE TRIGGER contact_split_phone BEFORE INSERT OR UPDATE OF phone ON contact
  FOR EACH ROW EXECUTE FUNCTION contact_split_phone();
SELECT mode, granted FROM pg_locks
WHERE  relation = 'contact'::regclass AND pid = pg_backend_pid() AND mode <> 'AccessShareLock';
COMMIT;
```

```text
         mode          | granted
-----------------------+---------
 ShareRowExclusiveLock | t
(1 row)
```

`SHARE ROW EXCLUSIVE` blocks writers and admits readers, so a busy table should get a
`lock_timeout` and a retry here as well. Now the experiment that shows why the trigger comes
first. Same interleaved traffic against each table, and the same reconcile query:

```sql
CALL backfill_phones('contact_naive', 0, 50000);
INSERT INTO contact_naive (id, name, phone)
  SELECT 100000 + g, 'New ' || g, '+91-98' || lpad(g::text, 8, '0') FROM generate_series(1, 500) g;
UPDATE contact_naive SET phone = '+91-9000000000' WHERE id BETWEEN 1000 AND 1299;
CALL backfill_phones('contact_naive', 50000, 100000);

SELECT count(*) FILTER (WHERE country_code IS NULL) AS never_backfilled,
       count(*) FILTER (WHERE country_code IS NOT NULL
             AND (country_code IS DISTINCT FROM phone_cc(phone)
               OR national_number IS DISTINCT FROM phone_nn(phone))) AS stale
FROM contact_naive;
```

```

```

Without the trigger, the 500 inserted rows are never backfilled and the 300 updated phones
are stale, and nothing reported an error. With the trigger the same traffic leaves zero and
zero. The last query is the other half of reconciling: the *distribution* of the new column
should match what you know about the data, and it shows the 91, 65 and 971 groups.

For the blast radius, hold an open `UPDATE` in one session and try writes from another. The
`sleep` only lets session A start; the outcome is decided by row locks and `lock_timeout`:

```bash
try_update() {   # $1 = id; prints one line
  psql -q -At -v ON_ERROR_STOP=1 -v VERBOSITY=terse -d ch24_ws2 <<SQL 2>&1 | sed 's/^psql:[^ ]* //'
SET lock_timeout = '300ms';
UPDATE contact_naive SET name = name || '.' WHERE id = $1;
SELECT 'writer B updated id $1';
SQL
}
for scope in "id <= 10000" "true"; do
  echo "-- writer A holds an open UPDATE where $scope"
  psql -q -d ch24_ws2 -c "BEGIN; UPDATE contact_naive SET name = name WHERE $scope; SELECT pg_sleep(4); ROLLBACK;" >/dev/null &
  sleep 1.5
  try_update 5
  try_update 60000
  wait
done
```

```text
-- writer A holds an open UPDATE where id <= 10000
ERROR:  canceling statement due to lock timeout
writer B updated id 60000
-- writer A holds an open UPDATE where true
ERROR:  canceling statement due to lock timeout
ERROR:  canceling statement due to lock timeout
```

A batch of 10,000 blocks writers to those 10,000 rows and nobody else; the whole-table
statement blocks everyone until it commits. A batch size is a choice about how much of the
table a backfill may freeze at once, and the answer should be "a number small enough that
nobody notices".

```sql
BEGIN;
SET LOCAL lock_timeout = '2s';
ALTER TABLE contact ADD CONSTRAINT country_code_present CHECK (country_code IS NOT NULL) NOT VALID;
SELECT mode FROM pg_locks WHERE relation = 'contact'::regclass AND pid = pg_backend_pid() AND mode <> 'AccessShareLock';
COMMIT;

BEGIN;
ALTER TABLE contact VALIDATE CONSTRAINT country_code_present;
SELECT mode FROM pg_locks WHERE relation = 'contact'::regclass AND pid = pg_backend_pid() AND mode <> 'AccessShareLock';
COMMIT;

SET client_min_messages = debug1;
ALTER TABLE contact ALTER COLUMN country_code SET NOT NULL;
RESET client_min_messages;
ALTER TABLE contact DROP CONSTRAINT country_code_present;
```

```text
        mode
---------------------
 AccessExclusiveLock
(1 row)

           mode
--------------------------
 ShareUpdateExclusiveLock
(1 row)

DEBUG:  existing constraints on column "contact.country_code" are sufficient to prove that it does not contain nulls
```

Only the first step needs the strong lock and it does no scan; validation scans under
`SHARE UPDATE EXCLUSIVE`, which lets reads and writes continue; and the `DEBUG` line shows
`SET NOT NULL` skipping its own scan because the validated constraint proves the property.

```sql
SELECT pg_relation_filenode('contact') AS filenode_before,
       pg_relation_size('contact') AS heap_before \gset
BEGIN;
SET LOCAL lock_timeout = '2s';
DROP TRIGGER contact_split_phone ON contact;
ALTER TABLE contact DROP COLUMN phone;
SELECT mode FROM pg_locks WHERE relation = 'contact'::regclass AND pid = pg_backend_pid() AND mode <> 'AccessShareLock';
COMMIT;
DROP FUNCTION contact_split_phone();

SELECT pg_relation_filenode('contact') = :filenode_before AS same_file,
       pg_relation_size('contact') = :heap_before AS same_size;
```

```text
        mode
---------------------
 AccessExclusiveLock
(1 row)

 same_file | same_size
-----------+-----------
 t         | t
(1 row)
```

`DROP COLUMN` is a catalog change under a brief exclusive lock. The file and its size are
untouched: the column's bytes stay in every row until the table is rewritten, so contract
frees the *name*, not the space. Reclaiming it is a separate, heavier operation (Chapter 37).
