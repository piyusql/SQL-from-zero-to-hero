# Chapter 32 Exercises — Locking, Deadlocks, and Concurrency Patterns

Every session here needs two or three `psql` terminals on one database. Label them, run
`\pset null '(null)'` in each, and type steps in the order given. The transcripts in the
solutions were captured from real runs with each step issued only after the previous one had
finished or was confirmed blocked; session prompts (`A=>`, `B=>`) are labels, terminals ran

scratch: the last line of each session drops its database.

## Practice Session 32.1 — Induce and read a deadlock

**Goal.** Produce a deadlock on demand, name the two statements from the error and the
server log, remove it with lock ordering, then build the harder foreign-key variant and
derive the table-lock conflict matrix by experiment.

**Setup.** Three terminals, A, B and O (observer), all on `ch32_w1`.

```bash
createdb ch32_w1
psql -X -d ch32_w1
```

```sql
CREATE TABLE accounts (
    id      int PRIMARY KEY,
    holder  text NOT NULL,
    balance numeric(12,2) NOT NULL CHECK (balance >= 0)
);
INSERT INTO accounts VALUES (1, 'Kavya Nair', 10000), (2, 'Rohan Deshmukh', 5000);

CREATE TABLE ledger (
    id         int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    account_id int NOT NULL REFERENCES accounts (id),
    amount     numeric(12,2) NOT NULL
);
INSERT INTO ledger (account_id, amount) VALUES (1, 100), (2, 100);
```

In A and B, run `SET deadlock_timeout = '3s';` (the default is 1 s; the longer margin makes
the outcome reproducible on a busy machine).

**Task.**

1. Run two transfers in opposite directions. A moves 1,000 from account 1 to account 2, B
   moves 500 from account 2 to account 1, each debiting first. Order the steps: A debits 1,
   B debits 2, A credits 2 (blocks), then, only once A is blocked, B credits 1. From O, while
   A is blocked, list who is blocked by whom without printing process IDs.
2. Read the error. Which session was cancelled, and why that one? What SQLSTATE? Does the
   client-side message contain either statement?
3. Find the two statements in the server log.
4. Rerun the same two transfers so that no deadlock is possible, by changing only what each
   transaction does first.
5. Build a deadlock with **no two updates on the same table in opposite order**, using the
   foreign key: A updates a `ledger` row, B locks the parent account `FOR UPDATE`, then A
   inserts a ledger row for that account, then B updates the ledger row A holds.
6. Write a script that takes every table-lock mode in one session and requests each of the
   eight in another with `NOWAIT`, and prints the 8 x 8 conflict matrix. Find which modes
   conflict with themselves.

**Solution.**

Steps 1 and 2. O's query shows the wait edge at the moment A is blocked; after B's second
statement the detector runs.

```text
A=> BEGIN;
A=> UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
B=> BEGIN;
B=> UPDATE accounts SET balance = balance - 500 WHERE id = 2;
A=> UPDATE accounts SET balance = balance + 1000 WHERE id = 2;
O=> SELECT left(w.query, 40) AS waiting, left(h.query, 40) AS blocked_by
O-> FROM pg_stat_activity w
O-> JOIN pg_stat_activity h ON h.pid = ANY (pg_blocking_pids(w.pid))
O-> WHERE w.datname = current_database();
                 waiting                  |                blocked_by
------------------------------------------+------------------------------------------
 UPDATE accounts SET balance = balance +  | UPDATE accounts SET balance = balance -
(1 row)

B=> UPDATE accounts SET balance = balance + 500 WHERE id = 1;
-- A's waiting UPDATE returns:
ERROR:  deadlock detected
DETAIL:  Process 161626 waits for ShareLock on transaction 221996; blocked by process 161627.
Process 161627 waits for ShareLock on transaction 221995; blocked by process 161626.
HINT:  See server log for query details.
CONTEXT:  while updating tuple (0,2) in relation "accounts"
A=> \echo :LAST_ERROR_SQLSTATE
40P01
A=> ROLLBACK;
-- B's waiting UPDATE returns:
B=> COMMIT;
A=> SELECT id, balance FROM accounts ORDER BY id;
 id | balance
----+----------
  1 | 10500.00
  2 |  4500.00
(2 rows)
```

The error reads as two edges: process 1 waits for a `ShareLock` on transaction T2, held by
process 2, and process 2 waits on T1, held by process 1. `ShareLock on transaction` is how a
row-level wait appears. A was cancelled because it began waiting first, so its
`deadlock_timeout` expired first and its check found the cycle; B, whose statement closed
the loop, completed after A's rollback (the balances show only B's transfer). The SQLSTATE
is `40P01`. The client message carries `HINT: See server log for query details` and no
statements.

Step 3. The statements are in the server log. On a server with a log file, look in
`log_directory` (`SELECT pg_current_logfile();` works when `logging_collector` is on); the
test container logs to stdout, so its log is `docker logs`. The lines below are the entry for
the deadlock above:

```text

2026-09-30 16:42:54.053 GMT [161626] DETAIL:  Process 161626 waits for ShareLock on transaction 221996; blocked by process 161627.
	Process 161627 waits for ShareLock on transaction 221995; blocked by process 161626.

2026-09-30 16:42:54.053 GMT [161626] STATEMENT:  UPDATE accounts SET balance = balance + 1000 WHERE id = 2;
```

Step 5. The `CONTEXT` line of the error names a statement nobody wrote: the foreign-key
check takes `FOR KEY SHARE` on the parent row, which conflicts with B's `FOR UPDATE`.

Step 6. Save this as `lockmatrix.py` and run `python3 lockmatrix.py ch32_w1`. It owns two
`psql` processes, sends one statement at a time, and reads each reply up to a sentinel
line, so no step depends on a clock.

```python
import subprocess, sys

MODES = ["ACCESS SHARE", "ROW SHARE", "ROW EXCLUSIVE", "SHARE UPDATE EXCLUSIVE",
         "SHARE", "SHARE ROW EXCLUSIVE", "EXCLUSIVE", "ACCESS EXCLUSIVE"]
ABBR = ["AS", "RS", "RX", "SUX", "S", "SRX", "X", "AX"]
DB = sys.argv[1] if len(sys.argv) > 1 else "ch32_w1"


def session():
    return subprocess.Popen(["psql", "-X", "-q", "-d", DB], stdin=subprocess.PIPE,
                            stdout=subprocess.PIPE, stderr=subprocess.STDOUT, text=True)


def run(p, sql):
    """Send one statement, read output up to a sentinel line."""
    p.stdin.write(sql + "\n\\echo __END__\n")
    p.stdin.flush()
    out = []
    for line in p.stdout:
        if line.strip() == "__END__":
            return "".join(out)
        out.append(line)


a, b = session(), session()
run(a, "CREATE TABLE IF NOT EXISTS lock_target (id int);")
print("held \\ asked " + " ".join(f"{m:>4}" for m in ABBR))
for ma, ha in zip(MODES, ABBR):
    run(a, "BEGIN;")
    run(a, f"LOCK TABLE lock_target IN {ma} MODE;")
    cells = []
    for mb in MODES:
        run(b, "BEGIN;")
        refused = "ERROR" in run(b, f"LOCK TABLE lock_target IN {mb} MODE NOWAIT;")
        run(b, "ROLLBACK;")
        cells.append("X" if refused else ".")
    run(a, "ROLLBACK;")
    print(f"{ha:<13} " + " ".join(f"{c:>4}" for c in cells))
run(a, "DROP TABLE lock_target;")
a.stdin.close(); b.stdin.close()
```

```text
held \ asked   AS   RS   RX  SUX    S  SRX    X   AX
AS               .    .    .    .    .    .    .    X
RS               .    .    .    .    .    .    X    X
RX               .    .    .    .    X    X    X    X
SUX              .    .    .    X    X    X    X    X
S                .    .    X    X    .    X    X    X
SRX              .    .    X    X    X    X    X    X
X                .    X    X    X    X    X    X    X
AX               X    X    X    X    X    X    X    X
```

`X` means the request was refused. The matrix is symmetric and matches the table in the
documentation. Modes that conflict with themselves: `SHARE UPDATE EXCLUSIVE`, `SHARE ROW EXCLUSIVE`,
`EXCLUSIVE`, `ACCESS EXCLUSIVE`. The rest do not, `ROW EXCLUSIVE` and `SHARE` among them,
which is why any number of writers run concurrently and several plain `CREATE INDEX`
statements can share a table.

Clean up: `dropdb ch32_w1`.

## Practice Session 32.2 — Job queue on `SKIP LOCKED`

**Goal.** Build a claim query that hands out each job exactly once to concurrent workers, and
prove it against the naive version, against plain `FOR UPDATE`, and against a worker crash.

**Setup.** Terminals W1, W2, W3 and O on `ch32_w2`.

```bash
createdb ch32_w2
psql -X -d ch32_w2
```

```sql
CREATE TABLE jobs (
    id         int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    payload    text NOT NULL,
    status     text NOT NULL DEFAULT 'queued',
    claimed_by text
);
INSERT INTO jobs (payload) SELECT 'dispatch SW-' || (1000 + g) FROM generate_series(1, 8) AS g;
```

**Task.**

1. Show that the naive claim (`SELECT` the first queued job, then `UPDATE` it by `id`) hands
   job 1 to two workers.
2. Write `claim_job(worker text)` using `FOR UPDATE SKIP LOCKED`. Have three workers each open
   a transaction and claim one job while the earlier claims are uncommitted. What does O see?
3. Let the workers claim in rotation, in autocommit, until the queue is empty. Prove with
   counts that every job was claimed exactly once and none was lost.
4. Reset the queue and run W1 and W2 with plain `FOR UPDATE` (no `SKIP LOCKED`). What happens
   to W2, and what does it return?
5. Reset the queue. W3 claims a job inside an open transaction and its backend is killed.
   What is the job's state afterwards?
6. Reset the queue. Have two workers each claim a batch of two jobs with one statement.

**Solution.**

Step 1. Both workers read job 1 before either wrote, and the second write silently
overwrote the first. Both believe they own the job:

```text
W1=> SELECT id FROM jobs WHERE status = 'queued' ORDER BY id LIMIT 1;
 id
----
  1
(1 row)

W2=> SELECT id FROM jobs WHERE status = 'queued' ORDER BY id LIMIT 1;
 id
----
  1
(1 row)

W1=> UPDATE jobs SET status = 'running', claimed_by = 'w1' WHERE id = 1;
W2=> UPDATE jobs SET status = 'running', claimed_by = 'w2' WHERE id = 1;
W1=> SELECT id, status, claimed_by FROM jobs WHERE id = 1;
 id | status  | claimed_by
----+---------+------------
  1 | running | w2
(1 row)
```

Step 2. Workers in an open transaction hold their row locks; the others skip them. O sees
every job still `queued` because nothing has committed.

```sql
CREATE FUNCTION claim_job(worker text) RETURNS TABLE (id int, payload text)
LANGUAGE sql AS $$
    UPDATE jobs SET status = 'running', claimed_by = worker
    WHERE jobs.id = (SELECT j.id FROM jobs j
                     WHERE j.status = 'queued'
                     ORDER BY j.id LIMIT 1
                     FOR UPDATE SKIP LOCKED)
    RETURNING jobs.id, jobs.payload
$$;
```

```text
W1=> BEGIN;
W2=> BEGIN;
W3=> BEGIN;
W1=> SELECT * FROM claim_job('w1');
 id |     payload
----+------------------
  1 | dispatch SW-1001
(1 row)

W2=> SELECT * FROM claim_job('w2');
 id |     payload
----+------------------
  2 | dispatch SW-1002
(1 row)

W3=> SELECT * FROM claim_job('w3');
 id |     payload
----+------------------
  3 | dispatch SW-1003
(1 row)

O=> SELECT status, count(*) FROM jobs GROUP BY status;
 status | count
--------+-------
 queued |     8
(1 row)

W1=> COMMIT;
W2=> COMMIT;
W3=> COMMIT;
```

Step 3. Sequential rotation makes the distribution deterministic (jobs 1, 4, 7 to `w1`, and so
on); the point is the invariant. Eight jobs, eight claimed, eight distinct IDs, eight with a
worker recorded, none queued.

```text
W1=> SELECT count(*) AS jobs,
W1->        count(*) FILTER (WHERE status = 'running') AS claimed,
W1->        count(DISTINCT id) AS distinct_ids,
W1->        count(claimed_by) AS with_worker
W1-> FROM jobs;
 jobs | claimed | distinct_ids | with_worker
------+---------+--------------+-------------
    8 |       8 |            8 |           8
(1 row)

W1=> SELECT claimed_by, array_agg(id ORDER BY id) AS ids FROM jobs GROUP BY 1 ORDER BY 1;
 claimed_by |   ids
------------+---------
 w1         | {1,4,7}
 w2         | {2,5,8}
 w3         | {3,6}
(3 rows)
```

Step 4. Without `SKIP LOCKED`, W2 blocks on job 1 until W1 commits, then finds job 1 no longer
`queued`, moves to the next row and claims job 2. That is correct and serialised: every worker
waits behind the one in front.

```text
W1=> BEGIN;
W1=> UPDATE jobs SET status = 'running', claimed_by = 'w1'
W1-> WHERE id = (SELECT id FROM jobs WHERE status = 'queued'
W1->             ORDER BY id LIMIT 1 FOR UPDATE)
W1-> RETURNING id, payload;
 id |     payload
----+------------------
  1 | dispatch SW-1001
(1 row)

W2=> UPDATE jobs SET status = 'running', claimed_by = 'w2'
W2-> WHERE id = (SELECT id FROM jobs WHERE status = 'queued'
W2->             ORDER BY id LIMIT 1 FOR UPDATE)
W2-> RETURNING id, payload;
O=> SELECT count(*) AS waiting FROM pg_stat_activity WHERE datname = current_database() AND wait_event_type = 'Lock';
 waiting
---------
       1
(1 row)

W1=> COMMIT;
-- W2's waiting claim returns:
 id |     payload
----+------------------
  2 | dispatch SW-1002
(1 row)
```

Step 5. The claim was part of the transaction, so terminating the backend rolled it back. No
reaper is needed for this design; the price is an open transaction for the life of the job.

```text
W3=> BEGIN;
W3=> SELECT * FROM claim_job('w3');
 id |     payload
----+------------------
  1 | dispatch SW-1001
(1 row)

O=> SELECT pg_terminate_backend(pid) FROM pg_stat_activity
O-> WHERE datname = current_database() AND state = 'idle in transaction';
 pg_terminate_backend
----------------------
 t
(1 row)

O=> SELECT id, status, claimed_by FROM jobs WHERE id = 1;
 id | status | claimed_by
----+--------+------------
  1 | queued | (null)
(1 row)
```

Step 6. `LIMIT 2 ... FOR UPDATE SKIP LOCKED` locks exactly the rows it returns, so the second
worker gets the next two:

```text
W1=> BEGIN;
W2=> BEGIN;
W1=> UPDATE jobs SET status = 'running', claimed_by = 'w1'
W1-> WHERE id IN (SELECT id FROM jobs WHERE status = 'queued'
W1->              ORDER BY id LIMIT 2 FOR UPDATE SKIP LOCKED)
W1-> RETURNING id;
 id
----
  1
  2
(2 rows)

W2=> UPDATE jobs SET status = 'running', claimed_by = 'w2'
W2-> WHERE id IN (SELECT id FROM jobs WHERE status = 'queued'
W2->              ORDER BY id LIMIT 2 FOR UPDATE SKIP LOCKED)
W2-> RETURNING id;
 id
----
  3
  4
(2 rows)

W1=> COMMIT;
W2=> COMMIT;
```

Clean up: `dropdb ch32_w2`.

## Practice Session 32.3 — Optimistic locking with a version column

**Goal.** Protect a read-modify-write with a `version` column, see it reject stale writers,
find the two ways to get it wrong, and compare its cost with pessimistic locking.

**Setup.** Terminals S1, S2, S3 and O on `ch32_w3`.

```bash
createdb ch32_w3
psql -X -d ch32_w3
```

```sql
CREATE TABLE coach (
    id         int PRIMARY KEY,
    seats_left int NOT NULL CHECK (seats_left >= 0),
    version    int NOT NULL DEFAULT 1
);
INSERT INTO coach VALUES (1, 10, 1);
```

**Task.**

1. Without a version check, have S1 and S2 both read the coach (10 seats), then each write
   back 9. What is the final count, and how many errors were raised?
2. Reset (`UPDATE coach SET seats_left = 10, version = 1;`). Have S1, S2 and S3 all read, then
   each try `UPDATE ... SET seats_left = ..., version = version + 1 WHERE id = 1 AND version =
   <what it read> RETURNING ...`. How many succeed? Retry the losers, re-reading each time,
   until all three seats are booked. How many attempts were needed?
3. Reset. Drop `version = version + 1` from the `UPDATE` (keep the `AND version = 1`). Run S1
   and S2 as before. What goes wrong?
4. Reset. S1 reads (the "edit form" opens), S2 changes the row through a path that does not
   check the version and does bump it, then S1 submits. What does S1's statement return, and
   what should the application say?
5. Reset. Book the three seats with `SELECT ... FOR UPDATE` instead: S1 locks, then S2 and S3
   request the lock (confirm both are waiting before S1 commits). Compare with step 2:
   attempts, failures, waiting.

**Solution.**

Step 1. Ten seats, two bookings, nine left, and no error: the lost update.

```text
          9 |       1
(1 row)
```

Step 2. One winner per version. The version is a ticket: whoever presents the current one
writes, everyone else matches zero rows. Attempts: S1 succeeds; S2 and S3 fail; S2 re-reads
and succeeds; S3 fails again; S3 re-reads and succeeds: six attempts, three failures, for three
seats.

Step 3. Without the increment, the guard never changes, so both writers pass it and the second
overwrites the first: the lost update is back, now with the appearance of protection. The
version must change in *every* statement that changes the row, including ones in other
applications and batch jobs; a trigger that bumps it is the safeguard when you cannot audit
every writer.

Step 4. Zero rows. The application should tell the user that the record changed since the
form was opened and offer to reload it, rather than retry blindly; the user's intent may no
longer make sense against the new state.

```text
S1=> UPDATE coach SET seats_left = 9, version = version + 1 WHERE id = 1 AND version = 1 RETURNING seats_left, version;

```

Step 5. Pessimistic locking has no failures and no retries; S2 and S3 wait, each seeing the
value the previous session committed. The cost is lock time, held from the read to the
commit, which is why it suits short transactions on contended rows and why a user must never
hold one open across a form.

```text
S3=> COMMIT;

```
