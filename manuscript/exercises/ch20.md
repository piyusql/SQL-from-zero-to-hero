# Chapter 20 Exercises — Keys and Identity Strategy at Scale

## Practice Session 20.1 — Measure bloat: bigint vs UUIDv4 vs UUIDv7 at 5M rows

**Goal.** Load the same five million rows under three key strategies and report, with
deterministic measurements only, what each does to the primary-key index and to the WAL.

**Setup.** A scratch database and a time-ordered UUID function. PostgreSQL 15 has no built-in
`uuidv7()` (it arrived in 18); on 18 or later you can skip the function and call the built-in.
This takes a few minutes and a few hundred MB of disk. **Do not time it and do not run
anything else against the server while it loads**: you are measuring counts and sizes, and
the clock would only measure your machine.

```bash
createdb ch20_ws1
psql -P null='(null)' -d ch20_ws1
```

```sql
CREATE EXTENSION pgstattuple;

CREATE FUNCTION uuidv7() RETURNS uuid
LANGUAGE sql VOLATILE PARALLEL SAFE AS $$
  SELECT encode(
           substring(int8send(us / 1000) FROM 3)
        || int2send((x'7000'::int | ((us % 1000) * 4096 / 1000)::int)::int2)
        || substring(uuid_send(gen_random_uuid()) FROM 9 FOR 8), 'hex')::uuid
  FROM (SELECT (extract(epoch FROM clock_timestamp()) * 1000000)::bigint AS us) t
$$;

CREATE TABLE ev_bigint (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
                        account_id int NOT NULL, amount_paise int NOT NULL);
CREATE TABLE ev_v4 (id uuid DEFAULT gen_random_uuid() PRIMARY KEY,
                    account_id int NOT NULL, amount_paise int NOT NULL);
CREATE TABLE ev_v7 (id uuid DEFAULT uuidv7() PRIMARY KEY,
                    account_id int NOT NULL, amount_paise int NOT NULL);
```

**Task.**

1. Prove `uuidv7()` is a valid version-7 UUID: version nibble, variant nibble, and that 100,000
   consecutive calls come out in order. Decode the embedded timestamp of one value and compare it to
   `clock_timestamp()`.
2. Load 5,000,000 rows into each table with one `INSERT ... SELECT` per table, running
   `CHECKPOINT` before each. Capture, for each, the WAL records, full-page images (`fpi`) and
   bytes, using `EXPLAIN (ANALYZE, WAL, ...)` rather than `pg_wal_lsn_diff`. Say why the
   latter would be the wrong instrument on a shared server.
3. `ANALYZE`, then report for each primary key: size, leaf pages, `avg_leaf_density` and
   `leaf_fragmentation` from `pgstatindex()`.
4. After a `CHECKPOINT`, insert 10,000 more rows into each and compare `dirtied` and `fpi`.
5. Reindex the UUIDv4 primary key and report density again. Then build a *fourth* table with
   the same UUIDv4 values but loaded in sorted order. What does that say about whether the
   problem is the type or the insertion order?
6. State your one-line recommendation for a 50-million-row `orders` table and one condition
   that would change it.

**Solution.**

**1 — validity.**

```sql
SELECT substr(id::text, 15, 1) AS version, substr(id::text, 20, 1) AS variant,
       to_timestamp(('x' || substr(replace(id::text, '-', ''), 1, 12))::bit(48)::bigint / 1000.0)
         BETWEEN clock_timestamp() - interval '5 seconds' AND clock_timestamp() AS ts_is_now
FROM (SELECT uuidv7() AS id) s;

CREATE TEMP TABLE probe (n int, id uuid DEFAULT uuidv7());
INSERT INTO probe (n) SELECT i FROM generate_series(1, 100000) i;
SELECT count(*) AS ids, count(*) FILTER (WHERE id < prev) AS out_of_order
FROM (SELECT id, lag(id) OVER (ORDER BY n) AS prev FROM probe) s;
```

```text
 version | variant | ts_is_now
---------+---------+-----------
 7       | 9       | t
(1 row)

CREATE TABLE
INSERT 0 100000
  ids   | out_of_order
--------+--------------
 100000 |            0
(1 row)
```

The version is `7`, the variant nibble is one of `8 9 a b` (RFC 4122/9562 variant `10`), and
the embedded time is now. Zero out of order in a run of 100,000 is what the 12-bit
clock fraction buys; it is not guaranteed across a clock step or two calls in the same
microsecond.

**2 — the loads.** One statement per variant, so the counters are for exactly that statement:

```bash
for t in ev_bigint ev_v4 ev_v7; do
  psql -P null='(null)' -d ch20_ws1 -Atq -c "CHECKPOINT" -c "EXPLAIN (ANALYZE, WAL, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF)
    INSERT INTO $t (account_id, amount_paise) SELECT i % 100000, i % 9973 FROM generate_series(1, 5000000) i" \
  | sed '/Planning:/,$d' | grep -E 'Insert on|^ +WAL|^  Buffers'
done
psql -P null='(null)' -d ch20_ws1 -Atq -c "ANALYZE ev_bigint" -c "ANALYZE ev_v4" -c "ANALYZE ev_v7"
```

```text

  WAL: records=10165225 fpi=12 bytes=700510572

  Buffers: shared hit=19284202 read=768649 dirtied=953874 written=670319, temp read=8545 written=8545
  WAL: records=10024805 fpi=571447 bytes=4171827003
Insert on ev_v7 (actual rows=0 loops=1)
  Buffers: shared hit=10269320 read=14 dirtied=51145 written=57376, temp read=8545 written=8545
  WAL: records=10019280 fpi=44 bytes=771641776
```

`pg_wal_lsn_diff(pg_current_wal_lsn(), start)` measures the *cluster's* WAL, so any other
client (autovacuum, another session, a replica's keepalive) lands in your number. `EXPLAIN
(WAL)` is per statement and per session. The indented `WAL:` line under the bigint scan is 15 MB of sequence WAL
(one record per 32 values) that the UUID variants avoid, and bigint is still the smallest. UUIDv4's
`fpi` is the signature: pages touched at random, each written whole after a checkpoint. Its
total is also the unstable number: in my runs the v4 load wrote between 1.28 and 4.17 GB, because
the count of full-page images depends on how many checkpoints the load straddles. Compare
direction here, and compare exactly in step 4.

**3 — the index.**

```sql
SELECT v.variant, pg_size_pretty(pg_relation_size(v.tbl::regclass)) AS heap,
       pg_size_pretty(pg_relation_size((v.tbl || '_pkey')::regclass)) AS pkey,
       s.leaf_pages, round(s.avg_leaf_density::numeric, 1) AS leaf_density, s.leaf_fragmentation
FROM (VALUES ('bigint', 'ev_bigint'), ('uuidv4', 'ev_v4'), ('uuidv7', 'ev_v7')) v(variant, tbl),
     LATERAL pgstatindex((v.tbl || '_pkey')::regclass) s;
```

```text

---------+--------+--------+------------+--------------+--------------------

 uuidv4  | 249 MB | 194 MB |      24695 |         69.9 |              49.76
 uuidv7  | 249 MB | 151 MB |      19187 |         89.9 |               0.11
(3 rows)
```

**4 — steady state.**

```bash

    INSERT INTO $t (account_id, amount_paise) SELECT i, i FROM generate_series(1, 10000) i" \
  | sed '/Planning:/,$d' | grep -E 'Insert on|^ +WAL|^  Buffers'

```

**5 — reindex, and the same values in sorted order.**

```sql
REINDEX INDEX ev_v4_pkey;
SELECT pg_size_pretty(pg_relation_size('ev_v4_pkey')) AS pkey,
       round(avg_leaf_density::numeric, 1) AS leaf_density, leaf_fragmentation
FROM pgstatindex('ev_v4_pkey');

CREATE TABLE ev_v4_sorted (id uuid PRIMARY KEY, account_id int NOT NULL, amount_paise int NOT NULL);
INSERT INTO ev_v4_sorted
SELECT id, account_id, amount_paise FROM ev_v4 ORDER BY id;
SELECT pg_size_pretty(pg_relation_size('ev_v4_sorted_pkey')) AS pkey,
       round(avg_leaf_density::numeric, 1) AS leaf_density, leaf_fragmentation
FROM pgstatindex('ev_v4_sorted_pkey');
```

```text
REINDEX
  pkey  | leaf_density | leaf_fragmentation
--------+--------------+--------------------
 151 MB |         90.0 |                  0
(1 row)

CREATE TABLE
INSERT 0 5010000
  pkey  | leaf_density | leaf_fragmentation
--------+--------------+--------------------
 151 MB |         90.0 |                  0
(1 row)
```

`REINDEX` builds the index bottom-up from sorted input, so it packs leaves to the fill factor.
Loading the *same* v4 values in sorted order gets the same density through ordinary inserts,
because each new key lands on the right edge. **The type is not the problem; random arrival
order is.** That gives you a cheap fix for bulk loads (sort first, or create the index after
the load) and none for OLTP inserts, where the arrival order is whatever the users do. It
also means a `REINDEX INDEX CONCURRENTLY` on a v4 key gives back density once, and the next
weeks of inserts undo it.

**6 — the recommendation.** `bigint GENERATED ALWAYS AS IDENTITY` with a separate random
`public_id uuid` if the id is exposed. What would change it: ids must be created by
clients or systems that cannot ask the database (offline mobile capture, merging several
writers). Then UUIDv7, not v4, so the index stays right-edge and the 16-byte width is the
only cost paid.

Clean up: `DROP DATABASE ch20_ws1;`

## Practice Session 20.2 — Migrate SERIAL to IDENTITY

**Goal.** Convert a populated `serial` primary key to `GENERATED ... AS IDENTITY` without
rewriting the table, losing the counter, or leaving an orphan sequence, and report exactly
which locks the migration takes.

**Setup.** A scratch database with a 200,000-row `serial` table, and a role that owns nothing.

```bash
createdb ch20_ws2
psql -P null='(null)' -d ch20_ws2
```

```sql
CREATE TABLE payments (id serial PRIMARY KEY, amount numeric(12,2) NOT NULL);
INSERT INTO payments (amount) SELECT i FROM generate_series(1, 200000) i;
DELETE FROM payments WHERE id > 199990;         -- the sequence is now ahead of max(id)
CREATE ROLE ch20_ws2_app LOGIN;
GRANT INSERT ON payments TO ch20_ws2_app;
GRANT USAGE ON SEQUENCE payments_id_seq TO ch20_ws2_app;
```

**Task.**

1. Record the sequence's name (with `pg_get_serial_sequence`), its `last_value`, the table's
   `max(id)` and the table's `pg_relation_filenode()`. Which number must the identity start
   from, and why is it not `max(id) + 1`?
2. Migrate in a single transaction: drop the default, drop the now-unowned sequence, add a
   `GENERATED BY DEFAULT AS IDENTITY` column definition that starts at the right value.
   Before `COMMIT`, list the locks your session holds on `payments`.
3. Prove no rewrite happened, that the next insert gets the right id, and that the
   application role no longer needs `USAGE` on a sequence.
4. Repeat the lock-acquisition with a second session holding a plain `SELECT` in an open
   transaction. What does the migration do, and what is the safe way to run it?
5. Switch the column to `GENERATED ALWAYS` and show the application's old habit of inserting
   explicit ids now fails loudly.

**Solution.**

**1 — inventory.**

```sql
SELECT pg_get_serial_sequence('payments', 'id') AS sequence_name;
SELECT last_value, is_called FROM payments_id_seq;
SELECT max(id) FROM payments;
CREATE TABLE filenode_log AS SELECT pg_relation_filenode('payments') AS filenode_before;
```

```text
     sequence_name
------------------------
 public.payments_id_seq
(1 row)

 last_value | is_called
------------+-----------
     200000 | t
(1 row)

  max
--------
 199990
(1 row)
```

The sequence is at 200,000 because the deleted rows consumed values 199,991–200,000.
Starting at `max(id) + 1` would *reuse* ids that were issued and might still exist in
logs, caches, downstream tables or an audit trail. Start from `last_value + 1`, which is the
value `nextval` would have returned next (`is_called` is true, so the next value is 200,001).

**2 — the migration.**

```sql
BEGIN;
SET LOCAL lock_timeout = '2s';
ALTER TABLE payments ALTER COLUMN id DROP DEFAULT;
DROP SEQUENCE payments_id_seq;
ALTER TABLE payments ALTER COLUMN id ADD GENERATED BY DEFAULT AS IDENTITY (START WITH 200001);
SELECT l.mode, l.granted FROM pg_locks l
WHERE l.relation = 'payments'::regclass AND l.pid = pg_backend_pid() ORDER BY 1;
COMMIT;
```

```text
BEGIN
SET
ALTER TABLE
DROP SEQUENCE
ALTER TABLE
        mode         | granted
---------------------+---------
 AccessExclusiveLock | t
 AccessShareLock     | t
(2 rows)

COMMIT
```

Doing it in one transaction is what makes it safe: no other session can insert between
the `DROP DEFAULT` and the new identity, because the `ACCESS EXCLUSIVE` lock is held from the
first `ALTER` to the `COMMIT`. The second lock row is one the same transaction also holds; the one that matters is
`AccessExclusiveLock`. The `DROP SEQUENCE` is allowed because the sequence's only
dependent, the column default, has already gone. On PostgreSQL 15 there is no way to attach an
*existing* sequence to an identity column; the new identity gets a fresh sequence, so the
starting value is the only thing that carries the counter across.

**3 — checks.**

```sql
SELECT pg_relation_filenode('payments') = (SELECT filenode_before FROM filenode_log) AS no_rewrite;
SET ROLE ch20_ws2_app;
INSERT INTO payments (amount) VALUES (1);
RESET ROLE;
SELECT max(id) AS newest_id FROM payments;
```

```text
 no_rewrite
------------
 t
(1 row)

SET
INSERT 0 1
RESET
 newest_id
-----------
    200001
(1 row)
```

The insert succeeded with only `INSERT` on the table. The old `USAGE` grant went with the
old sequence, and the new identity sequence was never granted to the role, so nothing but
the table privilege was involved. Under `serial` this same role needed a sequence grant
(Chapter 20, section 20.2).

**4 — the lock queue.** `ALTER TABLE` needs `ACCESS EXCLUSIVE`, which conflicts with every
other lock, including the `ACCESS SHARE` of a `SELECT` in an open transaction. A migration
that has to wait *also blocks everything queued behind it*, so it is the waiting, not the
`ALTER`, that hurts. Reproduce it with a session that holds a lock, and a migration that
gives up:

```bash
(psql -d ch20_ws2 -Atq -c "BEGIN" -c "SELECT count(*) FROM payments" -c "SELECT pg_sleep(4)" -c "COMMIT" | grep . ) &
sleep 1
psql -P null='(null)' -d ch20_ws2 -c "SET lock_timeout = '500ms'" \
     -c "ALTER TABLE payments ALTER COLUMN id SET GENERATED ALWAYS" 2>&1 | grep -E "ERROR|ALTER"
wait
```

```text
ERROR:  canceling statement due to lock timeout
199991
```

Always set `lock_timeout` on migrations and retry: a short, failed attempt is cheap, a long
wait is an outage. Chapter 52 builds this into a full migration procedure.

**5 — switch to ALWAYS.** The table was migrated with `BY DEFAULT` so that any legacy writer
that supplies its own id keeps working during rollout. Once the application no longer does:

```sql
ALTER TABLE payments ALTER COLUMN id SET GENERATED ALWAYS;
INSERT INTO payments (id, amount) VALUES (1, 1);
INSERT INTO payments (amount) VALUES (2) RETURNING id;
```

```text
ALTER TABLE
ERROR:  cannot insert a non-DEFAULT value into column "id"
DETAIL:  Column "id" is an identity column defined as GENERATED ALWAYS.
HINT:  Use OVERRIDING SYSTEM VALUE to override.
   id
--------
 200002
(1 row)

INSERT 0 1
```

Clean up:

```sql
\c postgres
DROP DATABASE ch20_ws2;
DROP OWNED BY ch20_ws2_app;
DROP ROLE ch20_ws2_app;
```
