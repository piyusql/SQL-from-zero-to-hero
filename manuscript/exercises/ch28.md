# Chapter 28 Exercises — Full-Text Search

## Practice Session 28.1 — Searchable product catalog

**Goal.** Turn a 60,000-row product table into a searchable catalog: a stored, indexed
`tsvector`, queries built safely from user input, and evidence that the index is used.

**Setup.** The generator builds a 60,000-row `catalog` (name, category, a two-sentence
description, price) deterministically from `md5`, so your counts will match the ones quoted
in the Solution. It needs no other dataset.

```bash
createdb ch28_ws1
psql -d ch28_ws1
```

```sql
\pset null '(null)'
SET max_parallel_workers_per_gather = 0;   -- pin plans: no parallel workers
CREATE TABLE catalog AS
WITH n(noun, category, material) AS (VALUES
  ('pressure cooker','kitchen','stainless steel'), ('iron tawa','kitchen','iron'),
  ('idli steamer','kitchen','stainless steel'), ('masala dabba','kitchen','stainless steel'),
  ('copper bottle','kitchen','copper'), ('steel tiffin','kitchen','stainless steel'),
  ('brass diya','decor','brass'), ('wall hanging','decor','cotton'),
  ('terracotta planter','decor','clay'), ('jute rug','decor','jute'),
  ('teak tray','decor','teak'), ('cotton kurta','apparel','cotton'),
  ('silk saree','apparel','silk'), ('linen shirt','apparel','linen'),
  ('handloom dupatta','apparel','cotton'), ('leather sandals','apparel','leather'),
  ('yoga mat','wellness','jute'), ('neem comb','wellness','neem wood'),
  ('herbal tea','wellness','tulsi'), ('ayurvedic hair oil','wellness','coconut oil')),
 a(adj) AS (VALUES ('handcrafted'),('pure'),('organic'),('durable'),('lightweight'),
  ('traditional'),('premium'),('festive'),('rustic'),('everyday')),
 o(origin) AS (VALUES ('Jaipur'),('Mysuru'),('Kanchipuram'),('Varanasi'),('Moradabad'),
  ('Kochi'),('Kutch'),('Lucknow'),('Darjeeling'),('Channapatna')),
 s(sentence) AS (VALUES
  ('Ideal for gifting during Diwali.'),('Easy to clean and dishwasher safe.'),
  ('Cooks rice and dal evenly.'),('Not suitable for induction cooktops.'),
  ('Comes in a reusable cloth bag.'),('Free from plastic and synthetic dyes.'),
  ('Suitable for daily cooking in small kitchens.'),('Colours do not fade after washing.'),
  ('Loved by customers in Bengaluru and Pune.'),('Cooked food stays warm for hours.'),
  ('A calming gift for the whole family.'),('Ships within two days across India.')),
 na AS (SELECT *, row_number() OVER () - 1 AS i FROM n),
 aa AS (SELECT *, row_number() OVER () - 1 AS i FROM a),
 oa AS (SELECT *, row_number() OVER () - 1 AS i FROM o),
 sa AS (SELECT *, row_number() OVER () - 1 AS i FROM s),
 g AS (SELECT id, decode(md5(id::text), 'hex') AS h FROM generate_series(1, 60000) id)
SELECT g.id, 'SKU-' || lpad(g.id::text, 6, '0') AS sku,
       initcap(aa.adj || ' ' || na.noun) || ' from ' || oa.origin AS name,
       na.category,
       initcap(aa.adj) || ' ' || na.noun || ' made of ' || na.material || ' by artisans in ' || oa.origin
         || '. ' || s1.sentence || ' ' || s2.sentence AS description,
       (200 + get_byte(g.h,7) * 12 + get_byte(g.h,8))::numeric(10,2) AS price
FROM g
JOIN na ON na.i = get_byte(g.h,0) % 20
JOIN aa ON aa.i = get_byte(g.h,1) % 10
JOIN oa ON oa.i = get_byte(g.h,2) % 10
JOIN sa s1 ON s1.i = get_byte(g.h,3) % 12
JOIN sa s2 ON s2.i = get_byte(g.h,4) % 12
ORDER BY g.id;
ALTER TABLE catalog ADD PRIMARY KEY (id);
ANALYZE catalog;
```

**Task.**

1. Try to add a `doc tsvector` generated column using the one-argument
   `to_tsvector(description)`. Read the error, and explain why the two-argument form fixes it.
2. Add `doc` as a stored generated column over `name || ' ' || description` using the
   `english` configuration, and build a GIN index on it. Report the heap size, the index
   size and the row count.
3. Count the products matching `pressure cooker` as a phrase, but not `induction`, using
   the constructor you would put behind a search box. Then show what the strict
   constructor does with the same raw text.
4. Show that a search for `tiffin diwali` uses the index, and report the heap pages it
   touched.
5. Count the rows a plain `ILIKE '%cooking%'` finds against the full-text search for
   `cooking`. Name the words that account for the difference.
6. Build a type-ahead: how many products match the prefix `kur`?
7. On a 20,000-row copy with its own GIN index, insert 100 more rows and inspect the
   pending list with `pageinspect` (`CREATE EXTENSION pageinspect` needs superuser). Then
   drain it.

**Solution.**

```sql
ALTER TABLE catalog ADD COLUMN doc tsvector
  GENERATED ALWAYS AS (to_tsvector(description)) STORED;
```

```text
ERROR:  generation expression is not immutable
```

The one-argument form reads `default_text_search_config`, which any session can change, so
its result is only stable within a statement. A generated column stores a value computed
once and must be reproducible from the row alone, so Postgres demands `IMMUTABLE`. The
two-argument form with a literal configuration name qualifies.

```sql
ALTER TABLE catalog ADD COLUMN doc tsvector
  GENERATED ALWAYS AS (to_tsvector('english', name || ' ' || description)) STORED;
CREATE INDEX catalog_doc_gin ON catalog USING gin (doc);
ANALYZE catalog;
SELECT pg_size_pretty(pg_relation_size('catalog'))         AS heap,
       pg_size_pretty(pg_relation_size('catalog_doc_gin')) AS gin,
       (SELECT count(*) FROM catalog)                      AS n;
```

```text
 heap  |   gin   |   n
-------+---------+-------
 27 MB | 2200 kB | 60000
(1 row)
```

```sql
SELECT count(*) FROM catalog
WHERE  doc @@ websearch_to_tsquery('english', '"pressure cooker" -induction');
SELECT to_tsquery('english', '"pressure cooker" -induction');
```

```text
 count
-------
  2575
(1 row)

ERROR:  syntax error in tsquery: ""pressure cooker" -induction"
```

`websearch_to_tsquery` reads quotes, `-` and `OR` and never raises a syntax error, which is
the property a search box needs. `to_tsquery` expects tsquery syntax and errors on anything
else.

```sql
\o /dev/null
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF)   -- warm-up, discarded
SELECT id FROM catalog WHERE doc @@ plainto_tsquery('english', 'tiffin diwali');
\o
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF)
```


A Bitmap Index Scan, and `Heap Blocks: exact` is the number of table pages visited, out of
roughly 3,400 in the table. The `Planning:` lines depend on cache state and can differ on
your machine.

```sql
SELECT count(*) FILTER (WHERE description ILIKE '%cooking%')        AS ilike_cooking,
       count(*) FILTER (WHERE doc @@ plainto_tsquery('english', 'cooking')) AS fts_cooking
FROM   catalog;
SELECT count(*) FILTER (WHERE description ~* '\mcooks\M')  AS cooks,
       count(*) FILTER (WHERE description ~* '\mcooked\M') AS cooked,
       count(*) FILTER (WHERE description ~* '\mcooking\M') AS cooking
FROM   catalog;
```

```text
 ilike_cooking | fts_cooking
---------------+-------------
          9354 |       26106
(1 row)

 cooks | cooked | cooking
-------+--------+---------
  9953 |   9435 |    9354
(1 row)
```

The stemmer reduces `cooks`, `cooked` and `cooking` to `cook`, so the full-text count is
at most the sum of the three word counts (a row holding two forms counts once). `ILIKE`
only finds the literal string.

```sql
SELECT count(*) FROM catalog WHERE doc @@ to_tsquery('english', 'kur:*');
SELECT count(*) FROM catalog WHERE doc @@ to_tsquery('english', 'kurta');
```

```text
 count
-------
  3104
(1 row)

 count
-------
  3104
(1 row)
```

The counts agree because `kurta` is the only lexeme that starts with `kur`; the chapter's
`cook:*` example is the one where they differ. `:*` is prefix matching and only exists in
`to_tsquery`. If you take a partial word from a
user, sanitise it (letters and digits only) before appending `:*`, because `to_tsquery` is
strict about syntax.

```sql
CREATE EXTENSION pageinspect;
CREATE TABLE ping AS SELECT * FROM catalog WHERE id <= 20000;
CREATE INDEX ping_gin ON ping USING gin (doc);
SELECT n_pending_pages, n_pending_tuples FROM gin_metapage_info(get_raw_page('ping_gin', 0));
INSERT INTO ping SELECT * FROM catalog WHERE id BETWEEN 20001 AND 20100;
SELECT n_pending_pages, n_pending_tuples FROM gin_metapage_info(get_raw_page('ping_gin', 0));
SELECT gin_clean_pending_list('ping_gin') AS pages_cleaned;
SELECT n_pending_pages, n_pending_tuples FROM gin_metapage_info(get_raw_page('ping_gin', 0));
```

```text
 n_pending_pages | n_pending_tuples
-----------------+------------------
               0 |                0
(1 row)

 n_pending_pages | n_pending_tuples
-----------------+------------------
               4 |              100
(1 row)

 pages_cleaned
---------------
             4
(1 row)

 n_pending_pages | n_pending_tuples
-----------------+------------------
               0 |                0
(1 row)
```

With `fastupdate` on, new entries go to a pending list instead of into the index proper. It
is drained by `VACUUM`, by `gin_clean_pending_list`, or when it outgrows
`gin_pending_list_limit`. The consequence is that write latency is bimodal: most inserts
are cheap, and an occasional one pays for the merge. (The `ping` copy holds a plain
`tsvector` column, since `CREATE TABLE AS` does not copy the generation expression.)

**Task.**

1. Show the stored vector for product 1 and identify which lexemes carry weight `A`.
2. Rank the query `tiffin OR rice` and group by score. How many distinct scores are there,

3. Rank `cooking` with `ts_rank(doc, q)`, `ts_rank(doc, q, 1)` (divide by

```sql
SELECT id, ts_headline('english', description, q,
       'StartSel=<b>, StopSel=</b>, MaxFragments=1, MaxWords=12, MinWords=5') AS snippet

WHERE  doc @@ q ORDER BY id LIMIT 3;
SELECT ts_headline('simple', 'Not suitable for induction cooktops.',
                   websearch_to_tsquery('english', 'induction'),
                   'StartSel=<b>, StopSel=</b>') AS mismatched_config;
```

configuration in the vector, the query and the headline.

`ts_stat` returns lexemes in their stored, stemmed form, which is why `cook` and `pressur`
are in the table rather than `cooking` and `pressure`.

```sql
SELECT t.word AS typed, l.word AS fixed, round(similarity(t.word, l.word)::numeric, 3) AS sim
FROM (VALUES ('presure'), ('dupata'), ('tiffn'), ('kurtha')) t(word)
CROSS JOIN LATERAL (SELECT word FROM lexemes WHERE word % t.word
```

`%` uses the threshold (default 0.3), so it is the candidate filter, and `ORDER BY
similarity` picks the best of them.

```sql
CREATE FUNCTION fix_query(q text) RETURNS tsquery LANGUAGE sql STABLE AS $$
  WITH typed AS (
    SELECT w, ord, (ts_lexize('english_stem', w))[1] AS stem
    FROM unnest(string_to_array(lower(trim(q)), ' ')) WITH ORDINALITY AS t(w, ord)
    WHERE cardinality(ts_lexize('english_stem', w)) > 0),
  fixed AS (
    SELECT t.ord, coalesce(e.word, n.word, t.stem) AS lexeme
    FROM typed t
    LEFT JOIN lexemes e ON e.word = t.stem
    LEFT JOIN LATERAL (SELECT word FROM lexemes
                       WHERE e.word IS NULL AND word % t.stem
                       ORDER BY similarity(word, t.stem) DESC, ndoc DESC LIMIT 1) n ON true)
  SELECT to_tsquery('simple', string_agg(quote_literal(lexeme), ' & ' ORDER BY ord)) FROM fixed
$$;
SELECT fix_query('the presure cooker') AS fixed;
```

```text
        fixed
----------------------
 'pressur' & 'cooker'
(1 row)
```

The word `the` is a stop word (`ts_lexize` returns an empty array), so it is dropped. A word
that is already a lexeme is kept. A word with no neighbour above the threshold is passed
through as typed, so it returns no rows rather than wrong ones.

The shopper who meant `cooker` is corrected to `cook`, because `cookr` is closer to `cook` by
trigrams. `ndoc` only breaks exact ties in similarity, and there is no tie here. Trigram
distance measures spelling, not intent.

```sql
SET pg_trgm.similarity_threshold = 0.5;
SELECT t.word AS typed, l.word AS fixed
FROM (VALUES ('presure'), ('dupata'), ('tiffn'), ('kurtha')) t(word)
LEFT JOIN LATERAL (SELECT word FROM lexemes WHERE word % t.word
                   ORDER BY similarity(word, t.word) DESC, ndoc DESC LIMIT 1) l ON true;
RESET pg_trgm.similarity_threshold;
```

```text
  typed  |  fixed
---------+---------
 presure | (null)
 dupata  | dupatta
 tiffn   | (null)

(4 rows)
```

Words that do not clear 0.5 get no correction (`(null)` here). A higher threshold trades
missed corrections for fewer wrong ones; short words have few trigrams and score low even
when they are one letter off, so a single global threshold is a blunt tool.

```sql
SELECT DISTINCT name, round(word_similarity('tifin', name)::numeric, 3) AS ws
FROM   catalog WHERE 'tifin' <% name
ORDER BY ws DESC, name LIMIT 5;
```

```text
                 name                  |  ws
---------------------------------------+-------

 Durable Steel Tiffin from Jaipur      | 0.625
 Durable Steel Tiffin from Kanchipuram | 0.625
```

`word_similarity` scores the query against the best-matching contiguous run of `name`, so a
short misspelt word can be matched against long text directly, and `<%` is its operator
form. It needs no vocabulary table, but it finds matching *names*, not lexemes, so it
cannot feed a corrected word back into the full-text query. Index mechanics for `<%` are
Chapter 27's.
