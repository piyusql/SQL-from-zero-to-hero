# Chapter 27 Exercises — Pattern Matching and Regular Expressions

## Practice Session 27.1 — Parse semi-structured logs

**Goal.** Turn 30,000 free-text application log lines into a typed table with one regular
expression, account for every line that did not parse, and produce a report whose denominators
you can defend.

**Setup.** A scratch database and a generated log. The lines look like a real service log:
a timestamp, a level, a service, then `key=value` pairs, with some lines that break the format
(a stack-trace fragment every 40th line) and some that carry optional fields.

```bash
createdb ch27_ws1
psql -d ch27_ws1
```

```sql
\pset null '(null)'
CREATE TABLE app_log (id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY, line text NOT NULL);
INSERT INTO app_log (line)
SELECT CASE
  WHEN g % 40 = 0 THEN '    at com.vyapar.pay.Gateway.charge(Gateway.java:' || (80 + g % 30) || ')'
  ELSE to_char(timestamp '2026-09-12 09:00:00' + g * interval '1 second', 'YYYY-MM-DD"T"HH24:MI:SS') || '+05:30 '
    || CASE WHEN g % 13 = 0 THEN 'ERROR' WHEN g % 5 = 0 THEN 'WARN' ELSE 'INFO' END || ' '
    || (ARRAY['checkout','payment','inventory','notify'])[1 + g % 4]
    || ' order=ORD-' || lpad((g * 7 % 9000)::text, 5, '0')
    || ' city=' || (ARRAY['Pune','Bengaluru','Kochi','Jaipur','Chennai','Lucknow'])[1 + g % 6]
    || CASE WHEN g % 13 = 0 THEN ' msg="gateway timeout" ms=' || (2000 + g % 1500) || ' retry=' || (g % 3)
            WHEN g % 5 = 0  THEN ' msg="slow response" ms=' || (800 + g % 900)
            ELSE ' msg="ok"' END
  END
FROM generate_series(1, 30000) g;

SELECT id, line FROM app_log WHERE id IN (1, 13, 40) ORDER BY id;
```

```text
 id |                                                     line
----+--------------------------------------------------------------------------------------------------------------
  1 | 2026-09-12T09:00:01+05:30 INFO payment order=ORD-00007 city=Bengaluru msg="ok"
 13 | 2026-09-12T09:00:13+05:30 ERROR payment order=ORD-00091 city=Bengaluru msg="gateway timeout" ms=2013 retry=1
 40 |     at com.vyapar.pay.Gateway.charge(Gateway.java:90)
(3 rows)
```

**Task.**

1. Write one `regexp_match` pattern that captures timestamp, level, service, order number,
   city and message, and use it in a `CROSS JOIN LATERAL` to create a table `parsed`. Keep every
   input row. Cast nothing that can fail.
2. Count how many lines parsed and how many did not. Show three of the unparsed lines.
3. Add `ms` and `retry` as integers, pulled out with `substring(... FROM ...)`. Explain why a line
   with no `ms=` gives NULL and why that is the right answer.
4. Report, per service, the number of requests and the share of them that are `ERROR`, and say
   what the `NULL` group is. Then compute the overall error rate twice, once over `count(*)`
   and once over parsed lines only, and say which one is the error rate.
5. The `key=value` pairs are extensible. Unpivot every pair of every line into
   `(id, key, value)` rows with `regexp_matches(..., 'g')` and list the distinct keys with counts.
6. Mask the order numbers (`ORD-01234` becomes `ORD-#####`) so a sample can go into a ticket.
7. Firmware strings in the `telemetry` database (`devices.firmware`, values like `2.2.0-rc1`)
   need the same treatment: split them into major, minor, patch and pre-release, and count devices
   per pre-release tag.

**Solution.**

```sql
CREATE TABLE parsed AS
SELECT l.id,
       m[1]::timestamptz AS ts, m[2] AS level, m[3] AS service,
       m[4] AS order_no, m[5] AS city, m[6] AS msg
FROM   app_log l
CROSS  JOIN LATERAL regexp_match(l.line,
   '^(\S+) (INFO|WARN|ERROR) (\w+) order=(ORD-\d+) city=(\w+) msg="([^"]*)"') AS m;

SELECT count(*) AS lines, count(level) AS parsed, count(*) - count(level) AS unparsed FROM parsed;
SELECT l.id, l.line FROM parsed p JOIN app_log l USING (id) WHERE p.level IS NULL ORDER BY id LIMIT 3;
```

```text
 lines | parsed | unparsed
-------+--------+----------
 30000 |  29250 |      750
(1 row)

 id  |                          line
-----+--------------------------------------------------------
  40 |     at com.vyapar.pay.Gateway.charge(Gateway.java:90)
  80 |     at com.vyapar.pay.Gateway.charge(Gateway.java:100)
 120 |     at com.vyapar.pay.Gateway.charge(Gateway.java:80)
(3 rows)
```

`CROSS JOIN LATERAL` with `regexp_match` keeps non-matching lines, with NULL in every column,
because the function returns one NULL row where `regexp_matches` would return none. That is
why the count subtracts. The stack-trace lines are expected noise (one in 40, 750 lines); the
point of counting is that if the number moves, the format changed.

```sql
ALTER TABLE parsed ADD COLUMN ms int, ADD COLUMN retry int;
UPDATE parsed p SET ms    = substring(l.line FROM ' ms=(\d+)')::int,
                    retry = substring(l.line FROM ' retry=(\d+)')::int
FROM   app_log l WHERE l.id = p.id;

SELECT count(*) FILTER (WHERE ms IS NULL) AS no_ms, count(*) FILTER (WHERE retry IS NULL) AS no_retry FROM parsed WHERE level IS NOT NULL;
```

```text
 no_ms | no_retry
-------+----------
 22154 |    27000
(1 row)
```

A line without `ms=` has no duration; NULL says so. Writing `0` would put thousands of
fictitious instant requests into any average. The leading space in `' ms=(\d+)'` matters: without it
the pattern would also match the tail of a longer key such as `runms=`.

```sql
SELECT service,
       count(level)                                                        AS requests,
       round(100.0 * count(*) FILTER (WHERE level = 'ERROR') / nullif(count(level), 0), 2) AS pct_error
FROM   parsed
GROUP  BY service ORDER BY service NULLS FIRST;

SELECT round(100.0 * count(*) FILTER (WHERE level = 'ERROR') / count(*), 3)     AS pct_of_all_rows,
       round(100.0 * count(*) FILTER (WHERE level = 'ERROR') / count(level), 3) AS pct_of_requests
FROM   parsed;
```

```text
  service  | requests | pct_error
-----------+----------+-----------
 (null)    |        0 |    (null)
 checkout  |     6750 |      7.69
 inventory |     7500 |      7.69
 notify    |     7500 |      7.69
 payment   |     7500 |      7.69
(5 rows)

 pct_of_all_rows | pct_of_requests
-----------------+-----------------
           7.500 |           7.692
(1 row)
```

Grouping by a NULL gives the NULL its own group, so the per-service table shows the unparsed lines
as a `(null)` service with zero requests instead of hiding them; `nullif` keeps that group from
dividing by zero. Per service the two denominators agree, because the noise lives in its own
group. Across the whole table they do not: dividing by `count(*)` counts stack-trace lines
as requests that did not fail, and understates the error rate. Only rows with a `level` are requests.

```sql
SELECT m[1] AS key, count(*) AS occurrences
FROM   app_log, regexp_matches(line, '(\w+)=("[^"]*"|\S+)', 'g') AS m
GROUP  BY 1 ORDER BY 2 DESC, 1;

SELECT regexp_replace(line, 'ORD-\d+', 'ORD-#####', 'g') AS masked FROM app_log WHERE id = 13;
```

```text
  key  | occurrences
-------+-------------
 city  |       29250
 msg   |       29250
 order |       29250
 ms    |        7096
 retry |        2250
(5 rows)

                                                    masked
--------------------------------------------------------------------------------------------------------------
 2026-09-12T09:00:13+05:30 ERROR payment order=ORD-##### city=Bengaluru msg="gateway timeout" ms=2013 retry=1
(1 row)
```

Here `regexp_matches` is the right tool: one line yields several rows, and a line with no
pairs correctly yields none. Note `ms` and `retry` appear only on the lines that carry them.

```sql
\c telemetry
\pset null '(null)'
SELECT m[1]::int AS major, m[2]::int AS minor, m[3]::int AS patch, m[4] AS prerelease, count(*) AS devices
FROM   devices, regexp_match(firmware, '^(\d+)\.(\d+)\.(\d+)(?:-(\w+))?$') AS m
GROUP  BY 1, 2, 3, 4 ORDER BY 1, 2, 3;
```

```text
 major | minor | patch | prerelease | devices
-------+-------+-------+------------+---------
     1 |     8 |     2 | (null)     |      45
     2 |     0 |     0 | (null)     |      43
     2 |     1 |     4 | (null)     |      71
     2 |     2 |     0 | rc1        |      41
(4 rows)
```

The optional group `(?:-(\w+))?` is unset for a release, and the array holds `NULL` for it,
so the pre-release column is `(null)` for stable versions. Anchoring with `^` and `$` means an
unexpected firmware string produces no row, not a wrong one; check
`SELECT count(*) FROM devices` against the sum if you want to prove nothing was dropped.

## Practice Session 27.2 — Index a prefix search

**Goal.** Reproduce a prefix `LIKE` that ignores its index, fix it three ways, and find what each
fix costs.

**Setup.** A scratch database on a cluster whose default collation is not `C` (check first; the
book's cluster uses `en_US.UTF-8`).

```bash
createdb ch27_ws2
psql -d ch27_ws2
```

```sql
\pset null '(null)'
SET max_parallel_workers_per_gather = 0;
CREATE TABLE contact (
    id    int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name  text NOT NULL,
    email text NOT NULL,
    sku   text NOT NULL);
INSERT INTO contact (name, email, sku)
SELECT (ARRAY['Anita','Rajesh','Priya','Arjun','Fatima','Harpreet','Meera','Imran','Sneha','Rohit'])[1 + g % 10]
       || ' ' ||
       (ARRAY['Rao','Kumar','Menon','Iyer','Sheikh','Singh','Banerjee','Reddy','Mukherjee','Patel'])[1 + (g / 10) % 10],
       'user' || g || '@vyapar.example',
       'SKU-' || lpad(g::text, 6, '0')
FROM generate_series(1, 200000) g;
ANALYZE contact;

CREATE FUNCTION explain_warm(q text) RETURNS TABLE ("QUERY PLAN" text)
LANGUAGE plpgsql AS $$
DECLARE l text;
BEGIN
    EXECUTE 'SELECT count(*) FROM (' || q || ') s';
    FOR l IN EXECUTE 'EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF) ' || q LOOP
        EXIT WHEN l LIKE 'Planning:%';
        "QUERY PLAN" := l; RETURN NEXT;
    END LOOP;
END $$;

SELECT datname, datcollate FROM pg_database WHERE datname = current_database();
```

```text
 datname  | datcollate
----------+-------------
 ch27_ws2 | en_US.UTF-8
(1 row)
```

**Task.**

1. Create an ordinary index on `sku` and explain `sku LIKE 'SKU-1500%'`. Record the node type and
   the buffers.
2. Rewrite the predicate by hand as a range (`sku >= 'SKU-1500' AND sku < 'SKU-1501'`) and explain
   it. What does that tell you about where the failure is?
3. Replace the index with one using `text_pattern_ops`. Explain the `LIKE` again, then explain
   `sku = 'SKU-000150'`, `sku < 'SKU-000150'` and `ORDER BY sku LIMIT 5`. Which of the four use the
   index?
4. Build a second table `contact_c` whose `sku` column is declared `COLLATE "C"`, with a plain index
   on it. Show that `LIKE` prefix, `=` and `<` all use that one index.
5. Show that `ILIKE 'sku-1500%'` uses none of these. Make a case-insensitive prefix search on
   `email` fast with an expression index, and prove it.
6. A user types `SKU_1500` into a search box and you build `LIKE input || '%'`. Show what `_` does to
   the row count, then fix it with escaping.
7. Prepare the statement `SELECT id FROM contact WHERE sku LIKE $1` and force a generic plan. Explain what
   happens, and what you would tell the application team.

**Solution.**

```sql
CREATE INDEX contact_sku_idx ON contact (sku);
SELECT * FROM explain_warm($$SELECT id FROM contact WHERE sku LIKE 'SKU-1500%'$$);
EXPLAIN (COSTS OFF) SELECT id FROM contact WHERE sku >= 'SKU-1500' AND sku < 'SKU-1501';
```

```text
                  QUERY PLAN
-----------------------------------------------
 Seq Scan on contact (actual rows=100 loops=1)
   Filter: (sku ~~ 'SKU-1500%'::text)
   Rows Removed by Filter: 199900
   Buffers: shared hit=2091
(4 rows)

                               QUERY PLAN
------------------------------------------------------------------------
 Index Scan using contact_sku_idx on contact
   Index Cond: ((sku >= 'SKU-1500'::text) AND (sku < 'SKU-1501'::text))
(2 rows)
```

A Seq Scan for `LIKE`, an Index Scan for the identical range. The index is fine; the planner will
not *derive* the range from `LIKE` under a locale collation, because in `en_US` a prefix does not
define a contiguous range. If you can write the range yourself the plain index works, which is a
legitimate fix when you control the SQL.

```sql
DROP INDEX contact_sku_idx;
CREATE INDEX contact_sku_pat ON contact (sku text_pattern_ops);
SET enable_bitmapscan = off;   -- pinned: at 100 rows the planner flips between Index and Bitmap Scan
SELECT * FROM explain_warm($$SELECT id FROM contact WHERE sku LIKE 'SKU-1500%'$$);
EXPLAIN (COSTS OFF) SELECT id FROM contact WHERE sku = 'SKU-000150';
EXPLAIN (COSTS OFF) SELECT id FROM contact WHERE sku < 'SKU-000150';
EXPLAIN (COSTS OFF) SELECT id FROM contact ORDER BY sku LIMIT 5;
RESET enable_bitmapscan;
```

```text
                                 QUERY PLAN
----------------------------------------------------------------------------
 Index Scan using contact_sku_pat on contact (actual rows=100 loops=1)
   Index Cond: ((sku ~>=~ 'SKU-1500'::text) AND (sku ~<~ 'SKU-1501'::text))
   Filter: (sku ~~ 'SKU-1500%'::text)
   Buffers: shared hit=6
(4 rows)

                 QUERY PLAN
---------------------------------------------
 Index Scan using contact_sku_pat on contact
   Index Cond: (sku = 'SKU-000150'::text)
(2 rows)

              QUERY PLAN
--------------------------------------
 Seq Scan on contact
   Filter: (sku < 'SKU-000150'::text)
(2 rows)

           QUERY PLAN
---------------------------------
 Limit
   ->  Sort
         Sort Key: sku
         ->  Seq Scan on contact
(4 rows)
```

`LIKE` and `=` use the index; `<` and `ORDER BY` do not, because the operator class compares bytes
and does not define the column's ordering. If you need ranges as well, you need two indexes.

```sql
CREATE TABLE contact_c (id int, sku text COLLATE "C" NOT NULL);
INSERT INTO contact_c SELECT id, sku FROM contact;
CREATE INDEX contact_c_sku ON contact_c (sku);
ANALYZE contact_c;
EXPLAIN (COSTS OFF) SELECT id FROM contact_c WHERE sku LIKE 'SKU-1500%';
EXPLAIN (COSTS OFF) SELECT id FROM contact_c WHERE sku = 'SKU-000150';
EXPLAIN (COSTS OFF) SELECT id FROM contact_c WHERE sku < 'SKU-000150';
```

```text
                               QUERY PLAN
------------------------------------------------------------------------
 Index Scan using contact_c_sku on contact_c
   Index Cond: ((sku >= 'SKU-1500'::text) AND (sku < 'SKU-1501'::text))
   Filter: (sku ~~ 'SKU-1500%'::text)
(3 rows)

                 QUERY PLAN
---------------------------------------------
 Index Scan using contact_c_sku on contact_c
   Index Cond: (sku = 'SKU-000150'::text)
(2 rows)

                 QUERY PLAN
---------------------------------------------
 Index Scan using contact_c_sku on contact_c
   Index Cond: (sku < 'SKU-000150'::text)
(2 rows)
```

One ordinary index serves all three. For identifiers, this is the design to choose: the collation is a
property of the column, and no query has to know about operator classes.

```sql
EXPLAIN (COSTS OFF) SELECT id FROM contact_c WHERE sku ILIKE 'sku-1500%';
CREATE INDEX contact_email_lower ON contact (lower(email) text_pattern_ops);
SELECT * FROM explain_warm($$SELECT id FROM contact WHERE lower(email) LIKE lower('User15000%')$$);
```

```text
              QUERY PLAN
---------------------------------------
 Seq Scan on contact_c
   Filter: (sku ~~* 'sku-1500%'::text)
(2 rows)

                                              QUERY PLAN
------------------------------------------------------------------------------------------------------
 Bitmap Heap Scan on contact (actual rows=11 loops=1)
   Filter: (lower(email) ~~ 'user15000%'::text)
   Heap Blocks: exact=2
   Buffers: shared hit=5
   ->  Bitmap Index Scan on contact_email_lower (actual rows=11 loops=1)
         Index Cond: ((lower(email) ~>=~ 'user15000'::text) AND (lower(email) ~<~ 'user15001'::text))
         Buffers: shared hit=3
(7 rows)
```

`ILIKE` folds case, and folding breaks byte order, so it scans. The expression index works because the
query is written as `lower(email) LIKE ...`, the same expression, and the application must write it that
way every time. If it cannot be guaranteed, the trigram index of Session 27.3 does `ILIKE` directly.

```sql
SELECT count(*) AS underscore_as_wildcard FROM contact WHERE sku LIKE 'SKU_1500' || '%';
SELECT count(*) AS escaped
FROM   contact
WHERE  sku LIKE replace(replace(replace('SKU_1500', '\', '\\'), '%', '\%'), '_', '\_') || '%';
SELECT count(*) AS literal_hyphen FROM contact WHERE sku LIKE 'SKU-1500' || '%';
```

```text
 underscore_as_wildcard
------------------------
                    100
(1 row)

 escaped
---------
       0
(1 row)

 literal_hyphen
----------------
            100
(1 row)
```

The unescaped `_` matches any character, including the intended `-`, so this particular typo still
returns rows: the query "works" and is wrong in a way no error will ever report. Escaped, `SKU_1500`
matches nothing, which is the true answer.

```sql
SET plan_cache_mode = force_generic_plan;
PREPARE by_prefix(text) AS SELECT id FROM contact WHERE sku LIKE $1;
EXPLAIN (COSTS OFF) EXECUTE by_prefix('SKU-1500%');
RESET plan_cache_mode;
```

```text
      QUERY PLAN
-----------------------
 Seq Scan on contact
   Filter: (sku ~~ $1)
(2 rows)
```

A Seq Scan, with the index present and the pattern a prefix. A generic plan is built without seeing the
parameter value, so it cannot rewrite `LIKE` into a range. Tell the application team to test through
the driver's prepared-statement path, and if the driver switches to generic plans, either pass
`sku >= $1 AND sku < $2` computed in application code, or keep custom plans for this statement.

## Practice Session 27.3 — Accelerate `%substring%`

**Goal.** Take a leading-wildcard search from a sequential scan to a bitmap index scan with `pg_trgm`, choose
between GIN and GiST with evidence, and find where trigrams stop helping.

**Setup.** As before. This session enables `pg_trgm`, which ships with the PostgreSQL contrib package.

```bash
createdb ch27_ws3
psql -d ch27_ws3
```

```sql
\pset null '(null)'
SET max_parallel_workers_per_gather = 0;
CREATE EXTENSION pg_trgm;
CREATE TABLE contact (
    id    int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name  text NOT NULL,
    email text NOT NULL);
INSERT INTO contact (name, email)
SELECT (ARRAY['Anita','Rajesh','Priya','Arjun','Fatima','Harpreet','Meera','Imran','Sneha','Rohit'])[1 + g % 10]
       || ' ' ||
       (ARRAY['Rao','Kumar','Menon','Iyer','Sheikh','Singh','Banerjee','Reddy','Mukherjee','Patel'])[1 + (g / 10) % 10],
       'user' || g || '@vyapar.example'
FROM generate_series(1, 200000) g;
ANALYZE contact;

CREATE FUNCTION explain_warm(q text) RETURNS TABLE ("QUERY PLAN" text)
LANGUAGE plpgsql AS $$
DECLARE l text;
BEGIN
    EXECUTE 'SELECT count(*) FROM (' || q || ') s';
    FOR l IN EXECUTE 'EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF) ' || q LOOP
        EXIT WHEN l LIKE 'Planning:%';
        "QUERY PLAN" := l; RETURN NEXT;
    END LOOP;
END $$;
```

**Task.**

1. Explain `email LIKE '%r15000%'` with no index. Record node type, rows removed, buffers.
2. Create a GIN trigram index on `email` and explain it again.
3. Create a GiST trigram index as well, compare all three index sizes against the table and against a
   B-tree on `email`, and say what the planner picks when both exist.
4. Explain `'%15%'` and `'%.example'`. For the first, force the index with
   `enable_seqscan = off` and report what it costs. Say why the second is not a trigram case.
5. Show that `ILIKE '%R15000%'` and the regex `~* 'R15[0-9]{3}@'` can use the same index. For the
   regex, report how many rows the index returned and how many the recheck kept.
6. Build a GIN trigram index on `name`, and show the `%` operator using it. Set
   `pg_trgm.similarity_threshold` to 0.5 and to 0.2 and compare row counts for `name % 'Mira Bannerjee'`
   over the distinct names.
7. Write cost: update 50,000 rows' `email` (a change that cannot be a HOT update) and report the growth of
   the B-tree, GIN and table sizes.

**Solution.**

```sql
SELECT * FROM explain_warm($$SELECT id FROM contact WHERE email LIKE '%r15000%'$$);
CREATE INDEX contact_email_gin ON contact USING gin (email gin_trgm_ops);
SELECT * FROM explain_warm($$SELECT id FROM contact WHERE email LIKE '%r15000%'$$);
```

```text
                  QUERY PLAN
----------------------------------------------
 Seq Scan on contact (actual rows=11 loops=1)
   Filter: (email ~~ '%r15000%'::text)
   Rows Removed by Filter: 199989
   Buffers: shared hit=1839
(4 rows)

                              QUERY PLAN
-----------------------------------------------------------------------
 Bitmap Heap Scan on contact (actual rows=11 loops=1)
   Recheck Cond: (email ~~ '%r15000%'::text)
   Heap Blocks: exact=3
   Buffers: shared hit=16
   ->  Bitmap Index Scan on contact_email_gin (actual rows=11 loops=1)
         Index Cond: (email ~~ '%r15000%'::text)
         Buffers: shared hit=13
(7 rows)
```

The trigram index turns "scan every row" into "find rows containing these trigrams", then a recheck. The
plan shape (Bitmap Index Scan, then Bitmap Heap Scan with a Recheck Cond) is the signature.

```sql
CREATE INDEX contact_email_gist ON contact USING gist (email gist_trgm_ops);
CREATE INDEX contact_email_btree ON contact (email);
SELECT relname, pg_relation_size(oid) / 1048576 AS mb
FROM   pg_class
WHERE  relname IN ('contact', 'contact_email_btree', 'contact_email_gin', 'contact_email_gist')
ORDER  BY 2, 1;
SELECT * FROM explain_warm($$SELECT id FROM contact WHERE email LIKE '%r15000%'$$);
```

```text
       relname       | mb
---------------------+----
 contact_email_gin   |  7
 contact_email_btree |  9
 contact             | 14
 contact_email_gist  | 25
(4 rows)

                               QUERY PLAN
------------------------------------------------------------------------
 Bitmap Heap Scan on contact (actual rows=11 loops=1)
   Recheck Cond: (email ~~ '%r15000%'::text)
   Heap Blocks: exact=3
   Buffers: shared hit=241
   ->  Bitmap Index Scan on contact_email_gist (actual rows=11 loops=1)
         Index Cond: (email ~~ '%r15000%'::text)
         Buffers: shared hit=238
(7 rows)
```

Both present: the planner chooses GiST here, and it reads about twenty times the index pages GIN does (about 250 against 13;
the GiST figure varies from build to build, 233 to 274 in our runs, so yours will differ). It prefers GiST on estimated cost even though GIN is cheaper to run, so if you keep only
one, keep GIN and drop the other; do not leave both.

```sql
DROP INDEX contact_email_gist;
SELECT * FROM explain_warm($$SELECT id FROM contact WHERE email LIKE '%15%'$$);
SET enable_seqscan = off;
SELECT * FROM explain_warm($$SELECT id FROM contact WHERE email LIKE '%15%'$$);
RESET enable_seqscan;
SELECT count(*) AS rows_matching, (SELECT count(*) FROM contact) AS table_rows
FROM   contact WHERE email LIKE '%.example';
```

```text
                   QUERY PLAN
-------------------------------------------------
 Seq Scan on contact (actual rows=17641 loops=1)
   Filter: (email ~~ '%15%'::text)
   Rows Removed by Filter: 182359
   Buffers: shared hit=1839
(4 rows)

                                QUERY PLAN
---------------------------------------------------------------------------
 Bitmap Heap Scan on contact (actual rows=17641 loops=1)
   Recheck Cond: (email ~~ '%15%'::text)
   Rows Removed by Index Recheck: 182359
   Heap Blocks: exact=1839
   Buffers: shared hit=2797
   ->  Bitmap Index Scan on contact_email_gin (actual rows=200000 loops=1)
         Index Cond: (email ~~ '%15%'::text)
         Buffers: shared hit=958
(8 rows)

 rows_matching | table_rows
---------------+------------
        200000 |     200000
(1 row)
```

Two characters produce no complete trigram, so the index returns everything and the recheck does the
work: more buffers than the scan. The pattern `'%.example'` is a different failure. It has plenty of
trigrams, but every row contains them, so the index cannot narrow anything, and the planner is right to ignore it.
Trigram indexing needs a pattern that is *rare*.

```sql
SELECT * FROM explain_warm($$SELECT id FROM contact WHERE email ILIKE '%R15000%'$$);
SELECT * FROM explain_warm($$SELECT id FROM contact WHERE email ~* 'R15[0-9]{3}@'$$);
```

The `%` operator uses the trigram index; the threshold changes *which rows qualify*, not just the
ranking. With only 100 distinct names in this generated data, the numbers show a threshold that admits
one name at 0.5 and many at 0.2. On real data, you tune the threshold against searches you know the answer to.

```sql
CREATE TEMP TABLE before AS
SELECT relname, pg_relation_size(oid) AS bytes FROM pg_class
WHERE relname IN ('contact', 'contact_email_btree', 'contact_email_gin');

UPDATE contact SET email = 'v2.' || email WHERE id <= 50000;

SELECT a.relname, b.bytes AS before_bytes, pg_relation_size(c.oid) AS after_bytes,
       pg_relation_size(c.oid) - b.bytes AS growth
FROM   before b JOIN pg_class c ON c.relname = b.relname JOIN pg_class a ON a.oid = c.oid
ORDER  BY b.relname;
```

```text
---------------------+--------------+-------------+---------

 contact_email_btree |      9887744 |    14270464 | 4382720
 contact_email_gin   |      7839744 |    13197312 | 5357568
(3 rows)
```

Every updated row writes a new tuple, a new B-tree entry, and new trigram entries in GIN. Compare the
growth columns in your own run: a trigram index gets one entry per distinct trigram of each new value,
against one for a B-tree, which is why it does not belong on a column that changes constantly without
measuring first. Sizes depend on vacuum timing, so quote yours, not ours.
