# Chapter 10 Exercises — Subqueries and EXISTS

## Practice Session 10.1 — Convert a correlated subquery to a join, and measure both

**Goal.** Take the query shape that causes more slow pages than any other, rewrite it as a
join without changing a single value in the output, and put a number on what the rewrite
bought.

**Setup.** The `retail` database loaded in Practice Session 2.3. No other setup.

```bash
psql retail
```

```sql
\pset null '(null)'
```

The last line matters for this session. Two of the columns you are about to produce are
NULL for some customers, and `psql` prints NULL and the empty string identically unless
you tell it not to.

**Task.**

Here is a customer summary for the Chennai delivery city, written the way it usually
arrives in a code review — one parenthesised subquery per derived column:

```sql
SELECT c.id, c.name,
       (SELECT count(*)            FROM orders o WHERE o.customer_id = c.id) AS order_count,
       (SELECT sum(o.total_amount) FROM orders o WHERE o.customer_id = c.id) AS lifetime_value
FROM   customers c
WHERE  c.city = 'Chennai'
ORDER  BY c.id
LIMIT  5;
```

1. Run it. Note what `order_count` and `lifetime_value` hold for a customer who has never
   ordered.
2. Run it again without the `ORDER BY`/`LIMIT`, under
   `EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF)`. How many `SubPlan` nodes are
   there, and what is `loops` on each? Multiply: how many scans of `orders` did the server
   perform?
3. Write the obvious join rewrite — `customers JOIN orders`, `GROUP BY`, `count(*)`,
   `sum(total_amount)`. Count its output rows and compare with step 1. Do not read on
   until you can explain the difference.
4. Fix the row count. Then check one specific customer's `order_count` against step 1 and
   fix that too. Two separate bugs.
5. `EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF)` the corrected join. Compare
   `Buffers: shared hit` and `Execution Time` with step 2.
6. Now drop the `WHERE c.city = 'Chennai'` from both forms, so the query covers all 1,000
   customers, and measure again. Which number grew, and by how much?
7. State the rule you would put in a code review, in one sentence.

**Solution.**

**Step 1.** The first five rows:

```text
 id  |      name       | order_count | lifetime_value
-----+-----------------+-------------+----------------
  29 | Vikram Nair     |           4 |       12178.80
  37 | Imran Pillai    |           3 |        4820.76
  40 | Suresh Kulkarni |           0 |         (null)
  56 | Nisha Patel     |           3 |        4634.70
 107 | Anita Joshi     |           1 |         291.26
(5 rows)
```

Customer 40 has never ordered. `count(*)` over an empty set is **0**; `sum()` over an
empty set is **NULL**, not 0. Two aggregates, two different answers to "nothing here" —
that asymmetry is in the SQL standard and it is about to matter twice.

**Step 2.** The plan:

```text
 Seq Scan on customers c (actual rows=47 loops=1)
   Filter: (city = 'Chennai'::text)
   Rows Removed by Filter: 953
   Buffers: shared hit=4054
   SubPlan 1
     ->  Aggregate (actual rows=1 loops=47)
           Buffers: shared hit=2021
           ->  Seq Scan on orders o (actual rows=2 loops=47)
                 Filter: (customer_id = c.id)
                 Rows Removed by Filter: 2498
                 Buffers: shared hit=2021
   SubPlan 2
     ->  Aggregate (actual rows=1 loops=47)
           Buffers: shared hit=2021
           ->  Seq Scan on orders o_1 (actual rows=2 loops=47)
                 Filter: (customer_id = c.id)
                 Rows Removed by Filter: 2498
                 Buffers: shared hit=2021
 Execution Time: 4.749 ms
```

Two `SubPlan` nodes, `loops=47` on each: **94 sequential scans of `orders`** to produce 47
rows. Each column you add to the select list adds another full pass. The `Filter:
(customer_id = c.id)` line with `Rows Removed by Filter: 2498` is the whole story — every
scan reads all 2,500 orders and keeps two.

4,054 buffers, where the entire `orders` table is 43 pages.

**Step 3.** The obvious rewrite, and why it is wrong:

```sql
SELECT c.id, c.name, count(*) AS order_count, sum(o.total_amount) AS lifetime_value
FROM   customers c JOIN orders o ON o.customer_id = c.id
WHERE  c.city = 'Chennai'
GROUP  BY c.id, c.name;
```

It returns **35 rows**. The original returned **47**.

An inner join keeps only customers that matched something in `orders`. Twelve Chennai
customers have never ordered, and the join deleted them. The correlated form could not
delete them, because a scalar subquery in the select list is evaluated *for* an outer row
that already exists — it never removes one.

This is the single most common defect in this rewrite, and it is invisible unless you
count. The report does not say "12 customers missing"; it says 35 customers, and 35 is a
plausible number.

**Step 4.** Two bugs, two fixes.

The row count needs a `LEFT JOIN`. The aggregate needs `count(o.id)`, not `count(*)`:

```sql
SELECT c.id, c.name, count(*) AS count_star, count(o.id) AS count_oid,
       sum(o.total_amount) AS lifetime_value
FROM   customers c LEFT JOIN orders o ON o.customer_id = c.id
WHERE  c.city = 'Chennai'
GROUP  BY c.id, c.name
ORDER  BY c.id
LIMIT  5;
```

```text
 id  |      name       | count_star | count_oid | lifetime_value
-----+-----------------+------------+-----------+----------------
  29 | Vikram Nair     |          4 |         4 |       12178.80
  37 | Imran Pillai    |          3 |         3 |        4820.76
  40 | Suresh Kulkarni |          1 |         0 |         (null)
  56 | Nisha Patel     |          3 |         3 |        4634.70
 107 | Anita Joshi     |          1 |         1 |         291.26
(5 rows)
```

Look at customer 40. The `LEFT JOIN` manufactured one row with every `orders` column
NULL, so `count(*)` — which counts *rows* and never inspects a value — reports **1**.
`count(o.id)` counts non-NULL values of `o.id` and reports **0**, which is what the
correlated subquery said.

`sum(o.total_amount)` needs no fix: aggregates other than `count(*)` skip NULL inputs, so
a single all-NULL row sums to NULL, matching the original exactly. If you would rather
report 0, that is `coalesce(sum(o.total_amount), 0)` — but make it a deliberate decision,
because NULL and 0 mean different things here ("never bought anything" versus "bought
nothing of value").

The correct rewrite is therefore:

```sql
SELECT c.id, c.name, count(o.id) AS order_count, sum(o.total_amount) AS lifetime_value
FROM   customers c LEFT JOIN orders o ON o.customer_id = c.id
WHERE  c.city = 'Chennai'
GROUP  BY c.id, c.name;
```

**Step 5.** Its plan:

```text
 HashAggregate (actual rows=47 loops=1)
   Group Key: c.id
   Buffers: shared hit=55
   ->  Hash Right Join (actual rows=112 loops=1)
         Hash Cond: (o.customer_id = c.id)
         ->  Seq Scan on orders o (actual rows=2500 loops=1)
         ->  Hash (actual rows=47 loops=1)
               ->  Seq Scan on customers c (actual rows=47 loops=1)
                     Filter: (city = 'Chennai'::text)
                     Rows Removed by Filter: 953
 Execution Time: 0.171 ms
```

47 rows, matching. **55 buffers against 4,054; 0.171 ms against 4.749 ms.**

Note that PostgreSQL flipped your `LEFT JOIN` into a `Hash Right Join` with `orders` on
the outside. That is not a different query — a left join with the sides swapped is a right
join, and the planner picks whichever side is cheaper to hash. Do not be alarmed by
`Right` appearing in the plan for a query you wrote as `LEFT`.

**Step 6.** Remove the `city` filter and the gap opens up. Correlated, one derived column
so the comparison is fair:

```text
 Seq Scan on customers c (actual rows=1000 loops=1)
   Buffers: shared hit=43012
   SubPlan 1
     ->  Aggregate (actual rows=1 loops=1000)
           ->  Seq Scan on orders o (actual rows=2 loops=1000)
                 Filter: (customer_id = c.id)
                 Rows Removed by Filter: 2498
                 Buffers: shared hit=43000
 Execution Time: 50.647 ms
```

Join:

```text
 HashAggregate (actual rows=1000 loops=1)
   Group Key: c.id
   Buffers: shared hit=55
   ->  Hash Right Join (actual rows=2697 loops=1)
         Hash Cond: (o.customer_id = c.id)
         ->  Seq Scan on orders o (actual rows=2500 loops=1)
         ->  Hash (actual rows=1000 loops=1)
               ->  Seq Scan on customers c (actual rows=1000 loops=1)
 Execution Time: 0.481 ms
```

The join's buffer count **did not move**: 55, exactly as with the filter. It reads each
table once whatever the output size. The correlated form went from 4,054 to **43,012** —
it scaled linearly with output rows, because that is what per-row work does.

Put the two side by side:

| Output rows | Correlated buffers | Join buffers | Ratio |
|-------------|--------------------|--------------|-------|
| 47          | 4,054              | 55           | 74×   |
| 1,000       | 43,012             | 55           | 782×  |

The ratio is not a property of the query. It is a property of how many rows you ask for,
and it grows without limit. A page that felt fine at 47 rows is 782× off at 1,000 and
worse at ten thousand.

Use buffers rather than milliseconds for this comparison. Timings move with cache state
and with what else the machine is doing; `shared hit` counts 8 KB pages touched and is
the same number on your laptop and on the production box.

**Step 7.** The review rule: **a correlated subquery in a `SELECT` list is acceptable only
when you can state an upper bound on the outer query's row count.** A record page or a
`LIMIT 20` list qualifies. An unbounded list does not, and it must be a join — with a
`LEFT JOIN` and `count(col)` rather than `count(*)`, or you will have traded a slow
correct answer for a fast wrong one.

## Practice Session 10.2 — `NOT EXISTS` vs `NOT IN`: the plans and the estimates

**Goal.** Establish, by measurement rather than by rule of thumb, that of the three ways
to write an anti-join only one produces a plan the planner can cost — and that the row
estimates are the part that actually hurts you.

**Setup.** The `retail` database. `customers.referred_by` is a nullable self-reference:
who referred this customer, if anyone. 726 of the 1,000 rows are NULL.

```bash
psql retail
```

```sql
\pset null '(null)'
```

Step 7 additionally uses the large `retail` variant — about 2,000,000 orders. If you built
`retail_lg` in Practice Session 8.2, it is still there and nothing more is needed. If not,
build it beside your small `retail` rather than over the top of it, since `load.sh` names
the database after the dataset and `./load.sh retail lg` would replace it:

```bash
cd path/to/sql-from-my-heart/datasets

createdb retail_lg
psql -d retail_lg -v ON_ERROR_STOP=1 -f retail/schema.sql
psql -d retail_lg -v ON_ERROR_STOP=1 -f retail/generate-lg.sql
```

About a minute, and 749 MB. Step 7 is optional — the first six steps stand on their own.

**Task.**

1. Count the customers who have never referred anybody, two ways: `NOT IN` over
   `referred_by`, and `NOT EXISTS`. You should get 0 and 783. This is the trap from
   Practice Session 7.1; do not spend time on *why* the counts differ, this session is
   about what the planner does next.
2. Run `EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF)` on four queries: the broken `NOT IN`,
   a `NOT IN` with `WHERE referred_by IS NOT NULL` added to the subquery, `NOT EXISTS`,
   and `LEFT JOIN customers r ON r.referred_by = c.id WHERE r.id IS NULL`. Exactly one
   plan contains a join node that names the operation you are performing. Which?
3. Now stop reading the node names and read the `rows=` numbers. For each plan, write down
   the estimate and the actual. One of them is exact, one is out by a factor of hundreds.
4. Form a hypothesis about where the `NOT IN` estimate comes from, then test it: run
   `EXPLAIN` (no `ANALYZE` needed) on three `NOT IN` queries whose subqueries have wildly
   different selectivity — every order, only returned orders, and only orders over 5,900.
   Does the estimate move?
5. Run the same three questions as `NOT EXISTS` and compare each estimate to the true
   answer.
6. Explain the `LEFT JOIN` form's estimate. One query against `pg_stats` will tell you
   where the number comes from.
7. *(Optional, needs `retail_lg`.)* Re-run the `NOT IN` and `NOT EXISTS` forms of
   "customers who have never ordered" against 300,000 customers and 2,000,000 orders, with
   plain `EXPLAIN`. Compare total cost. Then set `statement_timeout` to something you are
   willing to wait for, and try to actually execute the `NOT IN`.

**Solution.**

**Step 1.**

```sql
SELECT (SELECT count(*) FROM customers c WHERE c.id NOT IN (SELECT referred_by FROM customers)) AS not_in,
       (SELECT count(*) FROM customers c WHERE NOT EXISTS (SELECT 1 FROM customers x WHERE x.referred_by = c.id)) AS not_exists;
```

```text
 not_in | not_exists
--------+------------
      0 |        783
(1 row)
```

**Step 2.** Four plans.

Broken `NOT IN`:

```text
 Seq Scan on customers c  (cost=24.50..49.00 rows=500 width=4) (actual rows=0 loops=1)
   Filter: (NOT (hashed SubPlan 1))
   Rows Removed by Filter: 1000
   SubPlan 1
     ->  Seq Scan on customers  (cost=0.00..22.00 rows=1000 width=4) (actual rows=1000 loops=1)
```

Repaired `NOT IN`:

```text
 Seq Scan on customers c  (cost=22.68..47.19 rows=500 width=4) (actual rows=783 loops=1)
   Filter: (NOT (hashed SubPlan 1))
   Rows Removed by Filter: 217
   SubPlan 1
     ->  Seq Scan on customers  (cost=0.00..22.00 rows=274 width=4) (actual rows=274 loops=1)
           Filter: (referred_by IS NOT NULL)
           Rows Removed by Filter: 726
```

`NOT EXISTS`:

```text
 Hash Anti Join  (cost=34.50..70.45 rows=783 width=4) (actual rows=783 loops=1)
   Hash Cond: (c.id = x.referred_by)
   ->  Seq Scan on customers c  (cost=0.00..22.00 rows=1000 width=4) (actual rows=1000 loops=1)
   ->  Hash  (cost=22.00..22.00 rows=1000 width=4) (actual rows=274 loops=1)
         Buckets: 1024  Batches: 1  Memory Usage: 18kB
         ->  Seq Scan on customers x  (cost=0.00..22.00 rows=1000 width=4) (actual rows=1000 loops=1)
```

`LEFT JOIN … IS NULL`:

```text
 Hash Right Join  (cost=34.50..59.12 rows=1 width=4) (actual rows=783 loops=1)
   Hash Cond: (r.referred_by = c.id)
   Filter: (r.id IS NULL)
   Rows Removed by Filter: 274
   ->  Seq Scan on customers r  (cost=0.00..22.00 rows=1000 width=8) (actual rows=1000 loops=1)
   ->  Hash  (cost=22.00..22.00 rows=1000 width=4) (actual rows=1000 loops=1)
         Buckets: 1024  Batches: 1  Memory Usage: 44kB
         ->  Seq Scan on customers c  (cost=0.00..22.00 rows=1000 width=4) (actual rows=1000 loops=1)
```

Only `NOT EXISTS` produces a **`Hash Anti Join`** — the node whose name is the operation
you are performing. It is a first-class join: the planner can cost it, reorder it relative
to other joins, and choose hash, merge or nested-loop for it, and at execution it stops
probing the inner side the moment it finds one match.

The two `NOT IN` plans are not joins at all. `Filter: (NOT (hashed SubPlan 1))` is a
Boolean expression evaluated per outer row against a hash table built once. It cannot be
reordered, nothing can be pushed through it, and the hash must fit in `work_mem`.

The `LEFT JOIN` form *is* a join, but not the right one. `Rows Removed by Filter: 274`
records it constructing all 1,057 join rows and then discarding the 274 that matched.
Against a one-to-many relationship that is one constructed-and-discarded row per child.

**Step 3.** The numbers most people never look at:

| Form | Estimated | Actual | Error |
|------|-----------|--------|-------|
| `NOT IN` (broken) | 500 | 0 | — |
| `NOT IN` (repaired) | 500 | 783 | 1.6× low |
| `NOT EXISTS` | **783** | 783 | **exact** |
| `LEFT JOIN … IS NULL` | 1 | 783 | 783× low |

**Step 4.** The hypothesis worth forming is that 500 is not an estimate at all — it is
half of 1,000, the outer row count. Test it by varying the subquery enormously:

```sql
EXPLAIN SELECT c.id FROM customers c WHERE c.id NOT IN (SELECT customer_id FROM orders);
EXPLAIN SELECT c.id FROM customers c WHERE c.id NOT IN (SELECT customer_id FROM orders WHERE status = 'returned');
EXPLAIN SELECT c.id FROM customers c WHERE c.id NOT IN (SELECT customer_id FROM orders WHERE total_amount > 5900);
```

```text
 Seq Scan on customers c  (cost=74.25..98.75 rows=500 width=4)
   Filter: (NOT (hashed SubPlan 1))
   SubPlan 1
     ->  Seq Scan on orders  (cost=0.00..68.00 rows=2500 width=4)

 Seq Scan on customers c  (cost=74.93..99.43 rows=500 width=4)
   Filter: (NOT (hashed SubPlan 1))
   SubPlan 1
     ->  Seq Scan on orders  (cost=0.00..74.25 rows=272 width=4)
           Filter: (status = 'returned'::text)

 Seq Scan on customers c  (cost=74.25..98.75 rows=500 width=4)
   Filter: (NOT (hashed SubPlan 1))
   SubPlan 1
     ->  Seq Scan on orders  (cost=0.00..74.25 rows=1 width=4)
           Filter: (total_amount > '5900'::numeric)
```

The subquery estimate moves from 2,500 rows to 272 to **1**. The outer estimate is **500
every time.** Hypothesis confirmed: the planner has no selectivity model for
`NOT (hashed SubPlan)`. It cannot see inside a `SubPlan`, has no statistics describing its
output, and falls back to a fixed default for a negated clause of unknown selectivity.
It is not a bad estimate; it is the absence of one.

**Step 5.** The same three questions, as `NOT EXISTS`, against the true answers:

| Question | Actual | `NOT EXISTS` estimate | `NOT IN` estimate |
|----------|--------|-----------------------|-------------------|
| never ordered | 197 | **197** | 500 |
| never returned anything | 759 | 728 | 500 |
| never placed an order over 5,900 | 999 | **999** | 500 |

Two exact, one within 4%. That accuracy is not luck: an anti-join is estimated by the
same machinery as every other join — `n_distinct` and the most-common-value lists on both
sides of the join condition — which is real statistical information about real columns.
The moment the construct becomes a join node, the planner's entire selectivity apparatus
applies to it.

**Step 6.** The `LEFT JOIN` estimate of 1 is the most instructive of the three, because
nothing is broken. The planner estimates the join output perfectly well, then applies
`WHERE r.id IS NULL` as an ordinary filter on top of it. How selective is that filter?

```sql
SELECT tablename, attname, null_frac, n_distinct FROM pg_stats
WHERE  (tablename, attname) IN (('customers','id'), ('customers','referred_by'),
                                ('orders','id'), ('orders','customer_id'))
ORDER  BY tablename, attname;
```

```text
 tablename |   attname   | null_frac | n_distinct
-----------+-------------+-----------+------------
 customers | id          |         0 |         -1
 customers | referred_by |     0.726 |     -0.217
 orders    | customer_id |         0 |    -0.3212
 orders    | id          |         0 |         -1
(4 rows)
```

`null_frac` for `customers.id` is **0** — it is a `NOT NULL` primary key, so no row in
the table has a NULL there. The estimated selectivity of `r.id IS NULL` is therefore zero,
and PostgreSQL clamps a zero-row estimate up to the minimum of one row. Hence `rows=1`.

The statistics are perfectly accurate and the conclusion is wrong by 783×, because the
NULLs being filtered on **do not exist in the table**. They are manufactured by the outer
join, and `pg_stats` describes base tables, not join outputs. The planner would need to
recognise that `LEFT JOIN … WHERE pk IS NULL` *means* anti-join and rewrite it before
costing. PostgreSQL 15 does not do that. It does implement the opposite simplification —
a strict qualification above an outer join demotes it to an inner join — but `IS NULL` is
not strict, so that machinery never fires here.

On a two-table query an estimate of 1 costs you nothing. Put this node underneath another
join and the planner, believing it is joining a single row, will choose a nested loop —
and then execute it 783 times, or 45,104 times, or however many rows really come out.
Estimated-versus-actual is the master diagnostic of Chapter 34, *Deep Dive: `EXPLAIN` and
`EXPLAIN ANALYZE`*, and Chapter 35 is about why estimates go wrong. This is one of the
cleanest examples you will find: correct statistics, correct arithmetic, useless answer.

**Step 7.** At 300,000 customers and 2,000,000 orders, in `retail_lg` (`psql -d
retail_lg`). Two notes before the numbers. `orders.customer_id` is declared `NOT NULL`
here, so the `NOT IN` is semantically safe — this step is purely about plans. And the
large variant is generated with `random()`, so your counts and costs will differ from
mine in the last digits; the ratios will not.

```sql
EXPLAIN SELECT count(*) FROM customers c WHERE c.id NOT IN (SELECT customer_id FROM orders);
EXPLAIN SELECT count(*) FROM customers c WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
```

```text
 Finalize Aggregate  (cost=4784101841.72..4784101841.73 rows=1 width=8)
   ->  Gather  (cost=4784101841.50..4784101841.71 rows=2 width=8)
         Workers Planned: 2
         ->  Partial Aggregate  (cost=4784100841.50..4784100841.51 rows=1 width=8)
               ->  Parallel Seq Scan on customers c  (cost=0.00..4784100685.25 rows=62500 width=0)
                     Filter: (NOT (SubPlan 1))
                     SubPlan 1
                       ->  Materialize  (cost=0.00..71542.60 rows=2001173 width=4)
                             ->  Seq Scan on orders  (cost=0.00..53718.73 rows=2001173 width=4)

 Finalize Aggregate  (cost=66692.11..66692.12 rows=1 width=8)
   ->  Gather  (cost=66691.90..66692.11 rows=2 width=8)
         Workers Planned: 2
         ->  Partial Aggregate  (cost=65691.90..65691.91 rows=1 width=8)
               ->  Parallel Hash Anti Join  (cost=55726.00..65613.40 rows=31398 width=0)
                     Hash Cond: (c.id = o.customer_id)
                     ->  Parallel Seq Scan on customers c  (cost=0.00..4904.00 rows=125000 width=4)
                     ->  Parallel Hash  (cost=42045.22..42045.22 rows=833822 width=4)

```

**4,784,101,842 against 66,692 — a factor of 71,700.**

Two things changed at scale, and the first explains the second. Read the `NOT IN` plan
again: the filter is `NOT (SubPlan 1)`, not `NOT (hashed SubPlan 1)`. Two million values
will not fit in the default 4 MB `work_mem`, so there is no hash table. What replaces it
is a `Materialize` node, re-scanned once per outer row: 300,000 customers each walking
two million materialised rows.

`NOT EXISTS` returns 45,104 in around 90 ms on an otherwise idle machine. Now try the
other one:

```sql
SET statement_timeout = '60s';
SELECT count(*) FROM customers c WHERE c.id NOT IN (SELECT customer_id FROM orders);
```

```text
ERROR:  canceling statement due to statement timeout
```

Before adding the timeout I let it run for two and a half minutes with no sign of
finishing.

One honest caveat, since this session is about reading estimates carefully: the
`NOT EXISTS` estimate is not exact at this scale either. The `Parallel Hash Anti Join`
predicts 31,398 rows, but that is the estimate *per worker process*, and the total is not
three times it. Run the query without the `count(*)` wrapper and PostgreSQL shows you its
own arithmetic on the `Gather` node:

```sql
EXPLAIN SELECT c.id FROM customers c WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
```

```text
 Gather  (cost=56726.00..74149.00 rows=75356 width=4)
   Workers Planned: 2
   ->  Parallel Hash Anti Join  (cost=55726.00..65613.40 rows=31398 width=4)
         Hash Cond: (c.id = o.customer_id)
         ->  Parallel Seq Scan on customers c  (cost=0.00..4904.00 rows=125000 width=4)
         ->  Parallel Hash  (cost=42045.22..42045.22 rows=833822 width=4)
               ->  Parallel Seq Scan on orders o  (cost=0.00..42045.22 rows=833822 width=4)
```

**75,356, not 94,194.** The divisor is 2.4 rather than 3 because the leader process only
partly participates in a parallel scan — it also has to drain the workers' output queues —
so the planner counts two full workers plus 0.4 of a leader. Expect `/2.4` whenever you
scale a partial row estimate up by hand; `Gather` will do it for you if you let it.

So 75,356 against an actual 45,104, about 1.7× high. That is a normal join misestimate and
the planner recovers from it. The `LEFT JOIN` form at the same scale still estimates
`rows=1` against the same 45,104, having removed 2,000,000 rows by filter, and is not
even slower for it — across six alternating runs the two traded places, 83–104 ms against
87–98 ms. Its problem was never the clock.

The conclusion to take away is not "`NOT IN` is slower". It is that `NOT IN` against a
subquery is **fast right up until the subquery outgrows `work_mem`, and then it stops
being a query you can run at all.** The cliff is triggered by data growth, not by a
deploy, and by the time you hit it the statement was last edited long enough ago that
nobody connects the two. Against a literal list, `NOT IN` is fine. Against a subquery,
write `NOT EXISTS`.
