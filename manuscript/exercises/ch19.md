# Chapter 19 Exercises — Modeling Real Entities

## Practice Session 19.1 — Model order fulfillment end to end

**Goal.** Turn a paragraph of business rules into a schema in which every rule that can be a
constraint is one, then break each rule on purpose and read the error.

**Setup.** The small `retail` dataset supplies 40 orders, their lines and the products; the
shipping side is yours to invent. Everything is built in a scratch database and `retail`
is only read.

```bash

psql -d ch19_ws1
```

**The rules.** A Pune distributor tells you:

- Customers move house. Each order ships to one specific address, and a customer's history
  of addresses must be kept. A customer has only one delivery address in force at a time.
- An order has one or more lines: product, quantity, and the unit price on the day.
- An order may ship in several parcels, from different warehouses, on different days. A
  parcel carries part or all of some of the order's lines. It may never carry more of a
  line than was ordered, in total.
- A parcel is delivered no earlier than it shipped.
- Customers return goods against a parcel. Only what was in that parcel can come back, never
  more than it carried, and the reason is one of `damaged`, `wrong_item`, `not_needed`,
  `late`.

**Task.**

1. List the entities and the cardinality between each pair before writing any SQL. Which
   of them would a "checkout screen" design have collapsed, and which rule would it have
   lost?
2. Create the tables with primary keys, foreign keys, `ON DELETE` choices and `CHECK`s. Use
   composite foreign keys wherever a child must agree with a sibling reference.
3. Load the 40 orders, their lines and addresses (a first address for every customer; a
   second for even-numbered customers from 1 January 2025) and ship them: everything that
   left the warehouse in `retail` (status `shipped`, `delivered`, `returned`) ships in one
   parcel, except that on every third order line 1 ships half.
4. Break five rules and record the error each produces: an order shipping to another
   customer's address; a parcel delivered before it shipped; a parcel line taken from a
   different order; a return line for a line that parcel did not carry; a return with the
   reason `changed_mind`.
5. Two rules cannot be constraints: shipping more than ordered, and returning more than
   shipped. Enforce both with triggers that lock the parent row, and demonstrate each.
6. Build a view of ordered, shipped and returned per line, and list the orders that still
   owe stock. Explain why each child is aggregated before it is joined.

**Solution.**

**1 and 2.** Nine tables: `customers`, `products`, `customer_addresses` (one-to-many from
customers; retired rather than updated), `orders`, `order_lines` (the many-to-many between
orders and products, keyed by a line number because the same product can repeat),
`shipments`, `shipment_lines` (many-to-many between parcels and order lines), `returns`,
`return_lines`. A checkout-screen design would have held one address on the customer and
one `shipped_at` on the order, losing address history and partial shipments. The composite
foreign keys are `orders (customer_id, ship_address_id)`, `shipment_lines (shipment_id,
order_id)` and `return_lines (shipment_id, line_no)`. `order_lines` cascades from `orders`
(a line is part of its order); every other reference restricts.

```sql
\pset null '(null)'
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE customers (customer_id int PRIMARY KEY, name text NOT NULL, email text NOT NULL UNIQUE);
CREATE TABLE products  (product_id  int PRIMARY KEY, sku  text NOT NULL UNIQUE, name text NOT NULL);

CREATE TABLE customer_addresses (
    address_id   int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id  int  NOT NULL REFERENCES customers,
    line1        text NOT NULL,
    city         text NOT NULL,
    pincode      text NOT NULL CHECK (pincode ~ '^[1-9][0-9]{5}$'),
    valid_during daterange NOT NULL,
    UNIQUE (customer_id, address_id),
    EXCLUDE USING gist (customer_id WITH =, valid_during WITH &&));

CREATE TABLE orders (
    order_id        int PRIMARY KEY,
    customer_id     int NOT NULL REFERENCES customers,
    ship_address_id int NOT NULL,
    placed_at       timestamptz NOT NULL,
    cancelled_at    timestamptz,
    FOREIGN KEY (customer_id, ship_address_id)
        REFERENCES customer_addresses (customer_id, address_id));

CREATE TABLE order_lines (
    order_id   int NOT NULL REFERENCES orders ON DELETE CASCADE,
    line_no    int NOT NULL,
    product_id int NOT NULL REFERENCES products,
    quantity   int NOT NULL CHECK (quantity > 0),
    unit_price numeric(10,2) NOT NULL CHECK (unit_price >= 0),
    PRIMARY KEY (order_id, line_no));

CREATE TABLE shipments (
    shipment_id  int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id     int  NOT NULL REFERENCES orders,
    warehouse    text NOT NULL,
    carrier      text NOT NULL,
    shipped_at   timestamptz NOT NULL,
    delivered_at timestamptz,
    CHECK (delivered_at >= shipped_at),
    UNIQUE (shipment_id, order_id));

CREATE TABLE shipment_lines (
    shipment_id int NOT NULL,
    order_id    int NOT NULL,
    line_no     int NOT NULL,
    quantity    int NOT NULL CHECK (quantity > 0),
    PRIMARY KEY (shipment_id, line_no),
    FOREIGN KEY (shipment_id, order_id) REFERENCES shipments (shipment_id, order_id),
    FOREIGN KEY (order_id, line_no)     REFERENCES order_lines (order_id, line_no));

CREATE TABLE returns (
    return_id   int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    shipment_id int NOT NULL REFERENCES shipments,
    opened_at   timestamptz NOT NULL,
    UNIQUE (return_id, shipment_id));

CREATE TABLE return_lines (
    return_id   int  NOT NULL,
    shipment_id int  NOT NULL,
    line_no     int  NOT NULL,
    quantity    int  NOT NULL CHECK (quantity > 0),
    reason      text NOT NULL CHECK (reason IN ('damaged','wrong_item','not_needed','late')),
    PRIMARY KEY (return_id, line_no),
    FOREIGN KEY (return_id, shipment_id) REFERENCES returns (return_id, shipment_id),
    FOREIGN KEY (shipment_id, line_no)   REFERENCES shipment_lines (shipment_id, line_no));
```

The shipping load, with the trigger from step 5's first half already in place so that the load
itself is checked by it:

```sql
CREATE FUNCTION check_not_overshipped() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE ordered int; already int;
BEGIN
    SELECT quantity INTO ordered FROM order_lines
    WHERE  order_id = NEW.order_id AND line_no = NEW.line_no FOR UPDATE;
    SELECT coalesce(sum(quantity), 0) INTO already FROM shipment_lines
    WHERE  order_id = NEW.order_id AND line_no = NEW.line_no AND shipment_id <> NEW.shipment_id;
    IF already + NEW.quantity > ordered THEN
        RAISE EXCEPTION 'order % line %: ordered %, already shipped %, cannot ship % more',
              NEW.order_id, NEW.line_no, ordered, already, NEW.quantity
              USING ERRCODE = 'check_violation';
    END IF;
    RETURN NEW;
END $$;
CREATE TRIGGER shipment_lines_cap BEFORE INSERT OR UPDATE OF quantity, order_id, line_no
ON shipment_lines FOR EACH ROW EXECUTE FUNCTION check_not_overshipped();

INSERT INTO shipments (order_id, warehouse, carrier, shipped_at, delivered_at)
```

Now the return-side trigger, which mirrors the first: what a shipment line carried is the
ceiling for what may come back.

```sql
CREATE FUNCTION check_not_overreturned() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE carried int; already int;
BEGIN
    SELECT quantity INTO carried FROM shipment_lines
    WHERE  shipment_id = NEW.shipment_id AND line_no = NEW.line_no FOR UPDATE;
    SELECT coalesce(sum(quantity), 0) INTO already FROM return_lines
    WHERE  shipment_id = NEW.shipment_id AND line_no = NEW.line_no
      AND  return_id <> NEW.return_id;
    IF already + NEW.quantity > carried THEN
        RAISE EXCEPTION 'shipment % line %: carried %, already returned %, cannot return % more',
              NEW.shipment_id, NEW.line_no, carried, already, NEW.quantity
              USING ERRCODE = 'check_violation';
    END IF;
    RETURN NEW;
END $$;
CREATE TRIGGER return_lines_cap BEFORE INSERT OR UPDATE OF quantity, shipment_id, line_no
ON return_lines FOR EACH ROW EXECUTE FUNCTION check_not_overreturned();
```

**6.** The view, and the list of orders still owing stock:

```sql
CREATE VIEW order_line_progress AS
SELECT l.order_id, l.line_no, l.quantity AS ordered,
       coalesce(s.shipped, 0) AS shipped, coalesce(r.returned, 0) AS returned
FROM   order_lines l
LEFT   JOIN (SELECT order_id, line_no, sum(quantity) AS shipped
             FROM shipment_lines GROUP BY 1, 2) s USING (order_id, line_no)
LEFT   JOIN (SELECT sl.order_id, sl.line_no, sum(rl.quantity) AS returned
             FROM return_lines rl JOIN shipment_lines sl USING (shipment_id, line_no)
             GROUP BY 1, 2) r USING (order_id, line_no);

SELECT order_id, count(*) AS lines, sum(ordered) AS ordered, sum(shipped) AS shipped,
       sum(returned) AS returned, sum(ordered - shipped) AS outstanding
FROM   order_line_progress GROUP BY order_id
HAVING sum(ordered - shipped) > 0 AND sum(shipped) > 0 ORDER BY order_id;
```

Each child is aggregated to one row per `(order_id, line_no)` *before* the join. Joining

## Practice Session 19.2 — Adjacency list → closure table

**Goal.** Convert a real adjacency-list hierarchy into a materialized path and a closure

the reads in buffers.

```sql
ALTER TABLE emp ADD COLUMN path text;
WITH RECURSIVE t AS (

WITH RECURSIVE t AS (
```

**5.** The closure move has two halves. Delete every link from the moved subtree to
ancestors *outside* it, then insert the cross product of the new parent's ancestors (itself
included) with the moved subtree. Counts are the cost: the adjacency list changes one row.

```sql
BEGIN;
UPDATE emp SET manager_id = 5 WHERE emp_id = 15;
UPDATE emp SET path = '/1/5/15/' || substr(path, length('/1/4/15/') + 1) WHERE path LIKE '/1/4/15/%';
DELETE FROM emp_closure
WHERE  descendant IN (SELECT descendant FROM emp_closure WHERE ancestor = 15)
AND    ancestor NOT IN (SELECT descendant FROM emp_closure WHERE ancestor = 15);
INSERT INTO emp_closure
SELECT a.ancestor, d.descendant, a.depth + 1 + d.depth
FROM   emp_closure a CROSS JOIN emp_closure d
WHERE  a.descendant = 5 AND d.ancestor = 15;
COMMIT;
SELECT * FROM closure_check;
```

The adjacency list accepts the loop and the tree becomes unreachable from any root. In
the closure table, employee 2774 is already a descendant of employee 1, so attaching employee 1

is what turns that into a duplicate key.

```sql
CREATE TABLE dept_closure (
  ancestor int NOT NULL REFERENCES dept, descendant int NOT NULL REFERENCES dept,
  depth int NOT NULL, PRIMARY KEY (ancestor, descendant));
INSERT INTO dept_closure
WITH RECURSIVE t AS (
  SELECT dept_id AS ancestor, dept_id AS descendant, 0 AS depth FROM dept
  UNION ALL SELECT t.ancestor, d.dept_id, t.depth + 1 FROM t JOIN dept d ON d.parent_dept_id = t.descendant)
SELECT * FROM t;

WITH RECURSIVE t AS (
  SELECT dept_id AS root, dept_id, annual_budget FROM dept
  UNION ALL SELECT t.root, d.dept_id, d.annual_budget FROM t JOIN dept d ON d.parent_dept_id = t.dept_id),
rec AS (SELECT root AS dept_id, sum(annual_budget) AS total FROM t GROUP BY root),
clo AS (SELECT c.ancestor AS dept_id, sum(d.annual_budget) AS total
        FROM dept_closure c JOIN dept d ON d.dept_id = c.descendant GROUP BY c.ancestor)
SELECT count(*) AS departments,
       count(*) FILTER (WHERE rec.total IS NOT DISTINCT FROM clo.total) AS agree,
       count(*) FILTER (WHERE rec.total IS NULL) AS null_totals
FROM rec JOIN clo USING (dept_id);
```

```text
 departments | agree | null_totals
-------------+-------+-------------
          40 |    40 |           3
(1 row)
```

`sum` ignores NULL budgets, so a department whose whole subtree has NULL budgets totals
NULL; `IS NOT DISTINCT FROM` is needed to compare those, and the `null_totals` count shows
how many there are.

**8.** On a table this small the planner has to choose between five full scans of 62 pages
and 309 index probes. Predict first; then:

```sql
SET max_parallel_workers_per_gather = 0;
CREATE FUNCTION buffers_of(q text) RETURNS bigint LANGUAGE plpgsql AS $$
DECLARE j json;
BEGIN
    EXECUTE 'EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, FORMAT JSON) ' || q INTO j;   -- warm the cache
    EXECUTE 'EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, FORMAT JSON) ' || q INTO j;
    RETURN (j->0->'Plan'->>'Shared Hit Blocks')::bigint + (j->0->'Plan'->>'Shared Read Blocks')::bigint;
END $$;
VACUUM ANALYZE emp;
SELECT 'no index' AS variant, buffers_of($q$
  WITH RECURSIVE t AS (SELECT emp_id, salary FROM emp WHERE emp_id = 15
    UNION ALL SELECT e.emp_id, e.salary FROM emp e JOIN t ON e.manager_id = t.emp_id)
  SELECT count(*), sum(salary) FROM t$q$) AS buffers;
CREATE INDEX emp_manager_idx ON emp (manager_id);
ANALYZE emp;
SELECT 'index on manager_id' AS variant, buffers_of($q$
  WITH RECURSIVE t AS (SELECT emp_id, salary FROM emp WHERE emp_id = 15
    UNION ALL SELECT e.emp_id, e.salary FROM emp e JOIN t ON e.manager_id = t.emp_id)
  SELECT count(*), sum(salary) FROM t$q$) AS buffers;
```

Without the index the recursive query cost 333 buffers (five sequential scans of a 62-page
table); with it, 804 (a probe for each of the 309 employees found, about 2.6 buffers each).
The index made this query worse. A defensible conclusion needs the size of the table in it: an index pays when the
scans it replaces are large, and 62 pages is not large. The chapter's 500,000-row tree is
where the index earned its keep. Clean up: `DROP DATABASE ch19_ws2;` from another database.
