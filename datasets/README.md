# Sample Datasets

Three datasets run through the whole book. You learn one set of schemas in Part I and
spend the remaining eleven parts thinking about technique instead of re-reading an ER
diagram every chapter.

All human-readable values are Indian: names drawn from North, South, East and West
Indian naming patterns, Indian cities, Indian sites and regions, and `IN` as the
dominant country. Email domains use the reserved `.example` TLD so nothing in the sample
data can resolve to a real host. Money stays plain `numeric` with no currency symbol —
see the note under *retail* on why the amounts were not rescaled to INR.

Load them with the single entry point:

```bash
./load.sh retail sm        # one dataset, small
./load.sh all sm           # all three, small
./load.sh telemetry lg     # one dataset, large
```

Each dataset gets its own database, named after the dataset: `retail`, `telemetry`, `hr`.
`load.sh` drops and recreates that database, so re-running it is always safe and never
leaves you half-loaded.

Connection details come from the standard libpq environment variables:

| Variable     | Default                |
|--------------|------------------------|
| `PGHOST`     | `localhost`            |
| `PGPORT`     | `5432`                 |
| `PGUSER`     | your OS username       |
| `PGPASSWORD` | unset                  |

If your `psql` is not on `PATH` — common with Homebrew's keg-only `libpq` — point at it
directly: `PSQL=/opt/homebrew/opt/libpq/bin/psql ./load.sh all sm`.

The script refuses to run against a server older than PostgreSQL 15, and says so clearly
rather than failing halfway through a load.

## Two sizes

**`sm`** is about 10,000 rows per dataset. It loads in under a second and every result
set is small enough to read on screen. Use it for everything outside Part VIII.

**`sm` data is deterministic.** Values are derived from `md5()` of the row number, not
from `random()`, so the numbers printed in the book are the numbers you will see.

**`lg`** is 10,000,000+ rows for `telemetry` and proportionally large for the others. It
is generated by `generate_series` inside the server — there are no large data files in
this repository — and it uses `random()`, because at ten million rows the hashing costs
more than the data is worth and nobody reads the values anyway. Generate it when you
reach Part VIII.

## What is deliberately missing

These datasets arrive **untuned**, and that is not an oversight.

- **No indexes beyond primary keys.** Not even on foreign key columns — PostgreSQL does
  not create those for you, and finding that out is Practice Session 33.1.
- **No partitions.** Chapter 38 asks you to partition `device_events` by month and
  measure what changed. A pre-partitioned table has nothing to teach.
- **No `UNIQUE` constraints** beyond the primary keys, since each one is a free index.
- **No materialized views, no covering indexes, no extended statistics.**

`ANALYZE` *is* run at the end of every load. Planner statistics are not tuning; without
them every plan in Chapters 34 and 35 is wrong for reasons that have nothing to do with
what those chapters teach.

## Measured load times

Taken on an Apple Silicon laptop against PostgreSQL 15.10 in Docker. Treat them as a
floor, not a promise — a spinning disk or a small `shared_buffers` will be slower.

| Command                  | Time | Database size |
|--------------------------|------|---------------|
| `./load.sh all sm`       | ~1s  | ~28 MB total  |
| `./load.sh retail lg`    | ~53s | 749 MB        |
| `./load.sh telemetry lg` | ~50s | 2,352 MB      |
| `./load.sh hr lg`        | ~14s | 354 MB        |

All three large variants together are roughly two minutes and 3.5 GB.

## `retail`

Customers, the orders they place, the line items on those orders, and the product
catalogue. Used for joins (Chapter 9), aggregation (Chapter 8), subqueries (Chapter 10)
and the schema design work in Part V.

```
products ──< order_items >── orders ──< customers
                                            │
                                            └──< customers  (referred_by, self-reference)
```

| Table         | Columns |
|---------------|---------|
| `products`    | `id`, `sku`, `name`, `category`, `price`, `in_stock`, `created_at` |
| `customers`   | `id`, `name`, `email`, `country`, `city`, `signup_date`, `loyalty_tier`, `referred_by` |
| `orders`      | `id`, `customer_id`, `placed_at`, `shipped_at`, `status`, `discount_code`, `total_amount` |
| `order_items` | `id`, `order_id`, `product_id`, `quantity`, `unit_price` |

Relationships: `orders.customer_id` → `customers.id`; `order_items.order_id` →
`orders.id`; `order_items.product_id` → `products.id`; `customers.referred_by` →
`customers.id` (nullable).

The messiness is deliberate:

- **~20% of customers have no orders at all.** Orders are only ever placed by the
  lower-numbered customers, so `LEFT JOIN ... WHERE o.id IS NULL` has something to find
  (Practice Session 9.2).
- **`customers.referred_by` is mostly NULL.** This is what makes
  `WHERE id NOT IN (SELECT referred_by FROM customers)` return zero rows while the
  `NOT EXISTS` version returns hundreds — the trap in Practice Sessions 7.1 and 10.2.
- **Three quarters of orders have more than one line item.** Joining `orders` to
  `order_items` and summing `orders.total_amount` inflates the answer roughly threefold,
  which is the fan-out bug in Practice Session 9.4.
- **`orders.total_amount` is denormalised** and kept consistent with the sum over
  `order_items`, so that exercise has a correct answer to compare against.
- **Amounts are not rescaled to INR magnitudes.** `products.price` feeds the fan-out
  figures above, which several drafted chapters quote verbatim. Multiplying prices by an
  exchange rate would move every one of those numbers for purely cosmetic gain. The
  column is `numeric` and carries no currency symbol, so a chapter is free to describe
  it as rupees.
- **`shipped_at`, `city`, `loyalty_tier` and `discount_code` are all nullable** and all
  actually contain NULLs, for the three-valued-logic work in Chapter 7.
- **`country` is India-dominant.** `IN` holds 12 of the 20 weighted slots (~60%), with
  the remainder drawn from India's main trade and diaspora partners. In `sm`:

  | `IN` | `US` | `AE` | `MY` | `GB` | `AU` | `SG` |
  |------|------|------|------|------|------|------|
  | 609  | 100  | 93   | 58   | 55   | 43   | 42   |

  Chapter 1's worked example filters on a single country, so the dominant value has to
  return an interesting number of rows and the minorities have to be non-trivial.
- **`country` and `city` are independent, and that is deliberate.** All 20 cities are
  Indian, including for customers whose `country` is `US` or `AE`. Read `country` as the
  customer's **billing or registration country** and `city` as their **delivery city** —
  which is exactly the shape of a real Indian e-commerce business serving NRI and expat
  customers who ship to addresses in India. It is not a generation bug.

  It also makes the two columns genuinely useful for different things: `country` is a
  low-cardinality, heavily skewed column (7 values, one holding 61%) and `city` is a
  moderate-cardinality one (20 values, evenly spread, plus 128 NULLs). Chapters on
  statistics and selectivity need both shapes, and a single conflated "location" column
  would provide neither. **Prefer `city` for examples needing real selectivity** —
  `country = 'IN'` matches 61% of rows and will not produce an interesting query plan.

| Table         | `sm`  | `lg`      |
|---------------|-------|-----------|
| `products`    | 200   | 5,000     |
| `customers`   | 1,000 | 300,000   |
| `orders`      | 2,500 | 2,000,000 |
| `order_items` | 6,250 | ~5,000,000 (varies slightly; `lg` uses `random()`) |
| **total**     | **9,950** | **~7,300,000** |

## `telemetry`

High-volume time-series device events. This is the performance dataset: indexing
(Chapter 33), `EXPLAIN` (Chapter 34), statistics (Chapter 35) and partitioning
(Chapter 38).

```
devices ──< device_events
```

| Table           | Columns |
|-----------------|---------|
| `devices`       | `device_id`, `serial`, `model`, `firmware`, `site`, `region`, `installed_at`, `decommissioned_at` |
| `device_events` | `event_id`, `device_id`, `recorded_at`, `metric_name`, `metric_value`, `payload`, `severity` |

Relationship: `device_events.device_id` → `devices.device_id`.

- **`recorded_at` is `timestamptz`**, evenly spread over 3 months (`sm`) or 18 months
  (`lg`). Eighteen months is a clean monthly partition key for Chapter 38.
- **`device_id` is heavily skewed, not uniform.** A handful of very chatty devices and a
  long tail of quiet ones: in `sm` the busiest device produces 1,660 events while the
  quietest produces 11. Uniform data would make the planner's estimates correct and kill
  the misestimate exercises in Chapters 34 and 35 outright.
- **`payload` is `jsonb`** with nested objects and arrays (`fw`, `batt`, `rssi`, `tags`,
  `net.ssid`, `net.roam`) — the column Chapter 17 works on, including the GIN operator
  class comparison in 17.2.
- **`metric_value` is `numeric`**, with a range appropriate to each `metric_name`.
- **`severity` is NULL on ~90% of rows.** Sparse, low-cardinality and nullable makes it
  the right target for the partial index in Practice Session 33.3.

| Table           | `sm`  | `lg`       |
|-----------------|-------|------------|
| `devices`       | 200   | 5,000      |
| `device_events` | 9,800 | 10,000,000 |
| **total**       | **10,000** | **10,005,000** |

## `hr`

Employees, departments, and a self-referencing management hierarchy. Used for recursive
CTEs (Chapter 12), window functions (Chapter 25) and self-joins (Chapter 9).

```
departments ──< employees ──< salary_history
     │              │
     └──< departments      └──< employees  (manager_id, self-reference)
        (parent_dept_id)
```

| Table            | Columns |
|------------------|---------|
| `departments`    | `dept_id`, `name`, `location`, `cost_center`, `parent_dept_id`, `annual_budget` |
| `employees`      | `emp_id`, `full_name`, `email`, `dept_id`, `manager_id`, `job_title`, `hire_date`, `salary`, `status`, `terminated_on` |
| `salary_history` | `id`, `emp_id`, `effective_date`, `salary`, `reason` |

Relationships: `employees.dept_id` → `departments.dept_id`; `employees.manager_id` →
`employees.emp_id` (nullable, NULL for the CEO only); `salary_history.emp_id` →
`employees.emp_id`; `departments.parent_dept_id` → `departments.dept_id` (nullable).

- **The reporting tree is 7 levels deep in `sm` and 8 in `lg`**, with exactly one root
  (the CEO) and no cycles or orphans.
- **Branching is varied, not uniform.** Managers are drawn from the level above by hash,
  so in `sm` some managers have a single direct report and some have ten. A uniform tree
  makes Chapter 12's recursion and Chapter 25's "rank within manager" windows degenerate.
- **`salary` falls by level** with spread inside each level, so `RANK`/`DENSE_RANK` and
  top-N-per-group produce sensible results.
- **`salary_history` has 1–4 rows per employee**, always starting with the hire, giving
  `LAG`/`LEAD` something real to compute period-over-period against in Practice
  Session 25.3.
- **`departments` carries its own shallow hierarchy** via `parent_dept_id`, if you want a
  second, easier recursion target than the org chart.

| Table            | `sm`  | `lg`       |
|------------------|-------|------------|
| `departments`    | 40    | 1,000      |
| `employees`      | 2,774 | 1,000,000  |
| `salary_history` | 7,021 | ~2,500,000 (varies slightly; `lg` uses `random()`) |
| **total**        | **9,835** | **~3,500,000** |

## If you edit the generators

One trap, and it bit this repository once already. In the `generate-lg.sql` files every
`random()` sits inside a subquery that ends in `OFFSET 0`. That is an optimisation fence
and it is load-bearing.

Without it, PostgreSQL pulls the subquery up into the outer query, and a volatile
function in a `FROM` item that does not reference the outer row is evaluated **once for
the whole scan** rather than once per row. The first cut of `retail/generate-lg.sql` used
a plain non-correlated `LATERAL` and produced two million orders that all shared a single
`placed_at` and a single `status`, plus exactly four line items on every order. It loaded
without error and the row counts looked plausible. Only counting distinct values found it.

If you add a column, check it afterwards:

```sql
SELECT count(DISTINCT placed_at), count(DISTINCT status) FROM orders;
```

The `seed-sm.sql` files do not need the fence, because their `LATERAL` subqueries
reference the outer row and `_h()` is `IMMUTABLE` rather than volatile.

A second, quieter rule: **the value-pool arrays must keep their current lengths.** Every
statistical property of `sm` comes from `_h('seed' || i) % n` picking an index, so the
invariants survive swapping the *contents* of a 20-element name array but not its
*size*. Changing `% 20` to `% 24` silently reshuffles which customers have no orders and
breaks the `NOT IN` trap counts. Swap strings freely; leave the arithmetic alone.
